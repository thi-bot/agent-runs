# Code Style and Idioms

> Rules about Python/JS idioms, comments, loops, comparisons, buffer choice, and readability of implementation code.

**When to check**: When writing or reviewing implementation code for style and idioms.

## Rules

<!-- rule:1746 -->
- Prefer returning values from nested functions (async: read `task.result()`) over `nonlocal` — reserve `nonlocal` for simple shared state that can't be returned — Returning keeps the data flow explicit at the call site and avoids a dedicated state-holder class; the closure-based `nonlocal` pattern should only appear where returning isn't practical.
<!-- rule:4613 -->
- Never manually wrap and double-parse embedded server data (`JSON.parse(JSON.parse(...))`); serialize once via a Django template tag (`json_script` or a private admin template tag) so the client does a single parse. — Double-encoding (once in the view, again in the template) forces brittle client-side unwrapping and breaks whenever a layer changes its serialization — routing embedded data through `json_script` keeps a single source of truth and one parse on the client.
<!-- rule:395 -->
- Place explanatory comments directly above the regex/constant definition they describe, not at alias or inheritance reference sites — prevents duplicate and stale comments when the canonical source changes — Readers looking for the 'why' behind a pattern find it at the source, and updates only need to happen in one place.
<!-- rule:2042 -->
- Use `find … -delete` instead of `find … -exec rm {} \;` in shell/CI cleanup — avoids spawning one `rm` process per file. Keep `-print` before `-delete` for per-file logging, and verify `-delete` exists on all targets (GNU find, BSD/macOS find) before relying on it. — Spawning one `rm` per matched file makes cleanup scripts in `.github/workflows/` and other shell tooling slow on large trees; `-delete` handles the whole match set in-process. The `-print`-before-`-delete` ordering is the only way to log what was removed, since `-delete` implies `-depth` and silently swallows output. Confirming platform support matters because BSD/macOS `find` and GNU `find` differ in flag coverage — a script that works on Linux CI runners may fail for contributors cleaning up locally on macOS.
<!-- rule:2578 -->
- Use Python chained comparisons for range validation — e.g. `not lower <= value <= upper` instead of `value < lower or value > upper` — and keep the original inclusive/exclusive boundaries when negating — Chained comparisons are evaluated once per operand and read as a single range expression, so an accidental boundary flip (e.g. `<=` becoming `<`) is far easier to spot than in an `or`/`and` compound. Negating a chain is also a common source of off-by-one bugs when swapping `>` for `>=` — the original boundaries must be preserved verbatim.
<!-- rule:3986 -->
- Prefer explicit loops (counter or stack) over complex regex for paired/nested delimiter parsing — Explicit code makes nesting bugs visible at review time and easier to test than backtracking regex
<!-- rule:3221 -->
- Gate normalization/serialization on `DEBUG` only when it's purely for inspection — steps like populating `.args`/`.kwargs` must run in all modes, or non-debug executions persist incomplete data — Prevents DEBUG-vs-production divergence in stored task attributes. A step that's required for correct `.args`/`.kwargs` silently produces wrong results when `DEBUG` is off, since only the debug path runs it.
<!-- rule:4034 -->
- Keep related UI elements at consistent font sizes — e.g. sibling links, or a field label and its upload/URL display. — A single element rendering noticeably smaller than its neighbors reads as a styling bug, not an intentional hierarchy. Set one size for the group unless the difference conveys real hierarchy.
<!-- rule:4596 -->
- Compare multi-key objects as a single tuple in rich comparisons (`__lt__`/`__eq__`), not sequential `if` branches or `or`/`__eq__` shortcuts — a secondary field must never override the primary ordering. Guard tie-breakers so they only apply when the primary key is equal, handle nullable fields explicitly, and keep `try/except AttributeError: return NotImplemented` for cross-type comparisons. — Unguarded tie-breakers silently let a secondary field (e.g. `name`) win over the primary one (e.g. `order`), producing incorrect sort order; the `AttributeError` -> `NotImplemented` guard keeps comparisons with unrelated types returning `False` instead of raising.
<!-- rule:4739 -->
- Skip `Path.exists()` before `Path.mkdir(exist_ok=True, parents=True)` — `exist_ok=True` already handles existing dirs, so the pre-check is a redundant stat call that races under concurrent creation. — The pre-check adds a TOCTOU race: the directory can be created between `exists()` and `mkdir()`, causing an unhandled `FileExistsError`. `exist_ok=True` closes that window atomically.
<!-- rule:4483 -->
- Reuse derived state (`self.renamed_fields`, `external_aliases`) rather than recomputing inline — prevents divergent decisions across methods — Two methods recomputing the same decision drift apart; a flag that ignores one input (like an active `change_map` remap) silently treats aliased identifiers as unaliased, producing wrong rename/alias handling.
  Compute derived flags from all contributing inputs — e.g., `aliased or alias in change_map` — so remapped identifiers aren't missed
<!-- rule:4984 -->
- Fold `os.walk` directory filters directly into the loop that consumes them — skip building a filtered copy of `dirnames` and iterating it separately; avoids double iteration and a throwaway list allocation. Reserve in-place pruning (`dirnames[:] = ...`) for when the walk must not recurse into matched directories. — A separate filtered copy of `dirnames` costs an extra list allocation and a second pass over the same entries when the predicate only guards the next loop. In-place pruning is the only form that actually changes walk behavior, so use it only when you need to stop recursion into matched directories.
<!-- rule:6107 -->
- Use `list` for append-and-iterate buffers; `collections.deque` only for `appendleft`/`popleft`/`maxlen` — lists are faster unless queue semantics are needed (weigh list-resizing vs. deque overhead for very large buffers) — Plain `list` beats `collections.deque` for the common append-and-iterate pattern; deque's per-item overhead only pays off when queue-style access or a bounded size is actually required. Choosing wrong adds unnecessary cost to hot paths or complicates code that never needed deque semantics.
<!-- rule:5665 -->
- Iterate exceptions and tracebacks as two nested loops — outer over exceptions, inner over frames; extract the per-exception frame walk into a helper so each loop keeps a single responsibility. Merging both traversals into one stateful loop entangles collection state across exceptions, making the logic harder to reason about and to reuse. — Keeping exceptions and frames as two nested loops with a per-exception helper prevents collection state from leaking across exceptions and misattributing or reordering traceback frames, which a single stateful traversal would cause by entangling that state.
<!-- rule:601 -->
- Use `UNION ALL` over `UNION` for compound queries whose branches cannot overlap — e.g. `geometry_columns` + `geography_columns` — to skip the implicit `DISTINCT` sort/dedup. — Using plain `UNION` on disjoint spatial catalog branches like `geometry_columns` and `geography_columns` forces an unnecessary deduplication sort over the combined result, degrading introspection performance without changing correctness.
  **Why:** `UNION` forces a dedup over the full result, adding sorting overhead for datasets (like disjoint catalog tables) guaranteed to be duplicate-free.

<!-- rule:2150 -->
- Alphabetize library names within a single `{% load %}` tag; allow multiple libraries per tag — writing `{% load foo bar %}` is valid Django and splitting it across lines adds churn without benefit — Keeping multiple libraries in one alphabetized `{% load %}` tag prevents merge conflicts and review noise caused by arbitrary reordering or gratuitous splitting into separate tags, while still matching Django's valid multi-library syntax.
<!-- rule:3893 -->
- In logging helpers forwarding `format` and `*args` to a logger, never reassign those params — handle special cases with a dedicated logging call and early return, duplicating the call if needed. Reassigning repurposes the call and desyncs `format` from its args, producing `%`-format errors. — Logging helpers that accept `format` and `*args` exist to forward them verbatim to a logger. Reassigning either parameter (e.g. replacing `format` with a special-case string while leaving `*args` in place) breaks the format/args contract and can raise `TypeError`/`ValueError` at log time. A dedicated logging call with an early return preserves the originals; duplicating the call is cheap and safer. Passing `args=()` when substituting a placeholder-free message prevents leftover args from being forwarded into a format string that no longer consumes them.
  - When overriding a log message with a placeholder-free static string, pass an empty `args` tuple — otherwise the original `*args` are forwarded and raise formatting errors.
