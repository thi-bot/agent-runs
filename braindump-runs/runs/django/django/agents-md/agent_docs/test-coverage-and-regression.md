# Test Coverage & Regression Tests

> Rules on what new or changed behavior must be covered by tests: branch and exception coverage, boundary values, Unicode/encoding paths, revert-detecting regression tests, and parity with upstream or ORM semantics.

**When to check**: When adding or changing behavior and deciding what tests to write (branches, boundaries, edge cases, regression cases)

## Rules

<!-- rule:1228 -->
- Add tests for every new public or semi-public class/method in that component's existing test module (e.g., `tests/{app}/tests.py`) — cover documented behavior, edge cases, and failure modes (`TypeError`/`ValueError`); untested public APIs silently regress, and "sibling methods are already untested" is never a reason to skip. — Preserves the repo-wide convention that public API surfaces (in `django/db`, `django/core`, `django/contrib/*`, etc.) ship with corresponding tests in their component's test module. Without this, new APIs land without verification and quietly break for downstream users.
<!-- rule:792 -->
- Test every `except` clause, defensive guard, and error fallback by directly triggering its exception — an untested branch can be silently removed or broken without any test failing — This is a global testing standard across `django/` and `tests/`; if a branch can't be exercised by a realistic test, delete the handler rather than leaving it untested or writing a contrived test
<!-- rule:492 -->
- Assert exact redirect URLs (`Location`, incl. `next`) in tests for every redirect branch rather than using a test-client helper to emulate the redirect. — Helpers that mimic redirects can drift from real middleware/auth behavior, so exact-URL assertions (e.g. in Django middleware and password-reset confirm flows) catch regressions in redirect targets and `next` propagation that an emulated helper would silently miss.
<!-- rule:1167 -->
- Update `deconstruct()` tests when a field's defaults, optional args, or `__init__`/`deconstruct` overrides change — `deconstruct()` drives migration serialization, so untested changes silently produce wrong migrations — Assertions should cover the field's effective configuration (dropped framework defaults, preserved explicit kwargs, correct overrides). When expectations don't match, fix the tests rather than adding special-case `deconstruct()` logic — that special case ships and corrupts real migration output.
<!-- rule:4142 -->
- Port upstream tests alongside any upstream code port — verifies behavioral parity and branch coverage; skip tests that duplicate existing coverage — Porting code without its tests loses the upstream verification of behavior and edge cases, hiding parity gaps until production.
<!-- rule:611 -->
- Test optional args/flags with non-default values — if removing or defaulting the arg doesn't fail a test, the parameter is untested; fix the test or the API. — The first bullet prevents dead API surface by making tests the arbiter of whether a parameter is genuinely exercised. The second ensures aliases and sibling functions with the same optional parameter are not forgotten, and that branch-specific behavior — like the two `ManyToMany` descriptor paths or `exclude` in validation wrappers — is covered. The third guards against silent precedence bugs and factory functions that swallow arguments instead of forwarding them. The fourth avoids redundant default-value tests that duplicate existing baseline coverage while preserving simple construction tests as features grow.
  - Cover each parameter variant: aliases, sibling public functions, and every affected branch, e.g. normal vs. symmetrical `ManyToMany` descriptor paths and `exclude` forwarding in validation wrappers.
  - Verify explicit vs. implicit/default-source precedence, empty/legacy forms, and that parsed args are actually used and propagated through factories to generated objects.
  - For default behavior, omit args equal to the documented default and skip standalone default tests when existing baseline tests already cover that path; keep simple default-construction tests when extending for new optional features.
<!-- rule:724 -->
- Test boundary logic at the limit plus one step each side (`LIMIT-1`/`LIMIT`/`LIMIT+1`, `seconds=59` vs. the next unit) — values far from the edge never enter the branch, so truncation/slicing/range bugs ship undetected. — Boundary-sensitive logic (truncation, slicing, limits, counts, ranges, time thresholds, indexing) fails exactly at the edge; sampling values far from the boundary exercises only the trivial path. Degenerate counts and the paired normal case catch off-by-one and zero-length regressions that a single happy-path test misses. 'Fails when the condition is removed' is the proof the test actually reaches the boundary logic rather than passing for unrelated reasons.
    - Add degenerate inputs (`0`, negatives) for any `count`/`limit`/range param, and pair boundary special-cases (empty/zero-length) with a normal-case test — the zero case alone hides regressions on the common path.
    - Make the boundary test fail when the condition is removed, sizing fixtures to reach the failing index (≥3 items when the crash starts at index 2) — a test that passes without the guard means the guard is untested, so delete it or add a test that needs it.
<!-- rule:682 -->
- Test escaping/encoding with real neutralized characters (HTML specials, markup, operators, control/DEL) and assert exact single-escaped output — `&lt;`, uppercase `\u007F`/`\^@`, literal decoded chars, never raw controls or entities; double-escaping (`&amp;lt;`) is a bug to fix, not codify — Escaping tests are only meaningful when the input actually triggers the escape path; codifying double-escaped expectations like `&amp;lt;` hides the bug instead of catching it, and case/literal mismatches (`\u007f` vs `\u007F`) lock in the wrong output format.
<!-- rule:3467 -->
- Cover every supported field/column type in serializer/mapper tests — subsets miss type-specific bugs — A representative subset of field/column types leaves type-specific serialization/deserialization regressions undetected; the data-driven structure makes one case per type cheap and complete.
<!-- rule:3562 -->
- Test both cached and uncached paths when changing property/descriptor caching (e.g., swapping in `cached_property`) — silent cache-invalidation bugs only surface on the path you didn't test. Cover state-dependent recomputation and all supported input types, including lazy proxies. — Cache bugs are path-specific: they hide until the untested branch (uncached lookup, mutation-triggered recompute, proxy input) fires in production. Annotate non-obvious edge cases inline and tag the originating report as `(#NNNNN)` so future readers can trace why the regression test exists.
<!-- rule:4696 -->
- Never drop predicate/condition fragments (including constant booleans) from ORM query compilation to silence a crash — it hides the real bug and silently changes SQL semantics. — Dropping conditions to make crashes disappear produces valid-looking but semantically wrong queries; assertions on full query shape and explicit comments keep regressions from slipping in unnoticed.
  - In ORM regression tests, reproduce the reported query shape (including relation joins) and assert every original condition is present in the generated SQL/results — catches predicates lost during compilation.
  - Comment non-obvious query-compilation assertions — records why that SQL shape matters, not just what it checks.
<!-- rule:4884 -->
- Wrap `select_for_update()` tests and doc examples in `transaction.atomic()`, assert the SQL lock clause covers every expected table/model, and prefer `.get(pk=...)` for single-row locks — Django raises `TransactionManagementError` outside a transaction, and result-set-only assertions miss locks silently dropped from joined models (`select_related`, `values`, etc.); comment when `list(queryset)[0]` is required. — Prevents `TransactionManagementError` in tests/docs and catches regressions where a lock clause no longer covers all joined tables — a class of bug that result-set assertions cannot detect.
<!-- rule:1824 -->
- Test encoding/coercion paths (`django/forms/fields.py`, `django/http/request.py`, `HttpResponse`, management command output) with non-ASCII Unicode, non-default codecs, and bytestring/alternative inputs — for keys *and* values — so a silent fallback to the default charset fails the test instead of passing. — Guards against regressions where string casting, serialization, or form-field coercion silently fall back to the default charset or mishandle bytes; ASCII-only fixtures and implicit defaults hide those bugs.
  - In tests, write codecs explicitly (`.encode('utf-8')`) even when matching the default; in production, omit redundant defaults (`.encode()`) — explicit tests pin the intended codec, minimal prod code keeps the default meaningful.
<!-- rule:3861 -->
- Add regression tests in `tests/queries/test_qs_combinators.py` for any change to combined/combinator SQL compilation — nested unions, empty member lists, differing queryset counts, `ORDER BY` with slicing, and shared column sources (extra columns/annotations). — Combinator SQL compilation and `tests/queries/test_qs_combinators.py` are co-updated repeatedly; without these cases, recursive ordering-clearing and edge cases go untested.
    Nested unions must define ordering at both inner and outer levels so recursive ordering-clearing is exercised; keep fixtures readable by making the ordering column distinct from the returned field (e.g. reverse-order author names). Missing coverage lets silently-cleared ordering clauses — including those that are semantically required — ship broken.
