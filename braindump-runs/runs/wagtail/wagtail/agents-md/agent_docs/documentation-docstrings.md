# Docstrings, JSDoc & Code Comments

> Rules for writing docstrings, JSDoc/TSDoc comments, and inline code comments: placement, accuracy, grammar, documenting condition branches, defaults, sentinels, and rationale.

**When to check**: When writing or editing docstrings, JSDoc comments, or inline explanatory comments.

## Rules

<!-- rule:657 -->
- Document confusingly similar APIs in docstrings or at the call site — explain how they differ and when to use each. Near-duplicate names or delegated/optional variants (e.g. `rules` vs. `bulk_rules` on `MultiRuleRewriter`, public vs. private wrappers) invite callers to pick the wrong path or miss carried-over behavior. Note any differences in role, intended use, and parameters or behavior inherited from the delegate or optional path. — Prevents misuse of near-duplicate methods such as `rules` vs. `bulk_rules` on `MultiRuleRewriter` and makes public/private divergence and delegated behavior discoverable.
<!-- rule:345 -->
- Place JSDoc immediately above the declaration (`*/` flush against it, never inside the body) — IDE hovers and doc generators only associate adjacent comments — Doc tooling (TSDoc, TypeDoc, IDE hover) matches comments to declarations by adjacency, so blank lines or in-body placement silently break the association.
<!-- rule:439 -->
- Place explanatory comments on their own line above the code, not as trailing inline comments — avoids formatter-induced wrapping, keeps single-line statements intact, and minimizes diff churn. — When comments trail statements, reflowing them can force multi-line rewrites and noisy diffs; above-the-line placement keeps the code itself untouched.
<!-- rule:423 -->
- Document non-trivial classes, methods, constructors, and exported helper functions with behavior-focused JSDoc; for options objects, document each option's type and default. — Names alone don't convey usage constraints or side effects — undocumented options and effects cause misuse and bugs when callers guess.
<!-- rule:2263 -->
- Enumerate every branch in `Returns:` docstrings — describe conditions for all return values, not just the default case — Docstrings that only note the primary/default return path mislead readers about conditional branches, cached/mapped values, user-configurable settings, and fallbacks; describe conditions using the positive form ("returns X if it is set") so the doc matches the code rather than its inverse.
<!-- rule:1380 -->
- Write comments and docstrings in imperative, grammatically complete English (e.g. `# Handle ...`, not `# Handles ...`) — consistent wording keeps docs scannable and trustworthy across `wagtail` and `docs` — Imperative mood reads as guidance to the reader and matches the project's existing style; grammatical, complete phrasing avoids ambiguity in documentation examples that users copy verbatim.
<!-- rule:1983 -->
- Comment non-obvious literals, slice bounds, and thresholds (e.g. `[:10]`, `LIBRARY_LIMIT * 2`) with the exact value and its rationale — unexplained magic numbers silently drift; cite the source issue when known — Preserves scope (any numeric literal/bound/threshold), keeps the requirement to state the actual value and reference the originating issue when applicable, and gives the reviewer-facing WHY (silent drift + unclear intent) rather than a deontological 'always comment'.
<!-- rule:1350 -->
- Wagtail methods and functions, add concise docstrings that state the return value and explain non-obvious parameters or parsing/normalization logic. Do not include redundant product/project names (e.g. 'Wagtail') or user-facing documentation; keep docstrings focused on the code-level contract. — This is a general code-level documentation convention (docstring content) that applies to methods and functions throughout the repository, not to a single module. The sample files span multiple subdirectories within wagtail/ (wagtail/models, wagtail/contrib/forms, wagtail/contrib/wagtailfrontendcache), indicating the rule is not tied to any one directory. Per the decision criteria, a behavioral, entity-agnostic rule that governs 'methods and functions' broadly and shows multi-directory distribution should be placed in the root AGENTS.md as a global convention. Keeping docstrings focused on the code-level contract ensures developers get the return value and parameter semantics immediately without wading through redundant product names or user-facing docs that belong in the official Wagtail documentation.
<!-- rule:28 -->
- Name the referenced entity and define overloaded terms (`instance`, `single code base`, `SubMenuItem`) in plain domain language — vague shorthand misleads readers — Readers lacking project context cannot infer non-obvious term meanings; explicit definitions at the point of use prevent misinterpretation.
<!-- rule:2555 -->
- Name non-obvious calculations with descriptive variables; add an inline comment only if intent still isn't clear — self-documenting code outlives stale comments. Keep any such comment in sync when the calculation changes. — Magic offsets, averages, and aggregation/count adjustments are easy to misread and easy to break; a named variable encodes intent in code, while a comment can drift out of sync with the value it explains.
<!-- rule:1956 -->
- Document module vars, class attrs, and instance attrs with triple-quoted docstrings placed immediately after the declaration (`attr = default` or `attr: type`) — not Sphinx `#:` comments, which only Sphinx parses while docstrings are picked up by Sphinx *and* editors like VSCode. — Docstrings are the only form understood by both Sphinx and editor tooling (hover, autocomplete); `#:` comments silently drop docs for IDE users. For 1:1 constructor params, `:param:`/`:type:` fields give better IDE UX (param hover, call-site signature) than per-attribute docstrings, which duplicate the signature and bloat `__init__`. Scoped globally across library code and contributing docs (e.g. `wagtail/blocks/base.py`, `wagtail/blocks/struct_block.py`).
  - When a class's `__init__` params map ~1:1 to instance attributes, document them via `:param:`/`:type:` in the `__init__` docstring instead of attribute docstrings next to `self.x = ...` — constructor docs then surface on param hover and call-site typing, and the body stays clutter-free.
<!-- rule:1280 -->
- Attach JSDoc/docblocks to the exact field they describe, rewrite text copied from sibling docstrings, and mirror getter/setter docblocks — prevents docs from lying about behavior. — Misattached or copy-pasted docblocks mislead readers about which field or accessor actually behaves as described.
<!-- rule:911 -->
- In docstrings, list every accepted type when a parameter takes multiple (e.g. `str`, `Filter`, request object, or model instance) and describe behavior per-type where it differs, plus the return type — makes utility contracts unambiguous for callers — Polymorphic parameters are easy to misuse if the docstring only names one type; documenting each variant (and any behavior differences) prevents callers from passing the wrong shape and guessing at return values. Critical for reusable utilities whose contract must hold across modules in `wagtail/` and `docs/`.
<!-- rule:2005 -->
- Match docstring examples and branch comments to real behavior, incl. `return`/`yield` types — stale docs mislead callers and mask bugs — The rationale stays attached so the AI understands this is about caller trust and catching return/yield mismatches, not a style preference.

- When code handles an optional/nullable related object, make the absent/null behavior explicit: add an inline comment explaining why a nullable lookup or null-inclusive filter (e.g., `Q(site=None)`) is used and what scenario causes the relation to be missing; have resolvers return `None` for an absent relation instead of raising or returning an invalid value; and document (ideally with an example) that serialization omits the key entirely when the relation is null. — Cross-cutting behavioral contract for null/optional relations spanning resolvers, serialization, and API docs (e.g., `wagtail/admin/views`, `wagtail/contrib/redirects`, `wagtail/documents/api`, `docs/advanced_topics/api`). The absent-relation scenario isn't inferable from code, so callers silently break when behavior drifts between raising, returning invalid values, or emitting null vs. omitting keys.
<!-- rule:1011 -->
- When code intentionally wraps, extends, or diverges from a framework/library hook or callback, add an inline comment documenting what the underlying behavior is, what extra behavior is added, and why it is not implemented upstream. — Future readers can't tell an intentional override from an accidental one, and untracked divergence silently breaks when the upstream hook changes. This rule belongs in the root `AGENTS.md` because it applies to any code path (in `wagtail/` or `client/src/components/`) that overrides a hook — not to a single module or file.
<!-- rule:1862 -->
- Link to a rule's canonical definition when referencing third-party accessibility, lint, or static-analysis rules in docs or `.semgrep.yml` — readers can't act on an opaque rule ID alone, and the link survives version drift. — Rule IDs (e.g., Semgrep rules in `.semgrep.yml`, third-party a11y checkers) are opaque without context; linking the canonical source lets readers verify intent and adapt when upstream rules change. Applies to all documentation and config referencing external rule definitions.
<!-- rule:2248 -->
- Document transformations from external sources (`API`, forms, parsers) — the original shape isn't visible in code, so future readers can't verify intent. — Placed in root AGENTS.md because it applies across `client` and `wagtail` directories and isn't tied to any specific entity or cross-file sync.

<!-- rule:1478 -->
- Document non-obvious side effects that mutate `URL`/`hash`/`history` with imperative-voice JSDoc on public methods and inline comments above the raw API calls — signatures don't reveal these state changes, so uncommented code silently breaks navigation and history expectations. — Improves maintainability by making navigation/UI mutations discoverable to future readers and API consumers.
<!-- rule:2255 -->
- Comment intentional fallbacks and partial-data error paths — looks like a bug without context — Fallthrough logic (e.g., an upstream call returning empty or blank) reads as a defect to the next reader; an inline comment on the condition and why the fallback exists saves them from "fixing" deliberate behavior.

<!-- rule:2272 -->
- Comment why a value is dynamic or derived (e.g., `action` URLs, base content type ID vs `ct_value`) — otherwise future readers simplify or hard-code it; reference existing docs instead of duplicating the rationale. — Non-obvious dynamic or derived values invite well-meaning simplification; an inline comment preserves the intent and stops regressions where a raw value is substituted in place of the derived one.
<!-- rule:1445 -->
- Document async/event helpers in JSDoc with resolution conditions, default option values, and when `disabled`/falsy/zero timeouts or transitions resolve immediately — callers otherwise misread timing and break on edge cases — Makes resolution timing explicit, so users don't assume pending waits and hit bugs with `disabled`/falsy/zero values.
<!-- rule:730 -->
- Comment the *why* and *how* of third-party integrations and link official API docs at the integration point — Future readers can't infer external API contracts or wiring intent from the call site alone, making upgrades and debugging far slower.
<!-- rule:1535 -->
- Document non-obvious sentinel/default values (e.g., a negative delay disabling delay) — via JSDoc on typed properties and `__repr__` on sentinel objects so generated docs show the canonical name, not a generic repr. — Silent default semantics trip up users who can't tell from code what a value means; sentinels without `__repr__` render as opaque objects in generated docs, hiding their canonical identity.
<!-- rule:2112 -->
- Use identical signature names for shared params across sibling methods/hooks in `wagtail/blocks/base.py` and `docs/reference/hooks.rst`; cross-reference shared arg docs instead of duplicating — inconsistent names/signatures across a group break user expectations and searchability. — Sibling APIs sharing a calling contract read as one family to users; divergent names or duplicated arg docs silently drift apart over time.
<!-- rule:2903 -->
- Note the `annotate`/`select_related`/`prefetch_related` call that populates a model attribute — otherwise-invisible side-effect deps break silently — Side-effect-populated attributes have no visible origin at the use site; naming the queryset method makes the dependency discoverable so a later refactor doesn't drop the optimization and leave the attribute `None`/`AttributeError`-prone.
<!-- rule:2902 -->
- Batch recipients in notification dispatch instead of looping `send_notification`; comment why — prevents slow per-recipient sends and stops reviewers "simplifying" it back to a loop — The batching often looks like unnecessary complexity, so the comment preserves intent; the batching itself avoids perf regression across the codebase (evidence from `wagtail/admin` but applies wherever notifications are sent).
<!-- rule:510 -->
- Define each term and possible value inline in registries, mappings, and encoded fields — opaque tokens like `tracked` vs `indexed` or unnamed booleans get misread without the distinction spelled out — Project-specific role names and encoded booleans leave readers guessing at intent; inline definitions prevent misuse and preserve the original semantics as the registry evolves.
<!-- rule:953 -->
- Write DOM/ARIA validation warnings as complete, actionable sentences naming the element type, required attribute, and value (e.g. "Tab panel elements must have the `role='tabpanel'` attribute set.") — vague warnings leave developers guessing at the fix; call `role` an attribute, not an "aria attribute" — Concise rule with imperative mood, includes the concrete example verbatim, preserves the terminology correction (`role` is an attribute) as the WHY, and keeps the example format intact.
<!-- rule:2288 -->
- Implement `__str__()` on every Django model — gives readable instances in admin, shell, and logs — Django's admin, `shell_plus`, debug logs, and error messages all call `repr()`/`str()` on model instances. Without `__str__()`, you get opaque output like `<Article: Article object (7)>` instead of something meaningful, which slows debugging and makes admin list pages unusable. The project depends on this convention (see `wagtail/models/__init__.py`), so new models should match it.
<!-- rule:2963 -->
- In converter/transformation comments, name the format pair (e.g. `# editor-html conversion`), not the vendor impl (`Draftail`, `hallo.js`, `contenteditable`) — These `wagtail/` rich_text converters are reused by multiple editors — naming a specific implementation misleads readers as editors are swapped, and naming consumers that don't actually import the module is simply wrong. Attribute only real consumers; otherwise describe the conversion's function.
