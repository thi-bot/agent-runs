# Public API Design

> Rules for designing public interfaces, classes, signatures, return values, extension hooks, and framework-level configuration points.

**When to check**: When designing or modifying public classes, functions, or extension hooks.

## Rules

<!-- rule:3952 -->
- Give sortable table headers a distinct visual indicator for unsorted/ascending/descending, and announce both current sort state (direction + priority) and the next click action via accessible text — `aria-sort` alone doesn't tell screen reader users what clicking will do. — Screen reader users can't infer sort order or the effect of a click from a single attribute, so each header needs explicit state + action text.
<!-- rule:3150 -->
- Keep dataclasses mutable when fields change after construction; use `dataclasses.replace()` for copies. — `frozen=True` blocks post-construction updates. `dataclasses.replace()` produces explicit, validated updates — it re-runs `__post_init__`, so avoid duplicating validation in the deriving method unless it depends on external mutable state. If you must mutate a frozen instance, route `object.__setattr__` through one private helper.
<!-- rule:5606 -->
- Prefer the Null Object pattern over threading a boolean flag through helpers: define a real implementation and a no-op implementation sharing the same interface, letting the caller choose which to instantiate. The null variant must match the real interface exactly — no-op methods and any context manager yielding exactly once without extra bookkeeping. This keeps conditional checks out of every helper and avoids subtle bugs where a flag is forgotten or mismatched across call sites. — Boolean flags spread conditionals through helper code and cause mismatches when a caller forgets the flag or a new method on the real implementation lacks a matching no-op. A Null Object with an identical interface keeps call sites uniform and makes behavior differences explicit at instantiation.
<!-- rule:5890 -->
- Resolve output streams at runtime: take `None` and fall back to `sys.stdout`/`os.devnull`, never bind a stream as a default arg — a module-level default captures `sys.stdout` at import time, so it ignores redirection in tests and `call_command`. — Import-time binding of `sys.stdout` breaks output capture; a boolean mode flag duplicates the destination logic instead of letting callers swap the stream.
<!-- rule:6192 -->
- Fold post-processing into creation APIs or mutate in place — avoids forcing callers through `x = c.create(); x = c.modify(x)` follow-ups — Creation APIs that hand back an intermediate object requiring a second call on the same creator leak an implementation detail into every caller and make the object easy to misuse (e.g. skipping the follow-up leaves a half-configured result). Exceptions are intentional public transformation pipelines like `map`/`filter` chains, where each stage returning a new value is the point.
<!-- rule:2214 -->
- Return an explicit success/failure flag from conversion methods that fall back to the unchanged input — callers can't otherwise tell a completed conversion from a silent no-op — A method that silently returns the input when conversion fails is indistinguishable from one that legitimately converted to the same value, so callers can't branch on the outcome and bugs go unnoticed.
<!-- rule:6349 -->
- Return copies from public accessors of mutable internal collections; gate conversion in shared private helpers behind an explicit `force_list` flag — prevents callers mutating internal state and avoids unconditional conversion breaking raw-access APIs — Public accessors that return internal mutable collections leak state; a shared helper with a `force_list` flag keeps both raw-access and copied-list callers correct without surprising one of them with unintended copies.
<!-- rule:6212 -->
- Helper methods that may return a domain object or its key must always return the key — callers avoid `isinstance` checks, and mixed return types must never rely on `node == node.key` or matching `hash` semantics. — Callers shouldn't need `isinstance` branching to handle a helper's result. Depending on an object and its key comparing equal (e.g. `node == node.key`, `hash(node) == hash(node.key)`) silently breaks when the key type or equality/hash semantics change, so keep the return type uniform at the identifier.
<!-- rule:2790 -->
- When modifying size-sensitive serialized or protocol formats, account for new fields'/sentinels' byte overhead, prefer compact encodings, and update size limits to match the current spec rather than historical ones — prevents silent truncation and outdated limits from breaking wire compatibility. — Serialized formats like cookie storage (`django/contrib/messages/storage/cookie.py`) and ASGI protocol handlers (`django/core/handlers/asgi.py`) have hard byte-size ceilings. Adding fields without accounting for overhead — or keeping stale size limits after a spec change — causes silent truncation, rejected payloads, or interop failures with peers.
<!-- rule:2844 -->
- Omit `name`/default-alias on verbose aggregate classes — auto-derived aliases like `<field>__jsonarrayagg` leak into SQL and become unintended public API, so require callers to pass an explicit alias — Verbose auto-derived aliases (`<field>__jsonarrayagg`) surface in generated SQL and effectively freeze accidental behavior as public API. Requiring explicit aliases keeps the surface intentional; when a default is offered it should be a real shorthand, and docs must match the actual lowercased runtime output so users can trust the name they pass.
  - Set a default alias only for short, useful shorthands; document an alias only when intentionally supported, matching the lowercased runtime output (e.g. `<field>__jsonarrayagg`)
<!-- rule:4969 -->
- Validate free-form string discriminators (e.g. `backend_type`) against an allowlist and raise `ImproperlyConfigured` on unknown values, or keep generic registration helpers private (leading `_`) behind typed `register_{type}_backend` wrappers — otherwise typos fail silently and surface as misconfigured backends far from the call site. — A free-form string discriminator turns typos into silent no-ops: the helper registers nothing yet the caller believes it succeeded, and the failure only shows up later as a missing/misconfigured backend. Either validate the discriminator and raise `ImproperlyConfigured`, or make the generic helper private and expose typed `register_{type}_backend` wrappers so the type is checked at the call site.
<!-- rule:653 -->
- Hard-code standards-compliance flags in encoding helpers rather than exposing them as parameters — guarantees consistent compliant output (e.g. `idna.encode(domain, uts46=True, transitional=False)`); callers needing a different mapping must do it themselves before calling the helper. — Prevents bugs and inconsistency by ensuring helpers always emit standards-compliant output (e.g. IDNA 2008); non-standard mappings belong to the caller, not the helper's API surface.
<!-- rule:5989 -->
- Pass CLI file paths through verbatim — never append or infer extensions — Appending or guessing a file extension silently rewrites the user's input, so lookups fail on paths that actually exist and succeed on paths the user never asked for. Match what the user typed; if a shorthand (e.g. omitting an extension) is intentionally supported, document it with an inline comment.
<!-- rule:3180 -->
- Resolve relative delays (`run_after=timedelta(...)`) at enqueue time in task scheduling APIs — if you resolve them earlier (e.g., in `Task.using()`), the reference point and timezone become ambiguous; when enqueue-time resolution isn't possible, accept only absolute `datetime`s. — Relative delays are only unambiguous when anchored at enqueue, which is when the actual execution context (clock, timezone) is known. Deferring resolution to an earlier configuration/modification call like `Task.using()` forces a guess about which reference moment applies, producing silently wrong schedules across timezones or re-configuration.
<!-- rule:3183 -->
- Non-executing task backends (e.g. `Dummy`) must still drive each task to a terminal state like `failed` — leaving tasks `pending`/`running` breaks status polling and queue introspection — Non-executing backends that leave tasks in `pending`/`running` cause status polling and queue introspection to stall or misreport, and without documented terminal-state lifecycles callers cannot know which states such a backend will produce, leading to inconsistent handling and bugs.
  - Document each task backend's result/status lifecycle in its section of `docs/topics/tasks.txt` — callers need to know which terminal states a backend can produce when it never runs tasks
<!-- rule:2598 -->
- Accept per-view CSP overrides as a config dict with a `"DIRECTIVES"` key (same shape as the global CSP setting) — reuses the global config format so users don't learn a second schema. — Placement: root `AGENTS.md`, category `api_design`. These are cross-cutting conventions for all per-view CSP decorators and their docs (e.g. `docs/ref/csp.txt`), so they belong at the root rather than in a single module. The reasons: (1) mirroring the global CSP setting's `"DIRECTIVES"` dict shape lets users reuse one config format across global and per-view policies; (2) a uniform `enforced` / `report_only` convention keeps disposition handling consistent across decorators instead of forcing users to remember which flag or decorator variant applies; (3) rejecting redundant public mutators such as `csp_replace` / `csp_update` avoids API bloat when a full-policy override or an added argument already covers the use case.
  - Expose policy disposition on all CSP decorators via boolean `enforced` / `report_only` args — a single consistent convention selects enforced, report-only, or both; avoid mixing keyword flags with per-disposition decorators or hiding the disposition.
  - Don't add redundant CSP decorators like `csp_replace` / `csp_update` — full-policy override already covers those; extend existing decorators with args (e.g. a disable option) instead of growing the public API with directive-level mutators.
<!-- rule:2605 -->
- Store per-request values (e.g. `_csp_nonce`) on `request` and read the private attribute internally — keeps one value per request and avoids triggering lazy accessors that toggle optional behavior — Middleware helpers like `CSPMiddleware` generate a nonce once per request; caching it on `request` ensures every middleware method sees the same value instead of regenerating divergent ones, and internal construction reading `_csp_nonce` (not the public lazy attribute) prevents inadvertent activation of optional code paths gated on access state.
<!-- rule:1116 -->
- Wrap `{% block %}` around landmark elements in base/layout templates, not inside them — — e.g. `{% block footer %}<footer id="footer">…</footer>{% endblock %}` keeps overridden content inside `<footer>`/`<header>`/`<nav>`, so those landmarks remain overridable and axe `region` checks still pass
<!-- rule:3310 -->
- Configure `ModelForm` field callbacks only through `Meta.formfield_callback`, resolving via `opts.formfield_callback` — no base-class scanning or bare class attributes, since `ModelFormOptions` is the single lookup point. — Keeping `ModelFormMetaclass` behavior anchored to `ModelFormOptions` means callback resolution has one source of truth; scanning `__bases__` or honoring a bare class attribute duplicates resolution paths and diverges from how other `Meta` options are read.
<!-- rule:3516 -->
- Put shared hooks and helpers for sync/async variants on the common base class — Duplicating them or giving each subclass parallel hook names forces callers to override twice and lets the sync and async APIs drift apart — e.g. subclass `BasePaginator` instead of redefining hooks in both variants
