# Documentation for APIs and Features

> Accurate API return values, fetch modes, Extract transforms, uniqueness guarantees, permissions, admin hooks, MySQL/InnoDB behavior, app deletion migrations, command deviations, control-flow comments, and decorator/context-manager effects.

**When to check**: When documenting API behavior, feature reference, release notes, or complex implementation details.

## Rules

<!-- rule:5702 -->
- Register `Extract*` transforms only on field types containing the component — `ExtractHour`/`ExtractMinute`/`ExtractSecond` on `DateTimeField` only, `ExtractYear`/`ExtractMonth`/`ExtractDay`/`ExtractWeekDay` on `DateField` and `DateTimeField` — Registering a time-component transform on `DateField` (which has no time part) registers a transform that can never work, and advertising those invalid registrations in `docs/ref/models/database-functions.txt` and `docs/ref/models/expressions.txt` misleads users. Group and describe these transforms by supported field type in reference docs so documented behavior matches actual registration.
<!-- rule:1088 -->
- Document a method's return value as the value the implementation actually produces — vague labels and storage/representation types (e.g. SQL JSON types) mislead ORM users and break callers relying on the documented shape. — Inaccurate ORM and aggregate return-value docs lead callers to rely on the wrong Python type, row count, or result completeness—e.g. expecting `'[]'` instead of `[]`, treating matched rows as changed rows, or accepting silently partial multi-query results—which causes subtle data bugs and breaks code at runtime.
  - For database/ORM methods in `docs/ref/models/querysets.txt`, document: all submitted/affected objects returned even when conflicted or skipped; matched vs. changed/updated rows using the same terminology as related operations; precise count semantics (not loose "count of updated objects"); and non-trivial cardinalities (empty, single, multiple, multi-table-inheritance paths).
  - When a multi-query method's return is partial or unsupported, either aggregate across all queries or explicitly document/reject the unsupported combination — silent partial results cause subtle data bugs.
  - In `docs/ref/contrib/postgres/aggregates.txt`, `docs/internals/deprecation.txt`, release notes, and `docs/releases/*`, describe ORM aggregates/functions (especially JSON/array aggregates) by the actual Python type and structure the user receives (`list`, `[]`, "JSON array") — not the underlying SQL/JSON type.
  - Never write non-string values as strings: use `[]`, not `'[]'`; reserve `''` for genuine string returns — quoting a non-string return misleads users about the type they'll get.
<!-- rule:1541 -->
- Give built-in fetch mode callables explicit signatures without unused `**kwargs` — matches the real params, so introspection and error messages stay accurate — The fetch modes feature spans `django/db/models` code, `docs/topics/db` docs, and tests, so these conventions keep implementation, documentation, and terminology aligned across PRs — Inconsistent treatment of Django's fetch modes feature causes built-in fetch mode callables to accept unused **kwargs, modes to lack concrete examples, custom modes to be poorly documented extension points that are hard to implement and apply through `.fetch_mode(...)`, terminology to drift between 'on-demand' and 'lazy', re-export behavior to be unclear (`models.<mode>` versus imports from `django.db.models.fetch_modes`), and semantics to be misread as an ordered performance hierarchy or assumed not to propagate to related managers. This surprises users, encourages incompatible custom modes, and leaves maintainers repeatedly fixing API, documentation, naming, and behavioral inconsistencies.
  - Document each fetch mode with a concrete example, and cover custom modes as extension points — show both implementation and application via `.fetch_mode(...)` so users can follow end to end
  - Use consistent fetch mode terminology (`on-demand`, not `lazy`) — mismatched terms across code and docs confuse users comparing features
  - State fetch mode re-export behavior: access built-ins as `models.<mode>`, import classes from `django.db.models.fetch_modes` — prevents imports from the wrong path
  - Describe fetch mode semantics accurately: modes are not an ordered performance hierarchy, and they propagate to related managers — stops readers inferring a nonexistent speed ranking
<!-- rule:3163 -->
- State uniqueness scope explicitly; say 'uniqueness guarantee' not 'uniqueness rule' — vague docs hide whether uniqueness comes from a DB constraint or app-level enforcement, leaving readers unsure where to enforce it — Uniqueness can be enforced at the database layer or in application code; documenting only 'uniqueness' without scope or enforcement level makes callers assume one mechanism when the other is actually in play. Include examples of both so readers know not to rely on an implicit DB constraint.
<!-- rule:1621 -->
- When documenting MySQL/InnoDB index prefix or `CharField`/`VARCHAR` `max_length` limits, state the byte/character relationship, note that `row_format=dynamic` with `innodb_file_format=barracuda` lifts the 191-char utf8mb4 prefix cap, and link to the character-field docs in `docs/ref/databases.txt` rather than restating backend behavior — keeps `docs/topics/migrations.txt` guidance consistent and avoids drift between the two files. — The byte/character limit and the 191-char utf8mb4 prefix cap are commonly confused when users set `max_length` on unique `CharField`s; explaining them once in `docs/ref/databases.txt` and cross-referencing from `docs/topics/migrations.txt` (plus mentioning `row_format=dynamic`/`innodb_file_format=barracuda` as the workaround) prevents the two docs from telling users different things about the same backend behavior.
<!-- rule:2596 -->
- Remove cross-app migration references (and squashes) to a deleted Django app *before* deleting it — stale dependencies block migration generation and raise `NodeNotFoundError` reachable only with multi-app repros — Deleting a Django app without first removing or squashing cross-app migration references leaves other apps pointing at migrations for a component that no longer exists, so migration generation or deletion can fail with NodeNotFoundError and operators are surprised by unresolved dependency boundaries and cleanup work. The operational app-deletion requirement and the broader documentation requirements for destructive migration/app-deletion procedures must both state which non-Django-managed objects are cleaned up by other means and when before RemoveField, and describe table-deletion and relationship-updating migration effects. That prevents multi-app failures and keeps destructive procedures reproducible instead of letting stale dependencies rot in migrations.
  - In app-deletion docs (`docs/howto`, `docs/ref`, `docs/intro`), state cleanup order and boundaries: what's cleaned by other means and when (e.g. non-Django-managed objects before `RemoveField`), plus concrete table-deletion and relationship-updating migration effects
<!-- rule:1816 -->
- Document non-obvious management-command deviations (skipped `check=True`, fixed `encoding`, CI/platform workarounds) with an inline comment explaining why — undocumented deviations get "fixed" by the next reader. — Management commands in `django/core/management/commands` are frequently written with deliberate deviations from the standard `BaseCommand` pattern (e.g., omitted `check=True`, hardcoded `encoding`, CI/platform workarounds). Because these deviations look like mistakes, any reader who lacks the surrounding context may silently revert them. An inline comment preserves the "why" at the exact point of divergence. Separately, when a command's behavior intentionally differs from settings-driven defaults or from the behavior of `scripts/`-based sibling commands, users have no source of truth except `docs/ref/django-admin.txt`; documenting the real behavior there and flagging the inconsistency as intentional prevents the divergence from being reported as a regression.
  - When a command's behavior diverges from settings-driven defaults or sibling commands in `django/core/management/commands`, state the actual behavior in `docs/ref/django-admin.txt` and mark the divergence intentional — otherwise users and maintainers file it as a bug.
<!-- rule:2132 -->
- Comment non-obvious control flow (`connection-pool selection`, `router resolution`) inline: name the acting component, spell out fallback and edge cases, one sentence per step — PR descriptions aren't visible at the call site — A future reader debugging pool or router behavior sees only the method body, not the PR that introduced it; without the acting component, fallback path, and edge cases named in-code, the reasoning behind the branching is lost and re-derived (often incorrectly) during later changes.
<!-- rule:3366 -->
- Name the exact permission(s) a check requires — vague terms like "admin access" mislead users about what they actually need — Permission documentation is security-relevant: vague or scope-inflated descriptions cause operators to grant wrong permissions and readers to trust checks that don't actually gate the described action.
  - Describe only the objects/attributes the check governs — overstating scope creates false security expectations
  - Verify `and`/`or` connectors and required attributes against the code — permission docs silently drift from the real check
  - Applies to release notes, reference docs, permission-denied messages, and code comments
<!-- rule:270 -->
- Document `ModelAdmin` hooks with "Hook for…", the applicable admin view, return type/shape (e.g. a 4-tuple), and `request`/`obj` behavior for dynamic cases. — Undocumented or vaguely documented `ModelAdmin` hooks force subclassers to guess the expected return shape and whether `request`/`obj` are available, producing silently broken admin views whose docstrings no longer match the reference docs.
  Rationale: Keeps `django/contrib/admin/options.py` docstrings aligned with `docs/ref/contrib/admin/index.txt` — vague or mismatched hooks cause subclassers to return the wrong shape or misread when `request`/`obj` are available.
  Add a worked example when the hook involves complex customization.
<!-- rule:4692 -->
- Document non-obvious decorator and context-manager effects inline — state the causal mechanism, when it applies, what data it adds, why apparently contradictory combinations are valid, and which sibling decorators share the limitation; mark explanations temporary when the situation will change. Undocumented side effects cause misdiagnosis and duplicated fixes. — Non-obvious behavior from decorators/context managers leads developers to misread code, duplicate fixes, and reintroduce bugs. Listing affected siblings prevents re-discovery of the same limitation across the codebase.
