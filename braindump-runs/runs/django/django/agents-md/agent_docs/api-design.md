# API Design and Public Interfaces

> Rules for designing public APIs, class interfaces, decorators, manager methods, and reusable helpers with stable contracts.

**When to check**: When designing or changing public APIs, class interfaces, decorators, or reusable helper contracts.

## Rules

<!-- rule:3337 -->
- For `hashlib` calls, omit `usedforsecurity=True` (it's the default); pass `usedforsecurity=False` only for non-security uses like cache keys or ETags. — Explicit `False` lets non-security hashes (cache keys, ETags) run in FIPS environments where they'd otherwise be rejected; omitting the default `True` keeps calls clean and avoids implying a security intent that isn't there.
  Redundant `True` adds noise, while an explicit `False` lets non-security hashes (cache keys, ETags) run in FIPS environments where they'd otherwise be rejected.
<!-- rule:4592 -->
- **Require explicit relationship paths in ORM expression APIs** — e.g. in `django/db/models/expressions.py` and `django/contrib/gis/db/models/lookups.py`, make callers pass the relationship name/path and queryset rather than having internals auto-generate joins or unwrap composite values. Implicit traversal special-cases one usage pattern, hiding join costs and producing ambiguous semantics for other callers; explicit paths keep behavior predictable and generic across all expression APIs. — Implicit join generation or composite-value unwrapping makes the API behave differently for one caller shape than others, which hides query cost and breaks composability — explicit relationship name/path + queryset keeps the contract uniform.
<!-- rule:4354 -->
- Accept `force_insert: bool | tuple[type[Model]]` in MTI `save()`; normalize `True`→`(cls,)` and `False`→`()` so current-class-only behavior is unchanged. Require each tuple entry to be a `ModelBase` and a real base (`issubclass(cls, item)`) — typos would otherwise silently skip the forced insert. — The `force_insert` tuple API exists to force `INSERT`s on specific bases during diamond-shaped MTI, where the default behavior can pick the wrong base. Normalizing bools keeps backward compatibility; validating entries prevents silent no-ops; restricting docs to diamond inheritance avoids encouraging redundant or invalid tuple usage; and using concrete classes in tests ensures per-base forcing is actually exercised.
  - Document tuple `force_insert` only for diamond/multiple-branch inheritance (`D(B, C)` → `save(force_insert=(B, C))`), not linear ancestor chains — the default already inserts those, so documenting them misleads readers.
  - Test tuple `force_insert` interactions with `force_update` using concrete model classes, not `models.Model` — `models.Model` forces every base and hides the per-base behavior.
<!-- rule:5407 -->
- Expose upload-handler lifecycle hooks (e.g. cleanup) as overridable methods on `FileUploadHandler` in `django/http/uploadhandler.py`, and call them polymorphically from `django/http/multipartparser.py`. Never import concrete subclasses, use `isinstance` checks, or read handler-specific attrs like `.file` — keeps third-party handlers pluggable without parser changes. — `django/http/uploadhandler.py` defines `FileUploadHandler` as the extension point for third-party upload handlers; `django/http/multipartparser.py` consumes them. If the parser hardcodes knowledge of concrete handlers (imports, `isinstance`, `.file`), any handler that doesn't match those assumptions breaks the parser — outside contributors can no longer add handlers by subclassing alone, and lifecycle behavior like resource cleanup can't be customized per handler.
<!-- rule:5648 -->
- For non-mutating delegation on copies, use `super(Class, copied_instance).method(...)` — bare `super()` binds to the original instance, so the copy silently diverges from the object the caller is actually using. — Both halves guard the same class of bug: a clone that looks correct but is wired to the wrong instance or the wrong config. Explicit `super(Class, copied_instance)` forces the delegate call onto the copy, and threading caller args through the clone helper keeps the clone behaviourally identical to what the caller asked for.
  - Forward caller-supplied args (e.g., `name`, `driver`) into clone helpers instead of dropping them — the clone then inherits the caller's configuration rather than hardcoded or default state.
<!-- rule:6175 -->
- Access app-registry state via `Apps` methods/properties, not internals — Callers like `django/core/management/__init__.py`, database backends, and management commands should use named checks (e.g. `Apps.is_initializing`) instead of reading/assigning `apps.ready`, `apps.apps_ready`, `apps.models_ready`, `apps.all_models`, `apps.app_configs`, or `apps.stored_app_configs` directly — keeping transition and reset logic inside `django.apps.registry.Apps` prevents state inconsistency across call sites.
<!-- rule:5919 -->
- Reverse operand order in the `as_{backend}` override, not the public API — also flip `arg_joiner`/SQL operators so emitted SQL stays correct; keeps the wrapper's public interface stable across backends. — Prevents breaking callers of the wrapper while preserving per-backend SQL semantics.
<!-- rule:6291 -->
- Match `accept` attributes and doc MIME types to validator constraints — `image/*` promises subtypes the backend rejects — Exposing broader types than the server-side field accepts leads to confusing validation failures after upload.
<!-- rule:5016 -->
- For UTC/GMT date values (HTTP-date, GMT formatting), use timezone-aware UTC helpers — `datetime.datetime.now(datetime.timezone.utc)`, `formatdate(..., usegmt=True)` in `django/utils/http.py` — not naive `datetime.date.today()`/`datetime.datetime.now()` or manual GMT string assembly; naive calls inherit local time and produce wrong HTTP-date values in tests like `tests/utils_tests/test_http.py`. — Timezone-naive calls produce local-time values that silently break HTTP-date serialization and round-tripping; using timezone-aware UTC helpers keeps `django/utils/http.py` output and its tests correct regardless of the host's timezone.
<!-- rule:4574 -->
- Prefer dataclass-generated or identity-based equality for task/model classes (e.g. `django/tasks/base.py`) — custom `__eq__` added only to widen API surface invites drift — Placed globally (with a note that it applies to the Django task execution module, `django/tasks/base.py`, and model-layer dataclasses like `django/db/models/sql/datastructures.py`) so any assistant touching equality or ordering on dataclass-backed types finds it. The rule prevents two recurring problems: (1) equality semantics leaking into API design through scattered exclusions that future callers cannot discover, and (2) unstable ordering when non-unique fields such as priority or timestamps drive comparison. Both are silent-failure classes — they surface as test flakiness or subtle collection misbehavior rather than as compile-time errors.
  - Centralize equality exclusions in an explicit `__eq__` or slice of the canonical identity tuple — `compare=False`, boolean equality flags, or per-field comparisons scatter the contract and hide which field is excluded
  - Add `__lt__` only for a concrete caller, and base it on a unique identifier or stored instance — ordering on priorities or scheduling timestamps is unstable and can silently reorder collections
<!-- rule:5548 -->
- For Django GIS APIs accepting spatial references, name the parameter `srs` (not `srid`), accept polymorphic input (`SpatialReference`, WKT, PROJ string, integer SRID), and normalize integer-like strings to `EPSG:<srid>` in `SpatialReference.__init__` / `srs_input` in `django/contrib/gis/gdal/srs.py`. Mirror the accepted forms in `docs/ref/contrib/gis/gdal.txt`. — `srs` signals polymorphic input while `srid` implies an integer-only field; normalizing bare integers to `EPSG:<srid>` in one place keeps WKT/PROJ/SRID callers working through the same path, and keeping code and docs in sync prevents users from passing forms the parser silently rejects.
<!-- rule:5097 -->
- **Rule:** Relation-manager methods (`add()`, `remove()`, `set()`) and custom managers (`create_user()`, `create_superuser()`) accept the target field value: PK by default, or the `to_field` value when set. — Preserves Django's ID-based public contract for relation-manager and custom-manager methods, preventing backward-incompatible changes when `to_field` is set or when callers rely on scalar/list-of-scalar signatures.
  **Rationale:** These are public API contracts — users pass scalars for FK `_id` fields and lists of scalars for M2M. Silently accepting model instances or calling `.pk`/`.id` on args would break existing callers and diverge from Django's documented behavior.
  **How to apply:**
  - Take scalar ids for FK `_id` fields, lists of ids for M2M.
  - Respect `ForeignKey.to_field` — the accepted value is `to_field`'s type, not always the PK.
  - Don't auto-detect instances or coerce ids internally.
  - Document and test both the default-PK and `to_field` cases.
<!-- rule:6184 -->
- Pass lookup/transform variables via `__init__`, not dynamic classes or class attrs — enables reuse and per-query config — Django ORM lookup/transform stages (e.g. in `django/db/models` and `django/contrib/postgres/fields`) need to vary their parameters per query. Defining a new class per lookup causes class explosion and prevents caching/introspection; relying solely on class-level attributes makes every instance of the lookup share the same config, so queries with different parameters collide. An `__init__` (optionally paired with a callable/factory that binds args for a given query) keeps the stage class reusable while giving each query its own parameters.
<!-- rule:4521 -->
- Return generated text/data from helpers instead of printing — output in shared entry points silently becomes a de facto API that callers depend on and you can't change. — Observable output from widely-reused helpers is hard to detect and remove later; tests, wrapper scripts, and downstream tools latch onto it, so any change becomes a breaking change.
  Applies across `django/core/management/__init__.py`, `django/test/utils.py`, and similar frequently-invoked entry points: keep them side-effect-free and let the caller choose what to display.
<!-- rule:1430 -->
- Implement `__reduce__` on dynamically created classes that must be picklable across interpreters — default pickling resolves classes by name and can't reconstruct runtime-built ones — Dynamically constructed classes have no importable dotted path, so pickle's default by-reference mechanism fails on unpickle in another process. Returning an explicit reconstruction callable and args makes the class transportable without relying on import machinery.
<!-- rule:2613 -->
- For public decorators in `middleware`, `urls`, and `views`, support both bare `@decorator` and parameterized `@decorator(...)` forms — matches Django's ergonomic-defaults pattern and avoids breaking call sites; only add dual-form support when the API contract or usability demands it. — Dual-form decorators let users call `@decorator` for defaults and `@decorator(...)` to override per use, mirroring Django's own conventions in `middleware`, `urls`, and `views`. Adding both forms without a real contract need bloats the API surface and complicates introspection (e.g., distinguishing a decorator wrapping a function from a decorator factory), so reserve it for cases where ergonomics or backward compatibility require it.
<!-- rule:3401 -->
- Preserve the `process_rhs` contract when overriding it in Django lookups — delegate to `super().process_rhs(...)` when you add no logic, keep `rhs_params` a `tuple` (`django/db/models/lookups.py`, `db/models/fields/json.py`, `contrib/postgres/search.py`), and guard string ops on `params` with `isinstance(param, str)`. — The base `process_rhs` implementation relies on these assumptions to build and compare lookup parameters; deviating breaks cross-backend lookup behavior.
<!-- rule:4126 -->
- Centralize manager behavior on the base `Manager` in `django/db/models/manager.py`, not on subclasses like `GenericRelatedObjectManager` or new `get_for_*` helpers — All manager subclasses inherit it consistently, custom managers can override it, and the API surface stays small. Access it via `self.__class__._default_manager.method(...)` or existing methods with explicit options (e.g., `get_for_model(Model, for_concrete_model=False)`) rather than referencing concrete manager classes directly.
<!-- rule:1100 -->
- When adding or changing a supported model-field `choices` format, mirror it in `forms.ChoiceField.choices` — model and form layers parse `choices` independently, so a model-only change silently breaks form/admin rendering. — Django's model field and `forms.ChoiceField` normalize `choices` through separate code paths, so support for a shape (e.g. grouped, callable, enum) must be added in both places or forms/admins will render or validate incorrectly. Keeping exactly one test per supported shape, and removing tests for dropped shapes, keeps the supported-shape contract honest across model, form, and admin code.
  - Add `choices` tests at both the model and form/admin level, with one test per supported shape; delete tests for shapes you intentionally drop — stale shape tests mask regressions and give false-green suites.
<!-- rule:6115 -->
- Parse each request/query param from the key matching its meaning; store it in a purpose-named attribute, not a generic `params` dict — prevents aliasing bugs where one key silently feeds unrelated values and breaks when the param is renamed or repurposed. — View code that reuses one request key as another variable's source, or dumps everything into a broad `params` dict, hides which parameter actually drives each value. When the key is renamed or its meaning shifts, unrelated logic changes silently. Reading from the semantically correct key and storing it in a purpose-named attribute keeps each value tied to its source.
