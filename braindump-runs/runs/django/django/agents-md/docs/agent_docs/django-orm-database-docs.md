# Django ORM & Database Documentation

> ORM relations, model fields, choices, validation, through models, deletion, inheritance, and behavior descriptions.

**When to check**: When documenting Django models, QuerySets, lookups, relations, or database behavior.

## Rules

<!-- rule:665 -->
- In ORM filter/combine docs, use relation-spanning examples (`authors__name`, `entry__headline`) and link `spanning-multi-valued-relationships` — multi-valued joins silently change result sets, so local-field examples, 'other'/'different' wording, or implying chained filters are universally equivalent misleads readers. — Multi-valued relationships can produce duplicate rows and different join semantics than local fields, so spanning examples plus an explicit link to the `spanning-multi-valued-relationships` section prevent users from assuming chained filters are equivalent and from writing queries that return unexpected results.
<!-- rule:1538 -->
- Anchor new DB APIs to familiar ORM equivalents in `docs/topics/db/` and `docs/ref/settings.txt` — e.g., state `FETCH_PEERS` ≈ `prefetch_related()` and link to analogous write-ups like the `F()` concurrency note for `JSONSet` — so readers port intuitions instead of guessing. Add side-by-side raw-SQL vs. ORM examples, say when to prefer the higher-level call, and put an admonition when it already covers the use case, to keep escape hatches from becoming the default. — Django's DB docs are read by people who already know `prefetch_related()`/`F()` but not the new primitive; framing new or escape-hatch APIs as contrasts with those anchors prevents both misuse (reaching for raw SQL when the ORM suffices) and under-use (missing `JSONSet` because it isn't tied to the familiar `F()` story).
<!-- rule:2775 -->
- **Document each model validation method's skips individually** — the fields dropped by `exclude`, keyword args containing a `__` lookup separator, and virtual/generated fields like `pk` or `GeneratedField` — never claim uniform behavior across methods that share an `exclude` argument. — Shared arguments don't imply identical behavior: an `exclude` or a similar-looking signature can be honored by one method (`clean_fields(exclude=...)`) but ignored or handled differently by another (`full_clean`, `validate_unique`), so users who read a single blanket description miss real mismatches. For virtual/composite fields like a Django composite `pk`, resolve exclusions through constituents — excluding the virtual `pk` itself has no effect on `clean_fields(exclude=...)` while `full_clean` may still validate it via `validate_unique`, and excluding any constituent field should also exclude the virtual field. Flag surprising cases (e.g. a method that delegates to another validation step which still applies effects) with an admonition so readers don't have to infer them from the prose.
<!-- rule:2405 -->
- Update composite-pk generic detail-view docs with `<int:pk>` URL examples and `get_object()` resolution behavior — Users copy snippets from `docs/howto/composite-primary-key.txt` and `docs/ref/class-based-views/mixins-single-object.txt` into their URLConf and CBVs, so stale examples break composite-pk detail lookups. Also cover that URLConf patterns may split `pk_fields` attnames across any segment with no comma, that `get_object()` 404s on missing keys, and remaining gaps (`GenericForeignKey`, relational fields, Django admin).
<!-- rule:4545 -->
- Document ORM behavior generally, not by example; specify what's affected (`Model` vs rows/queries) — a single example implies coverage it lacks, and readers must know whether a `Model` instance or a DB row/queryset is at stake. — Behavioral prose in `docs/ref/models/` and `docs/ref/django-admin.txt` is read as general contract, not a single trace. Describing one path (or one backend) overstates or understates what actually happens, and conflating `Model` instances with database rows/queries sends readers to the wrong layer when debugging.
<!-- rule:1101 -->
- Describe `choices` as an ordered pair mapping (iterable of 2-tuples), not a concrete "dictionary" — the container type isn't part of the documented contract — `choices` accepts several shapes and the concrete container is an implementation detail users shouldn't depend on, so framing it as a "dictionary" misleads readers who may pass tuples. Ordered input-form docs before display-method docs let readers understand the accepted input before the derived output. Nested/grouped `choices` break the flat 2-tuple assumption, so describing optgroups next to `ModelChoiceIterator`/`ChoiceField.choices` prevents users from hand-rolling iteration. Leading with the constants-in-model pattern matches how most Django users define choices, so advanced Enum/`ChoiceEnumMeta` examples don't scare off the common case.
  - Enumerate all accepted `choices` forms (tuple, list of 2-tuples, dict, grouped list-of-tuples mapping name→dict) before derived-behavior sections like `get_FOO_display` — readers need to see inputs before outputs
  - Document nested `choices` (optgroups) beside `ModelChoiceIterator` and `ChoiceField.choices` — flat 2-tuple iteration doesn't apply to grouped choices
  - Show the constants-in-model-class pattern before `ChoiceEnumMeta`/Enum variants — most users only need the simple form; keep examples consistent with the canonical inheritance
<!-- rule:1423 -->
- In temporal field/lookup docs (e.g. `docs/ref/models/querysets.txt`), drop field-type qualifiers implied by context — write "fields" not "datetime fields". Match absence claims to the field type: time fields lack a date component; date fields lack a time component. Phrase descriptions naturally ("The date/time when {event}"). Redundant qualifiers and mismatched absence claims make reference docs harder to scan and spread inaccurate statements about field behavior. — ...
<!-- rule:3357 -->
- In `docs/` pages on `ManyToManyField` `through` models, use the auto-created `.through` accessor in examples and keep prose tight — the implicit accessor is what users actually have, so bespoke wording or manual-through examples mislead them. — Django's docs are the canonical reference users copy from, so example style and caveat coverage directly shape real schemas. Preferring `.through` matches what Django auto-generates, and flagging the lost unique constraint and required defaults prevents the two most common custom-`through` bugs (duplicate M2M rows and insert failures). Scope is `docs/`-only, so it belongs in `docs/AGENTS.md` rather than a repo-root file.
  - Document custom `through` model caveats explicitly: the implicit unique constraint is not auto-preserved, and non-PK fields may need defaults — omitting these lets users silently ship duplicate rows or `IntegrityError`s.
  - Applies across `docs/ref/models`, `docs/topics/db`, and `docs/howto`; since it's docs-only, keep it scoped to `docs/AGENTS.md` rather than root.
<!-- rule:2371 -->
- State each operation's effect on associated data and how manually-maintained fields stay populated — Readers can't infer which data changes when an operation runs, or how a field like a composite primary key stays filled — name the effect (e.g. 'sets the associated field values') and at least one mechanism such as `database triggers`, linking to external docs
<!-- rule:5117 -->
- Document abstract-specific behavior in the abstract base classes section of `docs/topics/db/models.txt`, cross-referencing the existing inheritance section rather than restating attribute lists — duplication drifts out of sync. — Duplicate attribute lists across docs and reference drift apart, so cross-referencing keeps a single source of truth. Without explicit scope (abstract vs. concrete vs. proxy-only) and rationale tied to Python inheritance, readers apply rules to the wrong model types and file bugs about `Meta` options on proxies.
  - State the exact scope of each inheritance behavior: `abstract`, concrete, or both; note that `Meta` inheritance applies to abstract and non-abstract models but not proxy-only models — readers otherwise misapply the rules.
  - Explain which attributes inherit (and which don't), tie the behavior to Python's standard inheritance rules, and specify how placeholders substitute into child models — the underlying rationale is what lets readers reason about edge cases.
