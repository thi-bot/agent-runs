# API Design & Public Interfaces

> Rules for designing public APIs, parameters/options, hooks, widgets, classes, and services: minimal honest signatures, explicit dependencies, backward compatibility, overridable hooks, and accessor design.

**When to check**: When designing or changing public APIs, class/method signatures, hooks, widgets, or extension points.

## Rules

<!-- rule:71 -->
- Keep methods single-responsibility: split unwieldy methods into purpose-named helpers at clear concern boundaries — hidden concerns in misnamed methods are hard to discover, test, and reason about. Avoid premature fragmentation of cohesive logic — over-splitting scatters related code. If a method gains a concern its name/docstring doesn't convey, extract a new purpose-named method and share common logic via private helpers. When a helper is decoupled from the class/collection that gave it context, rename it for its standalone responsibility rather than keeping its former-context name. — Purpose-named helpers make responsibilities discoverable and testable; legacy-context names mislead readers about what the code actually does.
<!-- rule:1877 -->
- Use `related_set.set(...)`/`.add()` and skip `.save()` for M2M relations — the manager persists the change; `.save()` triggers redundant writes and save signals — Related managers like `set()` and `add()` already persist many-to-many relations in Django. Calling `.save()` on the owner instance afterward causes redundant database writes and fires unnecessary save signals, which can trigger side effects like cache invalidation or signal handlers in code such as Wagtail's `admin`, `images`, and `users` modules.
<!-- rule:2437 -->
- When renaming URL routes, update all `reverse()` calls and add old→new mapping in release notes — stale names cause `NoReverseMatch`. — The route name is referenced across multiple apps (e.g., `wagtail/documents`, `wagtail/contrib/styleguide`) and docs release notes; missing a reference breaks at runtime, not import time.
<!-- rule:4 -->
- Pass dependencies explicitly as parameters (resolved DOM/jQuery nodes, callbacks) rather than capturing closure/ambient state — callers can't see hidden deps, which breaks reuse and testing; pass the target/action directly instead of an identifier the helper resolves internally — Explicit parameters make a function's dependencies visible at the call site, so it can be reused, mocked, and reasoned about without tracing enclosing scopes.
<!-- rule:677 -->
- Pass view/backend specifics via options (e.g., `ignoredButtonsSelector`), widget context, or data attributes — never hardcode CSS selectors, field IDs, or model constraints in shared utils/frontend JS; resolve dynamically via `field.get_bound_field(...).id_for_label` so behavior stays aligned with the calling view/form context. — Hardcoded selectors, IDs, and constraints couple shared utilities and JS controllers to one view/form, silently breaking when the same code is reused elsewhere. Caller-supplied options and dynamic resolution (e.g., `id_for_label`) keep reusable code context-agnostic.
<!-- rule:1344 -->
- Add parameters only when a concrete caller needs them — unused args, default assignments, and speculative options become dead API surface — A fixed default plus documented deterministic ordering beats an `order`/priority flag nobody sets
<!-- rule:1512 -->
- Keep model-specific helpers on the model class itself — `@staticmethod`, `@classmethod`, `@cached_property`, or `@property` — not as standalone utils functions, externally-set instance attributes, or new settings. Co-locates behavior with model state, aids discoverability, and enables per-instance caching. — Model-specific behavior lives where developers expect to find it, and `@cached_property`/`@property` can cache per-instance results — impossible when the same logic is scattered in utils modules or bolted on via ad-hoc attributes.
<!-- rule:184 -->
- Scope new behavior to the narrowest caller, component, or UI context it serves — Modifying a shared utility or globally-applied plugin for one caller's needs risks breaking unrelated consumers; keep changes local unless the behavior is genuinely universal
<!-- rule:2125 -->
- Re-export moved public names from the original module (or add a version-specific deprecation shim) — silent removals break downstream Wagtail imports [keep rule under 100 chars] — Wagtail's public modules (`wagtail.models`, `wagtail.admin`, `wagtail.search`, etc.) are imported directly by third-party packages and site code. Removing or relocating a public name without a shim breaks those imports at runtime with `ImportError`/`AttributeError`, often only surfacing in production. Re-exporting (or shimming with a `RemovedInWagtailXWarning`-style message) keeps old import paths working while steering users to the new location.
<!-- rule:1046 -->
- Aggregate every rendered component's `media` into the view context's `media` (via `get_media`/media collector), even if the component currently declares none — components can start exposing media later, and missing aggregation silently breaks their CSS/JS in the admin. — Treating `media` as part of a rendered component's contract (panels, forms, edit handlers, side panels, action menus) keeps Wagtail admin views forward-compatible: a component that adds `media` later still gets its assets loaded without touching every composing view. Views/templates that render a shared media-exposing component must include that component's media for the same reason.
<!-- rule:504 -->
- Mirror third-party library option names in public API — upstream docs match 1:1, so users don't need a translation layer; avoid local synonyms (e.g. `custom` for `spec`) or generic `_config` suffixes — API mirrors upstream docs; stable shape as options grow; comments prevent future devs from 'fixing' intentional naming divergence.
  - Group a library's settings under one nested `spec`/`config` object, not one top-level key per option — lets the interface grow without changing its shape
  - When the library is an implementation detail site authors shouldn't know, name the setting in project-domain terms instead
  - If a param, attribute, or config key intentionally diverges from upstream (misleading name, broader values — e.g. upstream `parentID` accepting any selector), add a brief comment at the definition or mapping site explaining the naming rationale and accepted values
<!-- rule:1804 -->
- Route all image handling in Wagtail code through Willow, never `PIL` directly — including tests, format conversions, and content-type lookups. Use Willow's `mime_type` property for format→MIME mapping instead of local helpers. Willow abstracts the imaging backend (Pillow is one implementation), so direct `PIL` imports bypass that boundary, risk diverging behavior across backends, and duplicate mappings that Willow already provides. — Willow is the abstraction layer; `PIL` is an implementation detail. Direct imports break backend-agnosticism and duplicate `mime_type` logic.
<!-- rule:1201 -->
- Prefer explicit, component-supported contracts over inference in component APIs — use structural type guards like `Array.isArray(prop)` rather than inspecting string values or prefixes; derive conditional UI from an explicit structural/state prop rather than the presence/absence of another prop; expose and query opt-in values (e.g., in `BASE_ATTRS`) instead of inferring intent from DOM structure; and use existing third-party component props/configuration instead of writing custom wrappers. — Inference-based contracts silently break when unrelated markup or prop values change, and they hide intent from callers — this pattern recurred across `Icon`, `ExplorerHeader`, `TooltipWrapper`, and `Minimap`. Configure existing third-party props rather than writing custom wrappers to avoid duplicating maintained behavior.
<!-- rule:1628 -->
- Distinguish absent (`None`) from blank (`''`, `[]`, `{}`) — conflating them corrupts output and hides bugs — Absent and blank trigger different downstream behavior throughout `wagtail/core`, `wagtail/admin`, `wagtail/images`, and `client/src`; using truthiness or empty-container fallbacks silently merges the two states, producing wrong output for optional blocks/widgets and defeating null-safety.
    - Test absence with `is None`, never truthiness; when a fallback is needed return a meaningful default, not `''`
    - Use `is None` in checks (or `hasattr(x, 'y') and getattr(x, 'y') is not None`) to guard optional attributes
    - When blank and absent behave differently, model the distinction with an explicit flag (e.g. `decorative`) instead of overloading `''` vs `None`
    - For optional block/widget values (e.g. `CharBlock`, `value_from_datadict`), preserve/default to `None` and don't pass `None` through value converters
    - Reserve `''` for non-nullable string model fields; use `None` everywhere the field can be null
<!-- rule:2615 -->
- Route file cleanup through `post_save`/`post_delete` signals and the storage API instead of form `save()` hooks or manual `MEDIA_ROOT` deletion — keeps every mutation path (admin, forms, `core/management/commands`, `images/management/commands`) consistent and works with non-filesystem backends — Signals cover all write paths; the storage API handles S3/remote backends that manual `MEDIA_ROOT` removal breaks.
<!-- rule:1615 -->
- Use `widgets.AdminPageChooser` with a `ModelChoiceField` for admin page selection, passing target models via `page_models=`. Don't hand-roll `ModelChoiceField` subclasses, custom label building, `RadioSelect` querysets, or manual `ContentType` lookups for `content_type` — the shared widget already handles chooser JS, permissions, and label rendering correctly. — Placement: repo-root `AGENTS.md` — this governs any Wagtail admin page-selection form across `wagtail/admin`, `wagtail/wagtailcore`, and `wagtail/wagtailadmin`, so it should surface as a project-wide convention rather than a per-module note.
  `PageChooserPanel.target_models()` must return the target model for a `ForeignKey` pointing at a specific model, even when no widget override is set — otherwise choosers over-resolve to base `Page` and lose type filtering.
  When resolving a lowest common ancestor, return the nearest non-creatable intermediate `Page` subclass instead of falling back to base `Page` — a creatable base fallback lets users pick page types the form never intended.
<!-- rule:460 -->
- Centralize shared or subclass-overridable defaults on the base class, its inner `Meta`, or a shared module-level mapping rather than duplicating literals in concrete subclasses — keeps subclasses thin and prevents drift when the base changes — The rule describes a general API-design convention for centralizing shared/overridable defaults. Evidence spans `wagtail/blocks/*.py` (base, `field_block`, `stream_block`, built-in blocks) and `wagtail/admin/views/generic/chooser.py`, plus `wagtail/admin/panels/base.py` — not scoped to a single directory. Behavioral rather than cross-file relationship; applies to general class-design patterns rather than a specific entity.
  - Express subclass/type-specific defaults declaratively (`Meta`, `get_default` hooks), not via custom constructor kwargs — kwargs defeat subclass configuration
  - Don't use sentinel `Meta.default` values on built-in blocks to encode type-specific fallbacks — leaves the base `Meta.default` generic and overridable
  - For chooser classes/blocks, declare an overridable class attribute defaulting to `None` and resolve it in the accessor via `self.<attr> or <DefaultClass>` (or `BlanketPermissionPolicy(None)` when no model exists) — avoids hardcoded class-scope defaults that subclasses can't override
<!-- rule:2361 -->
- Publish scheduled pages by publishing the existing revision with a non-null `approved_go_live_at` (`Page.get_scheduled_revision_as_object()`) in place — creating a fresh revision loses the approved content and diverges from the revision the editor signed off on. — Scheduled publishing is the act of publishing the already-approved revision, not updating the page; minting a new revision would publish unapproved content and break the audit trail between `approved_go_live_at` and what goes live.
<!-- rule:1990 -->
- Keep controllers and action classes single-purpose — generic controllers (`client/src/controllers/*`, `wagtail/core/actions/*`) are shared by every consumer, so embedding feature-specific UI logic, global side effects like `window.scrollTo`, or state flags that suppress events leaks behavior into unrelated features. Emit generic events, reuse the owning component's focus/transition logic, or fix the shared controller/plugin at its source instead. — Keeps shared controllers safe for all consumers, prevents cross-feature side effects, and preserves a consistent API surface for client and Wagtail action directories.
  - Split distinct behaviors into separate action methods or dedicated controllers, and implement nested/child operations directly or via shared helpers rather than constructing and executing other action instances — avoids hidden coupling and duplicated side effects.
<!-- rule:334 -->
- Use `wagtail.coreutils.accepts_kwarg` when introducing a new optional keyword arg to overridable, hook, or polymorphic callbacks — avoids fragile `__code__.co_varnames` introspection and ad-hoc `try`/`except TypeError` compat checks that silently break subclasses. — Override sites and hook implementations may not yet accept the new kwarg; `accepts_kwarg` lets you pass it only where safe without probing callable internals or catching unrelated `TypeError`s from inside the callee.
<!-- rule:2311 -->
- Return API errors as `success: false` + stable `error_code` + translated `errorMessage` — clients branch on `error_code`, not the human message, so wording stays free to change — The rule describes a repo-wide API/JSON error contract rather than anything tied to a single module. Evidence spans multiple directories (`wagtail/admin/views/pages/edit.py` and `wagtail/api/v3/errors.py`) plus frontend/project consumers, and the rule explicitly coordinates backend (Python) and frontend (TypeScript) definitions. Because it governs every API endpoint and both client and server code, `agents_md_root` gives the broadest, most findable placement.
  - Define error codes as a Python Enum in `wagtail/api/v3/errors.py` and mirror them in TypeScript — inline string literals drift between `wagtail/admin/views/pages/edit.py` and frontend consumers
<!-- rule:50 -->
- Detect cache hits with explicit `None`/`null` checks, not truthiness — empty containers (`[]`, `{}`) are valid cached results, so truthiness collapses "not cached" with "cached but empty" and misroutes callers that distinguish those states. Only collapse the two states when callers genuinely can't observe the difference, and skip redundant truthiness guards before assignment when a downstream `None`/`null` cache check already covers it. — Preserves sentinel semantics (`None` = not fetched vs. empty = cached-empty) so prefetch/cache consumers in `wagtail/models`, `wagtail/images/models.py`, and `client/src/controllers/RulesController.ts` don't misfire on empty-but-valid results or duplicate null-handling logic.
<!-- rule:2287 -->
- Use `str(obj)` when formatting model instances into messages, not hard-coded fields like `.title` — `__str__` stays canonical as models evolve, so field-poking drifts silently; for genuinely optional attributes use `getattr(obj, "attr", str(obj))` so diagnostic paths can't raise a secondary `AttributeError`. — Format model instances with `str(obj)` rather than duplicating fallbacks such as `getattr(obj, "field", str(obj))` or hard-coding `.title`; `__str__` is the maintained canonical representation, so hard-coded fields drift as models change and optional-attribute lookups risk raising `AttributeError` in the very paths meant to report errors.
<!-- rule:2389 -->
- **Wagtail modal/editor workflows**: handle AJAX submissions in-place using ModalWorkflow JSON conventions — check `request.is_ajax` and return `{'step': 'success', 'redirect': <url>}`; wire forms via `ajaxifyForm` with a `'success'` handler instead of full-page redirects or custom submit handlers. In-place handling preserves unsaved user input and avoids losing modal state. — Full-page redirects on modal submit discard unsaved input and break the editor's in-place flow; the ModalWorkflow JSON contract (`{'step': ...}`, `request.is_ajax`) and `ajaxifyForm` `'success'` handler are what the admin JS expects, so custom handlers silently break modal state.
<!-- rule:3028 -->
- Put dialog config `data-*` attributes on the dialog root, not the toggle — the toggle is the trigger, so co-locating data there breaks reuse when the same dialog is opened from multiple triggers. — why does this matter?
<!-- rule:1777 -->
- Return `FileResponse(open(path, "rb"))` for file-like content, not `HttpResponse` — it streams and closes the file for you, so never wrap it in a `with` block — Passing an open object directly lets Django manage the stream lifecycle; wrapping it in `with` closes the file before the response finishes sending.
<!-- rule:1784 -->
- Expose Block subclass-specific behavior via overridable hooks on the base `Block` class (property, attribute, or method with a sensible default), overriding only where a value exists — callers then stay subclass-agnostic, avoiding `child.block.field` coupling in shared code/templates and `isinstance`-style branching on known subclasses. — Hooks on the base `Block` keep shared templates and StreamField-handling code decoupled from concrete implementations, so adding a new block type doesn't require touching call sites. Enumerating subclasses or reaching into `child.block.field` couples shared code to specific implementations, breaking when subclasses are added or renamed.
  - When adding or refactoring such a hook, apply it uniformly across all sibling blocks that share the behavior (e.g. `StructBlock`, `TypedTableBlock`) — partial adoption leaves the old special-casing path alive and invites regressions.
<!-- rule:2200 -->
- Document guaranteed context-dict keys before the optional section and access them with direct indexing (`context['key']`) — fails loudly when a stated guarantee is broken, so contract drift surfaces early. — Guaranteed keys always exist, so direct indexing surfaces contract drift early instead of silently returning `None`; optional keys are genuinely absent in some callers, so `.get()` prevents spurious `KeyError`s. The `may also contain:` / `'key' = description` convention makes it unambiguous to readers which bucket a key belongs to.
  Document optional context-dict keys under a `may also contain:` section as `'key' = description` and access them with `context.get('key')` — tolerates callers that omit them, avoiding spurious `KeyError`s.

<!-- rule:1605 -->
- Pass 3+ config args as a destructured options object (`= {}`) placed after required args — adding fields won't break callers; prefer spread-able sequence params over `*args`, and keep required args (e.g. DOM elements) positional. — Options objects let you add configuration without breaking existing call sites, and keep signatures readable as they grow — positional lists silently shift meaning on every change. <!-- rule:612 -->
- When changing a constructor or method signature, update every call site across the repo, not just the diff — stale callers crash at runtime and often go unnoticed in tests. Append new optional params at the end, keep renamed params in their original positional slot (move the legacy alias to the end), and never promote an optional param to required in a public API without a deprecation path — preserves backward compatibility for external callers. — Signature changes silently break call sites outside the diff (including client `TypeScript` consumers of `wagtail` core/admin APIs), causing runtime failures that tests may miss. Positional compatibility lets downstream code keep working across upgrades.
<!-- rule:627 -->
- Design methods around the values they actually need: prefer parameters and locals over re-reading or reassigning `self` attributes, never reassign a parameter inside the body, and don't set an attribute that the caller already assigns from the method's return value — redundant state writes make data flow hard to trace and cause stale-value bugs. — When a method both reads/writes `self` and returns values the caller stores back, the same state has two owners; reassigning parameters likewise hides the original input. Explicit inputs and outputs keep the data flow obvious and prevent stale or duplicated state.
<!-- rule:1538 -->
- Express optional params and fallbacks as signature defaults — lets callers override behavior; `null` checks, `||` coalescing, and hidden local constants silently shadow their intent instead — Signature defaults make the fallback value and the caller-override contract visible at the call site. Re-implementing fallbacks in the body (via `null` guards, `||`/`??` coalescing, or a local constant that shadows the parameter) means a caller can pass a value and still be overridden — a silent bug that's hard to spot from the call site and frequently reappears across `wagtail/` and `client/src/` modules (e.g. `InitController.ts`, `initTagField.ts`, `collectors.py`).
