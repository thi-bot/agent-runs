# API Reference Documentation Conventions

> How to describe APIs, parameters, ordering, callbacks, import paths, and supported public contracts.

**When to check**: When writing or editing API reference pages and parameter or method documentation.

## Rules

<!-- rule:993 -->
- Document edge cases only when they're important, non-obvious, or config-dependent — rare/speculative cases in `docs/topics/` and `docs/ref/` bury the primary workflow users actually need. — When an edge case does warrant coverage, fold it into the relevant section as a sentence or small example instead of a standalone admonition, and describe the behavior that does occur rather than only what doesn't — lists of "this doesn't happen" are hard to scan and don't tell users what to expect. Keep it subordinate to the recommended workflow so the main path stays obvious.
<!-- rule:1217 -->
- Group related entries, field variants, and list items under shared headings in `docs/ref`, and document shared metadata once per group — keeps the option/attribute list scannable for lookup; duplicating descriptions, appending to mixed lists, or inserting topic-style headings interrupts the reference ordering readers navigate by. — Reference docs are scanned, not read linearly — sharing headings and metadata avoids repetition while preserving the consistent ordering readers rely on. Mixed lists and topic-style headings break that lookup flow.
<!-- rule:2688 -->
- In `docs/ref/` and `docs/releases/*.txt`, write SQL operator docs as "equivalent to the SQL `<OPERATOR>` operator" — not "shorthand for" — API reference files like `docs/ref/models/querysets.txt` and release notes are read by users cross-referencing many operators at once, so small wording variations ("shorthand for", "the same as", bare symbols) make equivalences look like different features and break search/scanability; naming the operator by the symbol users actually type ("`XOR` operator") is what lets them match docs to code.
  - Use "functionally equivalent", never "functionally the same as" — keeps terminology greppable and consistent across the docs
  - Describe operators with a direct verb + complete noun phrase carrying the code symbol (e.g. "`XOR` operator"); drop redundant syntax qualifiers
<!-- rule:5390 -->
- Document when a returned value differs from its input (transformed, normalized, coerced) — once, with caveats, instead of repeating across the API reference. — Docs like `docs/ref/models/querysets.txt` and `docs/ref/contrib/gis/gdal.txt` describe methods whose return values are often transformed, normalized, or coerced from their inputs. Documenting this once at the definition keeps readers from assuming the input is returned unchanged and prevents the same caveat from drifting across duplicate mentions.
  The rationale: each API reference page (`docs/ref/models/querysets.txt`, `docs/ref/models/fields.txt`, `docs/ref/contrib/gis/gdal.txt`) should state the retrieved-vs-input difference exactly once at the point of definition, so readers aren't misled that the original input is returned verbatim and so the same caveat doesn't drift across duplicate copies.
<!-- rule:1854 -->
- In API reference docs (esp. `docs/ref/*.txt`), write callable descriptions in simple present tense, active voice, with the callable as the subject (e.g., "``method()`` returns X"). Omit filler adjectives ("Existing"), tautologies ("declarative declaration"), and transition words ("then", "Next", "Finally"). State what the API does, not just how to call it. Avoid future tense ("will compute"), passive voice ("X will be returned by"), and release-note qualifiers ("new", "now", "added"). — Reference prose stays uniform and describes behavior/contract rather than release history — release-note phrasing ("now", "added") ages poorly and passive/future constructions obscure what a callable actually returns or does.
<!-- rule:3772 -->
- In `docs/ref/` (e.g. `docs/ref/models/querysets.txt`, `docs/ref/templates/api.txt`), define each argument/method before prose references it — readers build understanding sequentially, so back-references confuse them — Applies across all API/reference docs and release notes (docs/ref/, docs/topics/), so it lives as a documentation-scope guideline rather than being tied to any single file. Mirrors PEP 257/API doc conventions but anchored to this repo's `docs/ref/` layout.
  - List parameters in signature order; put grouped options next to the option they modify; broadly supported params before backend-specific flags — matches how readers scan the signature
  - Lead with the primary/correctness rationale before convenience motivations — readers need the fundamental "why" before nice-to-haves
  - Defer advanced or parameter-specific examples to dedicated subsections lower down — keeps the primary description scannable
<!-- rule:2872 -->
- Document mapping parameters by key: state key+value semantics and enumerate each known key (e.g. `kwargs['signal']`, `kwargs['kwargs']`) in its own row — a sample dict or single `repr` hides the structure users must supply. — Mapping params documented with only a sample value or one collapsed `repr` leave readers guessing at accepted keys and their types, driving misuse and support questions across `docs/ref`, `docs/topics`, and `docs/releases`. Enumerating keys with noun-phrase descriptions makes the contract explicit, matching how the rest of the documentation tree describes structured arguments.
<!-- rule:4037 -->
- In docs, describe callbacks by input and return type only — drop legacy string-resolution wording — Implementation details like string-based callback resolution no longer apply; documenting them misleads readers of `docs/ref/forms/models.txt` and `docs/intro/overview.txt` about the actual API contract.
<!-- rule:6358 -->
- In `docs/topics/http/urls.txt` and `docs/ref/urls.txt`, scope regex capture-group argument-passing behavior to `url()`/`re_path()` specifically (not URL patterns generally) — `path()` uses type converters, so generic wording misleads readers. State that named groups pass as keyword args, unnamed groups as positional args, and unnamed groups are ignored when any named groups exist — mirrors how `RegexPattern` actually dispatches, so docs match runtime. — In `docs/topics/http/urls.txt` and `docs/ref/urls.txt`, scope regex capture-group argument-passing behavior to `url()`/`re_path()` specifically (not URL patterns generally) — `path()` uses type converters, so generic wording misleads readers. State that named groups pass as keyword args, unnamed groups as positional args, and unnamed groups are ignored when any named groups exist — mirrors how `RegexPattern` actually dispatches, so docs match runtime.
<!-- rule:876 -->
- Describe externally observable behavior and required configuration in `docs/` (`docs/howto/`, `docs/ref/`) — not internals like `runserver`, `WSGI_APPLICATION`/`DEBUG` special-casing, or middleware-chain execution; internals drift and mislead users. — Django's docs must stay useful across releases and to readers who only need to know what Django does, not how it's wired internally. Documenting `runserver` internals or `WSGI_APPLICATION`/`DEBUG` special-casing ties the docs to implementation that changes between versions, and third-party setup that isn't essential to Django's behavior adds noise that goes stale. This convention applies throughout the user-facing docs, so it lives in a single `docs/AGENTS.md` covering `docs/howto/`, `docs/ref/`, and `docs/topics/`.
  - Omit tangential third-party links/setup from `docs/` unless essential to explaining Django's own behavior — keeps docs focused and maintainable.
<!-- rule:3213 -->
- In `docs/`, show public import paths (e.g., `django.db.models`, `mail.providers`) in examples — users import from these, so internal re-export paths break their code; put namespace/export rationale in code comments or design docs instead. — Users copy examples verbatim, so documenting internal re-export paths makes examples fail on import. Keeping justification of internal namespace boundaries out of user docs avoids exposing implementation details that may change without a public API change.
<!-- rule:1052 -->
- Merge extra class/form/method capabilities into the primary description in `docs/` (e.g. `docs/ref/models/querysets.txt`, `docs/topics/auth/default.txt`) — trailing `Also, ...` sentences read as afterthoughts and bury behavior readers scan for — Django's class, API, and reference docs are read by scanning, not linearly; a capability split off into its own `Also, ...` sentence is easy to miss and reads as an afterthought. Inlining it in the main description, in impersonal phrasing, keeps every capability in the place a reader already looks.
<!-- rule:4934 -->
- Document naming constraints as normative references to the language spec (e.g., 'must be a valid Python identifier') with links, not enumerated character classes — duplicates drift from the spec and mislead readers when the language changes; distinguish whole-token vs first-character restrictions explicitly (e.g., 'cannot be X' vs 'may not start with X'). — Enumerated character classes duplicate the language spec and go stale as the spec evolves, and conflating 'is X' with 'starts with X' leads users to write invalid values.
<!-- rule:5086 -->
- List supported field/input types by name in docs, not in collective phrases — vague wording makes users assume types like `FileField` work where they don't. Pick example classes that actually support the feature, and call out near-miss types that don't (e.g. model `FileField` can't do multiple files, so use a plain `Form`). — Readers check docs to confirm a specific type works before wiring it up; naming the supported types (and flagging lookalikes that don't qualify, like model `FileField` vs. plain `Form`) stops them from assuming support based on similar-sounding names.
<!-- rule:4247 -->
- Document `ResolverMatch` attributes (`tried`, `captured_kwargs`) in `docs/ref/urlresolvers.txt`, not just in tutorials — the reference is where users look up what's passed to a view. — Users debugging resolved URLs need an authoritative attribute list; burying it in prose leaves `captured_kwargs` (which exposes only the matched kwargs, not the merged `kwargs`) undiscoverable.
