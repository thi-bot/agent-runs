# django/db/models/ Guidelines

## API Design

<!-- rule:4221 -->
- Pickle the original `QuerySet`/`Query` class and full state directly — never rebuild via `model.objects.none()`; dynamically generated `QuerySet` subclasses need an explicit pickling strategy — Rebuilding drops prefetch lookups and column projection and assumes a default `objects` manager that dynamically generated `QuerySet` subclasses may not have; normalize derived state in `__init__` rather than mutating it in `__getstate__`.
<!-- rule:1626 -->
- ## Django ORM ORDER BY handling (`django/db/models`) — This rule targets the Django ORM internals that span `django/db/models/sql/compiler.py`, `django/db/models/sql/query.py`, `django/db/models/query.py`, and `django/db/models/fields/json.py`. Each clause exists to prevent a specific class of bug: dropped expressions, alias/expression identity mismatches, mutation of shared `Query` state during `resolve_expression()`, and silent semantic changes from unsafe ORDER BY pruning. The placement rationale scopes this to `django/db/models` because the constraints only matter to code in the SQL compilation layer — applying them repo-wide would be noise for docs and tests.
  When touching `_order_by_pairs`, ordering-subset comparison, or SQL compilation, preserve query semantics:
  - Include every expression source — `select`, `extra_select`, `annotations`, and `QuerySet.alias()` aliases — when resolving ORDER BY; omissions produce subtly wrong result sets.
  - Resolve annotation aliases to their underlying expression objects and append the resolved object, not the raw alias string — the raw alias isn't comparable at compile time.
  - Treat deprecated `extra_order_by` as raw SQL strings (not a dict), or bail out early when present — misinterpreting it corrupts the generated SQL.
  - Defer `resolve_expression()` on `order_by`/`group_by` until SQL compilation; clone the query when resolution is unavoidable — eager resolution mutates shared state and breaks caching.
  - Raise an explicit unsupported-feature error for combinations like annotation transforms with combined queries or unorderable composite primary keys — silently dropping or partially applying ordering hides bugs from users.
  - Only apply ORDER BY pruning/subset comparison as an optimization when expression comparison is reliable; otherwise return early and keep the full ordering — unreliable pruning changes query results.
<!-- rule:5742 -->
- In Django ORM internals, reconstruct model instances from database values using `Model.from_db()` after resolving deferred fields in the queryset iteration layer (e.g., `ModelIterable.__iter__` in `query.py`); do not manually instantiate and `setattr` fields. For temporary instances needed only to call instance methods, prefer the regular `Model(**data)` constructor over `from_db()` to avoid side effects from overridden loading hooks. — The rule is scoped to Django ORM internals under django/db/models and governs model reconstruction across the query/model-instantiation layer, especially query.py and base.py. It is not limited to a single file, and it is not merely a file-synchronization rule. Placing it in django/db/models/AGENTS.md makes it discoverable whenever an assistant works in the ORM internals where Model.from_db() and ModelIterable are implemented.
<!-- rule:3876 -->
- Resolve the fallback source before compiling a default — in `django/db/models` (e.g. `Case.as_sql`), compute from the always-matching branch instead of pre-assigning a fixed default, treating `FullResultSet` as the effective default and pruning unreachable cases. — An up-front fixed default can diverge from the actual branch, variable, or `Case` fallback it should mirror, producing wrong SQL when the source is another conditional — When a fallback is compiled from a fixed field before the branch or variable that actually supplies it is resolved, conditional SQL compilation can silently emit the wrong default, and an always-true `FullResultSet` case makes later Django `Case.as_sql` branches unreachable. That leaves dead branches and misleading defaults for maintainers, who may debug values that were never applied.
<!-- rule:1229 -->
- Set optional attributes as class-level defaults on `Lookup`/`Transform`/`Expression` bases (`None` for unset, `cached_property` for shared computed values, or a natural identifying attribute) — prevents `AttributeError` when read before `__init__`/`resolve_expression` assigns them, and keeps subclasses overriding only where the value actually differs. — Optional attributes read before assignment or varying by subclass cause `AttributeError` or force arbitrary placeholder values in `__init__`/`resolve_expression`. Declaring them on the base class makes the default explicit and lets subclasses override only meaningful differences, matching how Django's ORM hierarchies (`Lookup`, `Transform`, `Expression`) are expected to behave.
<!-- rule:4926 -->
- Pass `origin=self` and use `self.using` when building the `Collector` in `delete()` — a local `using` or `self.__class__` drops the instance/DB context that deletion signals and multi-DB routing rely on — preserves per-instance signal and multi-DB routing context
<!-- rule:4731 -->
- Check all three `Query` selection masks together — `select`, `annotation_select_mask`, `extra_select_mask` — when detecting explicit developer selection. — Checking only `value.select` or using `a or b` truthiness treats an empty `.select` as "no selection", but a default no-arg `values()` call can still carry annotations via `annotation_select_mask`/`extra_select_mask`. Testing all three masks together detects the explicit-selection case correctly, so the two evaluation sites under `django/db/models` don't diverge.
    An empty `.select` doesn't mean "no selection": default behavior (e.g. a no-argument `values()` call) can still carry annotations, so truthiness fallbacks like `a or b` or checking only `value.select` misclassify the default case. Test the explicit-selection condition directly, consistently across `django/db/models/query.py` and `django/db/models/sql/query.py`.
<!-- rule:3262 -->
- Pass explicit `tzinfo` through `TruncBase`/`Trunc`/`Extract` and backend trunc helpers instead of relying on QuerySet-level defaulting — keeps UTC-to-UTC comparisons and prevents UTC→local→UTC round-trips that shift results near DST boundaries. — When tzinfo is defaulted implicitly at the QuerySet layer, the same transform can behave differently depending on call site, and datetimes get converted back and forth through local time — losing correctness for `USE_TZ=True` users. A single explicit parameter keeps behavior centralized and consistent.
<!-- rule:675 -->
- **Subquery expression internals (`django/db/models`):** — Placed at `django/db/models/AGENTS.md` because the rule spans `sql/query.py`, `sql/subqueries.py`, `expressions.py`, and `fields/json.py` — the shared contract for `Resolvable`/`Compilable` expressions. Cloning in `resolve_expression` prevents subquery semantics from leaking into reused expression/query objects, and compiling via `get_compiler(connection=connection).as_sql()` preserves subclass `as_sql` behavior when nesting subqueries.
  - Have `resolve_expression` return a compilable clone with `clone.subquery = True` — returning `self` or an implicit iteration proxy leaks subquery semantics into shared instances.
  - Preserve subclass `as_sql` and compile embedded subqueries via `get_compiler(connection=connection).as_sql()` — keeps custom SQL overrides working.
  - Don't mutate shared `Query` internals (e.g. set `query.subquery = True` from aggregate helpers) — that flips semantics for every other consumer of the query.
<!-- rule:1576 -->
- Never assume model PKs are hashable in `bulk_update()` — dedupe/compare via equality-based matching or DB-prepared values, and document the hash/equality contract on custom PK field types — unhashable PKs silently break `set()`-based dedup. — These rules live under `django/db/models/` (primarily `bulk_update()` in `query.py`, with PK semantics in `query_utils.py` / `fields.py`) and protect callers who pass custom PK types. Assuming hashability excludes legitimate unhashable PKs; a single-pass, distinctly-messaged validation makes missing vs duplicate PK failures unambiguous; and refusing to write the PK field prevents in-place identity corruption.
  - Validate PKs in `bulk_update()` in a single fail-fast traversal (`set()` seen-check or `Counter`), with distinct `ValueError` messages for missing vs duplicate PKs — callers get an actionable error instead of a wrong write.
  - Reject the PK field from `bulk_update()`'s updatable fields — updating a PK corrupts row identity.
<!-- rule:5543 -->
- Resolve field-list args in public `QuerySet`/bulk ORM methods via `model._meta.get_field()` and validate before dispatching to backend code — rejects non-concrete and m2m fields where the backend would fail obscurely. For update field lists also reject primary-key fields; for conflict-target/unique field lists, allow primary keys and special-case the `'pk'` alias rather than resolving it as a concrete field name. — Field validation at the API boundary surfaces a clear error for unsupported field kinds (non-concrete, m2m, PK in update context) instead of letting the backend raise a cryptic failure. The `'pk'` alias is not a concrete field name, so conflict-target/unique handling must special-case it to keep `'pk'` usable in those APIs.
<!-- rule:1108 -->
- Set `alters_data = True` on data-modifying ORM methods, including `asave`/`adelete` — templates refuse to call marked methods, preventing accidental DB writes — Templates refuse to call methods marked `alters_data`, so this prevents accidental DB writes from template code.
<!-- rule:4604 -->
- In `Query.output_field`, pick composite vs scalar by selected-column arity: single-column selects unwrap to the column's `target`/`field` (or annotation `output_field`) even when `values_select` is populated — `values_select` alone must not force the composite path, or scalar `values()` results get mis-typed — Without arity-aware composite-field detection, `Query.output_field` (PR#21496) can return `None`, causing transform resolution to raise `AttributeError`; without rejecting a scalar `output_field` on composite expressions (PR#21636), callers get silent mis-typing or an ignored value. That inconsistency hides invalid ORM expression contracts until runtime and makes `values_select` cases especially surprising.
  - Multi-column/multi-annotation selects must return a non-`None` field usable by transform resolution — returning `None` breaks subsequent transform lookups
  - Raise `ValueError` when a scalar `output_field` is explicitly set on a composite result — silently ignoring it hides arity mismatches deeper in the pipeline
  - Test both arity paths with `values_select` populated and empty in `django/db/models/` tests — the arity/`values_select` interaction is the usual regression site
<!-- rule:630 -->
- Preserve GROUP BY correlation and aggregation semantics in `get_group_by_cols()` implementations across `django/db/models/lookups.py` and `django/db/models/expressions.py`: correlated subqueries must still contribute their outer references to the GROUP BY even when their own group-by columns are skipped, and aggregation subqueries must never be simplified to projecting a primary key — either shortcut silently changes the caller's grouping and produces wrong result sets. — These shortcuts look like safe optimizations but corrupt the surrounding query's grouping semantics.
<!-- rule:837 -->
- Validate ORM lookup paths by resolved field/alias availability, not nesting depth — depth-only checks in `django/db/models/sql/query.py` accept invalid chains that crash at the database. — Coarse structural checks that only measure nesting level in `django/db/models/sql/query.py` and related query builders let lookups through with missing aliases or joins, which fail at execution time rather than construction time. Basing validation on actual field/alias resolution catches these earlier.
  - Include the full nullable-alias chain for conditional expressions, and verify or add JOINs on subquery rewrites — assuming joins already exist produces queries the DB rejects.
<!-- rule:2670 -->
- ## Django ORM save path (`django/db/models/`) — The raw rule bundles four related save-path contracts for the Django ORM model layer (`django/db/models/fields/*`, `base.py`, `query.py`). Each bullet is imperative, keeps the concrete identifiers that matter (`update_fields`, `auto_now`, `Field.pre_save()`, `has_pre_save`, `FileField.pre_save()`), and states the failure mode the rule prevents: stale columns, unidentifiable compatibility hacks, save-path responsibilities leaking into field classes, missed custom-field overrides, and accidental file writes from probing.
  - Document that `update_fields` does **not** implicitly include save-time-updated fields such as `auto_now`; callers must list them explicitly — omitting them silently writes stale values to the column.
  - Comment compatibility workarounds around `update_fields`/`auto_now` behavior with what would break if removed — without it, future readers can't tell load-bearing hacks from leftover cruft.
  - Keep `Field.pre_save()` returning only the model attribute value — no expression-type checks, backend-feature fallbacks, or expression semantics; the save path in `django/db/models/base.py` owns those concerns.
  - Detect save-time mutation via a `has_pre_save`-style metadata attribute rather than checking flags like `auto_now` — custom fields override `pre_save()` without setting `auto_now`.
  - Never call `pre_save()` as a side-effect-free probe — `FileField.pre_save()` really saves the file, so probing writes unintended data.
<!-- rule:5326 -->
- Construct `Node` instances via `Node.create()` — it is the single overridable factory replacing `_new_instance()`, so direct `Node(...)`, `type(self)(...)`, or `super().__init__(...)` calls bypass subclass-specific construction. — Any code that hardcodes a constructor breaks when a `Node` subclass needs different initialization. `create()` builds a base `Node` and reassigns `obj.__class__`, letting subclasses control construction without duplicating logic across the `django/db/models/query_utils.py` hierarchy and its subclasses under `django/db/models/sql/`.
<!-- rule:3556 -->
- Implement behavior specific to a field or descriptor (e.g., `GenericForeignKey`, non-integer `AutoField`) inside that class — never special-case shared paths like `QuerySet.create()`/`acreate()` or inject defaults into generic field base classes. Ship such behavior via a dedicated refactor with its own tests, an issue reference, and documented public API (no `auto_created`-style internal flags). — The rule's core content is: field-specific logic belongs in the field/descriptor, not in shared `QuerySet`/field-base paths; and when such work is needed, do it as a scoped refactor with tests + issue + public API rather than an internal flag. Rationale explains the coupling/unpredictability cost and the reviewability benefit, matching the requested 'why' style without being deontological.
    Why: core queryset and field-base paths are shared by every model, so field-specific hacks there create hidden coupling and unpredictable behavior for unrelated fields — dedicated refactors keep the change reviewable and the contract public.
<!-- rule:3021 -->
- In `UpdateQuery.add_update_values()`, split keyword names on `LOOKUP_SEP` into local field + transforms only — `update()` can't join or alias, so reject lookups (`gte`, `startswith`) and related-field traversal. — UpdateQuery is the single parser behind QuerySet.update(), and an UPDATE statement has no join clause — so the keyword grammar must stop at transforms and skip lookups and related traversal that filter() supports. Resolving lhs/rhs without joins or aliasing (alias_cols stays False) is what makes that restriction enforceable. Pushing JSONField update lookups through the same transform machinery filter() uses (KeyTransform.get_update_expression calling unwrap_transforms()) means a new transform only has to be defined once, and .update() and .filter() can't drift apart in what a key path resolves to.
  - Resolve `lhs`/`rhs` with no joins or aliasing (keep `UpdateQuery.alias_cols = False`) — an `UPDATE` statement has no join clause to hang them on.
  - Route `JSONField` update lookups through transform composition (`KeyTransform.get_update_expression` → `unwrap_transforms()`), never `LOOKUP_SEP` parsing inside the field — keeps `.update()` semantics in sync with `.filter()`.
<!-- rule:2367 -->
- On `bulk_create`, expose `returning_fields` as an overridable arg; default it to `db_returning` fields plus fields with ≥1 compilable value expression — lets callers opt in without breaking signatures. — `bulk_create` must reconcile the public `QuerySet.bulk_create` API in django/db/models/query.py with the insert compiler under django/db/models/sql/. Making `returning_fields` an overridable argument instead of a hardcoded set lets subclasses and backends extend it without signature breakage, and including fields with a resolvable value expression ensures RETURNING covers values the caller actually supplied. Writing all returned fields — not just PKs — back onto instances (both PK-bearing and PK-less) keeps in-memory objects synchronized with database-generated defaults and computed columns; skipping either case would leave objects stale or force extra queries.
  - Assign every returned field (defaults, generated cols) back onto instances with and without explicit PKs — keeps objects consistent with the DB row.
<!-- rule:3495 -->
- In Django's SQL compiler, build INSERT statements against `qn(opts.db_table)` and skip `model._meta.computed_fields` in the column list — `self.qualified_table_name(...)` is for SELECT aliases, and writing to generated columns breaks `save()`, `create()`, and `bulk_create()`. — `self.qualified_table_name(...)` resolves aliases needed only in query clauses, so reusing it for INSERT emits the wrong target; including `computed_fields` makes the ORM try to write generated/computed columns that the database rejects. Affects `django/db/models/sql/compiler.py` and `django/db/models/query.py`. Scope: `django/db/models`. Category: api_design.
<!-- rule:1979 -->
- Keep `QuerySet` execution methods (`exists()`, `count()`) in `django/db/models/query.py` decoupled from the related field managers they may originate from — don't delegate through `_many_related_manager`, and don't trust `_result_cache is None` as evidence the queryset can be evaluated via its originating manager, since intervening `filter()`/`exclude()`/`annotate()` change the query and produce wrong results. — Placement note: this contract spans `django/db/models/query.py` (where `exists()`/`count()` run) and the manager/related-descriptor layers that construct the querysets, so the rule belongs at module scope rather than pinned to a single file.
  - Store manager-derived context (e.g. related field/instance used to auto-inject FK values) in a dedicated attribute on the `QuerySet` at manager initialization — `_known_related_objects` can hold multiple fields/instances after queryset combination, so inferring origin from it misattributes the FK source.
<!-- rule:4227 -->
- Inspect resolved expressions with `isinstance` (`Ref`, `Col`), not `hasattr` duck-typing — a resolved column reference is often `Ref`, not `Col`, so only `isinstance(expr, Col)` guarantees `target`/`slice_expression` exist and prevents `AttributeError`s masquerading as valid access. — In `django/db/models/expressions.py`, resolved column references can be `Ref` instances rather than `Col` instances. `Ref` and `Col` expose different APIs (`Col` has `target`/`slice_expression`; `Ref` does not), so duck-typing with `hasattr` or assuming `Col` leads to attribute errors or silently wrong behavior during expression resolution.
<!-- rule:5062 -->
- Reuse recursive column-reference helpers in predicates — don't gate on `contains_column_references` or hard-code top-level refs. Recursive predicates like `contributes_to_group_by` and expression-refers-to-column must recurse through wrappers (`OrderBy(RawSQL(...))`, nested `RawSQL`) so results match real query semantics; shallow checks silently misclassify GROUP BY / column usage in `django/db/models/sql/query.py` and `django/db/models/expressions.py`. — A separate non-recursive check duplicates logic and diverges as new expression wrappers are added, producing wrong results for nested expressions like `OrderBy(RawSQL(...))` in the SQL compiler.
<!-- rule:3604 -->
- Route all values through the same placeholder/cast path (e.g. `get_placeholder_sql`); never let callers like `Join` branch around it — keeps cast logic consistent and hides `Field` internals from `Join`. — Skipping the shared placeholder/cast resolution path for compilable vs. non-compilable values causes callers such as `Join` to duplicate or diverge cast decisions and couple to `Field` internals, leading to inconsistent SQL and fragile cross-file changes between `compiler.py` and `fields/related.py`.
<!-- rule:5983 -->
- Propagate metadata flags (e.g. `is_summary`) from the wrapped expression or summary context when wrapping ORM expressions like `Coalesce` around an aggregate — hardcoding them breaks grouping and summary values in nested expressions. — Django's `is_summary` flag drives GROUP BY / aggregate resolution; hardcoding it on derived expressions (e.g. `Coalesce`) desynchronizes them from the wrapped aggregate, producing incorrect SQL grouping and wrong summary results. Propagating from the wrapped expression or surrounding context keeps nested expressions consistent with the aggregate they wrap.
<!-- rule:783 -->

It is an API-design convention for the whole package, so an AI assistant working in this directory should encounter it scoped here rather than at the repo root.
<!-- rule:4702 -->

<!-- rule:6434 -->
- Expose optional field capabilities (e.g. slicing) as opt-in hooks on the `Field`/expression base classes, not via central dispatch. — Add a class flag or overridable method (returning the transform expression or `None`) on the base classes in `django/db/models/expressions.py` / `django/db/models/fields/__init__.py`. Hardcoded `get_internal_type()` lists or direct imports of contrib-specific transforms force edits to central dispatch for every new field and prevent third-party fields from declaring their own support.
<!-- rule:6425 -->

Delegating to the combination API keeps new dunders behaving identically to existing ones.
<!-- rule:4738 -->

Cover both types in regression tests in `django/db/models/`. — The ORM query layer (`django/db/models/query.py`, `django/db/models/sql/compiler.py`) resolves default output-field selection when `values()` is called with no arguments or when a `select` expression yields empty results. If the fallback collapses annotations to a generic placeholder instead of the field's declared output type, callers get wrong types or values at runtime. Tests must assert the returned default per output-field type (at minimum `CharField` and `DateTimeField`) so future refactors of the fallback path can't silently regress annotation contract.
<!-- rule:1404 -->
- Use boolean keyword flags for independent binary SQL options (e.g., `OrderBy(nulls_last=...)`, `UniqueConstraint(nulls_distinct=...)`) in `django/db/models/` — matches the surrounding ORM API and keeps option surfaces composable. — When one option implies another, derive the implied value internally rather than requiring callers to pass both, and never expose raw SQL string constants as public API — callers rely on kwarg-level semantics, and leaking SQL strings or coupled pairs breaks the composability callers already expect from neighboring options like `nulls_last`/`nulls_distinct`. For mutually exclusive options, follow the convention of the surrounding API (boolean flag vs. Enum vs. `on_delete`-style constant) rather than inventing a new pattern in `django/db/models/constraints.py` or `django/db/models/functions/json.py`.

## Error Handling

<!-- rule:4019 -->
- Re-raise `EmptyResultSet` or compile the expression's configured fallback (`default`, `empty_result_set_value`, `empty_aggregate_value`) as a bound parameter respecting `output_field` in `as_sql()`/compiler paths (`django/db/models/expressions.py`, `lookups.py`, `sql/compiler.py`) — hardcoded literals or sentinel objects break query shape and produce type mismatches — Django's SQL compiler relies on expressions emitting params with correct typing so backends can bind them properly. Substituting a literal or sentinel bypasses `output_field` conversion and query-shape consistency, causing backend-specific type errors and downstream breakage in `lookups.py` and `sql/compiler.py`.
<!-- rule:3486 -->
- In `related_descriptors.py` and `Model._prepare_related_fields_for_save`, validate at the operation entry point: reject unsaved instances in `.set()`/save paths, `None` for non-nullable FK/O2O, and reverse-manager writes with an operation-specific exception (name `operation_name`, say the instance "must be saved") — generic `TypeError` or router-disallowed errors hide the real cause from callers — The rule text is scoped to Django ORM related-field/descriptor internals, specifically `django/db/models/related_descriptors.py` and `_prepare_related_fields_for_save` in `django/db/models/base.py`. Both files live under `django/db/models`, so a directory-scoped AGENTS.md there is the most findable and precise home. The rule combines two things: (1) the error surfacing mechanism and (2) the counter-reaction to over-strict validation. Both are needed together.
  - Add a test per modified public method asserting the expected exception — locks in the error contract so future ORM changes can't silently regress it
  - Don't over-tighten past supported behavior: allow an unsaved related object with a PK set through `_prepare_related_fields_for_save`, and keep the `instance.pk is None` guard in reverse-manager `get_queryset()` so an unset relation returns an empty queryset instead of `ValueError`; revert stricter guards that cause in-the-wild regressions
<!-- rule:1124 -->
- Validate keyword args as settable model attributes in all ORM construction entry points (`Model.__init__`, `QuerySet.create()`, `get_or_create(defaults=...)`) — raise the same clear error `Model.__init__` raises, so users get identical diagnostics regardless of which entry point they call — Consistency across `django/db/models/base.py` and `django/db/models/query.py` prevents entry points from silently accepting typos or raising mismatched errors for the same bad input.
<!-- rule:4148 -->
- Guard query/relation resolution with an explicit in-progress set/dict of relation keys and short-circuit on cycles — catching `RecursionError` fires only after the stack is already blown and can't unwind partial resolution cleanly. — Placed in `django/db/models/AGENTS.md`: these constraints apply to `query_utils.py`-style resolution code, not the whole repo.
  - Never break a resolution cycle by returning an empty `WhereNode` or otherwise dropping conditions — a silent fallback changes the JOIN criteria and emits SQL that returns wrong rows, so preserve correct join semantics or let the error surface.

## File-Specific Rules

### `django/db/models/base.py`

<!-- rule:2955 -->
- In `_save_table`/`_assign_returned_values` (`django/db/models/base.py`), only re-fetch fields that truly need DB-side expression resolution — omitting literal `pre_save` values avoids useless round-trips on every `save()` — Eagerly refreshing DB-computed/readonly fields makes every `save()` issue extra queries, silently regressing write-heavy code. Deferring or assigning known `pre_save` values keeps saves cheap; doing so consistently in `_save_table`/`_assign_returned_values` avoids stale expression state on backends lacking `RETURNING`. Opt-out flags on `Model.save()` push the cost onto users and complicate the public API rather than letting `RETURNING` optimization absorb it.
  - Assign already-known `pre_save` results back on the instance in `_assign_returned_values` instead of re-selecting them — keeps `save()` cheap and backend-agnostic
  - On backends without `RETURNING`, defer unresolved fields rather than leaving stale expression state on the instance — prevents subsequent reads from returning the wrong value
  - Prefer lazy field deferral or an explicit opt-in refresh over eager re-selection — callers pay only when they actually read DB-computed fields
  - Don't add opt-out parameters to `Model.save()` — callers shouldn't have to flag a cheap query; rely on backend `RETURNING` to make these fetches fast over time
<!-- rule:6051 -->
