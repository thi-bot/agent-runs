# Code Style and Cleanliness

> Writing clean, maintainable code: control flow, local structure, and avoiding redundant state.

**When to check**: When refactoring or writing implementation code for clarity.

## Rules

<!-- rule:3000 -->
- Prefer the collection itself as the loop-state signal over a boolean flag — flags drift out of sync with actual unresolved/failed items and cause infinite loops or premature exits; if you must use a flag, update it in every branch that can affect the condition. — Using the collection of unresolved/failed items as the loop-control signal keeps the loop's continuation decision in sync with reality. Separate booleans are easy to leave stale when a branch is added or an early `continue`/`break` bypasses the update, leading to infinite loops, premature exits, or silently dropping items — a class of bug that spans every Django subdirectory where this pattern appears.
<!-- rule:5422 -->
- Group key-focused mutations before derived-value assignments when updating related state for the same key, and write values only in the branch that needs them — avoids redundant read-then-write round trips and stale derived values — Keeps related state updates for a key in one place so derived values reflect the final mutations, and skips write-back on branches that don't change anything, which otherwise cause redundant round trips.
<!-- rule:5443 -->
- Keep a value's computation, normalization, and use together — splitting them obscures provenance and risks drift when one changes without the other — When normalization lives far from the initial computation, or an assignment is hoisted into a separate conditional branch, future edits to one half easily miss the other — the adjacency makes provenance obvious and stale-assumption bugs visible.
<!-- rule:1179 -->
- Extract non-trivial loops/comprehensions out of loop headers into named private helpers or locals — headers stay readable and stack traces name the work — The codebase's inline `for`/comprehension clauses in headers (and fixed-point `while True` loops that re-scan nested structures) hide work behind an anonymous expression: readers must parse the whole clause to know what is iterated, profilers and debuggers attribute failures to the outer loop, and a fixed-point loop's exit condition is implicit. Named helpers or locals give the inner work a name to break on and reuse; recursion on nested structures makes the base case visible instead of relying on a convergence flag. Scope is global — this is structural, not tied to any one module.
  - Resolve recursive nested structures with recursion, not a `while True` fixed-point loop — the recursion mirrors the data's shape and makes the termination case explicit
<!-- rule:2717 -->
- Comment non-obvious fast-path bypasses in matching logic (e.g., skipping regex for plain string ops) — future refactors can't tell if the bypass is intentional — Matching/resolution code frequently takes shortcuts (e.g., bypassing regex for simple string comparisons) whose intent is invisible to later readers, and loose substring/suffix matching leaves unreachable branches that silently absorb refactors. Documenting bypasses and covering both outcomes keeps those branches honest and prevents regressions when the matching strategy changes.
  Test both matching and non-matching outcomes for matching/resolution branches — silent fallbacks stay hidden when only the happy path is covered
  Remove branches reachable only via loose substring/suffix matching when tightening matchers — dead paths mask bugs (see `django/urls/resolvers.py`, `django/contrib/auth/management/__init__.py`)
<!-- rule:57 -->
- Store state that must persist across iterations (caches) as instance attributes set in `__init__()`, not locals inside `__iter__()` — locals reset on each call and silently drop cached data when the iterator is re-entered. — When refactoring a function-based iterator into a class-based one, `__iter__()` can be called multiple times (e.g. `list(iter)`, `for` loops, `yield from`). Any cache or accumulator created as a local in `__iter__()` is rebuilt each time, so previously-computed state is lost and results silently diverge from the original function's behavior. Initializing it in `__init__()` keeps it alive for the iterator object's lifetime — matching the original closure semantics and preventing subtle bugs in serializers and other streaming code (e.g. `django/core/serializers/python.py`).
<!-- rule:5112 -->
- Merge a computed bound with `kwargs[dest] = min/max(value, kwargs.get(dest, value))` — the single expression replaces if/else key-presence checks, so no branch gets missed or duplicated when aggregating bounds in `django/db/models/fields/__init__.py`-style kwargs merges. — Using `kwargs.get(dest, value)` as the default makes the key-presence check implicit, so the merge works whether or not the caller supplied a bound. Explicit if/else on `dest in kwargs` duplicates the value expression and is easy to get wrong (e.g. leaving one branch unclamped).
<!-- rule:1559 -->
- Store data on the owning object, not in parallel maps keyed by the same object; allocate optional bookkeeping only when enabled — avoids sync bugs and wasted memory (see `django/db/models/query.py`, `django/db/migrations/graph.py`). — Parallel maps keyed by an object drift out of sync with the object itself, causing stale lookups and extra memory; lazily allocating optional structures keeps the common path cheap. Both patterns were cleaned up in `django/db/models/query.py` and `django/db/migrations/graph.py`.
<!-- rule:2762 -->
- Fold sentinel checks into existing eligibility conditions and set the sentinel at the guarded side effect; delete unused sentinel constants and the filtering, rezipping, or unpacking they require — avoids redundant passes over data and dead code that obscures the real control flow. — Sentinel checks that live separately from the eligibility condition force duplicate traversals and extra allocations; inlining them keeps a single decision point and removes no-op constants that would otherwise linger as dead references.
<!-- rule:4003 -->
- Append new fields to the end of tuple unpacking patterns; rebuild reordered tuples via explicit indexing instead of mutation — Tuples are immutable, so in-place edits raise `TypeError`, and inserting mid-pattern silently breaks unpacking order for existing callers.
<!-- rule:3863 -->
- Normalize and dedupe paths on insert; store shared prefixes once, join at use sites — avoids redundant intermediate state and drift between equivalent paths (see `django/core/management/commands/makemessages.py`, `django/db/models/fields/__init__.py`) — Matching the pattern already used in `django/core/management/commands/makemessages.py` and `django/db/models/fields/__init__.py`: keeping a single normalized, deduplicated source of truth (and factoring out shared prefixes) prevents equivalent paths from being treated as distinct during comparison, and avoids carrying redundant intermediate lists that later drift out of sync.
  - When comparing path collections, compare normalized forms — unnormalized duplicates silently break set/membership checks
<!-- rule:5679 -->
- Route all file opens through the single `open_method` helper, passing `mode` explicitly at every call site and in tests — keeps one consistent access path instead of drifting into ad-hoc helpers, dropped params, or `opener` callbacks — A single helper with an explicit `mode` makes read/write intent visible and comparable across code and tests; diverge and behavior like encoding/compression handling silently differs between production and test code
<!-- rule:4064 -->
- Extend collection filters/exclusion criteria additively (append to the existing tuple/set, reuse the same predicate) instead of replacing them with narrower or differently-scoped checks — duplicated or inverted criteria drift apart and silently regress previously-handled cases. — Narrowing a filter, or swapping a predicate for a slightly different one, looks harmless in a diff but quietly drops the cases the original criteria covered. Keeping new criteria additive preserves backward compatibility and prevents drift between the old and new conditions.
<!-- rule:2577 -->
- Write comparison expressions with the measured expression on the left and the constant on the right (e.g., `len(x) > 1`, not `1 < len(x)`). — Compared to traditional guard clauses, this ordering lets readers see the value being tested before the threshold, matching PEP 8 and the project's Django style. It prevents scannability issues in complex conditions where the threshold is a long constant.
