# API Design and Interfaces

> Rules for designing caller-facing APIs: overridable hooks, simplest abstractions, defensive cloning, immutable arguments, sentinels, slice semantics, wrapper attributes, registration/unregistration, and interface boundaries.

**When to check**: When designing or changing public APIs, method signatures, hooks, or wrapper classes.

## Rules

<!-- rule:3461 -->
- Expose customizable logic as a named overridable hook (e.g. `split()`) with a base implementation — subclasses override only the hook, not `__iter__` or shared control flow, so iterators/generators stay customizable without duplicating logic across parallel implementations — Reimplementing protocol methods or inlining alternative logic forces subclasses to copy control flow and breaks when base behavior changes; a single named hook keeps the extension point stable and lets the shared method drive the flow.
<!-- rule:2328 -->
- Prefer plain functions or class methods over standalone classes for stateless logic, and validated primitives over wrapper classes when only one use case is known. — Simpler abstractions keep the API surface small, making future changes easier and preventing dead wrapper layers that only exist to satisfy one caller.
<!-- rule:3914 -->
- Pass defensive clones of internal mutable state to signal receivers and external callbacks — external code must be read-only; mutations go through the operation API. — These three rules together define ownership of mutable state across the `db/models`, `sql`, `migrations`, and `expressions` layers. Giving out live references to signal receivers or callbacks leaks mutation capability outside the intended API and causes cross-cutting bugs when receivers mutate state the caller still holds. Cloning at the mutating method keeps the ownership boundary local instead of pushing defensive-copy obligations onto every caller, which scales poorly. The backward-compat rule prevents the common regression where a documented public method silently starts copying its inputs — callers that relied on the previous behavior (or on mutating the passed object) break without any signature change to warn them.
  - Clone at the mutating method (the ownership boundary), not at the call site — callers shouldn't need to know about defensive-copy requirements.
  - Don't add implicit copies inside documented public methods — existing callers may depend on live references; clone at the call site instead to preserve backward compatibility.
<!-- rule:289 -->
- Don't mutate arguments in callees — have callers set flags/state explicitly and callees `assert` preconditions, so side effects stay visible at the call site — Hidden in-callee mutation makes argument state changes hard to trace; pushing the mutation to the caller and asserting preconditions keeps the effect local and reviewable.
<!-- rule:5545 -->
- Shape interfaces around cohesive domain concepts, not minimal diffs — signature changes are cheaper than propagating leaked internals. — General interface-shaping principle with global scope; evidence spans `db/migrations`, `test/runner`, and `core/management/commands` in Django, so it applies repository-wide rather than to any single module.
  - Pass the whole domain object when callers need several related fields — destructured primitive args drift out of sync as the domain grows.
  - Expose a narrow high-level method when callers only need a single operation — forces them to sequence lower-level steps manually and couples them to the object's full surface.
  - Keep sub-steps and test-only seams inside — public test hooks lock callers to implementation details that should stay free to change.
<!-- rule:5325 -->
- Reconstruct same-type instances with `type(self)(...)`/`type(obj)(...)` — preserves subclass types and their `__init__`; hardcoded class names and `obj.__class__(...)` drop them, breaking subclasses (e.g. in `django/db/models/`, `django/contrib/gis/gdal/`) — The rule matters because hardcoding a concrete class name or reaching for `obj.__class__` (which can be shadowed by an instance attribute) bypasses whatever subclass the caller actually instantiated, silently discarding the subclass's overridden behavior and custom initialization. This breaks polymorphism in Django's model and GDAL layers, where users routinely subclass and expect clone/copy/reconstruction paths to return their type.
<!-- rule:2622 -->
- Reserve sentinel values for cases where they must be distinguished from valid domain values (including `None` or plausible user-supplied strings) — a plain constant or type-appropriate default avoids special-case comparison logic throughout the codebase. In JavaScript documentation snippets, prefer `undefined` over `null` for sentinels/defaults — `typeof null === 'object'` makes it indistinguishable from real objects. When a sentinel is justified, add a test that fails if it is swapped for an ordinary value — otherwise a regression silently collapses the sentinel into a valid input. — Sentinels introduce branches that must be honored everywhere; if a plain default suffices, every check is dead weight. The JavaScript case is a concrete footgun: `typeof null === 'object'` breaks object-detection idioms. The test requirement catches the silent failure mode where a sentinel is replaced by a valid value and nothing notices.
<!-- rule:2019 -->
- Encapsulate teardown in the owning class's cleanup helper (`_close()`, `close_pool()`); call that helper instead of duplicating cleanup or `hasattr`-checking backend-specific cleanup externally — keeps one authoritative teardown path so backends can't be missed. — Centralizing teardown in the owning class's helper (`_close()`, `close_pool()`) prevents duplicated or backend-specific cleanup invoked via `hasattr` from outside, which drifts as backends evolve and risks leaking resources. Ordering subclass cleanup before `super().close()` avoids using already-released shared state.
  - In overridden `close()`, run subclass-specific cleanup before `super().close()` last — calling super first tears down shared state the subclass still needs.
<!-- rule:5193 -->
- Treat canonical properties like `choices` as the single source of truth: derive other properties as projections, delegate wrapper attribute access to the wrapped object, and set values through the public property rather than a private helper — duplicating state lets copies drift out of sync when the canonical value changes. — derived/wrapper copies of the same value silently diverge from the source, producing stale behavior, and setting through a private helper bypasses whatever the public property does on assignment (validation, caching, notifications).
<!-- rule:3007 -->
- Call `ErrorList.render()` instead of `mark_safe(str(errors))`, and pass raw error messages (no `conditional_escape()`) — error containers already escape on `str()`, so manual escaping or pre-escaping double-escapes form errors. — Error collections like `ErrorList` escape their messages during string conversion. Wrapping `str(errors)` in `mark_safe()` or pre-escaping messages with `conditional_escape()` bypasses or duplicates that machinery, producing double-escaped output that displays incorrectly in admin views and forms. Using the collection's own `render()` keeps escaping consistent across Django's contrib code.
<!-- rule:4279 -->
- Never rewrite a user-supplied query's `SELECT`/`GROUP BY`/`ORDER BY`/`DISTINCT` — wrap it instead — Mutating clauses silently changes the caller's semantics in SQL generators (subquery pushdown, ORM expression helpers); narrower shapes belong in an outer wrapper or an explicit query form.
<!-- rule:2791 -->
- Normalize `bytes`/`str` at the top of API boundaries — decode `bytes`, wrap `str` in `StringIO` in serializer/deserializer constructors before parsing — Downstream type checks then target one normalized type instead of fanning out across input variants.
<!-- rule:3429 -->
- Keep parse/utility helpers policy-free — parse and raise on unrecognized input, defer validation, silent fallbacks, and error-to-boolean/default conversions to the calling code. Reserve argparse `type` converters for parsing/validating immediate input only; defer environment-derived values (e.g., `'auto'` → `multiprocessing.cpu_count()`) to a single-source-of-truth helper like `get_num_test_processes()`. Keeps helpers reusable and avoids duplicating environment-dependent logic across layers. — Low-level helpers that embed policy (silent fallbacks, error-to-default conversions, env lookups) duplicate environment-dependent logic at each call site and become untestable in isolation. Concentrating those decisions in the caller — or a dedicated helper like `get_num_test_processes()` — keeps a single source of truth and lets utilities stay pure parse/validate functions that raise on bad input.
<!-- rule:413 -->
- Name slice bounds `start`/`end` (`start`/`stop` for slice-object wrappers), never `length` — mirrors Python's `slice` so callers pass bounds through unchanged — Slice-based APIs and helpers in this codebase should be drop-in compatible with Python's `slice`: mirroring its parameter names and its `None`-for-omitted-bounds behavior lets users pass slice values straight through without translating names, calling `len()`, or special-casing missing bounds. Keeping helper-returned boundary positions as concrete integers (rather than `None` sentinels) means downstream code can index them without null checks, so callers don't have to guess whether a helper returned a position or a marker.
  - Pass `None` for omitted bounds instead of computing `len()` or branching — matches `slice` semantics and avoids off-by-one branching bugs
  - Return explicit integer offsets from boundary helpers, not `None` sentinels — callers can index results directly without null checks
<!-- rule:3365 -->
- Don't hardcode variant attributes in element wrappers (e.g., `rel="stylesheet"` on `Link`) — expose them so callers can emit `<link rel="icon">`; model attribute-dependent behavior via inheritance (base asset/media → element → attribute subclass); if an attribute is set internally, validate caller-passed values to avoid silent overrides or duplicate output attributes. — Hardcoding a variant like `rel="stylesheet"` on `Link` makes other valid HTML forms unreachable; exposing attributes and layering attribute-specific subclasses lets callers target each form without forking the class, while validation prevents silent overrides when both caller and implementation set the same attribute.
<!-- rule:3891 -->
- Expose an unregistration API alongside every registration API (global, class-, or instance-level) — enables cleanup and test isolation — Without a matching unregistration API, global serializer registrations and Django lookups cannot be undone, so cleanup paths and tests leave stale registrations that affect later code. If unregistration assumes prior registration or ignores scope, it can crash when no registry exists or remove class-level and other-instance registrations, surprising callers and making lifecycle bugs hard to trace. The global serializer and Django lookup registration/unregistration cases show that registration is incomplete unless unregistration is safe in any order and limited to the intended scope.
<!-- rule:3763 -->
- For parameters that accept `True` or an iterable of strings, either normalize the value at the validation boundary to the iterable form (e.g., `True` -> tuple of relevant items, `False` -> empty tuple) to avoid repeated type branching downstream, or, if not normalizing, validate and dispatch with `if param is True: ... elif isinstance(param, Iterable): ... else: raise TypeError(...)` and use an error message like 'must be True or an iterable' (not 'must be either a boolean or an iterable'). — This is a behavioral API-design convention (how to normalize/validate dual-form `True`-or-iterable parameters) rather than a file-level or cross-file coordination rule. Although the observed evidence comes from `django/db/models/`, the pattern is a general coding guideline that applies to any function accepting such parameters and is language/design-level rather than module-specific.
