# API Design & Public Interfaces

> Rules for kwarg/default handling, __eq__/__hash__ semantics, __all__ exports, parameter ordering, properties over getters, template-tag argument precedence, enum-based option types, delegation wrappers, NotImplementedError contracts, callable inspection, and deletion/CSRF entry-point semantics.

**When to check**: When designing or modifying a public class, method, or callable interface

## Rules

<!-- rule:439 -->
- In custom `__eq__`, guard with `isinstance(other, self.__class__)` and `return NotImplemented` for unsupported operand types — never `False`, raised exceptions, or string/serialized comparison. Returning `NotImplemented` lets Python fall back to the reflected comparison and keeps subclass-aware equality correct; the alternatives silently break it or mask type mismatches. Pick the guard class by the fields compared: normally `self.__class__`, but the base class that defines the fields when equality depends only on inherited base-class state. — Returning `NotImplemented` allows Python to try the reflected comparison and preserves correct subclass semantics; returning `False` breaks equality for subclass instances, raising diverges from `__eq__` conventions, and comparing string/serialized representations conflates distinct objects. The migration-deconstruction exception keeps field changes visible to the autodetector, and the `BaseConstraint` exception matches Django's existing constraint comparison pattern.
    Exceptions:
    - Migration deconstruction helpers may return `False` for type-mismatched `other` so changed field values are detected and migrations autogenerated.
    - `BaseConstraint` subclasses in `django/db/models/constraints.py` may delegate to `super().__eq__(other)` for non-matching subclasses instead of returning `NotImplemented`.
<!-- rule:1718 -->
- Merge `**kwargs` defaults with `kwargs.setdefault()`, `kwargs.pop(k, default)`, or `{**defaults, **kwargs}` — never `kwargs[k] = default`, which silently clobbers caller values and makes user config unconfigurable mid-call. If a caller value conflicts with an enforced default, respect it or raise explicitly. — Direct assignment overwrites what the caller passed, so options silently vanish. This bit us across `django` mail, GIS backends, Postgres fields, auth forms, `http.server`, and messages storage — always the same shape: a default re-stomped a user-supplied kwarg.
<!-- rule:592 -->
- Declare a module's public surface with dunder `__all__` (never a plain `all`), and keep every `__init__.py` re-export import in sync with it — an `__all__` entry is a public contract, so listing internal helpers, implementation-only classes (even if used as return types), side-effect-only imports (e.g. signal registration), or both a class and its singleton instance falsely signals support. — `__all__` is the declared supported interface; over-listing internal helpers, return-type-only classes, side-effect imports, or redundant class/singleton pairs commits the package to maintaining them, and undocumented leftovers (like `LocaleRegexProvider`) mislead users into depending on unsupported symbols.
  - Drop undocumented symbols with no verified usages from the public API (both the import and its `__all__` entry) — e.g. removed `LocaleRegexProvider` from `django/urls/__init__.py` — since stale entries promise an interface users may rely on.
<!-- rule:4177 -->
- Order params logically (primary subject first), and mirror that order at call sites — mismatched order causes silent positional-arg bugs and unreadable signatures. — Django's own signatures follow this (e.g. `django/utils/*`, `django/db/backends/*`), so scattered call sites across `tests/gis_tests` and backends stay consistent; adding params chronologically scrambles the API and makes positional calls fragile.
<!-- rule:2402 -->
- Expose zero-arg computed state and boolean predicates as `@property`, not methods/functions — enables truthiness checks like `bool(Model._meta.is_composite_pk)` and matches Pythonic Django API style. — Properties behave as values, so `bool(...)` and direct attribute access work naturally; methods require call syntax and break truthiness expectations. Attribute-style naming keeps discoverability consistent with Django's own APIs (`_meta`, connections, forms), and `get_*` signals an accessor that may take arguments, avoiding confusion at call sites.
  - Name properties like attributes (`is_usable`, `limit_value`, `loader_name`, `empty_aggregate_value`); reserve `get_*` for accessors that accept arguments.
  - Place predicates on the object they describe (e.g., `Model._meta.is_composite_pk`, connection `is_usable`) rather than standalone helpers taking the object as a parameter — keeps call sites readable and encapsulation intact.
<!-- rule:1133 -->
- In Django template tags/helpers, let explicit args replace the ambient fallback (`request.GET`, context processor default) — never merge the two, or caller intent is silently overridden. — Merging produces surprising results when a template author passes an arg expecting it to fully control the output.
<!-- rule:3240 -->
- In callable-inspection helpers, accept any callable (not just `types.FunctionType`) and unwrap descriptors: treat `staticmethod` access as a plain function, `classmethod` as a bound method (use `__func__`), and don't rely on `co_argcount` alone — misclassification silently breaks signature/arity checks for methods, decorators, and zero-arg callables. — Descriptor binding changes the shape of the underlying callable: `types.FunctionType` checks miss bound methods and wrapped/decorated functions, while `co_argcount` skips `*args`/`**kwargs` and bound `self`. Handling `staticmethod`/`classmethod` and testing bound/unbound methods, zero-arg, and decorated callables prevents helpers like `django/utils/inspect.py` and `django/tasks/utils.py` from misclassifying ordinary methods.
<!-- rule:1216 -->
- Use `enum.Enum` for fixed sets of related string/option constants (especially shared across APIs) — one conceptual value type per enum; alias existing module-level constants as enum member values so discoverability doesn't break references — Enum APIs are consumed across many Django modules and by third-party callers, so surfacing stable public base classes (and hiding internal metaclasses like `ChoiceEnumMeta`) preserves backward compatibility. Aliasing constants as enum values keeps existing references valid. The version-specific string-enum guidance avoids depending on non-public names, which aren't guaranteed to remain stable across Django or CPython releases.
  - Expose Django choice enums through minimal, purpose-named public bases (`Choices`, `IntegerChoices`, `TextChoices`), derive the metaclass internally, and let custom types mix in a primitive (`class Separator(bytes, models.Choices)`) — keeps user-facing APIs readable and avoids leaking `ChoiceEnumMeta` into callers
  - For string-valued enums, subclass `(str, enum.Enum)` on Python ≤3.10, or use `enum.StrEnum`/`models.TextChoices`/`ChoiceStrEnum` on 3.11+ — never import the non-public `django.db.models.enums.StrEnum` outside its defining module, since non-public names can shift between releases
<!-- rule:1713 -->
- Avoid delegation-only wrappers: call the target method directly, or alias it (`__str__ = render`, `__html__ = render`) — every redundant wrapper duplicates the original's contract and drifts when the target's signature or decorators change. — It prevents duplicated or copied delegation logic from silently drifting out of sync with the original method—losing its decorators, signature, or safety guarantees—and stops monkey-patched built-ins from breaking every other caller in the codebase.
  - When an override or wrapper is genuinely needed, delegate to the original implementation or write an explicit local version: preserve the original decorators, signature, and safety guarantees, and never copy internals or monkey-patch built-in types — copied internals silently break on upstream changes and monkey-patched builtins break every other caller.
<!-- rule:2173 -->
- Raise `NotImplementedError('Subclasses of X must implement y()')` for required abstract methods; give optional hooks a no-op default (`return []`, `pass`) — subclasses opt in without forcing every override or penalizing callers — This prevents ordinary methods from leaking the truthy NotImplemented sentinel that callers would mistake for a real result—since that sentinel is only valid in binary dunders to trigger reflected-operation fallback—while keeping required abstract methods explicit and optional hooks overridable without forcing every subclass to implement them.
  - Never `return NotImplemented` from a regular method — that sentinel only belongs in binary magic methods (`__eq__`, `__lt__`) to signal fallback to the reflected operation
<!-- rule:4909 -->
- In `__hash__`/`make_hashable()`, normalize only containers (dicts/lists/sets); pass primitives to `hash()` directly — Recursing nested sequences into tuples and sorting dict items at every level makes insertion-order-independent equal dicts hash identically, and never re-wrap the already-hashable result in a tuple — that breaks `__hash__`/`__eq__` consistency for objects compared by value.
<!-- rule:524 -->
- Keep deletion logic in `DeletionMixin`/`BaseDeleteView`; document and test only the POST/form confirmation path — `DeleteView`'s public contract is POST + confirmation form — adding DELETE to `FormMixin`, rerouting DELETE through a form, or testing/documented DELETE as the deletion method breaks backward compatibility for existing `DeleteView` subclasses and diverges from the documented, tested behavior.
<!-- rule:3808 -->
- Apply `csrf_protect`/`csrf_protect_m` only to state-changing entry points, not safe methods like GET/HEAD/OPTIONS — safe methods don't change state, so protecting them adds no security and breaks idempotent reads — Scoping CSRF to state-changing entry points outside transactions prevents broken idempotent reads, backward-incompatible deprecations, transactions opened by rejected requests, and misuse of CSRF as DoS protection while keeping terminology consistent with HTTP semantics.
  - Keep `csrf_protect` on POST handlers during deprecation, and move it into `dispatch()` only once deprecated unsafe-GET methods are removed — preserves backward compat while tightening coverage
  - Keep CSRF validation outside `transaction.atomic` — a rejected CSRF check should not open a transaction
  - Document "unsafe request" in `docs/ref/settings.txt` as POST or other data-changing methods — keeps the term aligned with HTTP semantics
  - Never use POST+CSRF as a DoS mitigation — CSRF guards against forged state changes, not request floods; use rate limiting instead
