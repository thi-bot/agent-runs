# Coding Guidelines

## API Design

<!-- rule:34 -->
- Store autosave/draft form state in a dedicated `FormState` record (or temp WIP revision type), never on the model instance — autosave must not create/update the model or trigger validation/workflows; those fire only on explicit Save/Publish/Schedule/Submit. This restores incomplete or invalid forms without running validation, avoids crashes when model definitions change, and reduces implementation risk by reusing existing form behavior. — Autosaving into the live model forces validation, revision creation, and workflow triggers on every keystroke-batch — Without the `FormState` persistence and restoration approach, Wagtail admin create/edit/autosave can save invalid or incomplete input into real model instances, trigger validation/workflows before an explicit Save/Publish/Schedule/Submit, and break when Django-form round-tripping is replaced by custom field assignment during model changes. That pollutes revision history, surprises editors by loading stale `Revision` data over newer autosaved work, and blocks collaborative-editing because incomplete content is not a shared draft; the dedicated `FormState` lifecycle keeps autosave state separate and restorable until a valid save.
<!-- rule:36 -->
- Exchange version markers on every save/autosave: return the persisted revision on success and require the client to send its last-known marker (`overwrite_revision_id` when present, else `loaded_revision_id`) on the next save — the discriminator (`created_at`, overwrite counter, or UUID) must be compared to catch stale writes before they land. — Without it, concurrent editors silently overwrite each other's newer revisions and the loser never knows.
<!-- rule:174 -->
- Preserve output shape when extending public interfaces — When extending template tags, fields, widgets, or APIs with a new model or syntax, existing callers rely on the current return type, field semantics, and template rendering — silent changes break them without a code change on their side. Gate new behavior behind explicit opt-in syntax or keep it as an implementation detail so both old and new usage paths coexist.
<!-- rule:48 -->
- Model each concurrent editing session as its own row with a unique session ID (e.g. `UUID`), not a `(object, user)` association or singleton — lets one user hold multiple live sessions without overwriting each other. — Per-session rows keep concurrent edits isolated, and a mutating version token is what makes optimistic-locking conflict detection actually work.
  - Route session-specific endpoints by session ID, authorize/filter by user ID, and defer user-level aggregation/dedup to query or UI layers — keeps API semantics unambiguous.
  - Use a version token that changes on every update (`timestamp`, `UUID`, `counter`) for optimistic concurrency, not the stable record ID — a static ID can't detect conflicting writes.
<!-- rule:233 -->
- Pass feature behavior to `ViewSet`/generic views as explicit opt-in attributes, not mixins on shared generic views — shared methods must take explicit context (`request`) args and never assume a view, request, or user exists, so they also work in non-view contexts like chooser widgets; subclass the view when you need its internals. — Implicit coupling via mixins on shared generic views makes helpers unusable outside a request/view context (e.g. chooser widgets) and makes overrides fragile: coder, subclass or explicit allowlist entries keep behavior discoverable and stable.
  - Expose view overrides only through an explicit allowlist with consistent signatures — arbitrary method matching, per-variation methods, and parity-only additions break silently when internals change.
<!-- rule:31 -->
- Resolve `permission_registry.get_policy(model)` in a `cached_property` and register policy instances per model — class-level policy binding or viewset-only `permission_policy` misses generic-FK/non-page targets; use a model-agnostic permission hook when coverage must extend beyond the viewset. — Dynamic lookup via `permission_registry` keeps overrides and per-request changes effective; direct imports of policy instances from app modules and class-level binding bake in stale policies, and viewset-scoped `permission_policy` silently fails to cover generic-FK targets.
<!-- rule:63 -->
- Enforce permissions in the operations/actions layer via the model `add`/`change`/`delete` permission system — checks in transport/view handlers alone let API, admin views, management commands, and CLI bypass authorization, and ad-hoc access controls drift from the platform model
<!-- rule:77 -->
- Bind keyboard shortcuts to rendered controls — no hidden modifier-only actions; enable a shortcut only when its action is visible/available. — Users discover features through the UI; shortcuts that fire without a matching visible control (e.g. a dropdown menu item) surprise users and can trigger actions on screens where the control isn't rendered.
<!-- rule:167 -->
- Design base Wagtail viewsets model-agnostic (no model-specific workflow) and register one endpoint per model, mirroring the existing read API — a shared base viewset avoids duplicating serializer/queryset logic across the snippet, page, and `ModelAdmin` endpoints. — Reusable viewset bases plus a single per-model endpoint keep the Wagtail API consistent across snippets, pages, and `ModelAdmin`. Type-dispatch in `wagtail_hooks.py` registration functions means both model-first and ViewSet-first call styles work, so adding a new model's endpoint never requires changing the hook signature or duplicating registration code.
  - In `wagtail_hooks.py`, make registration functions (e.g. `register_snippet`) accept either the model class or its ViewSet class as the first positional argument, dispatching on argument type — lets callers use model-first or ViewSet-first registration without separate hook functions.
<!-- rule:227 -->
- Name new built-in StreamField blocks `{Type}Block` (e.g. `ImageBlock`) — matches `RichTextBlock`, `CharBlock`, `EmailBlock` — Naming keeps the built-in block family discoverable and consistent for anyone grepping for a type. Serialization compatibility is the important one: if two blocks that mean the same thing serialize differently, downstream code and stored data diverge, and later consolidation becomes a data migration instead of a refactor.
  - When a new block type semantically overlaps an existing one, keep its JSON serialization compatible with that type — lets equivalent structures be handled uniformly and refactored later
<!-- rule:68 -->
- Validate only genuinely invalid workflow states, not legitimate editorial actions — blocking valid manual workflows forces users to bypass the API; when a validation would reject a real workflow, expose an opt-out rather than enforcing it unconditionally. — Workflow validations exist to prevent corrupt or inconsistent state, not to police editorial intent. A validation that fires on legitimate manual actions (e.g. redirects, re-writes, manual edits performed through the write API) blocks users from completing valid work and pushes them to circumvent the API entirely, which is worse than the invalid state it was meant to catch. When a check would block a genuine workflow, an opt-out flag keeps the safety default while leaving a supported escape hatch — an unconditional block turns a helpful guardrail into an obstacle.
<!-- rule:52 -->
- Define one canonical URL per API resource using explicit parent IDs (e.g. `/api/pages/<page-id>/revisions/<revision-id>/`), never implicit `-` placeholders. Parent-scoped endpoints carry parent context: `POST /api/pages/<parent-page-id>/add_child/?type=<app.Model>`. Alias shapes (e.g. `-` + `head`) must 301-redirect to the canonical path, not return payloads or undefined 404s. This keeps each resource addressable by a single stable URL, so caching, bookmarks, and clients don't diverge or silently resolve ambiguous parents. — Mixing canonical and alias URLs (like `-` wildcards paired with `head`) means the same resource is reachable at multiple addresses, which breaks caching, permalinks, and client assumptions and lets ambiguous parent-scoped routes silently resolve the wrong object. Enforcing one canonical URL and 301-redirecting aliases keeps resource identity unambiguous while preserving backward compatibility for existing callers.
<!-- rule:90 -->
- Use React mount/update/unmount for `StreamField`/`InlinePanel` block lifecycle — don't invent custom Wagtail block events — Wagtail's admin exposes no block-level event API; adding one creates a parallel lifecycle that diverges from how React actually mounts, updates, and unmounts block components, causing missed or duplicated handler calls.
<!-- rule:108 -->
- Register widget initialisers with `registerWidgetInit`, not per-widget `DOMContentLoaded` listeners — the helper centralises DOM-ready timing: it runs the initialiser immediately when the DOM is already loaded and otherwise attaches a `DOMContentLoaded` listener. Duplicating that logic per widget risks initialisers that never fire (scripts loaded after `DOMContentLoaded`) or run twice. — Widgets are frequently injected or lazily loaded after the document has already finished parsing, so a bare `DOMContentLoaded` listener never fires and the widget stays uninitialised. Routing every initialiser through `registerWidgetInit` keeps the ready-state check in one place, so late-loaded widgets still initialise and no widget has to reimplement the timing logic.
<!-- rule:80 -->
- Revision API responses: `meta` for metadata, top-level content fields (no `content` wrapper) — so create payloads double as GET responses and swapping the page's `meta` reconstructs that revision's representation. — Mirroring the page payload shape lets clients reuse create payloads against GET endpoints and reconstruct any revision by substituting the page's `meta` — a generic `content` wrapper would force bespoke parsing per endpoint.
<!-- rule:188 -->
- Name image rendition API options so they can't be confused with `src`/`source`/`original` — prevents users wiring a rendition option into a source slot — 
  - Document whether each rendition option references the source file or a rendition, plus its allowed filters — prevents misapplied operations on the wrong image
<!-- rule:221 -->
- Extend Wagtail admin display via `wagtail.admin.ui.tables.Column` subclasses in `list_display` or model property methods, not core `ViewSet`/`ModelAdmin` attributes; document the extension point. — Developer-side extension points avoid bloating the core admin API and keep customizations local, so other projects don't inherit one-off display logic. Documenting them lets others reuse the pattern.
<!-- rule:89 -->
- Expose before/after lifecycle hooks around mutations (`tree:beforeDelete`, `tree:beforeAdd`, `tree:afterAdd`), not just post-operation events like `tree:delete` — post-only events leave consumers no way to validate, veto, or capture pre-change state — A single post-operation event (`tree:delete`) fires too late for listeners that need to inspect or veto the pending change. Emitting paired `tree:beforeDelete` / `tree:afterDelete` (and `tree:beforeAdd` / `tree:afterAdd`) around each add/delete/move lets consumers hook either side of the mutation without a separate API.
<!-- rule:165 -->
- In the StreamField/Telepath client adapter interface, handle JS-unfillable types explicitly — Immutable/Submittable types like file uploads fail through the generic `setState` value API. Keep all other field types encapsulated in their adapters with no API changes. — File uploads and similar types cannot hold a JS-assigned value, so routing them through the shared `setState`/value-setting path breaks them; dedicated handling keeps the adapter contract intact for every other field type.
<!-- rule:166 -->
- Build `StreamField` admin field adapters agnostic to submission/serialization strategy — keeps one field usable across admin, auto-save, and API contexts — Serialize the complete field value server-side enriched with resolved display data (`IDs` → edit/live URLs, titles), render client-side via adapters instead of pre-rendered HTML, and support Django form, JSON/API, auto-save, and DRF flows. Avoids forking the widget per caller or locking it to one submission model.
<!-- rule:58 -->
- Pair every expiring/releasable lock with a client-side `keep_lock` endpoint (e.g. `current_url/keep_lock`) — Active editors poll it via `window.setInterval` to signal they're still working; keep-alive is best-effort because server-side expiry remains the source of truth, so long edits don't silently lose their lock.
<!-- rule:104 -->
- Pass explicit credentials/context to view-restriction filters and decision methods — never read from `HttpRequest` directly inside them. — Keeps the API usable from outside the request/response cycle (management commands, tests, batch checks) and avoids hidden coupling between restriction logic and `HttpRequest`. Makes credential-based decisions inspectable and easy to stub in tests.
<!-- rule:234 -->
- Provide a template tag emitting `rel="alternate" hreflang="..."` links for every page translation — renders the correct SEO alternates without hand-maintaining them per template — Emit links only for each translation's published status, and ensure output reflects publish/unpublish changes (no stale cache/static builds) — search engines otherwise index broken or missing language alternates when translations go live independently.
<!-- rule:175 -->
- Keep Wagtail hooks synchronous; don't add a sync/async flag to hook registration — let each caller decide async execution per invocation. — Encoding execution mode on registration couples every invocation of a hook to one choice: a hook can't be fast and inline in one path while background-dispatched in another. Leaving the flag off registration keeps hooks composable and lets callers opt into background execution where it's actually safe (e.g. side-effect-free `after_*` hooks) without forcing async on callers that need the result synchronously.
<!-- rule:182 -->
- Expose scheduling/execution mode (`cron`-style vs persistent) via existing Django management commands (`settings.py` or flags); don't replace the commands or add a backend per mode. — Keeps existing `manage.py` invocations working and avoids diverging backends/config for each execution mode.
<!-- rule:216 -->
- Document or explicitly declare metaprogrammed class attributes — IDEs and static analysis can't discover them, so keep generated names predictable for autocomplete and type checking. — Metaprogramming that generates attribute names dynamically (e.g. via `setattr` loops or metaclasses) is invisible to IDE autocomplete and static tools like `mypy` and `pyright`. Predictable, documented, or explicitly declared names preserve the developer experience of real attributes.
<!-- rule:199 -->
- Keep the JS framework behind widget/component APIs and ship focused docs — contributors build block/field widgets in `client/` without React expertise, so the admin frontend stays approachable and knowledge stays centralized. — Hiding React behind widget/component interfaces in `client/` and documenting only what's needed to build common block/field widgets keeps the Wagtail/Django Admin frontend contribution path accessible without deep JS framework knowledge.
<!-- rule:197 -->
- Use generic format collections (`WAGTAILIMAGES_ALLOWED_FORMATS`, `image.is.<format>`) instead of per-format flags like `is_svg` or `WAGTAILIMAGES_ALLOW_SVG` — new formats then work without API changes; accept `'*'` to allow any format. — Per-format boolean flags (`is_svg`, `WAGTAILIMAGES_ALLOW_SVG`) don't scale: every new format forces new flags and settings across the `wagtail.images` API. A collection keyed by canonical lowercase format with a `'*'` wildcard stays extensible and keeps configuration consistent. Deriving behavior from membership (rather than dedicated properties) avoids drift between API and settings. Using `Image.format` instead of the raw extension prevents misclassification of aliases like `.jpg`/`.jpeg`.
  - Derive format-specific behavior from membership in that collection, and read `Image.format` rather than the file extension — aliases like `.jpg`/`.jpeg` map to one canonical format, so extension checks misclassify images.
<!-- rule:32 -->
- Model required-on-save with a generic `required_on_save = True` attribute on the model field, not a panel subclass — any field can opt in without proliferating panel types. — Generic field attribute avoids one-off panel subclasses and title-specific hacks; panel-level override gives call sites flexibility without changing the model.
  Let admin panels like `FieldPanel` accept an optional panel-level `required_on_save` argument that takes precedence over the bound field's attribute — supports per-usage overrides while defaulting to the model's declaration.
  Set `required_on_save = True` on the Wagtail page `title` field — draft pages still need a title populated for page listings.
<!-- rule:215 -->
- Prefer `__init_subclass__()` over metaclasses for subclass initialization or generating attributes/methods on subclasses — it's simpler to read and maintain; reserve metaclasses for cases `__init_subclass__()` can't express, such as dynamically generated methods that are overridden in the same class body to call `super()` and therefore need an intermediate generated base class in the MRO. — Metaclasses add indirection that most subclass-init use cases don't need; the sole exception is when an override calls `super()` and requires a generated intermediate base in the MRO to resolve correctly.
<!-- rule:202 -->
- In `willow.plugins.svgsprite`, expose sizes via a named `get_size` operation that wraps `get_box` — don't make callers reach for `get_box` or hand-parse SVG XML. — Gives the plugin a stable public surface and reuses the tested `svglib`/`svgsprite` helper, so dimension bugs stay in one place instead of scattering across callers.
<!-- rule:67 -->
- Action endpoints: — Resource-scoped action URLs and body-less actions on existing resources keep request semantics unambiguous and prevent payload/target mismatches. Nesting revision actions under the revision path mirrors the model hierarchy, so callers can infer an endpoint's scope from its URL shape alone.
  - Scope to the resource in the URL: page-level actions use `/api/pages/<page-id>/<action>/` (e.g. `POST /api/pages/<page-id>/unpublish/`); revision-specific actions nest under the revision as `/api/pages/<page-id>/revisions/<revision-id>/moderation/<action>/` — mirrors the underlying model/view so the URL is self-documenting and prevents ambiguous scoping.
  - Omit the request body when the action operates on an already-identified URL resource — the resource's state is the input, so requiring a body invites drift between payload and target.
  - Keep URL structure aligned with the model/view hierarchy — diverging paths force callers to guess where an action lives.
<!-- rule:69 -->
- Target the explicit revision in moderation actions (revision-scoped endpoint or `publish` payload) — a revision awaiting moderation may not be latest, so implicit endpoints can accept the wrong content. — Because the revision awaiting moderation may not be the latest, acceptance and other state transitions must operate on the identified revision. This prevents the wrong content from being accepted or published.
<!-- rule:78 -->
- Mirror resource representation in create/update payloads — top-level metadata, nested `content` — flattening breaks the meta/non-meta convention and client round-trips. — Keeps request payloads structurally consistent with the resource representation, so clients can reuse the same schema and the project's meta/non-meta convention is preserved.
<!-- rule:168 -->
- Model optional admin views as overridable `{foo}_view_class` attrs; `get_urlpatterns()` registers URLs only when set — lets subclasses toggle views without rewriting routing — Wagtail viewsets (e.g. `SnippetViewSet`) are designed to be subclassed. Optional views exposed as overridable `{foo}_view_class` attrs plus conditional registration in `get_urlpatterns()` keep routing consistent across subclasses. Preferring `PermissionHelper` denial (return `False`) over removing classes/URLs preserves a stable URL surface and avoids surprises for templates or actions that reference those views. Any admin UI that assumes a view exists must degrade gracefully to avoid broken links or dead actions when a view is disabled or absent.
  - Disable a view via a custom `PermissionHelper` returning `False` instead of removing view classes or URL patterns — keeps routing stable and avoids breaking UI code that assumes routes exist
  - Guard admin UI against absent/disabled views — don't render links or actions that assume a `{foo}_view_class` is registered
<!-- rule:102 -->
- Render `StreamField`/`InlinePanel` block action bars inside the block's interactive area, not above its boundary — keeps focus/keyboard scope within the block so users can reach its actions without leaving it — Action bars placed outside the block boundary break the focus order: keyboard and screen-reader users can't reach a block's actions from within the block they're editing, and the association between block and controls becomes ambiguous.
<!-- rule:151 -->
- Only anchor comments/annotations on revision-stable content paths — supports nested `StructBlock` fields — `StructBlock` field paths persist across revisions so nested comment anchoring stays correct; `ListBlock` child IDs are reassigned when contents change, so anchors silently point at the wrong block unless paths are re-anchored on edit or comment granularity is rejected there.
  For `ListBlock` (unstable child IDs), add path re-anchoring on edit or disallow comment granularity — otherwise comments drift to the wrong block across revisions
<!-- rule:231 -->
- Put shared fields on a common `StructBlock` base that `UnionBlock` members subclass; render type-specific output in each constituent's `get_context` or template. Avoid duplicating shared fields or requiring a custom `StructValue` for common cases — keeps choice fields composable and spares callers boilerplate — Parallel struct definitions with duplicated shared fields drift apart, and forcing a custom `StructValue` on every consumer of a `UnionBlock` choice field adds boilerplate for the common case. A unified hierarchy with shared fields on the base and per-block context/template rendering keeps the API usable and consistent across Wagtail block types.
<!-- rule:237 -->
- Use server-side expiry (heartbeat + staleness timeout) as the source of truth for ephemeral state; add an explicit release/delete endpoint only when expiry latency is unacceptable. — Client-side lifecycle events (`visibilitychange`, `focus`/`blur`) and periodic pings are unreliable for correctness — backgrounded tabs, crashed clients, and dropped connections still leave stale sessions. Heartbeat pings plus server-side staleness timeouts guarantee cleanup regardless of client behavior. An explicit release endpoint is only worth adding when real-time feedback or immediate cleanup is required.
<!-- rule:6 -->
- In headless/static-generation integrations, bulk-fetch shared data at build time (e.g. the full redirect list once) and prefer one consolidated `GraphQL` query per page over many `REST` calls — avoids per-request N+1 latency and keeps builds deterministic. — Static builds run once and are cached, so per-page `REST` fan-out multiplies latency and can hit rate limits, whereas a single `GraphQL` query reuses a shared fetch and makes output reproducible.
<!-- rule:29 -->
- **Expose template parity in Wagtail REST APIs** — surface focal points, redirects, settings, snippets, and CRUD/search so headless clients get the same features as server-rendered templates. Judge backend support by whether core stores the data *and* exposes it via API, even with an external renderer. — Headless frontends otherwise become second-class citizens, missing data and operations that server-rendered templates rely on; treating "stored + API-exposed" as the bar for core support keeps parity decisions independent of where the renderer lives.
<!-- rule:181 -->
- Generate content-dependent derived assets (e.g., image renditions) in the save/publish workflow or a background worker, never inline in the request/response cycle — keeps page requests fast and avoids recomputing renditions on every render. When pre-generating at publish time, render the page template internally to discover all required variants so none are missed. — Inline rendering of renditions blocks the request/response cycle, causing slow page loads and duplicate work on every render.
<!-- rule:200 -->
- Preserve existing default output of `wagtail.images` template tags when adding format-aware options; expose new behavior via opt-in args/modifiers/dedicated tags — templates relying on current rendering must not change. — These rules preserve backward compatibility of existing image template output while making SVG/animated GIF rendering first-class. Without them, template authors must hand-write `{% if %}` branches per format and track filter/format compatibility themselves, and SVG renditions get unnecessarily rasterized — losing crisp vector output and quality.
  - Drive format variation (SVG, animated GIF) with sensible format-aware defaults instead of `{% if %}` branches or exposing format/filter combos that force authors to remember compatibility rules.
  - Render SVG renditions via vector-native attributes (`width`, `height`, `viewBox`, `preserveAspectRatio`, root-group `fill`/bgcolor) rather than rasterizing; deliver SVG by default and gate rasterization-requiring filters behind an opt-in flag like `preserveSVG` so developers can still choose rasterization for style fidelity.

## Documentation

<!-- rule:1 -->
- Proofread spelling/typos in docs and RFC/spec prose before merging — including inside inline literals and narrative rationale — Misspellings in `draft/` and `text/` documentation ship into published specs; narrative prose is authored content, not code, so typos there are defects, not stylistic choices.
<!-- rule:116 -->
- Write valid Markdown: `[text](URL)` with non-empty link text (never `[](path)` or `[url](URL)`), headings and numbered list items on their own lines, and closed inline code spans — malformed links render as literal text or broken anchors, and unclosed backticks swallow the paragraphs that follow. — Keeps documentation rendering as intended across `docs/`, `text/`, and other Markdown files.
<!-- rule:111 -->
- Write complete, grammatical sentences in RFC/docs prose — fragments, comma splices, and run-ons make RFCs ambiguous and unreviewable — RFC and documentation prose (including headings) is read as specification text, so elliptical fragments like "When should ..." or "Any ..." and run-on/comma-spliced sentences create ambiguous requirements; split independent clauses into their own sentences, capitalize the new first word, comma-set non-restrictive `which` clauses, and start contrasting drawbacks with "However". Keep `whereas` as one word, prefer "and that" over contrastive "but" when the contrast is already implied, and separate rejected alternatives with "or" (not a comma) when the intended reading is "not A or B". Maintain parallel structure in lists and standard transitions so readers can scan requirements consistently. Applies globally to any RFC/documentation markdown under `text/` and root `README.md`.
<!-- rule:126 -->
- In RFC/spec rationales and comparison sections, reserve `must`/`required` for true constraints and use `ideally`/`should` for preferences — mislabeled wording misleads readers about what is actually required — Readers of RFC rationales, decision, and comparison sections treat `must` as a hard constraint; applying it to preferences distorts the decision record.
<!-- rule:163 -->
- **Document every parallel variant of a Wagtail feature and each affected subsystem** — for example `Image` vs `Document` models, pages vs internal APIs, live vs draft revisions, `wagtail start` vs existing-project setup, separated vs combined content trees. Undocumented counterparts leave users unsure which variant a guarantee or behavior applies to. State exact scope per variant instead of absolute words like "never", and explicitly call out intentional divergences (e.g. backward-compatibility guarantees) or unsupported variants rather than leaving their behavior undefined. — Wagtail features with parallel counterparts or structural variants often share guarantees (or deliberately don't). If a design doc or docs page covers only one variant, readers may assume the same behavior applies to all of them, leading to incorrect usage or broken assumptions. Explicitly scoping each variant — and naming intentional differences or unsupported cases — keeps the documentation accurate and prevents ambiguity about backward-compat exceptions.
<!-- rule:65 -->
- Document breaking changes to default behavior in developer docs and release notes — not just the user guide — with a deprecation warning, an opt-in/opt-out flag, and exact steps to restore prior behavior; a user-guide mention alone strands downstream developers. — Developers cannot migrate safely without a documented compatibility flag and rollback steps. Deprecation in dev docs and release notes gives integrators time to adapt; burying the change in the user guide hides it from the people who actually upgrade their code.
<!-- rule:95 -->
- Use official names in docs: `Sass`, `JavaScript`, `React`, `Wagtail's` (not `Wagtails`) — inconsistent casing and misspelled project names look unprofessional and misname real projects. — Technology names have official capitalization (`Sass` not `SASS`, `JavaScript` not `Javascript`, `Alpine`, `Stimulus`, `React`) and project names are proper nouns requiring official casing and possessive apostrophes (`Wagtail's` not `Wagtails`). Deviating from these conventions makes documentation look sloppy and misrepresents the actual projects being described.
<!-- rule:50 -->
- Document the config model in RFCs *before* implementation: state default vs opt-in/opt-out, name settings with `ENABLE_*` (feature toggles) or `REQUIRE_*` (mandatory input) prefixes, and specify bypass authority/permissions for mandatory behavior — enumerating affected tags/values against an undefined contract leads to inconsistent semantics and rework — Configuration semantics — default state, setting names, and who can bypass mandatory behavior — are hidden assumptions that resurface as bugs once tags/values are enumerated or implementation begins. Locking the model down first (with unambiguous `ENABLE_*`/`REQUIRE_*` prefixes) keeps later RFC sections, config APIs, and implementations aligned and avoids relitigating scope mid-implementation. Applies to RFC/spec documents under `documentation/rfc/`.
<!-- rule:105 -->
- Form plurals without apostrophes (`RFCs`, `PRs`, `all calls`) and use sentence case for non-proper nouns mid-sentence — save apostrophes for possessives and contractions only — In documentation prose, an apostrophe before `s` reads as a possessive (`RFC's` = belonging to an RFC), so using it for plurals misparses the sentence. Sentence case for common nouns mid-sentence ("all calls") keeps prose consistent with the repository's README.md and text/ conventions without capitalizing terms that aren't proper nouns.
<!-- rule:189 -->
- Hyphenate compound modifiers that precede a noun (`server-side HTML`, `client-side code`, `backwards-compatible API`) — unhyphenated pairs misattach to the wrong word and read as copy errors in rendered docs — Drops the 'prefer/always' framing for a flat imperative, and keeps the three concrete hyphenation examples (`server-side HTML`, `client-side code`, `backwards-compatible API`) that make the rule unambiguous. Notes the `text/` and `draft/` doc locations observed in the repo so the style applies repo-wide to documentation prose, not code. Each rationale names the concrete failure it prevents — misparsed modifiers and unreadable run-on prose — instead of appealing to a style guide.
  Split long run-on sentences into shorter ones across `text/` and `draft/` docs — shorter sentences keep the point legible and produce cleaner diffs and translations
<!-- rule:62 -->
- In `RFCs` and `API docs`, name the exact validation trigger and outcome (error type, status code, error response) — vague prose like "an error" leaves implementers guessing what to build and test against. — Specification documents are the contract implementers code against. A phrase like "an error is returned" doesn't tell them which error type, HTTP status, or response body to produce, so different implementations diverge and tests can't assert behavior. Naming the precise condition and outcome keeps the spec verifiable and interoperable.
<!-- rule:99 -->
- Attribute config flags and API conventions in docs/RFCs to the entity that actually defines them — Prevents readers from mistaking package-specific or application-level additions for library/framework features — e.g., a custom flag mimicking React's API is not a React feature.
<!-- rule:131 -->
- Apply org-wide root-file standards (e.g. `CONTRIBUTING.md`) to every project including the main one — ship a reusable template projects can adopt/amend, and where the content already lives in the docs, add a minimal root file that links to it instead of duplicating, so there's a single source of truth — Ensures org-wide standards reach all projects without duplicating content, keeping docs a single source of truth, and keeps contributor-facing policies actionable by aligning them with the actual contribution and review workflow.
  - Pair contributor-behaviour policies with proposed updates to the contribution and code-review process — otherwise the policy isn't actionable
<!-- rule:18 -->
- Move follow-up items from a closed release `N` to `vN+1` — work filed under the release being closed is never revisited. — ...Put these in the AGENTS.md inside the roadmap documentation dir (e.g. alongside `roadmap-updates` / release planning docs)...
  Write `future release cycles`, not `the next release cycle` — unresolved items often carry over past a single version boundary.
<!-- rule:64 -->
- Distinguish independent permission gates in docs and UX (e.g., UI/editor access vs. page-lock content modification) — never assume one grants the other; when an action is blocked, tell the user how to get access, and document this permission-denied messaging in any RFC that adds permission rules. — Treating one permission as implying another lets users with editor access silently fail on locked content, and a blocked action with no guidance (e.g., "contact an admin") leaves them unable to recover — spelling out each gate and its denial message keeps permission semantics honest across docs and UX.

## Code Style

<!-- rule:198 -->
- Use Stimulus controllers for Wagtail admin interactivity and `fetch` over `$.ajax` — keeps admin JS consistent and jQuery-independent — Stimulus controllers make interactive admin behavior reusable and testable; replacing `$.ajax` with native `fetch` removes the jQuery dependency from admin frontend code.
<!-- rule:186 -->
- Define the deletion strategy for Django models with multi-table inheritance or generic FKs: use `Model.delete(keep_parents=True)` to drop children while preserving the base `Page`, and add a `GenericRelation` mixin (or a periodic management command fallback) to purge dependent generic-FK rows. — Django does not auto-cascade multi-table inheritance or generic foreign keys, so programmatic deletions and plain `DeleteView` usage leave orphaned child records and dangling generic-FK references; `keep_parents=True` preserves the shared base `Page` while removing children, and a `GenericRelation` mixin (or periodic management command) is the sanctioned cleanup path.
  **Why:** Django does not cascade either relationship, so `DeleteView`-only or programmatic deletes silently orphan child records and generic-FK dependents — `keep_parents=True` is the only way to remove a `Page` subclass without wiping its `Page` base.
<!-- rule:92 -->
- Don't reject JS-driven responsive layouts for perf alone; debounce the resize handler when the update is costly — preserves the intended UX without resize jank. — JS-driven layout switching (e.g., changing layout on `resize`) is often the simplest way to get the desired responsive behavior; debouncing the handler addresses the actual performance cost without discarding the UX goal.
<!-- rule:103 -->
- Set the Wagtail admin minimum viewport to `360px` and allow horizontal scroll below it; treat up to `768px` as the mobile/tablet breakpoint. Complex nested UIs reflow badly when squeezed, so scrolling keeps layouts usable. — Wagtail admin panels nest deeply; forcing them to reflow below 360px produces broken layouts, while hiding controls breaks UX for narrow-screen users.
  - Don't hide admin info or actions (e.g. block type labels, duplicate controls) for being "too narrow" unless verified they truly don't fit at `360px` — silently dropping controls hides functionality from users.
<!-- rule:161 -->
- Only conditionally render the new feature-flagged admin UI elements — never move or re-order existing ones (e.g., page status, page history) between enabled and disabled flag states; place new UI inside an existing area that already shows related metadata. — Flag states must differ only by the new elements, so the surrounding Wagtail admin layout, selectors, and tests stay identical whether or not the flag is on; relocating existing elements or introducing a new conditional region breaks those shared assumptions and makes the UI jump between states.

## Config

<!-- rule:125 -->
- Resolve redirect URLs in documented, explicit precedence order: existing pages win over redirects by default — implicit ordering lets redirects silently shadow real routes — Explicit precedence keeps routing predictable as redirect features evolve (e.g. `redirects-admin-changes`, `redirect-improvements`). Applying redirects first without excluding `auth`/`admin` login routes risks blocking authentication and denying access to the admin UI.
  - When redirects take precedence, always exclude `auth` and `admin` login routes — otherwise a stale redirect can block login or lock admins out
<!-- rule:57 -->
- Make lock/reservation/session expiry configurable (`settings.LOCK_EXPIRY_MINUTES`) and measured from last activity, not acquisition — hardcoded acquisition-timers expire still-active work, and baked-in values force redeploys to tune — Acquisition-time expiry kills locks/reservations/sessions that are still in use, and non-configurable timeouts require code changes to adjust for different environments or load.
<!-- rule:59 -->
- Expose env-specific API tokens via configuration/settings (with documented dump/restore or startup reseeding) instead of relying only on CMS admin/DB edits — keeps them intact when databases are copied between environments. — Tokens edited only through the CMS admin or DB get clobbered when a database is copied between environments, silently breaking integrations; keeping them in configuration makes environment setup reproducible.
<!-- rule:154 -->
- In Wagtail i18n, define `Locale` records via the `WAGTAIL_CONTENT_LANGUAGES` (formerly `WAGTAIL_LANGUAGES`) setting, not admin-UI edits — Keeps config as the source of truth so deployments don't require manual admin edits; startup should additively create missing `Locale` records (leave orphans for the developer to clean up) and validate any chosen `Locale` against the current configured list, so imperfect record/setting sync never blocks a valid choice.

## Dependencies

<!-- rule:91 -->
- Evaluate third-party UI libs (e.g., `react-beautiful-dnd`) before hand-rolling patterns like drag-and-drop; document build-vs-buy rationale (maintainability, testability, reuse, accessibility) if you build custom. — Accessible drag-and-drop (touch + keyboard) is hard to get right, and the admin frontend, streamfield/inlinepanel, and RFC 26 proposals all benefit from reusing proven libraries rather than accumulating bespoke code that drifts in behavior and accessibility.
<!-- rule:2 -->
- Ship opt-in feature dependencies as install extras (`wagtail[api]`), not base requirements, and keep core/admin imports free of them. — Forcing heavy libs (e.g. DRF, rasterisation libs) on every user bloats base installs and breaks the dependency-free win; refactor such imports to plain Django/stdlib, keep the fallback path usable (e.g. render original assets as-is), and document a bypass for the library-presence check.
<!-- rule:205 -->
- Check a dependency's `package.json` (`module`, `main`, `types`, `exports`) before adding transpilation for it — Dependencies that already publish ESM/UMD/CJS builds and type definitions don't need a TypeScript/Webpack/Jest transpile step — adding one duplicates work and can break resolution.

## Deprecation

<!-- rule:26 -->
- Deprecate public APIs, parameters, models, and features in-place with warnings before removal — immediate breaks fragment downstream users and force urgent migrations; only extract to a separate package when repo ownership and maintenance responsibility are explicitly defined — Public APIs, parameters, built-in models, modules, and features are consumed by external users who need time to migrate. Sudden removal causes breaking changes that force rushed upgrades or pin users to old versions; in-place deprecation under a legacy/obsolete name (without a fixed removal timeline) plus a clear migration path gives consumers a stable runway. Extracting code to a separate package is only safe when someone is committed to maintaining it — otherwise it becomes orphaned.
<!-- rule:143 -->
- Write a data migration backfilling existing records when a new model/field replaces legacy tracking — records left in the old state silently diverge, and legacy special cases accumulate. — Category: deprecation, scope: project-wide. Placed in the root `AGENTS.md` because the practice applies to any model, field, or workflow that replaces a pre-existing tracking/data mechanism anywhere in the repo.
  - If the new system isn't an exact replacement for the legacy behavior, design the two to coexist rather than forcing a migration — a lossy backfill corrupts data.

## General

<!-- rule:157 -->
- Never let cross-locale page operations proceed silently (locale changes, cross-locale moves, redirects/links to translated pages) — first check whether a translation exists in the target locale, then either block the action with a user-facing explanation (including side effects like internal links that won't update) or apply an explicit locale-resolution fallback (request language, site settings, or defined fallback). Silent failures trip `unique_together` on `locale` and produce ambiguous localized URLs and cross-locale links. — Cross-locale operations that can hit `unique_together` on `locale` or leave internal links/redirects pointing at the wrong translation fail invisibly and yield ambiguous routing — an explicit check plus user notification or fallback turns silent corruption into a resolvable action.
<!-- rule:201 -->
- Register Stimulus controllers explicitly in `client/src/includes/stimulus.ts` — not via Webpack's `require.context` — Keeps identifier-to-file mappings searchable in one place, controls what enters the bundle, and avoids coupling the setup to a Webpack-only API that must be shimmed for Jest or other bundlers.
<!-- rule:209 -->
- Sanitize/whitelist user-uploaded SVGs on upload — strip dangerous elements like `<script>` and attributes like `xlink:href` before storage or processing; unprefixed SVG in Wagtail's media origin enables stored XSS against authenticated editors. — SVG is both an image format and an active document. Wagtail image uploads flow through storage and delivery paths an attacker can influence, so sanitization at upload, safe headers/origin at serve, and a documented `<img>`-only embedding contract are needed together; skipping any one reopens XSS on editor sessions.
  - Serve stored SVGs with `Content-Disposition: attachment` or from a separate origin — serving directly from the site origin lets a crafted SVG execute script in the app's cookie/session context.
  - Document `<img>` as the only supported SVG embedding context (secure animated mode) — other contexts (`<object>`, `<iframe>`, inline `<svg>`) re-enable scripting that sanitization was meant to block.
<!-- rule:155 -->
- Qualify Wagtail content-language settings with `CONTENT` or an explicit term — e.g. `WAGTAIL_CONTENT_LANGUAGES`, `WAGTAIL_MULTILANGUAGE_SITE`. Never use names like `WAGTAIL_I18N_ENABLED` that overlap with Django's `USE_I18N` — keeps UI/backend i18n distinct from content-language config. — Prevents ambiguity with Django's `USE_I18N` UI/backend i18n settings; overlapping names confuse which system a setting configures.
