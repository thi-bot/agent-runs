# docs/ Guidelines

## Documentation

<!-- rule:115 -->
- In Markdown docs, nest headings sequentially — never skip levels (e.g. `##` → `#####`) or flatten all headings to one level; broken outlines break TOC/anchor generation and accessibility — Sequential nesting preserves the document outline that TOC/anchor generators and screen readers rely on; flattened or skipped levels silently produce wrong or missing navigation entries.
<!-- rule:83 -->
- Reserve inline code (`` ` ``) for real identifiers (`Page`, `RichTextField`, `wagtailsnippets_app_model`): classes, models, fields, modules, settings, template tags, commands, paths, URL names, HTML tags, API names — not user-facing feature names, UI labels, proper nouns, or concepts like 'many-to-many' or 'workflow tasks section'. Tagging prose terms as code confuses readers about what's a symbol vs. a concept, and misformats search results. — code formatting marks identifiers an editor or reader can look up; over-formatting turns UI labels and concepts into false symbols, while under-formatting hides real names users need to type verbatim.
<!-- rule:711 -->
- In `docs/` Markdown, use a single space between words and around inline `code` spans — prevents prose from running together when double spaces are collapsed or omitted. — The rule is scoped to Markdown documentation under `docs/`, so it belongs in `docs/AGENTS.md` where assistants editing that tree will encounter it. Double spaces are stripped by most renderers, and missing spaces around inline code cause the code span to visually merge with adjacent prose, hurting readability. It is a directory-scoped convention, not a cross-file synchronization rule, so no repository-root entry is needed.
<!-- rule:2730 -->
- Format external links in `docs/**/*.rst` as inline hyperlinks: `` `Link text <URL>`_ `` with a space before `<` — RST requires that space to parse the reference, and attaching the link to the referenced concept (not an incidental value) keeps docs readable and easily searchable. — In RST, an inline external link only parses correctly when the syntax is `` `Link text <URL>`_ `` with a space before `<URL>`; omitting that space causes the link to render as literal markup or a broken reference instead of a working external resource. Linking the relevant concept or term rather than an incidental value keeps those external links consistently styled and semantically meaningful, so readers can tell what each destination supports and the links do not become misleading as the surrounding sentence changes.
<!-- rule:550 -->
- Follow Diátaxis tutorial principles in `docs/getting_started/` and `docs/tutorial/` — tutorial readers need a single linear path, so extra context causes them to lose the thread and fail the walkthrough. — Tutorials succeed only when readers reach a working result on the primary path; background and alternatives dilute that path and cause drop-off, while misplaced notes force readers to hunt for context out of order. See `docs/getting_started/tutorial.md`, `docs/getting_started/tutorial.rst`, and `docs/tutorial/create_contact_page.md` for the established pattern. Concrete conventions: omit non-essential background and alternative approaches; write concise, direct prose with neutral transitions; place notes and configuration guidance adjacent to the concept they explain or immediately before the command they modify; format sequential UI steps as numbered lists with instructional prose separated from bold UI labels.
<!-- rule:563 -->
- Write tutorial steps as explicit imperatives, placed where the action first applies — keeps readers from re-reading setup twice or missing mandatory commands. — The rule applies to tutorial/procedural docs under `docs/` (e.g., `docs/getting_started/tutorial.md`, `docs/tutorial/deployment.md`).

Bullets:

- Format steps and sub-steps consistently — mixed prose and stray code blocks confuse readers about what to run vs. what's narration.
- Keep exact commands and required actions verbatim; don't soften mandatory steps into optional or casual prose — users will skip required setup and hit downstream failures.
- State each setup detail once, at the point it's first needed — repetition bloats tutorials and makes maintenance error-prone when details change.
- Prefer imperative/second-person phrasing ("Run `make build`") over passive/descriptive prose ("The build would be run") — matches how readers scan procedural docs.
<!-- rule:698 -->
- In command/option docs, spell out expected output, prompt responses, effect scope (e.g., per-item), defaults/omitted behavior, and when to pick each alternative — implicit details force users to trial-and-error. — These details are what users consult docs for; leaving them implicit causes wrong invocations and support churn.
<!-- rule:1103 -->
- Write Sphinx cross-references (`:doc:`, `:meth:`, intersphinx/inventory links) that resolve — build docs locally to verify, and enable `nitpicky = True` (or `-n`) in CI so broken refs fail the build. Unresolved links ship silently as plain text otherwise. — Sphinx degrades unresolved references to plain text without error, so only a nitpicky build catches them — keeping `docs/` navigable and only one tangential file (`wagtail/models/pages.py` + `docs/conf.py`) touches this rule's surface.
<!-- rule:1388 -->

  - In index entries, name the emitted markup tag/class (e.g. ``<div class="rich-text"></div>``) instead of describing it abstractly — readers copy these, so they must be exact.
  - Keep full module reference detail in `docs/reference/contrib/{module}.md` and link to it from topical/advanced-topic guides — duplicated docs drift out of sync.
<!-- rule:2045 -->

Misplacement, weak actionability, and missing cross-links also cause Wagtail security, deployment, and feature documentation to duplicate or drift, creating a maintenance cost and surprising readers who trust one page to be complete.

<!-- rule:737 -->

Skipping cross-framework comparisons, restated context, and one-off subsections keeps command references scannable without adding navigational overhead.
<!-- rule:1448 -->
- In `docs/reference/settings.md` (and other settings docs), describe each setting by the user-visible behavior it toggles, not internal jargon or quoted UI labels — readers need to predict what actually changes. — These conventions appear across many docs (`docs/reference/settings.md`, `docs/advanced_topics/customisation/page_editing_interface.rst`, `docs/advanced_topics/privacy.md`), so phrasing users can act on is what keeps the reference trustworthy.
  - List only options that can be enabled/disabled; document always-on features separately — avoids sending users hunting for a nonexistent switch.
  - For settings that disable or alter existing functionality, state the side effects on related features, whether existing data/usage stays visible, and whether the change is admin/editor-only vs public-facing — prevents silent breakage surprises.
<!-- rule:834 -->
