# Testing Patterns and Regression Coverage

> Rules for boundary tests, regression tests, edge cases, branch coverage, mocks, transaction callbacks, auth/template tests, and isolating ambiguous fixes.

**When to check**: When writing or updating tests for new behavior, fixes, or edge cases.

## Rules

<!-- rule:721 -->
- Test truncation filters at boundaries using the exact `[:N]` slice and `str()`/`repr()` call from the production path — boundary cases (exact length, `0`, negative) catch off-by-one and conversion drift where a test's truncation diverges from production. — Truncation bugs hide at the edges: off-by-one slices and `str()` vs `repr()` mismatches only surface when the test reproduces the production length and string conversion exactly, so reusing `[:200]` and the same conversion keeps the two paths equivalent.
<!-- rule:2428 -->
- Add a regression test with an input that behaves differently when you change string-splitting (`maxsplit`, `split()` vs `rsplit()`) — the test must fail without the change. — Splitting tweaks in `django/db/models/query_utils.py` and `django/core/mail/message.py` slipped through because existing tests passed with or without the behavioral argument; a failing-without-change test is the only proof the new behavior is actually exercised.
<!-- rule:1283 -->
- Test early-return guards and fast paths separately from the main success path — catches divergence between fast and fall-through branches — Fast paths often skip validation or setup that the full path performs; without a dedicated test, code drift lets the two branches return different results for the same input, silently breaking callers that rely on consistent behavior.
<!-- rule:3121 -->
- When wrapping a callable with `@sensitive_variables(...)` (or similar scrubbing decorator), add a regression test that raises inside the callable and asserts the named variables are absent from the technical error report — happy-path tests pass even after the decorator is dropped, so a silent removal leaks secrets (see `django/contrib/auth/forms.py`). — A decorator relies on the exception path to scrub data; a success-path test never exercises that code, so it cannot detect decorator removal. Triggering the failure path and asserting exclusion is the only way to catch a regression that would leak sensitive values into technical error reports.
<!-- rule:2891 -->
- Test method names must be unique within a test class or module; when adding or moving a test, check for existing names and choose a distinct, descriptive name instead of creating a duplicate. — Duplicate test method names silently shadow or overwrite the earlier definition, so one of the tests never actually runs and the intended coverage is lost without any visible failure.
<!-- rule:2256 -->
- Test and document intentional validator exclusions (e.g., `DomainNameValidator` rejecting IPv4/IPv6) — silent exclusions read as bugs — Intentional exclusions in validators look like bugs when undocumented — covering them in `tests/validators/tests.py` locks the behavior and the `docs` reference explains why a well-formed input is rejected.
  In `tests/validators/tests.py`, add cases for well-formed inputs the validator deliberately rejects, and note the exclusion in the `docs` reference — otherwise users (and future maintainers) hit the rejection without context and treat it as a regression in `django/core/validators.py`.
<!-- rule:3985 -->
- Add edge-case tests whenever you touch delimiter/template-tag parsing (e.g. `django/template/base.py`, `django/urls/resolvers.py`) — cover empty/adjacent pairs, unmatched openers/closers, nesting, reversed combos, repeated searches, and end-of-input boundaries; these mismatches slip through happy-path tests. — Delimiter parsing fails silently on unbalanced, nested, or boundary cases, so covering them is what actually catches the regressions.
<!-- rule:3688 -->
- Test every character in regex character classes and every branch of alternations — dropping one branch silently breaks input handling — A regex like `[a-z0-9_]` or `foo|bar` looks fine when one branch is missing; only a test that feeds each alternative catches the regression. Without per-branch coverage (e.g. in `django/contrib/admindocs/utils.py` or `django/contrib/staticfiles/storage.py`), a removed character or alternative fails silently in production instead of in CI.
<!-- rule:4309 -->
- Cover new branches in `django/utils/http.py` parsing helpers (e.g. `_parseparam`) with tests for quoted values, embedded delimiters, and escape sequences — silent branch regressions corrupt HTTP parsing for every caller — HTTP parsing helpers in `django/utils/http.py` handle delimiters, quotes, and escapes through conditionals whose edge cases rarely surface in normal requests. Untested branches rot silently and break real clients. The delete-and-check-fails step catches tests that pass without actually exercising the branch; CPython's `Lib/test/test_cgi.py` already codifies the tricky quoted/escaped cases worth mirroring.
  - Verify each branch test by temporarily removing the condition; if no test fails, the edge case is unguarded. Use upstream `Lib/test/test_cgi.py` as reference for quoted/escaped parameter cases
<!-- rule:4609 -->
- Test every distinct composite-field query-building path — cover multi-sub-field/multi-column RHS and aggregates over nested composite paths — Single-sub-field happy-path tests miss breakage in the multi-column RHS and nested-aggregate code paths that composite field support introduces.
<!-- rule:4743 -->
- Preserve every existing lookup-type branch and state adjustment when editing ORM query/lookup conditionals (`django/db/models/fields/json.py`, `related_lookups.py`, `django/db/backends/mysql/operations.py`) — a dropped "unrelated" branch silently regresses existing lookup behavior and tests. — ORM lookup conditionals route several lookup types and backend-specific state (e.g. JSON, related-field, and MySQL operation paths) through the same `if`/`elif` chains. Adding a new feature often edits those shared conditionals, and removing or narrowing a branch that looks unrelated to the change quietly breaks an existing lookup type — the failure only surfaces in existing tests or at runtime for users of the untouched lookup.
<!-- rule:5197 -->
- Match mock return values to the real function's documented return type — use `[]` for list-returning funcs, a tuple for documented triples; mismatched containers let `TypeError`s slip past tests that should catch them. — A mock returning the wrong container shape makes tests pass against a contract the real code never has, so type/iteration errors only surface in production.
<!-- rule:5266 -->
- In tests, register `transaction.on_commit(...)` directly inside `captureOnCommitCallbacks(execute=True)`; avoid extra `transaction.atomic()` — nested atomic blocks register outside the capture and callbacks silently never fire — `captureOnCommitCallbacks` only captures callbacks registered while its context is active; wrapping them in another `transaction.atomic()` or firing them eagerly inside the helper bypasses that capture, so the assertions pass vacuously or fail with callbacks that never ran.
<!-- rule:3477 -->
- Test multi-db relations by exercising `allow_relation()` (e.g. reassigning a FK after save) and asserting persisted state with `assertSequenceEqual(instance.relation.all(), expected)`, not just that no exception was raised. — A router returning `None`/default silently permits cross-database relations, so "no exception" passes even when the relation was never saved — covering both the disallowed and explicitly-`True` router cases (including `set(..., bulk=False)` cross-db save/duplication) catches silent data loss.
<!-- rule:3591 -->
- Add focused tests in `tests/auth_tests/test_templatetags.py` (tags) or `tests/auth_tests/test_templates.py` (template behavior) whenever auth template tags or templates change — indirect coverage won't catch regressions in these files. — Auth template tags and templates are exercised obliquely by other tests, so a change that breaks rendering or tag output can pass CI until a downstream view fails. Focused tests in `auth_tests` pin the behavior where the change is made.
<!-- rule:6064 -->
- When a fix's layer is ambiguous, write a focused failing test first — surfaces the bug via public behavior and identifies the layer that actually needs patching (`django/contrib/admin/options.py` vs `django/utils/decorators.py`) — Landing a fix in the wrong layer hides the real cause and creates regressions; a failing test through public API proves which layer owns the bug.
<!-- rule:3867 -->
- Test the guard branch of type-conditional code (e.g., `Expression` where `Value` is expected) and assert the input passes through unchanged — untested branches silently mishandle inputs. — Testing guard branches and locking helper step order prevents silent regressions where unexpected types bypass transformations or refactored validation steps run out of order, producing incorrect results without any existing test failing.
  - Add a regression test locking step ordering when extracting a validation/transformation sequence into a helper — reordering silently changes behavior.
<!-- rule:3640 -->
- Prefer `django.test.utils.garbage_collect` and extracted helper functions over ad-hoc `gc` calls in test code — centralizing GC setup keeps its purpose documented so critical steps aren't silently dropped. — Ad-hoc `gc` manipulation scattered across `tests/` and `django/test/runner.py` hides *why* a step exists; when it's undocumented it gets deleted during cleanup and subtly breaks GC-sensitive tests.
<!-- rule:5629 -->
- Test new `get_context_data()`/`extra_context` hooks and wrappers in generic class-based views, asserting the resulting context values — untested context forwarding breaks silently. Keep tests minimal: pass only what's needed (e.g. `{'extra_context': dict()}`) and use concrete values only when asserting on them. — Context modifying hooks and wrappers silently break when not exercised by tests. A test that passes the only context it needs and asserts on concrete values ensures new behavior is actually verified without coupling to unrelated context.
<!-- rule:3539 -->
- In URL-decoding regression tests (under `tests/`, mirroring `django/` source areas), include encoded characters in **both** the path and query string — decoding bugs frequently hide in only one component, so a query-only or path-only test passes while the other stays broken — Decoding logic is often applied separately to path and query components in Django, so a regression test covering only one can silently miss the other's bug. Inline decode comments let reviewers verify the assertion's intent without re-deriving what `%2F` or `%C3%A9` should become.
  - Annotate each encoded sequence with the value it decodes to (e.g. `# %2F -> /`) — makes expected output checkable at a glance instead of requiring a mental decode
<!-- rule:3954 -->
- Test descriptor semantics directly, not per call site — cover class-level and instance-level access, subclass/inheritance scenarios, and `AttributeError` regression cases (see `django/db/models/query_utils.py`, `django/utils/functional.py`, `tests/model_meta/tests.py`). Rationale: descriptors are shared across many call sites, so per-call-site tests miss inheritance paths and let infinite recursion slip through where an `AttributeError` should be raised. — Descriptors like those in `django/db/models/query_utils.py` and `django/utils/functional.py` are reused across many call sites, so one-test-per-call-site leaves gaps in inheritance behavior and recursion guards. Focused semantic tests document the intended behavior once and catch regressions such as infinite recursion where an `AttributeError` is expected.
<!-- rule:1598 -->
- Modify deferred-field handling (`defer()`/`only()`, `get_deferred_fields()`, deferred loading)? Add regression tests in `tests/defer/tests.py` covering every affected path — deferred-field bugs silently drop columns or reload stale data, so untested paths regress unnoticed. Specifically exercise: explicitly deferred generated fields still appearing in `get_deferred_fields()`; `refresh_from_db()` reloading both explicit `.defer('field')` and model-level default-deferred fields; the `'pk'` alias passed alongside the concrete PK name (including chained `.only()`/`.defer()` calls); and a nested `Prefetch` given an explicit `.only(...)`/`.defer(...)` `queryset` rather than a bare `Prefetch`. Run the `defer` test app including `select_related()` cases and fix regressions. — Deferred-field changes span `django/db/models/sql/query.py`, `base.py`, and `query.py` plus multiple suites (`tests/defer`, `tests/prefetch_related`), so a fix in one path routinely breaks another. These specific cases (`get_deferred_fields()` on generated fields, `refresh_from_db()` with both defer styles, the `'pk'` alias, explicit-`queryset` `Prefetch`) have historically been the silent-failure points.
<!-- rule:2801 -->
- Test optional trailing fields both supplied and omitted — assert the full form and the shortened form, plus combinations where an earlier optional field is absent while a later one is present. Partial-argument parsing bugs (e.g. in `django/contrib/messages/storage/cookie.py`, `tests/mail/tests.py`) only surface in these shortened/combination cases, and full-form-only tests silently miss them. — Serialization/deserialization code and public constructors accepting tuples with optional trailing fields can misparse when an earlier optional field is omitted but a later one is supplied. Testing only the full form leaves these off-by-one positional bugs undetected; covering shortened and mixed-presence forms pins down the parser's behavior across all accepted shapes.
<!-- rule:3118 -->
- Assert new user-facing output in tests, incl. 0/1/multiple values (e.g. `shell`, `runserver`) — untested output changes ship silently and edge-case gaps hide regressions — When user-facing output changes, tests that don't assert the new text (or omit 0/1/multiple-value cases) fail to catch regressions, letting broken command output reach users unnoticed.
<!-- rule:2611 -->
- Test every configuration combination and assignment path (`class` defaults, constructor overrides) — untested paths silently regress when options interact or are set through different routes. — Configuration options that can be enabled together or assigned through multiple supported paths (class-level defaults vs. constructor overrides) create a combinatorial surface where individual options may work but their interactions or alternate assignment paths do not. Tests covering each combination and each path catch these regressions before they ship.
<!-- rule:5116 -->
- **Testing model inheritance:** Derive expected inherited field attributes from the derived class's MRO (first class defining the field wins) — and test both `ConcreteParent, AbstractParent` and `AbstractParent, ConcreteParent` orders, since C3 linearization can shadow a concrete field with an abstract one. — Order-dependent shadowing means a hardcoded expectation from one base-class order will silently pass while the reverse order breaks.
<!-- rule:4248 -->
- When changing request-body parsing in `django/http/request.py`, wrap parse failures in explicit error handling and add regression tests in `tests/requests_tests/tests.py` covering missing headers, empty bodies, and header precedence — prevents silent parser regressions — Request-body parsing is a common source of subtle edge-case bugs; explicit error handling plus targeted regression tests in `tests/requests_tests/tests.py` catch missing-header, empty-body, and header-precedence failures before they ship.
<!-- rule:5647 -->
- Assert both parsed and serialized cookie attributes when testing `HttpResponse.set_cookie` — use `assertEqual` on `c['name']['samesite'] == 'lax'` and `assertIn` on `'SameSite=lax'`; name-only checks miss dropped, mis-cased, or mis-serialized directives (update `tests/httpwrappers/tests.py` alongside `django/http/response.py`). — Cookie attributes flow through two distinct stages — parsing (`c['name']['samesite']`) and serialization (`Set-Cookie` output) — and each can break independently. A test that only checks the attribute name exists (e.g. `'samesite' in c`) passes even when the value is silently dropped, lowercased, or never emitted in the header, letting regressions ship in `django/http/response.py`.
<!-- rule:2530 -->
- Add a regression test in `tests/shell/tests.py` whenever you change how the `shell` management command builds the `exec()` context (e.g. the globals argument) — assert executed code still sees built-in globals (`__name__ in globals()`) and imported namespace objects. — Globals-handling regressions in `django/core/management/commands/shell.py` silently break `shell` for users while leaving existing tests green, so the exec-context contract needs explicit coverage. Behavior-named tests survive refactors of the mechanism, and a shared script helper keeps the command-option and stdin paths in sync so one path can't drift untested.
  Name the test for the behavior, not the mechanism (use `test_command_option_globals`, not `_with_imports`), and share one script helper across the command-option and stdin paths instead of duplicating near-identical scripts.
<!-- rule:3524 -->
- Change choice normalization in `django/utils/choices.py`? Update `tests/utils_tests/test_choices.py` in the same change — untested edge branches regress silently. — The normalization guards (top-level-only callable guard, `Promise`/`str`/`bytes` passthrough, iterable shape handling) are easy to break accidentally; without targeted regression tests the breakage surfaces only at runtime in user code or system checks.
