# Assertion Precision and Observable Contracts

> Assert exact observable behavior, equality contracts, string representations, and error output rather than superficial indicators.

**When to check**: When asserting on output, equality, serialization, errors, reprs, or other observable contracts.

## Rules

<!-- rule:1952 -->
- Add dedicated `__str__`/`__repr__` tests with exact literal expected strings when output is user-visible, logged, or used as a test identifier — catches formatting regressions that silently break logs and diagnostics. — String representations surface in logs, diagnostics, and test identifiers, so tiny formatting changes are easy to miss without exact-literal assertions; self-derived expected values defeat the test entirely, and nested-class reprs differ between CPython releases.
  * Write the expected `__str__`/`__repr__` value as a concrete literal (class name, attrs, quote delimiters); interpolate only env/OS-dependent values (e.g. paths) via `!r`. Never derive it from the object under test (e.g. `__class__.__qualname__` or its fields) — tautological expectations pass even when output is wrong.
  * Skip `repr` assertions for locally defined/nested classes — their format varies across Python versions and causes flaky CI.
<!-- rule:4914 -->
- Assert the `__hash__` contract in tests: equal identity keys produce equal `hash()` values and differing keys produce different values — bare `hash(obj)` calls or `isinstance(obj, Hashable)` checks pass even when hashing is broken. — Only comparing `hash()` outputs across equal vs. differing keys actually verifies consistency and distribution, which is what callers rely on for dict/set correctness. Skip cases for unrelated/invalid types and don't duplicate coverage already handled by the canonical hashability test — redundant cases add noise without catching real regressions.
<!-- rule:3799 -->
- Test `QuerySet.raw()`/`RawSQL` by asserting computed values, not smoke-level shape: compare instances to expected fields (all composite-PK components), check annotations via `.values_list()`, and pin exact messages with `assertRaisesMessage` — superficial assertions let PK-resolution and annotation bugs slip through. — Raw SQL bypasses the ORM's field mapping, so bugs show up in the resolved values (wrong/missing composite-PK components, malformed annotation rows, wrong error text) rather than in obvious failures. Asserting the actual computed behavior — full instance field equality, `.values_list()` annotation output, and the exact `assertRaisesMessage` text for missing-PK cases — catches these regressions where looser checks (e.g. `len()`, truthiness, or generic `assertRaises`) pass silently. Applies to raw-SQL tests under `tests/composite_pk/tests.py` and `tests/annotations/tests.py`.
<!-- rule:5600 -->
- Build expected `ErrorList`s with the same `error_class` as the actual object, and test dict-based errors across different key orders and key mismatches — comparing the full string output catches `error_class`-dependent formatting and dict ordering/equality regressions that assert-by-value tests miss — Django validation and error-list tests — placing in `tests/AGENTS.md` keeps it discoverable wherever regression tests for `ErrorList` behavior are written.
<!-- rule:5591 -->
- Name introspection test helpers after the exact metadata they return, and assert that value across every relevant returned object — presence/type checks miss bugs that corrupt metadata values. — Introspection regressions typically produce a wrong metadata value on an object that still exists; asserting only presence or type lets the bug pass.
<!-- rule:5292 -->
- Assert normalized equivalents compare equal and survive `pickle`/`deepcopy` — e.g., `Index('foo') == Index(F('foo'))` — when testing expression and constructor equality — catches `__eq__`/`__reduce__` regressions in `tests/expressions/tests.py` and `django/db/models/indexes.py` where non-normalized inputs would silently diverge — Expression and model/index constructors normalize their inputs, so two spellings of the same expression (e.g. `Index('foo')` vs `Index(F('foo'))`) must compare equal. Direct equality assertions alone miss `__eq__` or `__reduce__` implementations that only handle the pre-normalized form, which then breaks `pickle`/`deepcopy` roundtrips — a real failure mode for query and schema objects.
<!-- rule:3782 -->
- Assert named-row APIs (`values_list(named=True)`, `in_bulk()`) with `assertEqual` on both `_fields` and attribute values — `assertTupleEqual` compares positionally and passes even when field names regress. — `assertTupleEqual` cannot distinguish a namedtuple from a plain tuple, so field-name bugs slip through; asserting `_fields` plus attribute access locks in the named contract users actually depend on.
<!-- rule:6121 -->
- In negative `LIKE`-escaping tests (e.g. `rebate__endswith="%"` in `tests/migrations/test_operations.py::test_add_constraint_percent_escaping`), put the wildcard in a non-matching position — use `"1http://10%$"` rather than `"10$"` — so the test only passes when escaping works and fails under a mis-escaped constraint. — A fixture value without the wildcard passes even when escaping is broken, silently hiding the bug the test exists to catch.
<!-- rule:625 -->
- In tests of `OuterRef`-based correlated-subquery ordering, order by an expression combining a local field with the outer anchor (e.g. `Abs(F(<local_field>) - OuterRef(<outer_field>))`) — a bare `.order_by(OuterRef(...))` is constant per outer row, so it's a no-op that validates nothing. — An `OuterRef` resolves to a single value for each outer row, so `order_by` on it alone can't distinguish or reorder rows within the subquery — the test passes regardless of whether ordering works. Mixing in a local field (e.g. `Abs(F(<local_field>) - OuterRef(<outer_field>))`) gives the sort key variation per outer row, actually exercising the correlated ordering path.
<!-- rule:1953 -->
- Test custom `repr`/truncation wrappers against their configured limits, deriving stdlib parts with `reprlib` — catches wrapper bugs without re-testing stdlib — Scope: tests. Covers wrappers around stdlib formatting/truncation behavior; testing them directly catches bugs in their specific limits and choices, while deriving stdlib portions via helpers keeps the suite from reimplementing stdlib behavior. Reusing verified wrappers as expected-value sources prevents copy-pasted logic that would mask regressions.
  - Reuse a verified wrapper to compute expected values in related tests — duplicating its logic hides wrapper regressions
