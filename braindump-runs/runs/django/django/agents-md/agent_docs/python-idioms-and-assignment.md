# Python Idioms and Assignment

> General Python coding idioms: assignment style, dict defaults, mapping key assignment, bit flags, dunder calls, keyword argument spacing, cache invalidation, stack inspection avoidance, and multiline output assembly.

**When to check**: When writing ordinary Python code, formatting output, or reviewing Python style.

## Rules

<!-- rule:4321 -->
- Call side-effect-only functions without assigning their result — use bare calls, or drop unused return values. Assign to `_` only when a bare expression triggers a `pointless-statement` lint (e.g., the call under test inside `assertRaises*`). — Unused assignments to `_` or a name imply the return value matters, hiding the fact that the call is purely for its effect; bare calls (or `_` only where linting requires it) keep intent explicit and avoid dead-variable noise across Django source and tests.
<!-- rule:1636 -->
- Use `dict.setdefault(key, default)` for check-then-assign — atomic under CPython's GIL and avoids `try`/`except KeyError` boilerplate. Applies to lazily populating nested/options dicts (e.g. `params.get('OPTIONS') or {}` then `setdefault('CLIENT_OPTIONS', {})`) and caller-provided mappings where caller values take precedence. — The check-then-assign variants (`if key not in d`, `d.get(key, default)`, `d.update({...})`, `try`/`except KeyError`) do redundant lookups, race under threads, and diverge in style; `setdefault` is atomic under the GIL and canonical. The exceptions matter because blind `setdefault` hides missing-key bugs, wastes work on expensive defaults, and silently corrupts caller-supplied config.
  - Index directly (`d["key"]`) when the key is guaranteed present — silent masking hides real `KeyError` bugs.
  - Use explicit `if key not in d:` when the default is expensive — `setdefault` args are evaluated eagerly every call.
  - Never call `setdefault` on a caller-owned dict (it mutates receiver state) — build `{**defaults, **caller_config}` instead.
  - Don't initialize dicts/vars with values unconditionally overwritten before first use.
<!-- rule:160 -->
- Use one assignment per line in Python (`self.a = a` / `self.b = b`, not `self.a, self.b = a, b`; `a = v` / `b = v`, not `a = b = v`) — parallel and chained forms hide which value lands where, so reordering or extending one silently rebinds the other. Reserve tuple unpacking for real iterables. Applies to docs examples too. Exception: `x = self.x = expr` on one line is fine within the line-length limit. — Independent values are clearer and safer as separate statements: parallel tuple assignment (`self.a, self.b = a, b`) and chained assignment (`a = b = value`) couple unrelated names, so inserting, removing, or reordering one value quietly changes the binding of another. In a codebase as large as this (Django `django/*` sources and `docs/*` examples), that kind of silent rebinding is a real bug source. Reserving unpacking for actual iterables keeps the idiom's meaning obvious, and applying the rule to documentation examples keeps samples copy-pasteable. The narrow exception — assigning the same expression to a local and a `self.` attribute in one line — is allowed because it stays within the project's line-length limit and reads naturally.
<!-- rule:3670 -->
- Avoid stack/frame inspection for caller-context decisions — pass explicit flags, hooks, or move the condition to the caller instead — Frame introspection (`inspect.stack()`, `inspect.currentframe()`, `sys._getframe()`) is slow, breaks under wrappers/decorators/Cython, and hides the actual conditional dependency from callers and type checkers. If introspection is truly needed (e.g., external-use or deprecation warnings), walk only the required frames via `inspect.currentframe().f_back`, or use `traceback.extract_stack()` filtered by module prefix; derive names from frame attrs like `f_globals['__name__']`, `f_code.co_filename`, `f_code.co_qualname` instead of `inspect.getmodule()`; document any negative stack-index math; and `del` frame references after use to avoid reference cycles.
<!-- rule:4549 -->
- Assemble multiline output as a list of lines and `"\n".join()` them — avoids trailing-newline and separator bugs that per-line concatenation introduces. Keep blank lines and section separation in the rendering/template layer, not as empty entries in the data — empty entries leak into output and break layouts when filters change. Emit explicit separators between concatenated fragments, and omit the trailing separator when no value follows it — prevents dangling `,`/`|`/blank lines in console output. — These patterns keep human-readable console output (Django management commands, test reporters, diagnostics) consistent across the codebase; mixing data and layout produces extra blank lines, doubled separators, and trailing punctuation that consumers and doctests then have to match.
<!-- rule:2556 -->
- Assign each key at most once when building mappings, namespaces, or context dicts — dedupe literal/tuple entries and check `key in d` before adding generated keys; silent overwrites hide bugs and drop values — Duplicate literal keys in a dict literal silently collapse to the last value, and generated keys can clobber hand-written entries — both cause hard-to-trace value loss in `context`/`namespace`/mapping construction.
<!-- rule:636 -->
- Build bitmasks with `|=` from named flag constants — never `=`, string reparsing, or `& ~flag`. Overwriting or reparsing silently drops flags set by other layers — Direct assignment and `& ~flag` on a full mask discard flags contributed elsewhere (e.g., in `django/utils`, GIS backend, and filesystem storage where flags flow across layers), while reparsing a string is fragile and lossy. OR-ing named constants composes flags safely.
<!-- rule:2279 -->
- Call dunder methods via built-ins (`len(x)`, `repr(x)`), not `x.__len__()` or `len(list(x))`. — Keeps call sites idiomatic and lets classes define their own polymorphic behavior via the dunder instead of forcing `isinstance` branches or eager list conversions.
<!-- rule:5604 -->
- Format keyword arguments without spaces around `=`, per PEP 8 (e.g. `default=False`, not `default = False`), including when the value begins with a unary operator (`buffer=not no_buffer`) and inside docstrings and documentation code samples. This avoids flake8 E251 violations. — Aligns with `flake8` E251 so lint runs stay green across `tests/`, `django/`, and `docs/`. Note PEP 8 exception: keep spaces around `=` when annotated, e.g. `def f(x: int = 0)`.
<!-- rule:2991 -->
- Clear caches in place with `.clear()` instead of rebinding `{}` — preserves container identity so existing references stay valid — In-place clearing keeps the same dict/list object identity, so anything holding a reference to the cache (e.g. `self._state.related_managers_cache` on a model instance) sees updates instead of a detached old container. Redundant resets and per-save unconditional clears add work without changing behavior when invalidation is already handled by the surrounding assignment or existing hooks. Related-manager caches are populated per variant, so missing one (like `GenericRelation`'s) leaves stale entries behind.
  - Don't add cache resets that are redundant — existing invalidation machinery or the next assignment already refreshes the cache
  - In `Model._save_parents()`, skip `related_managers_cache` resets unless genuinely required; if needed, `.clear()` `self._state.related_managers_cache` rather than assigning `{}`
  - Update all related-manager variants together, including `GenericRelation`'s — partial invalidation leaves stale entries
  - Avoid unconditional cache initialization/clearing on every save unless the cache is known to exist or be populated — wasted work on hot paths
