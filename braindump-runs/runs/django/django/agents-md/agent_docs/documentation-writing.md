# User-Facing Documentation

> Rules on documenting shared parameters once with cross-references, Python type/protocol terminology, stating exact runtime conditions and concurrency contracts, describing container return shapes, provenance attribution, safe example content, regenerated artifacts, and removing extraneous docs.

**When to check**: When writing reference/tutorial docs, release notes, or documentation examples

## Rules

<!-- rule:1506 -->
- Document parameters, defaults, and shared behavior once, in the canonical location for the group: the common parent, the section actually implementing it, or a shared file like `docs/topics/forms/formsets.txt`. Cross-reference from delegating/subclass pages (e.g. `docs/topics/forms/modelforms.txt`) instead of restating. Merge repetitive paragraphs into one concise paragraph — duplication drifts out of sync and readers can't tell which copy is authoritative. — Duplicating parameters, defaults, and shared behavior across parent and delegating pages lets the copies drift out of sync, so readers cannot tell which version is authoritative and fixes may be missed in one location.
<!-- rule:2727 -->
- Say `attribute` for dot-access members (not `property` or `member`), and reserve `property` for the `@property` decorator — matches Python's own semantics and prevents readers from confusing plain attributes with descriptor-backed ones. — Describing by the guaranteed protocol or access mechanism keeps docs, tests, and identifiers accurate to what the code can rely on, avoiding misleading claims about concrete types or descriptor behavior.
  Say `key` for subscript access (`obj[key]`) and `dict-like` when the object isn't guaranteed to be a `dict` — describes the protocol the code actually relies on rather than a concrete type.
<!-- rule:2562 -->
- Gate each documented behavior on the exact runtime condition the code checks (required arg combination, enabled setting, supplied value), and describe effects as observable outcomes — inventing conditions the code never checks or explaining internal mechanisms misleads readers — Readers consult reference/tutorial docs to know when a behavior applies; if docs describe a condition the code path doesn't actually check, or explain internals instead of what the user observes, the docs become wrong and untestable.
<!-- rule:419 -->
- Use reserved example domains (`example.com`, `.test`) in docs and test fixtures — real third-party hosts leak intent and can receive unintended traffic — Keeps examples safe to run and makes it obvious the content is illustrative, not a live dependency.
<!-- rule:3275 -->
- Document Python iteration/indexing protocols by exact term: `iterable`, `sequence`, `iterator`, `async iterator`; link `__iter__`/`__getitem__` to Python docs on mention, and say `returns an iterator` (not `yields`) for iterator-returning methods — inconsistent wording like `yields` makes readers guess whether the value is lazy or materialized. — Precise protocol terms and doc links keep docs/ and docstrings consistent, so users can tell whether a value is consumed lazily or fully materialized.
<!-- rule:4185 -->
- Document the exact concurrency contract for public APIs and tests — specify which operations run concurrently vs sequentially, any per-thread invocation limits, and thread-safety guarantees, and qualify constraint-dependent outcomes rather than asserting absolute guarantees. Users and tests will otherwise assume stronger thread-safety than the code actually provides, leading to subtle races in production. — Prevents callers from assuming thread-safety or ordering that the implementation doesn't guarantee.
<!-- rule:4542 -->
- Add provenance comments/docstrings to code copied, adapted, vendored, or backported from external sources (including CPython) — names the original source, version, and license/attribution file so attribution stays accurate and license-compliant. For PSF-derived code, use `# Copyright (C) Python Software Foundation (see LICENSE.python).` (no year), and update or remove it once the code diverges. — Vendored code drifts from its upstream; a stale or missing attribution misrepresents the source and can break license compliance — keeping the comment in sync with the actual code makes the divergence (and the correct license) obvious to future readers.
<!-- rule:2098 -->
- Name the real container type in docs — `list`, `tuple`, `set`, `dict` — and for tuples spell out each element's type and meaning (including bare booleans). Docstrings, annotations, and examples must match the implementation's actual return value (length, order, delimiter), e.g. a tuple example stays `(10, 0)` not `[10, 0]`, a set stays `{'a', 'b'}` not `['a', 'b']`. Mismatched container shape or delimiter silently misleads callers who unpack or index the result, so annotations, docstrings, and examples drift out of sync with the code and break user code that trusts them. — When docs, docstrings, annotations, and examples disagree about the container type — a list described as a tuple, a set shown with list literals, or a tuple example with the wrong arity or element order — callers who unpack or index the return value write code against the wrong shape and hit runtime errors. Keeping all four in sync prevents silent contract drift across `docs/`, module docstrings, and release notes.
<!-- rule:526 -->
- Update `docs/**/_images/` screenshots in the same PR when a change alters the rendered admin UI or documented UI text — otherwise screenshots drift from actual behavior and mislead readers. — Django's docs ship static screenshots (e.g. `docs/ref/contrib/admin/_images/`, `docs/intro/_images/`) that visibly age the moment `django/contrib/admin/` CSS, templates, or UI text changes. Leaving them untouched makes the docs contradict the shipped admin; bundling unrelated cleanups into the same PR bloats the diff and obscures the actual UI change.
  Don't refresh screenshots solely to fix unrelated pre-existing staleness — keeps diffs scoped and reviewable.
<!-- rule:2267 -->
- Keep docs/docstrings scoped to their topic; when removing content, strip its leftover artifacts (`.. _name:` link targets, `.. currentmodule::` directives, orphaned `Example:` lines, now-meaningless reST indentation) — Orphaned scaffolding — dead link labels, stray Sphinx directives, stale references, and indentation kept only for removed directives — breaks reST/Sphinx builds and leaves readers following pointers to nothing.
<!-- rule:2871 -->
- **Use standard Python type/ABC terms in docs and API prose** — e.g. prefer `iterable`, `sequence`, `mapping`, `callable`, `bytes`, `namedtuple`, and `QuerySet` over informal terms like 'dict-like', 'bytestring', or 'array'. When multiple concrete representations are accepted, name the broadest contract the implementation actually guarantees and keep one familiar example for approachability ('a `dict` or other `mapping`'), describing behavior conditionally per representation. Name special supported types such as `QuerySet` explicitly when valid as input or return. Accurate contracts prevent misleading users about accepted inputs and returned values, and consistent terminology across `docs/ref/` and release notes keeps the API reference coherent. — Using standard Python type/ABC terminology (e.g. `mapping` over 'dict-like', `bytes` over 'bytestring', `namedtuple` over 'named tuple', `list` over 'array') in docs and API naming prevents users from misjudging which inputs are accepted and what is returned. Naming the broadest contract the implementation actually guarantees (e.g. `iterable`, `QuerySet`) while keeping one familiar concrete example keeps reference docs accurate without sacrificing approachability, and consistency across `docs/ref/` and release notes avoids contradictory prose.
<!-- rule:3748 -->
- Edit man page source in `docs/ref/*.txt`, never `docs/man/` — hand-edits there are overwritten by the release regeneration, silently losing changes and desyncing generated artifacts from their source. — `docs/man/` is release-generated output from `docs/ref/*.txt`. Manual edits or commits under `docs/man/` get clobbered the next time the release process regenerates man pages, so the fix appears to vanish and the source of truth drifts from what ships.
