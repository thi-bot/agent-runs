# Documentation Content and Accuracy

> Writing and maintaining user-facing docs and reference material with accurate, complete, and non-duplicative content, including licensing/attribution, moved documentation, command behavior, search fields, return values, encoding details, security warnings, and destructive-operation warnings.

**When to check**: When writing, moving, or reviewing project documentation, reference docs, release notes, or user-facing help text.

## Rules

<!-- rule:1209 -->
- Write complete license/attribution text inline in `LICENSE`/`docs` (never end on a colon or lead-in), name the actual copyright holder, scope directory claims to covered assets, and verify external attributions like `GNU` — stale or misplaced notices are legal and trust bugs. — A LICENSE or attribution notice that ends on a colon or placeholder, names the wrong copyright holder, claims coverage of a whole directory when only some assets are licensed, or repeats unverified upstream attributions like GNU creates real legal ambiguity about who owns and licenses the code, so the rule keeps those notices complete, accurate, and scoped — preventing compliance failures and the trust damage they cause.
<!-- rule:1847 -->
- Use `login`/`logout` as nouns and `log in`/`log out` as verbs in user-facing docs and UI — never mix forms (e.g. `login and log out`), since inconsistent terminology reads as a bug and confuses users. For the phrasal verb, match the preposition to the object: `log in to <app/service>`, `log in on <browser/device/tab>`; avoid duplicated or fused forms like `in in` and `logging into`. — Inconsistent login/logout wording looks like a typo or broken copy in help text and UI strings, which undermines trust; matching prepositions to the object keeps instructions grammatically correct across `docs/` and `django/views/templates/`.
<!-- rule:1982 -->
- Enumerate `shell` auto-imports in `docs/howto/custom-shell.txt` and `docs/ref/django-admin.txt` as a code block — name `connection`, `reset_queries`, `models`, `settings`, `timezone`, note all models from all apps are in the default namespace, and state scope limits (e.g. only objects with `__module__`) rather than vague prose. Keeps docs matched to `django/core/management/commands/shell.py`; users rely on the documented namespace. — This matters because `shell`'s auto-import namespace and its opt-out/override hooks are user-facing contract that scripts and tooling depend on, so undocumented or vague prose drifts from `shell.py` and silently breaks the documented namespace and override behavior.
  - List `shell` disable paths in the same docs: the per-run `--no-imports` flag and the `get_auto_imports()` override — keeps opt-out discoverable without reading source.
  - Docstring overridable hooks like `get_auto_imports()` with the exact names imported plus a concrete example — shows override authors what they are replacing.
<!-- rule:1211 -->
- Preserve upstream license, copyright, and provenance headers verbatim in bundled assets (e.g. `django/contrib/admin/static/admin/img`, `js/vendor`) — rewritten or summarized notices misstate attribution and can violate upstream license terms — Bundled/vendored third-party assets (`django/contrib/admin/static/admin/img`, `js/vendor`) ship with their own license headers, and those headers are legally operative. Rewriting or summarizing them breaks attribution accuracy and license compliance; stale version strings misattribute which release is actually bundled; duplicating license text locally creates drift against the upstream canonical notice. Applies repo-wide to any future vendored asset.
  - Update embedded version and source attribution (e.g. `Font Awesome Free vX.Y.Z ... Copyright YYYY`) whenever the vendored asset is regenerated — stale headers attribute the wrong version
  - Reference the upstream project's canonical attribution page instead of duplicating license text in local files — keeps a single source of truth and prevents notice drift
<!-- rule:1581 -->
- Move, don't delete, relocated docs content; keep headings/anchors and commit the move separately — Deleting instead of moving loses content, and leaving a duplicate copy in place lets the two drift; preserving headings/anchors keeps existing inbound links valid, and a standalone move commit keeps surrounding edits reviewable.
<!-- rule:4477 -->
- Treat `REMOTE_ADDR`, `X-Forwarded-*`, and trusted auth headers as untrusted by default — clients can spoof them unless a reverse proxy strips or overwrites them first — These headers are attacker-controlled at the network edge. Framework docs, config, and forms that trust them by default (`REMOTE_ADDR`, `X-Forwarded-*`, trusted auth headers) let any client impersonate identity or location unless a reverse proxy strips/overwrites them. Opt-in, configurable trust forces the deployer to acknowledge the requirement instead of inheriting a silent hole, and generic documentation stays correct as new proxy headers appear.
  - Gate proxy-header trust behind explicit opt-in config, not blanket defaults or soft dependencies — silent trust is a spoofing hole wherever no stripping proxy sits in front
  - Document the spoofing risk and required reverse-proxy mitigation generically rather than per-header — narrow lists miss new headers, and deployers own deployment-specific limitations
<!-- rule:3054 -->
- State the charset, its controlling attribute, and fallback in encoding docs — vague "properly decoded" hides real behavior and misleads debuggers. — Naming the exact charset, which attribute sets it, and the default/fallback behavior lets readers trace the actual transformation instead of guessing at what "properly encoded" means.
<!-- rule:2099 -->
- Document return values in a standalone sentence, not a trailing `, and returns ...` clause. — Readers scan method docs for the value they get back; burying it in the behavior sentence hides return type, ordering guarantees, and empty/single-item edge cases — a pattern this repo relies on in both `docs/ref/*.txt` and backend docstrings like `django/db/backends/base/introspection.py` and `django/db/backends/base/schema.py`. State the returned value directly (e.g., "Return a list of `<items>` for `<context>`"), never narrate the access (`accessing X will return`) or pad with boilerplate like `all the`/`all`. Call out empty returns and single-item vs. list behavior explicitly, since callers branch on those without reading the source.
<!-- rule:3791 -->
- In doc examples and view docstrings, mirror responses verbatim from the public API or overridable helper (same response class, no invented subclasses, no restating helper-owned serialization) — drifting docs mislead users who copy the example instead of reading the source — Docs that invent subclasses or hard-code a helper's default serialization become stale the moment the helper changes, and users copying the example get a mismatched response class. Pointing examples at the actual public API or designated overridable helper (e.g. Django's view response classes and helpers) keeps examples correct as the real definitions evolve.
<!-- rule:5248 -->
- Document destructive or advanced operations with one prominent warning near the start of the description — name the concrete failure mode in plain language and, when available, the safe preview (e.g. `--plan`); skip vague or duplicated value-specific admonitions. Users skim docs, so a single specific warning (with a preview command) prevents data loss that vague or repeated warnings let through. — Duplicated and vague warnings get skimmed past; a concrete failure mode plus a preview command like `--plan` lets users avoid destructive mistakes. Applies wherever destructive ops are documented (reference docs, CLI help, release notes, docstrings).
