# Database Backend SQL Generation and Type Mapping

> Rules for constructing backend SQL, mapping field/data types, handling timezone and date/time conversions, RETURNING clauses, EXPLAIN options, and flush/sequence SQL behavior.

**When to check**: When writing or modifying database backend SQL generation, type mappings, query-analysis helpers, or flush/sequence SQL.

## Rules

<!-- rule:1534 -->
- Represent per-type/per-field behavior in backend-level mappings (defaults, type maps, ranges, feature maps) and consult them via `.get(key, default)` — avoids sentinel comparisons, direct indexing, and per-type special-casing across `django/db/backends/*`. — Centralizing behavior in mappings keeps backends (base, mysql, oracle) consistent, prevents `KeyError`/sentinel drift when new types or fields are added, and makes third-party backends extensible without patching individual code paths.
<!-- rule:907 -->
- Return early on empty/no-op input in SQL-generation helpers, then emit SQL without re-checking derived state — Post-guard re-checks (truthiness of the built object, membership in allowed keywords) are redundant once the no-op case is handled, and they drift out of sync as the helper evolves — hiding the empty case behind stale conditions instead of the explicit early return.
<!-- rule:3300 -->
- In `explain_query_prefix()` (`django/db/backends/*/operations.py`), keep display options separate from execution options: `verbose` controls only `VERBOSE`, while side-effecting options like `ANALYZE` need their own explicit opt-in parameter with docs — silently executing queries on what looks like a display call is a real footgun. — Applies to every backend's `operations.py`, not the wider repo, so it lives at `django/db/backends/AGENTS.md`. Mixing analyze options into display-only parameters causes unintended query execution; unnormalized values slip invalid SQL past Python-side validation.
  - Pass EXPLAIN options through when the backend validates them with clear errors; map/normalize values that must be translated to valid SQL (e.g. PostgreSQL `SERIALIZE` accepts only `TEXT`/`BINARY`) — keeps Python values and emitted SQL consistent across backends.
<!-- rule:5712 -->
- In `typecast_time`/`typecast_timestamp` helpers under `django/db/backends/*`, normalize fractional seconds to exactly 6 digits using the `int((microseconds + '000000')[:6])` pattern. — `datetime.time`'s microsecond field only accepts 0..999999, but backends return varying digit counts — truncation shortens >6, padding lengthens <6. Stick with the slice pattern (not `ljust`/`rjust`) so every backend implementation of the shared base helpers in `django/db/backends/utils.py` behaves identically.
<!-- rule:5082 -->
- Apply timezone conversions (`CONVERT_TZ`, etc.) only when source and target timezones differ — unconditional conversion adds needless SQL and can alter results for matching zones. Pass timezone names through the `params` list rather than interpolating them into the SQL string — keeps queries parameterized and avoids injection in `django/db/backends/*/operations.py`. — In `django/db/backends/mysql/operations.py` and `django/db/backends/oracle/operations.py`, timezone names come from user/session config; string interpolation exposes backends to injection and skipping the equal-timezone check produces unnecessary `CONVERT_TZ` calls that can corrupt datetimes.
<!-- rule:1518 -->
- Gate type-specific special-casing on an explicit type mapping (or discriminator), not on broad category membership like `_is_limited_data_type` / `_limited_data_types` — broad sets silently capture newly added types, so each backend under `django/db/backends` (MySQL, PostgreSQL, SQLite, Oracle) must opt types in deliberately. — Opt-in per exact type forces a conscious decision whenever a new type is introduced; category-set checks like `_limited_data_types` in `django/db/backends` schema editors would otherwise apply special handling to unrelated types that a future change happens to add to the category.
<!-- rule:6407 -->
- Document that query-analysis helpers (e.g. `EXPLAIN ANALYZE`) execute the query and may mutate data via volatile functions — recommend wrapping them in a rollbackable transaction so callers avoid persistent side effects — Skipping this doc hides that helpers like `EXPLAIN ANALYZE` aren't read-only: even plain `SELECT` can mutate data through volatile functions, and unaware callers may leave persistent changes behind.
<!-- rule:5244 -->
- Track `RETURNING` bind vars as a tuple (`_insert_vars`, not `_insert_id_var`) — single-var tracking limits backends to returning only the insert id — The single-var pattern only supports returning the insert id, so any backend needing multiple returned columns (Oracle, PostgreSQL, etc.) needs `_insert_vars`. Iterating all bound vars and matching `%s` placeholders keeps the RETURNING clause order aligned with the returned tuple, and preserving the driver-version-specific result handling avoids regressions on older DB drivers.
  - Build `RETURNING` as comma-separated columns with matching `%s` placeholders, iterate all bound insert vars, and raise `DatabaseError` on empty values — keeps driver-version-specific result handling intact
<!-- rule:2298 -->
- In `InsertReturnParameter.types`, list only field types the backend actually supports as primary keys — Oracle can't index LOB columns, so including `TextField` or `BinaryField` there generates invalid DDL. — Oracle cannot use LOB columns as primary keys, so mapping `TextField`/`BinaryField` in the Oracle `InsertReturnParameter.types` would emit DDL the database rejects. Other backends should follow the same pattern: mapping unsupported types breaks `RETURNING`-style inserts for those fields.
<!-- rule:5464 -->
- In `sql_flush()` for `django/db/backends/*/operations.py`, avoid per-table `ALTER TABLE ... AUTO_INCREMENT`/sequence resets — with `TRUNCATE` the sequence is already reset, so emit resets only via `sequence_reset_by_name_sql(style, sequences)` when `sequences` are supplied; choose `TRUNCATE` for tables whose sequences must reset and `DELETE` for the rest, with no row-count/size heuristics. Sequence state stays consistent with the flush without duplicated or conflicting reset SQL. — Duplicated inline reset SQL bypasses `sequence_reset_by_name_sql` and can desync sequences from the actual flush behavior; `TRUNCATE` already resets them, and using `DELETE` on those tables would leave sequences stale.
