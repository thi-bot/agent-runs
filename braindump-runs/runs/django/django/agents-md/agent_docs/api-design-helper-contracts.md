# API Design and Helper Contracts

> Designing public interfaces and helpers with stable identity, structured URL parsing, mapping merge precedence, single-source state, named return structures, focused helper responsibilities, secure token generation, and explicit signal contracts.

**When to check**: When designing or refactoring public APIs, helper functions, data containers, signals, or security-sensitive utilities.

## Rules

<!-- rule:4205 -->
- Derive `__eq__`, `__hash__`, and cache keys from an `identity` tuple of data attributes — never from `id(obj)`. — `id(obj)` is only unique while the object is alive, so reusing it as a memoization key or dict/set member silently collides across instances (e.g., in `reverse_related.py`, `query.py`, `sql/datastructures.py`). Hash via `hash(self.identity)` and exclude `self.__class__` from the tuple so equal values compare equal regardless of subclass.
<!-- rule:2585 -->
- Use `urllib.parse` (`urlsplit`/`urlparse`, `urlencode`) and named components (`.path`, `.netloc`, `.query`) when handling URLs, not substring tests or tuple indexing — Manual `"?" in url` checks, numeric tuple indexes like `parts[1]`, and query-string concatenation mis-handle fragments, IPv6 hosts, and percent-encoding, and drift from `urllib.parse`'s own semantics used elsewhere in `django/http` and `django/views/generic`. Pick `urlsplit` over `urlparse` when the query is irrelevant (skips the `params` split), and fall back to a non-allocating string check only in hot paths where parsing cost matters.
<!-- rule:1254 -->
- Order merged mappings so higher-precedence ones come last, and document that precedence in the signature/docstring — later dicts override earlier ones, so the order defines the override semantics. — Makes `later-wins` override behavior explicit at the call site and in docs, so callers can predict which value wins when keys collide across merged sources.
<!-- rule:5477 -->
- Keep one canonical attribute per concept — derive dependents, don't alias, repurpose, or duplicate state. — Django classes like `Query`, `HttpRequest`, and migration state often have multiple readers/writers; duplicated or repurposed fields drift apart and cause subtle bugs where one path updates state the other doesn't see.
<!-- rule:2712 -->
- Return named structures (`dataclass`, class, dict, `namedtuple`) for multi-value returns, not bare tuples. — Positional tuples silently break when arity changes or callers unpack and ignore fields; named types self-document and survive added fields. Reserve `namedtuple` for APIs that intentionally expose tuple indexing/unpacking; otherwise prefer `dataclass`, vanilla class, or dict with descriptive keys for attribute-only containers, internal return types, tests, and transient debug metadata.
<!-- rule:1756 -->
- Pass `self.__class__` as the signal sender, not `self` — receivers filter on `sender=`, and an instance won't match. — Senders and receivers share a contract: senders must publish a stable identity (`self.__class__`) so receivers can filter, and receivers must filter once—via `sender=` or an in-receiver check—so handlers fire only for their intended sender. `Signal.connect()` already uses weak references, so `weak=True` is redundant; `weak=False` is reserved for deliberate strong holds. App-scoped handlers reached via broad signals like `pre_migrate`/`post_migrate` cannot rely on `sender=` alone and must inspect `kwargs["sender"].label`, while receivers already registered with `sender=` shouldn't re-check. Django code shows this pattern across `django/core/files`, `django/core/handlers`, `django/contrib/contenttypes`, and `django/contrib/auth`.
  - Omit `weak=True` in `Signal.connect()`; weak refs are the default — pass `weak=False` only when a strong ref is intentional.
  - Scope the sender on exactly one side: pass `sender=` at connect when fixed, otherwise verify inside the receiver (for app-scoped receivers, check `kwargs["sender"].label`).
    - Prevents handlers firing on unintended senders; redundant checks on a `sender=`-pinned receiver just add noise.
<!-- rule:901 -->
- Design helper functions with explicit contracts: read inputs from their own parameters, return single results directly, and name auxiliary return values by their role. — Enclosing-scope reads hide dependencies and break when the helper moves or is called elsewhere; wrapping a lone result in a dict forces callers through an ad-hoc shape; role-based names like `extra_env` stay accurate when the final merged structure changes — unlike names borrowed from the eventual target.
<!-- rule:3902 -->
- Pass derived values to helpers instead of raw source state; group tightly coupled calc/mutation in one documented place — prevents scattered logic from drifting out of sync across `django/db/backends/utils.py`, `django/utils/timesince.py`, and `SelectFilter2.js` — Helpers that take raw state become coupled to internal representation and entangle unrelated state checks, mutations, and derived calculations; consolidating coupled logic in one spot keeps each helper reusable and testable without scattering coordinated updates.
<!-- rule:3901 -->
- Preserve the missing-vs-sentinel distinction when merging layered mappings — in Django ORM lookups and i18n catalogs (`django/db/models/query_utils.py`, `django/views/i18n.py`), stripping `None` or injecting defaults breaks unregistration; return the base mapping directly when there are no overrides — Collapsing 'key absent' and 'key set to `None`' into one state silently resurrects or drops entries that callers intended to unregister; materializing a default sentinel for keys present in no source does the same from the opposite direction. Returning the base mapping unchanged when no overrides exist avoids needless copies and keeps identity for callers that compare or cache results.
<!-- rule:2656 -->
- Generate security-sensitive random values with `secrets` or `django.utils.crypto`, never hand-rolled `os.urandom()` + custom encoding — DIY versions silently lose entropy or break URL-safety. In `django/middleware/csp.py`, `LazyNonce._generate` returns `secrets.token_urlsafe(16)` (128-bit, 22 chars, URL-safe). Prefer `get_random_string` from `django.utils.crypto` over reimplementations unless a benchmark shows a real difference, and define `RANDOM_STRING_CHARS` in `django/utils/crypto.py` as `string.ascii_letters + string.digits` — not a literal alphanumeric string. — This prevents security-sensitive values from silently losing entropy or becoming non-URL-safe (breaking CSP nonces) when hand-rolled `os.urandom()` encoding is used, and it keeps the random-string alphabet defined once in `django/utils/crypto.py` instead of duplicating a literal that can drift from `RANDOM_STRING_CHARS`.
