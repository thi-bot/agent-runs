# Pythonic Idioms & Iteration

> Rules promoting idiomatic Python: iteration/enumerate/zip, attrgetter/itemgetter, augmented assignment, list mutation, enums, pathlib, loop-invariant hoisting, single-source assignment, deliberate caching, and lookup-map defaults.

**When to check**: When writing Python control flow, iterations, or value handling and choosing the idiomatic construct

## Rules

<!-- rule:133 -->
- Initialize each variable, attribute, or dict key at the exact control-flow point its value is determined — assign at most once per execution path. Don't pre-init a default that every branch overwrites; hoist a shared default before the branch when multiple branches would duplicate it; only initialize before branching when a later branch could leave the variable unbound. For values set inside conditionals, compute in a local intermediate and do one final assignment. In constructors, normalize/coerce once and assign the transformed value directly to the attribute (e.g., `self.max_digits = int(max_digits)`) instead of storing the raw value and overwriting it later or only converting into a temp. If an attribute must be reassigned to a derived value, use a distinctly named local and comment the semantic change. — Single-assignment-at-derivation-point avoids stale overwrites, unbound-variable bugs when a branch doesn't assign, and duplicated defaults across branches — the control flow then reads as one authoritative assignment per path rather than a pre-init plus scattered rewrites.
<!-- rule:3033 -->
- Use `operator.attrgetter('<attr>')` / `operator.itemgetter(<idx>)` for simple access — replaces `lambda` accessors, runs faster and stays picklable. — These operators are implemented in C and are picklable, unlike `lambda obj: obj.attr` closures. Use them for `sorted()` keys (e.g. `key=operator.attrgetter('name')`) and callback arguments (e.g. in `django/db/models` and `django/forms`) where a trivial accessor is all that is needed.
<!-- rule:1160 -->
- Cache derived values only when inputs are static/immutable — caches over mutable inputs (reassigned or truncated attributes) otherwise serve stale values — Caching a derived value whose inputs can be reassigned or truncated leaves readers with stale data, and caching dynamic state such as validation errors makes transient failures persist after the underlying input changes. Mutating a cached value without invalidating it either serves stale results or forces eager recomputation, surprising callers that expect the cache to match current inputs. Invalidate the cache on mutation and recompute lazily on next access so cached derived values stay consistent with mutable inputs.
<!-- rule:979 -->
- Use `list.append(item)` for single-element additions — `list += [item]` and `list.extend([item])` allocate a throwaway one-element list per call. — Avoids a per-call allocation of a temporary one-element list wherever a single item is appended across `django/core`, `django/template`, `django/db`, and `django/contrib`.
<!-- rule:1224 -->
- **Use idiomatic `Enum` APIs** — compare members with `is`, check membership with `isinstance(value, EnumClass)`, and iterate the enum class directly instead of `EnumClass.__members__.values()`, which adds indirection and hides `Enum` alias/identity semantics. — Idiomatic `Enum` usage keeps identity checks correct in the presence of aliases and avoids the confusing `.value` hop that both loses the member's display meaning and breaks reconstruction via `EnumClass[...]`.
  - **Consume enum members directly, no `.value` indirection** — encode display symbols/pictograms as the enum value so formatting code interpolates the member itself (`f"{self.category} {description}"` for `str`-derived enums), and when serializing for code that rebuilds via `EnumClass[...]` serialize `member.name`, since the underlying value won't round-trip.
<!-- rule:5176 -->
- Omit dispatch/lookup entries equal to the fallback value in `.get(key, default)` or `except KeyError` paths — duplicates drift when the fallback changes and mask which keys are genuine exceptions. — The rule text already embeds the why. I kept the project-relevant patterns (`.get(key, default)`, `except KeyError`) because they define the trigger condition, and the rest is rationale.
<!-- rule:6183 -->
- Prefer augmented assignment (`+=`, `-=`, `*=`, `%=`) over self-reassignment like `index = index + 1` — the idiom used throughout Django's codebase (`db/models`, `contrib/postgres/fields`), keeps diffs concise and matches surrounding style. — Consistency with existing Django source style and more concise diffs; readers expect the idiomatic form.
<!-- rule:768 -->
- Prefer direct iteration over manual index bookkeeping—iterate a sequence directly when the index is unused, and use `enumerate(seq, start=N)` (dropping redundant `start=0`) when you need both index and element. This avoids `range(len(seq))` subscripting and off-by-one drift. — These are global Python code-style guidelines applied across unrelated modules (e.g. `django/db`, `django/contrib`, `django/utils`, `tests`), so they live in the root AGENTS.md rather than any single directory. Idiomatic iteration avoids off-by-one bugs and misaligned parallel loops; the `zip` ordering caveat prevents silent element mismatch when combinining ordered and unordered/filtered collections.
  - Use `zip()` (wrapped in `enumerate(zip(...))` when the index is needed) for parallel sequences — index-based `range(len(...))` loops misalign when lengths differ.
  - Never positional-`zip()` an unordered or filtered collection (e.g. a `set`) against a parallel list — match elements by an explicit stable key (e.g. object ID) or ensure both collections are ordered and aligned first; order is not guaranteed otherwise.
  - Use slicing or slice assignment with a step for stepped/alternating transforms — clearer than index-modulus logic.
<!-- rule:472 -->
- Use `Path` methods (`joinpath`, `resolve`, `parents`, `parts`, `read_text`, `exists`, `is_file`) for construction and containment checks, not `os.path` or string prefix/substring comparisons — string checks silently misjudge symlinks, `..`, and trailing separators. — String prefix/substring checks and `os.path` helpers fail on symlinks, `..`, and trailing separators, causing wrong containment results. `Path.resolve()` gives a canonical path with documented behavior, while `Path.absolute()` is undocumented. Keeping values as `Path` in tests prevents regressions back to `os.path` and keeps path handling consistent across `tests/`, `django/core/checks/`, `django/conf/`, and `setup.py`.
  - Prefer `Path.resolve()` over `Path.absolute()` (undocumented) when canonicalizing; test containment with `path == other or path in other.parents` and use `Path.parts` for directory/module membership — keeps tests portable across OS path semantics.
  - Keep test paths as `Path` objects end-to-end (e.g. `.joinpath()`, `.read_text()`, `.exists()`, `.is_file()`) rather than converting to `str` — avoids `os.path`-based regressions and keeps assertions consistent.
<!-- rule:1176 -->
- Hoist loop-invariant lookups and conditionals to the outermost loop they depend on — avoids redoing the same work every iteration — Consolidated the four related sub-rules (hoisting, caching, precomputing, single-pass derivation) into parallel bullets, kept every project-specific reference (`connections[using].features.<flag>`, `multiprocessing.get_start_method()`, `_meta.get_field()`) so the rule stays grounded in real call sites, and attached a concrete perf or correctness rationale to each bullet so the 'why' is self-contained.
  - Cache repeated getters in descriptively named locals before loops — e.g., `connections[using].features.<flag>`, `multiprocessing.get_start_method()`, `_meta.get_field()` — re-invoking getters or re-indexing per iteration is a common perf pitfall
  - In per-row/per-object loops, precompute reusable values (column slices, reusable sets, prepared fields) once and reuse — keeps hot loops cheap
  - Build derived outputs from one source (annotations, lookups, subset checks) in a single pass, reusing locals — prevents repeated reconstruction and duplicate expensive calls
  Category: code_style
  Scope: global
  Placement rationale: Applies to loop code across the whole codebase — evidence spans 13 files under the `django` package (models, SQL compiler, cache backends, admin, migrations, sitemaps, DB backends) plus a test file — so it belongs at the top level rather than scoped to any single module or file.
