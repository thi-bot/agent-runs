# User-Facing Documentation & Guides

> Rules for README files, tutorials, release notes, styleguides, and contributor docs: audience, canonical URLs, linking, accuracy, terminology, and changelog discipline.

**When to check**: When writing or editing READMEs, tutorials, guides, styleguides, contributor docs, or release notes.

## Rules

<!-- rule:1890 -->
- Add before/after screenshots to any PR with visual or `client/` SCSS changes — reviewers verify both the bug and the fix — PR-hygiene rule, not tied to a single module. Without screenshots, reviewers can't confirm the visual regression existed or that the change resolves it.
<!-- rule:864 -->
- Link community/chat resources to a stable landing page (e.g. `https://wagtail.org/slack/`), naming the channel in prose (`#translators`) — direct signup/archive/internal URLs skip ground rules like the Code of Conduct and `#support` and break for readers who haven't joined yet. — Direct deep links bypass onboarding (Code of Conduct, `#support`) and 404 or dead-end for users who aren't members yet.
<!-- rule:1394 -->
- Render styleguide template components through the same shared includes/controllers as production — keeps docs accurate and avoids drift. — Styleguide examples that duplicate or fake production markup go stale and mislead, so they must exercise the real `wagtailadmin/shared/*` includes and controllers. Conversely, `wagtailadmin/shared/tabs` and other production templates should stay free of styleguide-only example markup.
<!-- rule:1157 -->
- In `README.md` setup/onboarding and `docs/` narrative & customization pages, lead with user-facing purpose before file paths or APIs — readers stay oriented without implementation context — Documentation is read top-down by people who don't know the codebase yet; burying purpose behind implementation details makes setup docs unusable and drives support questions.
<!-- rule:386 -->
- Don't edit `CHANGELOG.txt` or `docs/releases/{version}.md` in PRs — maintainers curate entries at merge — target release may shift, and concurrent edits cause merge conflicts
<!-- rule:492 -->
- Document only supported, stable behavior; omit or mark quirks as `advanced` with caveats — prevents users relying on undocumented internals that may change without notice — Users treat docs as a contract; presenting unsupported behavior as recommended creates breakage when internals shift. Prefer omission over warnings, and if an unsupported pattern must be mentioned, label it advanced with caveats and ensure the description matches the implementation.
<!-- rule:36 -->
- Use canonical `https://` URLs in docs, code examples, and templates — avoid redirects, URL shorteners, and tracking hashes; stable links don't rot or trigger mixed-content warnings. — Canonical `https://` links stay valid longer and avoid security warnings from redirects/tracking params. Single-source version-dependent URLs (via resolver/constant) so version bumps don't leave stale hardcoded links scattered across the repo. When updating one hardcoded URL, update all related occurrences in the same change.
<!-- rule:775 -->
- Describe API members in user-facing docs (`docs/*.md`, `docs/reference/**.rst`) and docstrings by how users access them, not by internals — docs stay correct when implementation changes. Call it a property/attribute when used without `()`, describe return shape/exclusions instead of restating the name, omit details like caching, and disambiguate design-time vs runtime terms. — This convention spans many unrelated files — `wagtail/admin/userbar.py`, `wagtail/models/__init__.py`, `wagtail/core/blocks/stream_block.py`, and the reference docs — so it belongs as a global AGENTS.md rule rather than a directory-scoped one.
<!-- rule:139 -->
- Use descriptive inline links in `docs/**/*.md`, `README.md`, and PR templates (`[Wagtail docs](https://docs.wagtail.org)`), not reference-style defs or empty `[text]()` — ref definitions drift out of sync and empty targets render as broken links — Reference-style link definitions and empty targets (`[text]()`) silently break when surrounding text is edited, and backticked URLs look like code but aren't clickable. Inline links with descriptive text keep docs scannable and links resilient across `docs/`, README, release notes, and PR templates.
  - Use `<https://...>` autolinks for standalone URLs instead of backticks — backticks make the URL non-clickable unless it's intentionally a literal code value
  - Bare URLs are fine only when the URL is itself the link label — Markdown auto-linkifies them

<!-- rule:2098 -->

Conflating it with "supported" (a project goal) makes people trust a QA signal that doesn't exist.
