# Configuration & Build Tooling

> Configuring tools and builds: exact section names, Black/tox setup, pyproject.toml options, validator settings shape, app-registry ordering, Dockerfile volume conventions, and cache-control/release build choices.

**When to check**: When editing config files (pyproject.toml, tox, ini), settings, Dockerfiles, or release build commands.

## Rules

<!-- rule:1927 -->
- Match `setup.cfg`/`pyproject.toml`/ini section names exactly to what the consuming tool expects — a typo makes the section silently ignored, so the setting never takes effect and the failure only surfaces later. — Tooling reads configuration by exact section name; a misspelled header is dropped without warning, leaving the option unapplied and producing confusing downstream errors.
<!-- rule:816 -->
- Run `black --check .` from repo root in tox; exclude files via `[tool.black] extend-exclude` in `pyproject.toml` — Black's `.` scans every Python file (package, tests, `setup.py`, scripts, docs) and honors `.gitignore`; narrowing target paths silently drops files from checking, while `extend-exclude` keeps intentional exclusions (e.g. invalid-syntax test fixtures) explicit and centralized.
<!-- rule:1910 -->
- In config middleware, resolve per-view values from the view function/decorated callable first and use `settings`/middleware defaults only as fallback — reversed order lets defaults shadow per-view overrides. Drop `view_class`/class-attribute compat branches once function-level attributes are the norm; stale branches silently outrank the new source. — The middleware pattern in files like `django/contrib/auth/middleware.py` must let explicit per-view/decorator configuration win over global defaults, otherwise site-wide settings quietly override intentional view-level choices. Keeping `view_class`/class-attribute compatibility branches after migrating to function/decorator attributes causes the old class lookup to shadow or double-resolve the new source, producing hard-to-trace config bugs.
<!-- rule:3540 -->
- Make every runtime path derived from `[tool.django]` in `pyproject.toml` configurable in that same section; default to the `pyproject.toml` parent directory. — Hardcoding paths derived from `[tool.django]` forces users to edit source or find workarounds, while anchoring defaults to the `pyproject.toml` parent directory prevents checkout- and install-dependent behavior from silently breaking `sys.path` and other runtime paths.
    Hardcoding paths like `sys.path` entries forces users to edit source or override by other means, and defaults anchored to `pyproject.toml` keep behavior predictable across checkouts and installs.
<!-- rule:482 -->
- In `django/db/backends/oracle/creation.py`, grant only the privileges listed in Django's Oracle notes (e.g. `SELECT ON v$parameter`) — never aggregate roles like `SELECT_CATALOG_ROLE`; update the notes alongside any new grant so the documented setup stays the source of truth for what the test user needs — Broad catalog roles grant privileges the test suite never exercises, so the test user drifts from the documented minimum and hides which grants are actually required. Keeping the grants in `creation.py` and the Oracle notes in sync makes the documented setup reproducible.
<!-- rule:3878 -->
- Use first-match semantics for ordered handler lists (e.g., Django logging handlers) and don't add system checks for multiple matches — the defined order is the deterministic selection contract, so checking for duplicates would contradict it — The list order is the API for picking which handler applies; treating the last entry (or hard-failing on multiple matches) changes behavior that callers rely on and adds a check the ordered-list design already makes unnecessary.
<!-- rule:5554 -->
- Shape pluggable-validator settings like `AUTH_PASSWORD_VALIDATORS` — a plain list of dicts with `NAME` and optional `OPTIONS`, not custom containers or validator instances — Users and third-party tools already parse `AUTH_PASSWORD_VALIDATORS` by that shape; matching it keeps validator collections introspectable, overridable per-deployment, and consistent across settings.
<!-- rule:1312 -->
- Build namespaces from `apps.get_models()` in default registry order, never `reversed()` — earlier `INSTALLED_APPS` entries must win for duplicate model names, matching Django's own resolution order. — In `django/core/management/commands/shell.py` and similar namespace builders, reversing the model iterator lets later-registered apps shadow models from earlier apps, producing different bindings than Django's app registry or `models` module would give — breaking user expectations for which app
<!-- rule:1931 -->
- For release builds, use `python -m build` without `--wheel` or `--sdist` flags so the wheel is built from the sdist, verifying sdist-to-wheel buildability. — Without `--sdist`/`--wheel`, `build` produces the sdist first and then builds the wheel from it, so release verification actually exercises the sdist→wheel path users hit; building the wheel directly from source skips that. Keep `extras/Makefile` and `docs/internals/howto-release-django.txt` in sync so documented release steps match the real invocation.
<!-- rule:2604 -->
- When a response embeds a per-request CSP nonce in a header, set `Cache-Control: private` (e.g. via `patch_cache_control(response, private=True)`) rather than `no_store`, so shared/public caches cannot serve a stale nonce to other clients while private client caching remains allowed. — For when a response embeds a per-request CSP nonce, use `Cache-Control: private` — `no_store` blocks legitimate private caching, and weaker directives let shared caches replay one client's nonce to another.
<!-- rule:5002 -->
- Don't `COPY` app source into paths a runtime volume mount will overlay — the mount hides those files, so they bloat the image and mislead readers about what actually runs. — The rule matters because COPY into a volume-mounted path is wasted and confusing — the mount shadows the copied files, so what runs differs from what's in the image. An unintended VOLUME breaks local/test workflows by creating anonymous volumes that keep old data between container recreations.
  - Don't add `VOLUME` just to enable bind mounts — `docker-compose` and `docker run -v` mount without it, and a stray `VOLUME` spawns anonymous volumes that retain stale data across container recreations.
  - Use `VOLUME` only as deliberate image metadata documenting expected mount points, and keep that convention consistent across Dockerfiles.
<!-- rule:5312 -->
- Pass admin widget lookup/config params as separate `data-*` attributes (append them in the client-side query function), not concatenated into `get_url()` URLs like `data-ajax--url`; assert those attributes in tests — Keeps `django/contrib/admin/widgets.py` widget options decoupled from URL construction, so `tests/admin_widgets/test_autocomplete_widget.py` can verify each option independently.
<!-- rule:3297 -->
- Quote variable-built paths passed to commands in `Makefile` recipes and `.bat` files — unquoted paths get mangled by spaces, glob expansion, and word splitting. Quote only the path args that need protection (not every variable reference); in batch files, avoid `tokens=*` when parsing paths. — Variable expansion in shell recipes and batch files is word-split before the command sees it, so paths with spaces or glob characters silently resolve to the wrong file — or several files. Blanket-quoting every variable reference obscures intent and can break non-path args, and `tokens=*` in `for /f` collapses path fields incorrectly in `.bat` parsing.
