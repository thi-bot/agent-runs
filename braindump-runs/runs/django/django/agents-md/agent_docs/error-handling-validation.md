# Error Handling and Input Validation

> Rules for raising, catching, and reporting errors; validating user input and collection data; and failing safely without masking failures.

**When to check**: When adding or changing error handling, validation logic, exception paths, or failure responses.

## Rules

<!-- rule:2183 -->
- Keep backend `check()` scoped to `self.engine` and its own options (e.g. `libraries`) — no global `settings.TEMPLATES` scan; it's an instance method, so global scans duplicate system checks and break per-engine isolation — Backend `check()` methods live on the backend class itself (django/template/backends/), so they can only see their own config; moving template-wide validation there duplicates work that belongs in django/core/checks/. Conversely, checks that live under django/core/checks/ (like security/CSP) must handle every configured backend, or non-Django engines such as Jinja and django-rusty-templates go unvalidated.
  - Make cross-cutting checks (e.g. security/CSP) iterate all `settings.TEMPLATES` backends — hard-coding `django.template.backends.django.DjangoTemplates` silently skips Jinja and django-rusty-templates
<!-- rule:3652 -->
- Raise decorator errors as `<decorator>() requires ...`; for `@decorator` misuse, say it must be called and show `@decorator()` vs `@decorator` — missing parens is otherwise cryptic to debug — The parenthesized decorator name matches how users must call it, and the correct/incorrect usage comparison tells them the exact fix. Users who write `@decorator` without parens get an obscure error and often don't realize the decorator was never invoked; naming the missing call and contrasting `@decorator()` with `@decorator` makes the repair obvious.
<!-- rule:4449 -->
- Null-check `querySelector`/`querySelectorAll` results before calling methods on them — both return `null` when nothing matches, so unguarded calls throw `TypeError` — DOM lookups return `null` rather than throwing, so any method call on an unverified result is a latent `TypeError`. Conversely, in scripts whose loading is already constrained by the template to a page where the element is present, an existence check adds noise and obscures the invariant; the guard belongs at the load boundary, not inside the script.
  - Skip null guards inside scripts that are only loaded in contexts where the target elements are guaranteed to exist — dead guards hide the load-path invariant that makes the script safe
<!-- rule:4079 -->
- In Django multi-field system checks (e.g., `ForeignObject`), restrict errors to definitively broken multi-column forms — keep valid single-column usage working. Cover both variants in `tests/invalid_models_tests/test_models.py` and document supported combinations in `docs/releases/6.0.txt`. — Over-eager checks in `django/db/models/fields/related.py` reject valid single-column usage that previously worked, and without tests/docs covering both cases the supported matrix becomes unclear — causing regressions and user confusion.
<!-- rule:5638 -->
- Resolve external CLI paths with `shutil.which` before `subprocess.run` — fail clearly or fall back rather than crashing on missing tools — Optional tools (database binaries, `psql`, `sqlplus`) aren't always on PATH or installed; using an unresolved name in `subprocess.run` raises an opaque `FileNotFoundError` or silently invokes the wrong binary, so resolving first lets tests and setup (e.g. `django/db/backends/oracle/creation.py`, `django/core/management/utils.py`) report a clear, actionable error or skip cleanly.
<!-- rule:6004 -->
- Filter sentinel values (e.g. `None` for unset primary keys) at the call site before invoking shared duplicate-detection helpers, and check missing-sentinel errors before duplicate errors — keeps the helper reusable and prevents missing-data errors from being masked by duplicate detection — Shared duplicate-detection helpers should stay generic; pushing sentinel filtering to call sites avoids baking collection-specific defaults into a reusable utility. Ordering sentinel checks first ensures a missing primary key (`None`) surfaces as a missing-data error rather than a confusing duplicate error.
<!-- rule:5011 -->
- Route invalid or missing request input through the view's error-display path (`validlink`/`invalid` flag, validation message, correct HTTP status), not a raised exception — unhandled raises surface as 500s instead of user-facing feedback. — In `django/contrib/admin/views/main.py` and `django/contrib/auth/views.py`, bad user input is expected and recoverable, so letting an exception propagate turns a routine validation failure into an unhandled server error.
<!-- rule:568 -->
- **Guard pickled attribute access with `getattr(..., default)` and persist stable values instead of re-deriving from mutable config (e.g. the current `URLconf`).** Pickles written by older code lack newly added attributes, and any mutable config at unpickle time may differ from when the object was saved (see `query.py`, `urls/resolvers.py`) — re-deriving silently corrupts restored state instead of raising. — Pickled objects survive code changes and cache boundaries, so an attribute added today is absent in yesterday's pickles; defaults keep deserialization working, and storing stable data (rather than reading the live `URLconf` or similar) ensures the restored object reflects its original value, not whatever config happens to be active now.
<!-- rule:654 -->
- Catch the narrowest Unicode exception the guarded code can raise — use `UnicodeDecodeError`/`UnicodeEncodeError` for a single operation, base `UnicodeError` only when both decoding and encoding can fail — and let it propagate when the caller should see it — swallowing or lossy `replace` handlers hide real IDNA/encoding bugs; in particular, `punycode()` in `django/utils/encoding.py` must not catch `UnicodeError`. — Matching the caught exception to the actual failure mode keeps unexpected Unicode/IDNA errors visible instead of silently corrupting output. Blanket `UnicodeError` catches and lossy handlers in helpers like `punycode()` mask bugs that should surface to callers.
<!-- rule:2292 -->
- Don't swallow or fake framework/object init failures — let the original exception surface so callers (e.g. in `core/management`, `db/models/fields/composite`, `db/migrations/state`) see the real failure instead of a misleading success. — Covers the global invariant that initialization failures must remain observable and object state must match reality. Preventing swallowed exceptions stops downstream callers from operating on broken objects; the explicit validation catches the suppressed invariant; and consistent state flags prevent half-initialized objects from silently propagating through Django's management, model, and migration code.
  - When suppression is unavoidable (signal/ordering timing), add an explicit validation of the invariant the suppressed exception enforced — otherwise the bug is hidden.
  - If raising aborts init, set readiness/state flags explicitly (`usable`/`unusable`) instead of leaving a half-initialized object — callers can then rely on the flag rather than guessing.
