# wagtail/ Guidelines

## API Design

<!-- rule:2241 -->
- Parse host/port with Django's `split_domain_port(request.get_host())`, not manual splits — handles IPv6 brackets and edge cases — Roll `request.META['SERVER_PORT']` in when the port is absent from the host string, and default by scheme (443 for HTTPS, 80 for HTTP). Manual `rsplit(':')` breaks on bracketed IPv6 hosts and misclassifies default ports; Django's util already handles these cases so redirects and URL building stay correct.
<!-- rule:2749 -->
- Use lock helpers (`page.locked_by`, `page_perms.page_locked()`) for lock UI/state — `page.owner` and manual `get_lock()` misreport lock state, hiding or faking the indicator. — The rule specifies concrete Wagtail lock APIs (`page.locked_by`, `page_perms.page_locked()`) instead of the incorrect `page.owner`/`get_lock()` approaches, and captures four distinct behavioral requirements (helper choice, accessible state-specific messaging, cache invalidation on transitions, and indicator visibility independent of surrounding forms). Each clause carries its own rationale so the AI knows why it matters, not just what to do.
  - Render distinct, accessible titles for "locked by you" vs "locked by another" — generic text gives users no recovery path.
  - Update/clear cached lock state on transitions into/out of lock — avoids stale indicators after unlock.
  - Keep the lock indicator outside optional surrounding forms — it must render even when the form is conditionally hidden.
<!-- rule:2605 -->
- In `wagtail/search/backends/*`, subclass the canonical query classes in `wagtail/search/query.py` — don't reinvent backend-local duplicates or intermediate helper bases; a shared hierarchy is what lets normalizers/compilers stay in sync. — Keeps the query API uniform across backends and prevents divergent, drifting implementations.
<!-- rule:209 -->
- When copying a Wagtail page, copy only the source page's direct `view_restrictions` (e.g. `self.view_restrictions`), never ancestor-inherited ones b1 avoids leaking parent-only access rules to the new page. — Copying inherited restrictions silently clones ancestor-only access policies onto the new page; skipping the copy when the destination is already restricted preserves the parent's intent without overwriting it, and decoupling the logic from `to` keeps direct copies (where `to` is `None`) behaving correctly.
  Resolve the destination parent as `to` if provided, else `self.get_parent()`; skip copying source restrictions when that parent has any view restrictions (including inherited); don't gate the copy on whether `to` was passed.
<!-- rule:1649 -->
- Delegate coercion to the wrapped chooser's `to_python()` or use `TypedChoiceBlock`, not custom logic — one conversion path avoids divergence in `wagtail/blocks/field_block.py`. — Form-field coercion and JSON serialization happen at different stages, so string round-trips silently break non-string choice keys unless normalized in `to_python`; reuse of `TypedChoiceField`/wrapped chooser `to_python` keeps a single conversion path and consistent behavior across single- and multi-select blocks.
  - Use `TypedChoiceBlock` (wraps `TypedChoiceField(coerce=...)`) instead of overriding `to_python` on a plain `ChoiceField` — reuses validated Django machinery.
  - Normalize non-string choice keys in the block's `to_python` after deserialization — `TypedChoiceField(coerce=...)` only fires during validation, but JSON/StreamField round-trips values as strings.
  - Apply the same `to_python` normalization to `MultipleChoiceBlock` — multi-select must stay consistent with `ChoiceBlock` and chooser-wrapping blocks in `wagtail/images/blocks.py`.
<!-- rule:1171 -->
- Resolve menu hooks in `WagtailRegisterable.register_with_wagtail`, not `is_shown()` — decide hook selection at registration time based on `self.add_to_settings_menu`/`self.add_to_admin_menu`, set `menu_hook = None` when neither flag is set, and skip `hooks.register` entirely. Registering an item that `is_shown()` always filters adds dead hooks and wasted per-request overhead. — Config-driven menu decisions belong at registration time in the entrypoint, not deferred to `is_shown()` at render time. Selecting the hook (or `None`) upfront keeps the registered hook list truthful, avoids per-request filtering of items that can never show, and makes it obvious from `register_with_wagtail` whether the plugin participates in each menu. The same gating should apply to optional entrypoint initialization, so unused menu items don't trigger setup work.
<!-- rule:1651 -->
- Name API serialization methods `get_api_representation(self, value, context=None)` — `render_api` is not a recognized hook, so custom blocks would silently serialize as raw values. — Wagtail's API serializer looks this method up by name; wrong names break custom `StructBlock`/`ImageBlock` output.
<!-- rule:1525 -->
- Resolve requests to the handling page before checking redirects — page routing takes precedence, redirects are fallback-only so real pages aren't shadowed — AI assistants editing routing code in Wagtail need to know redirect lookup is a fallback, and that `RoutablePageMixin` helpers must return the serving page; reversing this shadows pages with redirects and breaks callers relying on the page object.
  - Applies to `RoutablePageMixin` helpers: return the handling page, not the internal route/subpage — callers expect the page that serves the response
  - See `wagtail/models/__init__.py` and `wagtail/api/v2/views.py` for existing behavior
<!-- rule:933 -->
- In `wagtail/contrib/search_promotions` templates, resolve picks through the recommendation relation (`searchpick.recommendation.page` for the target, pick/recommendation title for the heading) so both internal-page and external-link picks render from one code path — Combined into module-scoped bullets: preserves the `searchpick.recommendation.page` / `searchpick.page.title` references and the two distinct render paths (frontend vs. admin listing) that a single bullet would flatten, while stating the concrete failure mode (external picks dropped) as the why.
  - Admin pick listings must fall back to the external title when `searchpick.page` is `None` (render `searchpick.page.title` if set, otherwise the external title field) — otherwise external-only picks silently disappear from the editor's UI
<!-- rule:1800 -->
- In Wagtail query internals (`wagtail/query.py`), iterate selected queryset columns via `queryset.values_list(named=True)` and access rows as namedtuples (`row.field`, `row._fields`, iterate `row`) — not `queryset.values()` with dict-style `.keys()`/`.values()` — since namedtuple rows are cheaper to build and unpack than per-row dicts on hot iteration paths. — Preserves Wagtail-specific API contract (`values_list(named=True)`, namedtuple `_fields`) that AI assistants commonly miss, and states the perf/ergonomics reason (namedtuples avoid dict allocation) rather than just citing convention.
<!-- rule:3008 -->
- Instantiate `ModelAdmin` helpers (e.g. `helpers/url.py`, `options.py`) through their factory and configure them via `set_*` methods, not optional constructor args — default and overridden paths then share one implementation — Helper classes like those in `wagtail/contrib/modeladmin/helpers/url.py` and `options.py` are subclassed and overridden; adding optional constructor params fragments initialization across paths, while `set_*` setters (called from `__init__` for defaults and conditionally for overrides) keep one authoritative implementation.
  - Call each `set_*` only when a non-empty value is provided, and apply defaults in `__init__` by invoking the same setter — keeps a single code path so subclasses can't silently diverge
<!-- rule:2599 -->
- Return the created submission from Wagtail form-processing methods and pass it to the landing-page render hook as the explicit `form_submission` keyword arg — overrides and templates can then read submitted data directly instead of re-querying or relying on ambient state. — Scoped to `wagtail/wagtailforms` — spans form-processing methods and their callers, so both sides of the contract must agree on the return value and argument name.
<!-- rule:3017 -->
- In `wagtail/contrib/forms/models.py`, compose abstract page classes from capability mixins (`FormPageMixin`, `EmailFormMixin`) instead of embedding everything in one abstract page — keeps capabilities independently reusable (e.g. `AbstractEmailForm` inherits its email handling from `EmailFormMixin`) — Rule is imperative and concrete; rationale explains why mixin composition matters (reusability of discrete capabilities). All project-specific identifiers (`wagtail/contrib/forms/models.py`, `FormPageMixin`, `EmailFormMixin`, `AbstractEmailForm`) are preserved in backticks. Slightly long but the rationale justifies the length; could be trimmed to just the first clause if space is tight.
<!-- rule:2512 -->
- In `wagtail/contrib/modeladmin`, give every configurable `ModelAdmin` attribute a `get_<attribute>()` getter and call it from views — lets subclasses override behavior without patching views. If the value depends on the active request/user, take `request` as the getter's first positional arg and pass the live request. — Attribute-to-getter pattern is Wagtail's extension contract for ModelAdmin; subclasses override the getter (often request-aware) rather than monkeypatching views or duplicating config.
<!-- rule:3076 -->
- Keep public registration functions thin and timing-independent, delegating work to `_register_{x}_actual()` / `_register_{x}_immediate()` helpers called from both the public function and `register_deferred_snippets()` — a shared helper avoids `DEFER_REGISTRATION`-style flags that make behavior depend on call time. — The `wagtail/snippets/models.py` registration flow defers registrations until app loading completes. If the public function is re-invoked from `register_deferred_snippets()` (or gated on a global flag), registration behavior becomes timing-dependent and late `wagtail_hooks` calls silently do nothing, since nothing drains the queue after `ready()` runs.
  - In deferred-registration mode, have the public function detect calls made after `ready()` and register immediately — no later handler flushes items queued post-`ready()` (e.g. from `wagtail_hooks`).
<!-- rule:450 -->
- Pass `for_update=True` to `self.get_form_class()` when building forms for existing instances in snippet edit/update views — omitting it falls back to the create-time form class, dropping edit-only fields/validation. Audit analogous paths like `revisions_revert` in `wagtail/snippets/views/snippets.py` for the same flag. — The `for_update` flag selects the update-specific form class; without it, edit views silently instantiate the create-time form and lose update-only fields and validation.
<!-- rule:2451 -->
- Store form-field options in a single `self.field_options` dict in `FieldBlock` subclasses (not separate attrs) — one source of truth per field, easy to override. — Keeping options in `self.field_options` (e.g., `required`, `help_text`, `widget`) means subclasses and overrides patch one dict instead of tracking scattered attributes. Using `field_options.get('option')` when filling defaults handles absent keys and explicit `None` the same way, so subclasses can pass `None` to opt out without triggering `KeyError`.
  - In `field`, copy `self.field_options`, patch defaults via `field_options.get('option')`, then `forms.CharField(**field_options)` — `get` treats missing keys and explicit `None` uniformly and avoids `KeyError`.
<!-- rule:2846 -->
- Add adapters for stdlib types shared by Python and JS (e.g. dates) as built-ins in `wagtail/core/telepath.py`, not via external adapter modules loaded through `appconf` — keeps core telepath primitives available everywhere without app-specific registration. — Placed in wagtail/AGENTS.md so the rule is visible both when editing the base `wagtail/core/telepath.py` module and when tempted to add an adapter under `wagtail/admin` or elsewhere.
  - Before promoting a type to a core telepath primitive, confirm its Python and JS representations round-trip compatibly — an incompatible pair will leak lossy or surprising serialization into every consumer.
<!-- rule:2850 -->
- Add `created_at` to temporary/staging upload models — lets you identify and prune stale uploads (e.g. `wagtail/documents/models.py`) — Without a timestamp, orphaned or abandoned uploads can't be aged out, leading to unbounded storage growth and stuck staging records.
<!-- rule:1647 -->
- Put shared `BoundBlock` render context logic (e.g. injecting `id`) in base `BoundBlock.render_as_block`, not in each subclass's `render` override. — Keeps `render` and `render_as_block` consistent across all `BoundBlock` subclasses (`wagtail/blocks/list_block.py`, `wagtail/blocks/stream_block.py`) without duplicating the override in every block.
<!-- rule:2649 -->
- Keep `EmbedValue.__init__` side-effect-free — no embed lookups, HTML fetching, or template rendering in constructors; expose `html` as a `cached_property` calling `get_embed(url)`/`embed_to_frontend_html(self.url)` (catch `EmbedException`), or resolve explicitly in the `{% embed %}` tag render or via `get_embed()` in `clean()`. — Cheap, side-effect-free constructors keep value objects safe to instantiate anywhere (serialization, comparisons, tests), and deferring lookups to first access avoids duplicate network calls and rendering work when the value is never consumed.
<!-- rule:2600 -->
- Keep multi-word splitting aligned between search query classes (`Term`, `PlainText`) and backend adapters — validate each parser (e.g. `plainto_tsquery`) before adopting Python-side tokenization, so tests match real query semantics — Query classes and backend parsers can interpret the same input differently; a shared Python-side split that ignores backend behavior makes tests pass while production queries silently diverge.

## Testing

<!-- rule:1474 -->
- Scope search backend tests to real query semantics in `wagtail/search/tests/test_backends.py`: use prefix terms for autocomplete, expect `Term` to match one indexed term only, include phrase queries, and cover both `PlainText` and `RichText` fields — assertions that ignore a query class's actual semantics mask real backend divergences. — Each search backend (e.g. Postgres, SQLite, Elasticsearch) implements word-prefix matching, term matching, and phrase handling differently; `PlainText` and `RichText` also index differently. Asserting against a class's imagined behavior rather than its real semantics lets regressions and cross-backend inconsistencies pass silently.
<!-- rule:1143 -->
- Drive admin view/form tests through a real POST to the admin edit view and assert the resulting state change (e.g., object actually removed) — direct model method calls or plain `ModelForm` validation skip the view/formset wiring these tests exist to protect. Include a success-path case alongside blocked/failure cases, since a fix that only rejects input can still be broken on the happy path. For Wagtail inline panel/formset regression tests, assert the formset behavior on the edit response. Avoid `fields = '__all__'` on models with no own fields — the resulting empty form can never be invalid, so it can't exercise the fix. — Testing the admin view flow (via real POST) is what actually exercises inline panel/formset fixes; bypassing it (direct model calls, plain ModelForm, empty fields) leaves the regression untested.

## Code Style

<!-- rule:1298 -->
- Derive permission labels from `name` or `action.replace('_', ' ')` (e.g. `f"Can {action.replace('_', ' ')}"`) — never parse `codename` into labels, since codenames are lossy machine identifiers — Codenames exist for programmatic matching/classification; splitting them with whitespace/underscore tricks like `.rsplit(maxsplit=1)` loses information and couples display text to internal identifiers. Using `name` or a predictable `action`-derived format keeps labels accurate and translatable (`{% trans %}`, with `gettext_noop` for stored constants so translation happens in the template).
<!-- rule:1682 -->
- Pass Django booleans into JS as unquoted literals — `{{ value|yesno:'true,false' }}` or `{% if value %}true{% else %}false{% endif %}`; the quoted `"false"` is truthy in JS — Template-interpolated context values default to strings, and in JavaScript the string `"false"` evaluates as truthy — silently inverting logic in any `if (config.flag)` check. Emitting real `true`/`false` literals keeps the JS-side value matching the Python-side boolean, so feature flags and settings passed from Wagtail's admin templates behave the same in both languages. Applies to any context value crossing the Django-template → JavaScript boundary, e.g. in object literals or `data-*` payloads.
<!-- rule:2265 -->
- Reuse the message button component/style for action buttons in admin messages, placing them adjacent to the main message and before nested `ul.errorlist` — keeps button styling consistent across `wagtail/admin/templates/wagtailadmin/base.html` and `wagtail/wagtailadmin/messages.py` and avoids buttons nested inside error markup. — Placing action buttons after `ul.errorlist` nests them inside error markup, which breaks layout and styling; reusing the existing message button component keeps the admin message UI visually consistent across template and Python message code.
<!-- rule:2058 -->
- Aggregate Wagtail hook results with explicit `if url := hook_fn(user, size):` checks and `extend`/`sort`/`return` — beats opaque `itertools.chain.from_iterable` flattening, keeping per-hook truthiness and ordering visible to readers — Explicit assignment expressions and list operations make per-hook truthiness and result ordering obvious during review and debugging; `itertools.chain.from_iterable` hides both.
<!-- rule:3024 -->
- In `wagtail/contrib/forms` submission listing templates (`index_submissions.html`, `bulk_actions/list_form_submissions.html`), derive table columns/headers from the form's `fields`/submission data — only hard-code fixed metadata like submission date. Wrap the table in a horizontally scrollable container. — Forms are user-defined, so hard-coded columns break for any non-default field set and render wide tables unusable.

## Error Handling

<!-- rule:2544 -->
- Guard `is_active`/`is_superuser` on the acting user in self-edit forms and bulk actions — prevents users from locking themselves out or escalating privileges — Users editing their own profile or applying bulk user actions can accidentally deactivate themselves (`is_active=False`) or strip/alter protected flags like `is_superuser`. Silently allow it and you get admin lockouts or privilege changes that are hard to audit or reverse. Pair the guard with negative tests asserting those flags are unchanged after a self-edit or bulk operation so the protection can't regress unnoticed.
<!-- rule:2450 -->
- In `wagtail/embeds`, call `get_embed`/`embed_to_editor_html` directly and catch `EmbedException` locally — `ignore_errors=True` and empty-string existence checks silently hide provider failures from callers. — Applies to embeds code across files like `rich_text.py` and `blocks.py`; local handling keeps error semantics explicit rather than swallowed.
<!-- rule:2447 -->
- Include backend name, config key (e.g. `DISTRIBUTION_ID`), and affected URL(s) in cache purge failure logs — operators can't identify which service and URL failed otherwise — Logging only a generic error leaves operators unable to trace which provider or URL failed during a purge, making incident triage much slower.
<!-- rule:2687 -->
- Use semantically correct exceptions in `wagtail/templatetags/` — `ImproperlyConfigured` for config errors (e.g., unresolvable named URL patterns), `ValueError` for bad arguments (e.g., `pageurl`/`fullpageurl` receiving non-`Page` objects) — keep `TemplateSyntaxError` out of runtime paths, since callers and tests need to distinguish misconfiguration from syntax issues, and add tests asserting the exception on invalid input. — Distinguishing `ImproperlyConfigured` and `ValueError` from `TemplateSyntaxError` lets integrators catch the right class and keeps error semantics consistent across `wagtail/templatetags/` and `wagtail/images/templatetags/`; tests asserting the raised exception lock in that contract.
<!-- rule:2648 -->
- Validate embed URLs eagerly at save time in `wagtail/embeds/blocks.py`, not via lazy/cached properties or `validators=[URLValidator()]` on `wagtail/embeds/models.py` fields — field-level validation never runs in the embed workflow, so such validators are dead weight and invalid URLs go unreported to users (mirror how rich text embeds surface errors). — See rule_text above — the rationale is inline.

## Naming

<!-- rule:2840 -->
- Qualify oEmbed-specific exceptions in `wagtail/embeds/finders/` with `OEmbed` in the class name (e.g. `AccessDenied{Provider}OEmbedException`) — callers can then distinguish them from generic provider errors when catching. — An unqualified name like `AccessDeniedException` forces callers to guess which failure mode they're handling and risks collision with non-oEmbed exceptions raised by the same provider.
<!-- rule:2545 -->
- Use stable, machine-readable identifiers for form field names and field types in `wagtail/contrib/forms` and `wagtail/wagtailforms`, and expose idents like `clean_name` in API field definitions alongside human-readable labels — decoupling idents from display labels keeps API clients and stored submissions working when labels are edited. — Machine-readable identifiers allow programmatic consumption while stable naming prevents breaking form submissions and API consumers. Including both `clean_name` (ident) and label in field definitions means localization or copy changes don't invalidate saved data or downstream integrations.
<!-- rule:2476 -->
- Tag auto-generated numeric slug suffixes in `wagtail/wagtailcore/models.py`: increment `-N` in place (`-5` → `-6`) instead of appending (`-5-2`) — preserves user-authored numbers and stops later uniqueness passes from double-suffixing. — Slugs like `some-slug-5` may have a user-authored `5` or an auto-appended one; without tracking which, collision handling either clobbers user intent or stacks suffixes (`some-slug-5-2`).
<!-- rule:3016 -->
- Call a form submission an 'entry', not a 'document', in `wagtail/contrib/forms` — matches the `FormSubmission` model and keeps the submissions listing terminology consistent. — The underlying model is `FormSubmission` and the existing submissions listing already uses 'entry' — diverging names (e.g. 'document', generic `Form`) create two vocabularies for one concept and make it easy to wire up the wrong class.
  - Name classes, files, and labels for submission-handling functionality `FormSubmission`, never `Form` — avoids collisions with unrelated `Form` concepts in the same module.

## Documentation

<!-- rule:1395 -->
- Give each styleguide row/example a distinct markup variant — near-duplicates waste readers' time and the styleguide serves as copyable reference docs — The Wagtail styleguide in `wagtail/contrib/styleguide/templates` is copyable reference documentation, so its own markup (`valid`, `unique` `id`s, etc.) sets the example developers will follow — near-identical rows dilute the value of each example.
<!-- rule:2782 -->
- When a field lacks a configurable boost and `get_weight(field.boost)` can't be used, pass a hard-coded weight with an inline comment explaining the bypass, the missing boost, and the safety assumption. — Hard-coded weights silently drift from the boost-based weights around them; documenting why `get_weight` was bypassed and what makes the literal safe keeps future readers from treating it as an oversight or breaking the assumption during refactors.
<!-- rule:2774 -->
- In `wagtail/project_template/` docs and comments, say `your hosting platform` (second person), not `the hosting platform` — the template is copied into each user's own project, so second person correctly frames infrastructure they own. — The template's docs ship inside every generated project; 'the hosting platform' implies one shared platform, which misleads users into thinking Wagtail ships or dictates infra, while 'your hosting platform' correctly signals user-owned deployment.

## General

<!-- rule:886 -->
- In Django settings packages, put env overrides in `settings/local.py` imported *after* overridable settings, and override individual nested keys instead of reassigning whole dicts; if a dict setting must be replaced (e.g. `DATABASES`, `REST_FRAMEWORK`), define *every* required key — Django does not merge dict settings with defaults, so partial dicts silently drop configuration. — Placing overrides after the base settings ensures they win, and nested-key edits preserve defaults that Django would otherwise discard when a dictionary is wholesale replaced — a common source of subtle prod-only misconfiguration across `base.py`, `production.py`, and `local.py`.

## File-Specific Rules

### `wagtail/query.py`

<!-- rule:658 -->
- Define aliases like `private = not_public` in `wagtail/query.py` by direct assignment or delegation — never duplicate the canonical method's logic. Keep the original method name intact and add docs/tests — duplicating drifts out of sync and breaks callers relying on the original API. — Duplicated logic silently diverges when the canonical method changes, and renaming/removing the original breaks backward compatibility for `QuerySet` callers. Assignment-based aliases keep behavior and docs in lockstep.
<!-- rule:1891 -->
- In `wagtail/query.py` QuerySet proxy methods, run cheap argument validation and early-return guards before calling `self._chain()` — skips the clone cost on invalid or no-op calls — Placing guards before `self._chain()` avoids paying for an unused clone when the call is invalid or returns early anyway.

### `wagtail/whitelist.py`

<!-- rule:462 -->
- Keep `BEAUTIFUL_SOUP_FEATURES` in `wagtail/whitelist.py` at `html.parser` — `lxml`/`html5lib` alter serialization output that downstream Wagtail code depends on — Configure BeautifulSoup via the module-level `BEAUTIFUL_SOUP_FEATURES` constant in `wagtail/whitelist.py`, defaulting to `html.parser` — not `lxml` or `html5lib` — because those parsers change the serialized pseudo-HTML that Wagtail's consumers rely on. Explicitly detect optional parsers such as `lxml` in the `wagtail/compat.py` feature list rather than suppressing BeautifulSoup warnings, so missing dependencies surface instead of silently degrading. Any change to this parser configuration must come with tests asserting the serialized output still meets Wagtail's requirements, including self-closing tags and entity handling.
  - Detect optional parsers like `lxml` in the `wagtail/compat.py` feature list instead of suppressing BeautifulSoup warnings — silent fallback masks missing deps
  - Before changing parser config, add tests covering self-closing tags and entity handling — those serialization quirks are what breaks callers
