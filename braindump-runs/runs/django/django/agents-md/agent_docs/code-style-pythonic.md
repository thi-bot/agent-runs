# Pythonic Code Style

> Prefer built-ins and direct constructs, avoid shadowing builtins, use set operations, handle accumulators in control flow, and avoid unnecessary compatibility shims.

**When to check**: When writing or refactoring Python implementation code for readability and idiomatic style.

## Rules

<!-- rule:5024 -->
- Handle fixed `fields` sets explicitly instead of looping: declare heterogeneous form fields directly and access `fields` mappings/keysets without intermediate variables or `.items()` iteration — matches the declarative style in `django/forms`, `django/contrib/admin`, and `django/db/migrations` and keeps field handling type-checkable — Django's form and migration internals expect explicit, declarative `fields` collections; looping and branching on type or wrapping access in intermediate variables obscures which fields exist and diverges from the surrounding code style.
<!-- rule:54 -->
- Use explicit `continue`/`else`/`return` for generator skips and early exits — helper `None` returns leak `None` to consumers and run code on skipped/invalid state (`django/core/serializers/python.py`, `django/template/base.py`) — Generator `yield` statements pass values straight to callers, so delegating a skip to a helper that returns `None` makes the generator emit `None` instead of nothing, and fallthrough after a skip/exception executes code that assumed valid state. Writing the branch explicitly inside the generator keeps the emitted sequence correct.
<!-- rule:5436 -->
- Use each database client's exact CLI syntax in `dbshell` — `-d` for PostgreSQL databases, sqlite3's single-dash `-help`; GNU-style `--help` and ambiguous positional args silently misfire — Each backend's client (psql, sqlite3, etc.) parses argv differently: PostgreSQL requires `-d` to disambiguate the database from positional args, and sqlite3 only recognizes single-dash `-help`, so GNU-style flags and positional arguments silently produce the wrong target or no-op. Documenting a real SQL-command example alongside `dbshell -- <args>` keeps the user-facing reference in `docs/ref/django-admin.txt` copy-pasteable and consistent with what `tests/dbshell/` exercises.
  - Include a concrete SQL example in the `dbshell -- <args>` docs (`docs/ref/django-admin.txt`) — users copy-paste these verbatim
<!-- rule:3916 -->
- Defer cloning until the mutation path is actually reached; run cheap early-exit checks against the original object first. When an early return skips cloning, check every independently modifiable property, not just one — otherwise requested changes to the unchecked properties are silently dropped. — Cloning is expensive, so short-circuiting on the common no-op case avoids the cost. But the shortcut is only safe if it accounts for all fields that can differ; a single-property check makes changes to the other properties a silent no-op.
<!-- rule:1990 -->
- Prefer `string` module constants (e.g., `string.ascii_letters + string.digits`) over hardcoded character-set literals; define an explicit literal or use the project's compat shim only when the exact alphabet is semantically important or the constant is unavailable (e.g., Python 2-only `string.letters`). Typo-proofs alphabets and keeps Python 2/3 compat consistent across modules like `django/utils/crypto.py` and `django/middleware/csrf.py`. — Hardcoded character sets (like `'abcdefghijklmnopqrstuvwxyz'`) are prone to silent typos that weaken crypto/CSRF token entropy, and they diverge across modules. `string`-module constants also paper over Python 2/3 differences — except where an attribute is version-specific, in which case the compat shim or an explicit literal is the only portable option.
<!-- rule:1159 -->
- Resolve the effective source/default (including `None`) before post-processing; don't duplicate `getattr`/`callable` fallbacks or mutate the selected source. — Collecting fallback resolution in one place makes override behavior consistent, and never mutating the source keeps caller-owned values (like `None` defaults) safe — post-processing should copy first, then apply source-specific metadata.
<!-- rule:2140 -->
- Extend existing field-type handling in schema operations instead of adding standalone special-case blocks — keeps `django/db/backends/*/schema.py` (and `django/contrib/postgres/fields/`) paths consistent across backends; isolate only when the generic path genuinely can't work, and document why. — Special-case blocks accumulate in `DatabaseSchemaEditor` subclasses and `django/contrib/postgres/fields/` registrations, causing backends to drift and new field types to be handled inconsistently. Reusing or relaxing the existing field-type/constraint logic keeps behavior uniform across schema alteration backends; when a generic path truly cannot cover a case, the documented reason prevents future readers from collapsing the block back into the shared path and reintroducing the bug it worked around.
<!-- rule:5445 -->
- Process `__init__` params in signature order and follow base-class setup for inherited params — keeps subclass behavior consistent with the base class — Signature order matches what readers expect from the declaration, and reusing the base class's normalization for corresponding params (e.g. in `django/contrib/postgres/search.py`, `django/forms/widgets.py`) prevents subclasses from silently diverging in how they interpret the same input.
<!-- rule:4180 -->
- Don't shadow or alias built-ins (no `_list = list`) — they need no import; alias only if a benchmark shows a real gain. — Shadowing built-ins (including aliasing like `_list = list` as a micro-optimization, or importing the `builtins` module to work around a name clash) makes call sites ambiguous and silently breaks code in the same scope that expects the real built-in. The common case in this repo is a module that intentionally exposes a public callable under a built-in name such as `format`: defining the implementation under a non-shadowing name and binding the public name at the end of the module keeps the built-in available throughout the module while still exporting the intended API.
  - To expose a callable under a built-in name (e.g. `format`), define it under a non-shadowing name and assign the public name at module end — shadowing at definition time hides the built-in for the whole module.
<!-- rule:5027 -->
- Use `functools.reduce` only for true folds — prefer `getattr`, indexing, or an explicit loop when clearer; `reduce` obscures simple access but reads well for merges like `reduce(self.merge, filter(None, self._js_lists))` (`django/forms/widgets.py`, `django/views/generic/dates.py`) — `reduce` hides intent for simple attribute or index access, forcing readers to reconstruct the loop mentally. Reserving it for genuine binary merges keeps call sites obvious, while still allowing idiomatic folds where no clearer built-in exists.
<!-- rule:5483 -->
- Initialize accumulators from the first element; handle terminal cases in `break`/`return` branches — in-loop emptiness checks and post-loop counters give wrong results on empty or early-exit loops — Separator-delimited builders and suffix lists are the common case: initializing from the first element avoids a leading/trailing delimiter, appending suffixes in the `break` branch keeps partial results off the shared accumulator, and returning replacement results immediately avoids short-circuit values leaking into downstream consumers. Emptiness checks and post-loop counters assume the loop always runs to completion, which breaks on empty inputs and early exits.
<!-- rule:5823 -->
- Merge field/attribute-name collections (e.g. `ignore`, `readonly_fields`, `flattened_fieldsets`) with `set.union` and deduplicate instead of concatenating lists or manually iterating — chained list merges silently emit duplicate names — These rules govern how Django code merges collections of field or attribute names across the DB backend (`django/db/backends/base/schema.py`) and admin helper (`django/contrib/admin/helpers.py`) layers. Using `set.union` prevents duplicate entries that arise from naive list concatenation. Locally adapting sequence-typed APIs avoids forcing a type change into a public interface, keeping callers that depend on `tuple`/`list` behavior working unchanged.
  - When an existing API exposes field names as a `tuple`/`list`, adapt locally (e.g. `ignore.union(non_db_attrs)`) rather than changing the public type — preserves backward compatibility for callers relying on the exposed sequence
<!-- rule:4919 -->
- Define repeated key→value mappings once as a named `dict`; reuse at every call site — inline copies drift out of sync when one is edited and the other isn't — Both a membership test and a value lookup over the same keys are the same fact expressed twice; a named `dict` keeps them consistent. Likewise a display-name map built from the same keys is redundant — deriving from the key (via `replace('_', '-')` or similar) means one edit updates every consumer, instead of silently diverging copies.
  - Derive trivially computable values at use time (e.g. `name.replace('_', '-')`) instead of storing a parallel mapping — derivable entries go stale when the source data changes
