# Testing Patterns & Assertions

> Rules for structuring tests, choosing assertions, managing fixtures and cleanup, testing hooks/flags, and writing regression tests in the project's framework conventions.

**When to check**: When writing, modifying, or reviewing tests.

## Rules

<!-- rule:1847 -->
- Write tests as `unittest`/`django.test.TestCase` classes with `self.assert*` methods — pytest-style functions and new parametrization frameworks won't run in Wagtail's CI. — Wagtail's test discovery, `runtests.py`, and `tox` environments are built around unittest-style classes; introducing pytest idioms silently skips or breaks tests across `wagtail/images/tests`, `wagtail/tests`, `wagtail/contrib/settings/tests`, and `wagtail/api/v2/tests`. Keep the existing `TestCase` subclass pattern instead of adding a new framework or parametrization style.
<!-- rule:1553 -->
- Scope context-manager assertions to only the raising/emitting call — do setup (construction, etc.) before the `with`; statements after a raising call inside the block never execute, and setup that also warns makes `assertWarnsMessage` unreliable. — Concise, actionable bullets for AGENTS.md with project-specific identifiers preserved (`assertRaisesMessage`, `assertWarnsMessage`, `warnings.catch_warnings(record=True)`, `render()`), each carrying its why (dead code, false positives, unreliable warning capture, convention consistency).
  - Put post-call assertions after the `with assertRaises` block, not inside it — code following the raising call inside the block is dead and never runs.
  - Assert the specific exception type and message with `self.assertRaisesMessage(ExcType, expected_message)` for exceptions the project raises — bare `assertRaises(Exception)` passes on unintended errors.
  - Use `self.assertWarnsMessage(WarningClass, expected_message)` instead of `warnings.catch_warnings(record=True)` — matches project convention and drops manual capture bookkeeping; scope it to just the emitting call (e.g. `render()`), not object instantiation.
<!-- rule:1563 -->
- **Clean up global state in `afterEach`/`finally`** — reset document listeners, shortcut managers, collected events, signal handlers, and global hooks even when a test fails. Register and reset collected events in `beforeEach`; reset global listeners in `afterEach` to prevent cross-test leakage (applies to Stimulus controller tests in `client/src/controllers` and admin tests in `wagtail/admin/tests`). — Cross-test leakage causes flaky, order-dependent tests that are hard to debug; `afterEach`/`finally` guarantees cleanup even on test failure.
<!-- rule:1017 -->
- Test every new public API option beyond the default: non-default values, omitted/fallback, `None`/disabled (assert skipped vs. still enforced), and boundary cases like the parameter passed more than once. — Defaults-only tests miss the branches that actually break — fallback paths, disabled checks, and duplicate-specification edge cases silently diverge from documented behavior.
<!-- rule:1532 -->
- Never commit `it.only`/`describe.only` or `it.skip`/`describe.skip` — they silently disable test suites in CI, letting regressions ship unnoticed. Fix the test, delete it, or (only for external-dependency blocks) add a `TODO` naming the exact unskip condition. — Focused tests (`it.only`/`describe.only`) hide every other test in the file, so CI reports green while most of the suite never runs. Skipped tests accumulate as silent coverage decay — an untracked skip looks identical to a passing test to anyone reading CI output. The exception is narrow: an external dependency outage, documented with a `TODO` stating when the skip lifts, so the work resurfaces instead of fossilizing.
<!-- rule:564 -->
- Copy-op tests: populate source, re-fetch the copy from DB, and assert the actual copied fields/relations (`draft_title`, `GenericRelation` objects omitted) — not just that copy didn't raise. — Copy actions commonly appear to succeed while silently carrying over excluded data or stale revision fields; asserting on the persisted re-fetched object catches these regressions that a no-error check misses.
<!-- rule:1098 -->
- Run and smoke-test affected code locally before committing. — This rule transforms a broad development practice into concrete, actionable bullets tailored to the Wagtail repository. It preserves the project-specific directories (`wagtail/admin`, `wagtail/images`, `wagtail/core`, `docs`) highlighted in the placement rationale and uses backticked identifiers for clarity. Each bullet leads with an imperative verb (Smoke-test, Verify, Confirm), includes the *why* (runtime issues are invisible to static review), and stays concise enough to live in the root AGENTS.md as a globally applied guideline. The bullets are ordered from the general commit-time habit to the more specific rendered/interactive case, then to the concrete symbol/import check, matching the original rule's progression.
  - Smoke-test affected code before committing — runtime problems (missing imports, rendering bugs, event-handler typos) only surface when the code actually runs.
  - Verify rendered/interactive changes locally, not just via diff review — invalid event types and handler typos fail silently in static review.
  - Confirm every newly referenced symbol is imported and the module/entry point runs in a local dev environment before submitting changes across `wagtail/admin`, `wagtail/images`, `wagtail/core`, or `docs`.
<!-- rule:75 -->
- Test real production code, not copies — duplicated implementations drift and pass even when production breaks. Import existing classes (they already expose the needed internal state) and use plain built-in values; avoid test-only subclasses or helper classes unless the behavior under test requires them. If the implementation isn't importable, refactor it for exposure or test via a public API — never import future or nonexistent APIs. — Copied logic hides regressions and goes stale as production evolves; importing the real implementation keeps tests honest and reduces maintenance.
<!-- rule:843 -->
- Assert hard-coded literal expected values with exact assertions (e.g. `assertEqual`) — deriving them from production constants, the code under test, or helper logic makes tests tautological and unable to catch regressions; reserve `assertIn` for cases where any of several values is legitimately acceptable. — Two-tiered bullet: a global testing convention plus a nested sub-bullet for the Wagtail form/settings case. Each clause carries its own WHY (tautological tests, hidden mismatches) while preserving the specific API references (`assertEqual`, `assertIn`, `(value, label)` tuples, Wagtail form/settings tests) that make the rule actionable.
    - In Wagtail form/settings field-choice tests, assert the complete expected list of `(value, label)` tuples as literals — splitting value sets from label mappings or re-deriving values programmatically hides label/value mismatches.
<!-- rule:368 -->
- Test helper/utility functions across all supported inputs, documented edge cases (e.g., URL parts deliberately dropped/preserved, non-model values, typo-catching cases), and graceful handling of unsupported/missing input — untested branches in shared utilities silently propagate bugs to every caller. Reuse existing related test modules instead of adding new scaffolding — keeps fixtures and imports consolidated and avoids duplicate setup. — Helper/utility functions are shared across many call sites, so untested edge cases (URL handling, non-model values, missing input) can cause subtle breakage far from the change. Reusing existing test modules keeps fixtures and imports consolidated.
<!-- rule:34 -->
- Clear cached state that can leak across tests in `setUp`/`tearDown` (Django caches, class-level caches, `@cached_property`) — prevents order-dependent test failures — Test code spans many directories, so this belongs in the root AGENTS.md; leaked cache state causes flaky, order-dependent failures.
  - Reset `@cached_property` with `del`, wrapped in `try`/`except AttributeError` when access order varies — the attribute may not exist yet
  - Use known reset hooks, test helpers, or public APIs to clear class-level caches rather than mutating private internals — keeps tests resilient to refactors
<!-- rule:44 -->
- Match test docstrings/comments to that test's own assertion — never copy from a sibling test — Docstrings naming the wrong status code, settings flag, or unchanged state read as spec, so future readers and AI assistants trust them over the code and miss real regressions. Behaviour changes in `wagtail/**` Python tests and `client/src/controllers/*.test.js` must carry a renamed or rewritten docstring in the same commit.
<!-- rule:541 -->
- Use specific `unittest` assertions — `assertIsInstance(obj, Type)` over `assertTrue(isinstance(...))`, `assertIsNone`/`assertIsNotNone` over `assertEqual(x, None)`, `assertEqual(actual, expected)` over `assertTrue(actual == expected)`, and canonical `assertEqual` (not the deprecated `assertEquals`) — so failures print the real values instead of `False != True` — The rule governs how unittest-style assertions should be written across all test code, and the evidence shows application in test files spread across many distinct directories (wagtaildocs, contrib/redirects, snippets, admin, core, images, embeds, etc.). It is a general coding convention for an entire language/test framework, not a module-specific or single-directory rule, and it describes no relationship between specific files.
  - Pick `assertTrue`/`assertFalse` for truthiness but `assertIs(value, True)`/`assertIs(value, False)` when only the exact boolean will do — swapping these hides bugs like `1 == True` passing a strict `True` check
  - When asserting an object is passed through unchanged, compare to that exact object (`assertEqual`/`assertIs`), not just `assertIsInstance` — a type-only check passes even when the wrong instance is returned
<!-- rule:1130 -->
- Assert exact order where production code guarantees it; use `assertCountEqual`/`assert_unsorted_results` for unordered results — `set(...)` hides duplicate rows — Production code with explicit ordering should be verified byte-for-byte, but unordered querysets must use order-insensitive assertions that preserve duplicates; converting to `set(...)` silently masks duplicate results and regressions.
<!-- rule:154 -->
- Pass explicit `count=` (usually `count=1`) to `assertContains`/`assertTemplateUsed` and keep counts stable across unrelated edits — catches duplicate renders and unintended template inclusion. — Exact occurrence counts turn 'element shows up' into 'element shows up precisely once,' so regressions that duplicate or double-render a component (e.g. an extra `{% include %}` or repeated block) fail loudly instead of passing silently. Stable counts also prevent tests from breaking when the fixture grows for unrelated reasons.
<!-- rule:1142 -->
- Structure tests as Arrange-Act-Assert, with assertions between each phase — Assert the arranged state before acting, and add intermediate assertions after — otherwise a failing test can't distinguish a broken setup from a broken action under test.
<!-- rule:218 -->
- Keep inline HTML test fixtures minimal and well-formed: only the DOM needed, valid matched closing tags, two-space indent, short elements on one line, attributes on separate indented lines for larger fixtures — Whitespace and stray attributes leak into assertions — especially `assert_select`/exact-HTML comparisons — causing brittle or failing tests
<!-- rule:59 -->
- Toggle settings/feature flags in tests with Django's `override_settings` — class-level when shared across tests, method-level for one-offs. Patch the setting, not internal helpers, and cover both enabled and disabled paths when behavior branches — settings patches are restored automatically, avoiding cross-test leakage and keeping coverage honest. — `override_settings` auto-reverts after the test, so mutating module settings or patching helpers leaks state into other tests. Covering both branches catches features that silently break when the flag flips.
<!-- rule:1331 -->
- Pair every bug fix with a regression test — verify it **fails on the unfixed code** and passes once the fix is restored (revert the fix or run the test-only branch to check). — Targets the reported bug precisely and confirms the fix isn't masking legitimate behaviour.
    - Test the **specific broken behaviour**, not a broad or incidental operation — a passing broad test doesn't prove the bug is fixed.
    - Add a parallel **control test** expected to pass with and without the fix — catches over-broad fixes that suppress valid behaviour.
<!-- rule:703 -->
- In permission tests, model every distinct auth state (none, granted, elevated) with real users, groups, and object-level permissions — `admin`/`non-admin` proxies and mocked permission methods skip the actual permission logic. — Real objects catch regressions in the checks that actually run in production.
<!-- rule:35 -->
- When testing caching or cache invalidation, exercise the production request/view path and assert the observable caching effect: use query-count assertions such as `assertNumQueries` to verify cold-cache misses and warm-cache hits (repeated operation performs zero queries), and for invalidation assert downstream values that depend on the cleared cache rather than only that the cache was cleared. Do not simulate cache hits by assigning cache attributes directly. — ... is the reason ...
<!-- rule:446 -->
- Test both branches of conditional UI (feature flags/settings, locale/translation availability, permission-gated admin controls, bulk actions) — assert the control renders when enabled AND is absent when disabled. Check rendered output, not just form/object state. Negative-only tests pass on selector typos or unrelated removals, and miss regressions where a disabled control still renders. Re-verify after consolidating per-model views into shared base views (locale UI can be silently dropped) or refactoring permission context (`wagtail/admin/tests/test_privacy.py`, `wagtail/snippets/tests/test_history_view.py`, `wagtail/admin/tests/pages/test_bulk_actions/test_bulk_move.py`). Positive/negative assertions may live in separate methods per existing test organization. — The rule is a general testing convention, not tied to a single file, entity, or module. Evidence spans multiple test areas across the repository (wagtail/admin/tests/pages/test_bulk_actions/test_bulk_move.py, wagtail/snippets/tests/test_history_view.py, wagtail/admin/tests/test_privacy.py, plus admin templates and snippet views), i.e. several distinct directories. Because the rule applies wherever conditional UI is tested—feature-flag/setting-gated UI, locale/translation-gated UI, and permission
<!-- rule:1464 -->
- Test view/template rendering changes against the test client — assert both the exact context sent to the template and the rendered HTML — Context wiring (e.g., profile-derived flags like keyboard-shortcuts-enabled in `test_keyboard_shortcuts.py`) can break silently while the template still renders, so cover computed vs. request-supplied context and confirm tests fail pre-change.
<!-- rule:459 -->
- Extract non-trivial logic from components, callbacks, and templates into standalone named utilities, and cover each with focused unit tests — even if controller/integration tests already exercise them indirectly. This isolates behavior so failures point at one unit instead of a whole flow. — Indirect coverage hides which piece broke; standalone named utilities + focused tests make failures localizable and utilities reusable across `client` and `wagtail/admin`.
<!-- rule:1155 -->
- Assert on each audit-log entry's recorded `action`, `message`, and `timestamp` — count-based checks miss content regressions — Audit-log tests in `wagtail/admin/tests`, `wagtail/tests`, and `wagtail/core/tests` should verify what users actually see/get recorded, not incidental test-only state.
<!-- rule:1801 -->
- When a review suggests a stronger assertion (e.g. `html=True` or a specialized matcher), apply it to every equivalent assertion in the same test module — leaving some behind invites repeated review churn and hides which style is canonical. — Within a test module, mixed assertion styles mean reviewers re-flag the same fix on every pass and readers can't tell which form is preferred.
<!-- rule:239 -->
- Build expected URLs in rendered-HTML assertions with the same helpers the template uses: `django.utils.html.escape` (+ `urlencode` for query params) for query-string URLs, `versioned_static()` for static assets — hand-rolled URLs drift from the render path and cause false failures — Tests that hand-build expected URLs diverge from what the template actually emits (escaping, cache-busting query strings, versioned asset paths), so the assertion fails for reasons unrelated to the change under test. Mirroring the render path's helpers keeps assertions meaningful and stable.
<!-- rule:930 -->
- Assert only intended, supported behavior — tests that codify no-ops (`null` event), parameterless factory fallbacks, or speculative cases freeze accidental behavior into the public contract; test required params and resulting object shape instead, and delete out-of-scope tests rather than preserving them. — Codifying incidental behavior in tests turns accidental implementation details into contractual obligations, making refactors and bug fixes look like regressions. Only tests of required parameters and supported call paths describe behavior the API actually promises to maintain.

<!-- rule:2 -->
- Pair `assertNumQueries(N)` with a comment explaining what makes up `N`, and only on paths genuinely affected by the change under test — bare counts on unrelated code paths are noise that breaks on refactors — Treat query-count assertions as performance tests, not pass/fail hoops.
  - Never raise an `assertNumQueries` count to make a test pass — a changed count signals a real regression (usually an N+1); fix the query and tighten the count to the new lower value
<!-- rule:366 -->
- In Wagtail admin search/filter tests (`wagtail/images`, `wagtail/documents`, `wagtail/snippets`), assert exact expected results with `assertContains`/`assertNotContains` instead of diffing result sets between views — cross-view comparisons pass even when both views are wrong. Always include at least one non-matching object that must be absent (catches over-inclusive filters), assert that empty queries don't trigger required-field validation errors, and group test cases by the field/filter under test rather than by result cardinality. — Exact assertions + a known non-match catch filter over-matching, and empty-query checks catch validation regressions; grouping by field keeps coverage gaps visible.
<!-- rule:1662 -->
- Keep the shared cross-backend search suite backend-agnostic — no `@unittest.expectedFailure`, no backend-specific workarounds, no divergent-semantics assertions in shared tests; backend quirks here silently weaken coverage for every other backend. — Shared tests must prove cross-backend parity; workarounds hidden in the shared suite mean other backends aren't really being tested.
<!-- rule:451 -->
- Migrate tests when refactoring utilities into controllers or copying suites across modules — don't delete coverage — Adapt entity-specific references (signal/view/template/URL names), fixtures, and setup assumptions to the destination module's interface, and add cases for its error/config behavior. Deleting or blindly copying tests leaves the new module untested against its own contracts and hides regressions.
<!-- rule:851 -->
- Test both override and default paths for customizable hooks — e.g. `getattr(model, "<hook>_form_class", DefaultForm)`, `get_gravatar_url` (`default_params={"d": "mp"}`), and `get_avatar_url` in `wagtail/users/utils.py` / `wagtailadmin_tags.py` — a missing fallback silently breaks the uncustomized case. — Wagtail hooks like form-class customization and avatar/Gravatar resolvers must keep working when no override is supplied; without explicit tests for both branches, regressions in the default fallback (e.g. Gravatar/static URL) ship unnoticed.
<!-- rule:601 -->
- In locale-dependent tests, activate the intended locale the way production does — mismatched activation (query params vs `LocaleMiddleware`, stale caches) hides real translation regressions
<!-- rule:971 -->
- Fetch test ORM objects via semantic lookups (e.g. `Site.objects.get(is_default_site=True)`) and read expected IDs from the public `obj.pk`, never hardcoding, manually assigning, or reading `obj.pk.db_value` — concrete PKs vary across DB backends and test ordering, so they make tests brittle. — Keeps tests portable across databases and robust to insertion order, and avoids depending on internal database-value representations like `obj.pk.db_value`.
<!-- rule:1115 -->
- Test Wagtail revisions through real `save_revision()`/`revision.publish()` calls — mocking internals or hand-assigning source-of-truth fields hides the behavior under test. — This is a cross-cutting testing convention spanning `wagtail/admin/tests`, `wagtail/tests`, `wagtail/snippets/tests`, and `wagtail/contrib/forms/tests`. Real save/publish logic catches regressions in the revision lifecycle that mocks bypass.
  - Simulate validation failures with `page.save_revision(clean=False)`, not by mocking `Revision.publish` — exercises the real save path.
  - Call `revision.publish()` for admin/scheduled publishing tests instead of setting `approved_go_live_at` — avoids testing a shortcut the code never takes.
  - Explicitly call `save_revision()` to create the revision under test — don't rely on implicit revision creation.
  - Cover both save paths: initial (no `overwrite_revision_id`) and overwrite (with `overwrite_revision_id`) — path-specific bugs otherwise slip through.
  - Derive expected values from the returned `Revision` and Wagtail's timestamp renderer — hardcoded/formatted timestamps and DB null-ordering are brittle.
  - Reserve direct field setup for tests that intentionally assert a field is the source of truth.

<!-- rule:1555 -->

<!-- rule:1482 -->
