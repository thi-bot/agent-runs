# Documentation and Comments

> Writing docs, READMEs, help text, and inline comments: explain non-obvious intent, use accurate names, proofread prose, keep voice impersonal and commands executable, avoid internal links, and don't duplicate defaults in help text.

**When to check**: When writing or reviewing documentation, README setup steps, help text, or inline comments

## Rules

<!-- rule:28 -->
- Document non-obvious Django model/admin fields with `help_text` or inline comments — spell out singleton constraints, custom `choices`, legacy-only fields, and fields that override/filter synced data so editors know when and why to use them. — Non-obvious model/admin fields and `get_context` transformations encode intent that isn't visible from the code alone. Without `help_text`/comments, editors can't tell which fields are singletons, legacy-only, or override synced data, and maintainers must reverse-engineer why rows were transposed or data reshaped.
  - Comment non-obvious `get_context` transformations (e.g. transposed rows, reshaped data) — explain why the transform happens and what consumes the context, or future maintainers must reverse-engineer intent.
<!-- rule:17 -->
- Avoid private wikis, intranet pages, and vendor-specific URLs in code comments, config, and `docs/` — use a repo wiki or stable shortlink instead; external contributors can't reach private resources, and deep intranet paths break when the host reorganizes. — External contributors can't open private resources, and deep intranet paths break when the host reorganizes.
<!-- rule:23 -->
- Use official product/tool/team names with proper capitalization in docs headings — miscased or generic headings in `README.md` and `docs/frontend/support-runbook.md` break search and hide the owning team. — Written for readers who only see the final text: it preserves the two anchor paths, names the failure modes (searchability + ownership), and gives a scoped imperative rather than a bare 'follow conventions'.
<!-- rule:147 -->
- Proofread comments, docstrings, and docs before committing — errors mislead future readers — Comments, docstrings, and documentation are permanent, so a typo or duplicate word committed once will confuse and mislead every future reader who encounters it.
<!-- rule:211 -->
- State prerequisites (required CLI tools, exact permission level, platform family) separately from the commands in README setup/usage and developer docs — copy-pasted commands fail when a missing prerequisite is only implied. — These rules target README setup/usage instructions and developer docs, including Docker-related setup guidance. Readers copy-paste documented commands, so implicit prerequisites, unstated execution context, and non-runnable container steps are the main source of setup failures: a missing CLI tool or permission level is only discovered at runtime, a command meant for a container is typed into the host shell (or vice versa), and container-only steps break because `docker`/`docker compose` are not installed inside the container the user is already in. Preferring `docker compose run <service> <command>` keeps steps copy-pasteable across host and container, and providing a `docker compose run` equivalent for container-only constraints gives readers a working path instead of a dead end.
  - Tag every command step with its execution context (`local terminal` vs an exact container/service, e.g. `Docker Desktop terminal`) and verify the command runs there — unlabeled steps leave readers guessing where to type.
  - Make container-scoped steps directly executable: prefer `docker compose run <service> <command>`, include the exact shell-entry command when a shell is required, and document container-only constraints with a `docker compose run` equivalent — `docker`/`docker compose` aren't available from inside the container.
<!-- rule:196 -->
- Write `README.md` and `docs/` in direct imperative second-person ("run this command") — users scan for actions; first-person narrative ("I ran", "my terminal") and hedged phrasing ("you can", "seems to", "firstly") read as storytelling rather than reference. Keep README command sections command-focused: imperative for required steps, subject-first for optional tooling. Reserve tutorial voice for actual tutorials. — README and docs are used as reference material where readers look up specific commands. First-person, tutorial-style narration ('I used', 'my terminal') and uncertain phrasing ('seems to', 'you will have to') force readers to parse prose to extract the action, and ambiguous constructions ('on possibly your editor') cause misconfigurations. Direct second-person imperative keeps commands scannable and unambiguous. Tutorials are the exception because sequential narrative genuinely helps learners follow along.
<!-- rule:192 -->
- Don't rewrite user-facing template copy — headings, subheadings, `title=`, or `{% trans %}` strings — unless it's a definite defect (typo, spelling); fix such defects before merging. Reworded `{% trans %}` strings silently drop existing translations, and copy tweaks are out of scope for code changes. — Changing copy is out of scope for code changes, invalidates existing translations for `{% trans %}` strings, and introduces unreviewed user-facing UX changes.
<!-- rule:180 -->
- Describe UI actions generically in user-facing help (e.g. `wagtailio/roadmap/models.py` help text, `README.md`) — hard-coded admin paths and labels go stale the moment the UI moves — Docs that spell out exact admin navigation paths or button labels silently rot as the UI changes, leaving users following dead instructions; explaining *why* an action matters and linking the authoritative source lets readers adapt when the steps drift.
  - Pair non-obvious tools/UI actions with a one-line reason and a link to authoritative docs — readers can't infer intent from a bare command
<!-- rule:157 -->
- Don't write `help_text` claiming blank input falls back to a field's `default` when that `default` only pre-populates the form's initial value — Django stores blank as empty, not the default, so the help text misleads users. — Django's `default` on a model field only seeds the rendered form's initial value; submitting the field blank saves an empty value, so help text promising the default is wrong and users silently get empty data instead. Applies to any model field repo-wide, e.g. `wagtailio/features/blocks.py`.
<!-- rule:213 -->
- Write descriptive link text, keeping punctuation outside: `[steps for Windows](url).` — assistive tech and search engines read link text out of context, so `[steps.](url)` / `[here](url)` conveys nothing. — Link text is extracted by screen readers and search-engine crawlers in isolation from the surrounding sentence, so generic labels like `here`, `steps`, or `link` lose all meaning for those readers. Trailing punctuation inside the brackets gets read aloud as part of the label, so it belongs outside the link.
