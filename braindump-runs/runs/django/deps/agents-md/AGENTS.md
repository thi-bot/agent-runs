## Documentation

<!-- rule:10 -->
- Lead DEPs with an explicit Motivation section — concrete use cases, not assumed desirability — Reviewers in `draft/` and `accepted/` need to judge proposals on stated problems, not infer intent. Link each user difficulty to the benefit it enables, and reframe listed drawbacks that are deliberate design choices as features, so readers don't misread intentional tradeoffs as defects. Extended background belongs in the Motivation section, not scattered through the design.
<!-- rule:84 -->
- In DEP and governance docs (`draft/`, `accepted/`, DEP 0020 text), express lifecycle, support, and rotating-term boundaries as release milestones (`next Feature Release`, `.x` cycles, the 3-year LTS window), not fixed calendar intervals — milestones stay valid as schedules slip, while "six months" silently drifts — Release-milestone boundaries self-correct when the release schedule shifts; calendar durations don't, so readers get stale or wrong guarantees.
<!-- rule:34 -->
- In docs, spell defined terms, role names, enum members, proper nouns, and tech names exactly as declared in source or canonical usage (`Django`, `Markdown`, `HTTPS`, `New Year's Day`, `server-sent events`) — inconsistent spelling/casing breaks search and reader trust — Documentation-only rule. Kept identifiers in backticks and preserved the concrete examples (`Django`, `HTTPS`, `server-sent events`, `New Year's Day`) since those are the parts an AI assistant would otherwise mangle. Split into three bullets so the casing rule, the code-identifier exception, and the emphasis-consistency rule can each be applied independently. Placement: `docs/AGENTS.md` (or the repo's docs root) so it loads whenever docs files like `template.rst`/`template.md` are edited.
  - Preserve exact casing only for code identifiers, package names, and URLs; prose terms follow the canonical/official form — prevents silent drift from the definition
  - Reuse the introduction's emphasis style (bold, italic, `code`) on every later reference to the same term — helps readers recognize it as an established term
<!-- rule:1 -->
- Name proposal docs `{status}/{number}-{slug}.{ext}` in `draft/` or `accepted/` — zero-padded `{number}` and kebab-case `{slug}` keep DEPs discoverable and sortable. — Consolidates the DEP lifecycle rules for the `documentation/proposals/` tree into per-bullet actions covering naming, slug accuracy, single-source content, and status/number/location synchronization so an assistant editing a DEP produces a file whose name, path, and metadata all agree.
  - Point `{slug}` at the proposal's canonical, proposal-level topic with correct spelling — prefer the top-level subject over narrow implementation details so the filename reflects what the DEP is actually about.
  - Update the `{slug}` when a proposal's title or subject changes — stale slugs mislead readers searching for the file.
  - Keep each DEP's content in its single canonical file — duplicating or scattering it across files destroys the authoritative copy.
  - Set `:Status:` to `Draft` while under review and `Accepted` once approved — a mismatched status hides whether the proposal is actionable.
  - Move drafts to `accepted/{number}-{slug}.md` in the same PR that flips `:Status:` to `Accepted` — directory, `:Status:`, `:DEP:`, and filename must all agree on lifecycle state, or readers can't tell what's approved.
  - Replace `XXXX`/`0000` placeholders in the title and `:DEP:` field with the assigned DEP number — leftover placeholders break cross-references and look unfinished.
  - Verify a new draft's number is unique against existing DEPs, issues, and PRs before adding it; on collision, renumber and update both `:DEP:` and the `draft/NNNN-*` filename — duplicate numbers make DEP references ambiguous.
<!-- rule:23 -->
- In `*.rst` files (including `draft/`/`accepted/` DEP docs), use RST-native markup, not Markdown — use indentation for block quotes instead of `>`, since Markdown syntax renders as literal text or breaks the build. — RST parsers treat Markdown as plain content, so `>` quotes and Markdown emphasis leak into rendered output.

- Separate paragraphs and block-level constructs with blank lines — RST requires the blank line to terminate blocks; omitting it merges them or raises parser errors.
- Use single spaces between words and wrap prose at the project line length (typically 79/80 cols) — matches existing `*.rst` indentation and keeps diffs reviewable.
- Indent bullet-list continuation lines consistently (typically two spaces after `* `) — misindentation turns continuation text into a nested block or a parse warning.
- Prefer ASCII `--` for em/en dashes over literal Unicode dashes or a plain hyphen, leaving typographic rendering to the renderer — consistent source stays ASCII-safe and renders correctly across tools; if the project permits Unicode punctuation, use an em dash for parenthetical/emphatic breaks, never a bare hyphen (which reads as a range or minus).
<!-- rule:65 -->
- Bullet: Link docs and RST cross-refs with canonical, verified targets: — Preserves the exact canonical URL templates and the `final/`/`dev` conventions that DEPs and templates depend on, so authors resolve links correctly instead of guessing paths.
  - Use the canonical URL form and confirm the target path exists before linking — dead links fail doc builds and mislead readers. Use `https://github.com/{org}/{repo}/blob/{branch}/{path}` for repo files, `https://raw.githubusercontent.com/{org}/{repo}/refs/heads/{branch}/{path}` for raw files, the `dev` version path for Django docs, and `final/` for finalized DEPs; give every named reference a matching `.. _target:` definition and never link to files that do not yet exist.
<!-- rule:50 -->
- In design/spec/proposal docs, give exact API signatures, defaults, return types, and usage sketches — vague specs let implementers guess and drift from the reference implementation. — Concrete signatures keep proposals testable and unambiguous across `draft/` and `accepted/` docs.
<!-- rule:88 -->
- Write `.rst` external links as `` `Descriptor <URL>`_ ``; every link in a group needs its own trailing `_`, and trailing punctuation goes after the closing backtick — Sphinx renders `_`-less links as plain text. — These conventions keep hyperlinks rendering as links in Sphinx-built docs and avoid syntax that silently degrades to literal text or invalid reST.
  Reserve `<...>` for the URI target of an inline link; write standalone URLs bare (no angle brackets), and point named standards at an authoritative source — angle brackets around a bare URL are invalid reST and break rendering.
<!-- rule:201 -->
- In RFC 2119-style specs (e.g., Django DEP `.rst` files), use exact uppercase normative keywords (`MUST`, `SHALL`, `SHOULD`, `MAY`) paired with a direct action verb — no mixed-case variants, passives, or causative phrasing. — RFC 2119 keywords are only normative when uppercase and unambiguous; mixing cases or using "are permitted to"/"shall cause to be published" makes requirements non-machine-checkable and invites contradictory readings across DEPs like 0012, 0010, and XXXX.
<!-- rule:42 -->
- Format code identifiers and filenames per markup language — backticks in Markdown, double backticks in reStructuredText (with preceding space). Avoid needless backslash escapes in Markdown. — Docs here mix `.md` and `.rst` (e.g. `draft/email-providers.md`, `draft/0006-channels.rst`); using the wrong inline-code syntax renders as literal text or breaks cross-references instead of formatting identifiers.
<!-- rule:115 -->
- Link current discussion venues (`Django Forum`, `django-dev`, `Trac` for bugs) in process/governance docs — stale references send readers to dead channels — Superseded venues like the `django-developers` mailing list still appear in `draft/experimental-apis.rst`, `draft/0010-new-governance.rst`, and `final/0001-dep-process.rst`; leaving them in place misdirects contributors to inactive discussion channels and contradicts the project's current practice.
<!-- rule:161 -->
- Quote external sources verbatim in docs — paraphrasing or inventing plausible-sounding attribution misrepresents what the source actually says — 
  - Use canonical spellings for tools, packages, projects, and UI labels — a wrong or guessed name breaks search and misleads readers
  - When an external label varies across versions or views, describe the element's function instead of quoting it, and skip parenthetical details — parentheticals read as the external project's own implementation choices
  - Reproduce quotes from emails or other sources exactly rather than rebuilding them from memory — invented quotes are unfalsifiable to readers
<!-- rule:66 -->
- Link docs references to their canonical source (library repo/docs, GitHub team handle) and use descriptive link text, not bare `here`; if no link exists, use the exact identifier — keeps references resolvable and avoids stale or ambiguous pointers. — Ensures readers can always trace a reference back to its authoritative source, and prevents link rot or duplicate links from cluttering nearby prose.
<!-- rule:155 -->
- In reStructuredText (including DEPs in `draft/*.rst`), write footnote refs with a trailing underscore (`[1]_`, `[#]_`) and keep labels unique — Sphinx errors on bare `[1]` and warns on duplicate labels; use `[#]_` / `.. [#]` when footnote order may shift. — Broken footnote syntax fails the docs build, and reused labels like `[1]_` produce duplicate-label warnings; autonumbered `[#]_` footnotes avoid renumbering churn when content moves.
<!-- rule:35 -->
- Keep DEP migration examples minimal: show the simplest idiomreplacement call (no defensive `try`/`except`), mirroring the original code's style so readers can diff old and new forms at a glance — 
  - Document only proposal-specific constraints or rejected operations in migration sections — restating generic migration workflows adds noise and obscures what the proposal actually changes
<!-- rule:3 -->
- When a formatting convention, process, or named entity changes, update every affected location (`draft/`, `final/`, `template.md`, cross-references) to the desired end state — partial edits leave stale references; document the target state, not the audit procedure used to find them — Cross-references and templates drift out of sync when only the occurrence under review is updated, so readers hit contradictory guidance. Recording the search/audit procedure instead of the end state also dates the docs as soon as the audit is done.
<!-- rule:60 -->
- In governance DEPs, document the non-consensus path: disagreement resolution, transparency (publishing rationale/dissent), and when decisions are published — keeps the process usable when consensus fails — Process/governance docs (governance DEPs, both `accepted/` and `draft/`) that describe only the consensus path leave nothing to follow when agreement can't be reached. Phrasing around "if there's agreement" makes every later step implicitly conditional on consensus, so the non-consensus path never triggers. And a doc that drops the consensus requirement without an alignment expectation invites approvals that contradict the community's clear preference.
  - Phrase publication rules as "when there's a decision", not "if there's agreement" — avoids silently gating steps on consensus
  - When stating consensus isn't required for approval, add that decision-makers should align with the majority community view and avoid approving highly controversial or minority-only proposals — keeps non-consensus approvals legitimate
<!-- rule:69 -->
- Link to canonical sources for process details in `DEP`/process docs; don't restate them. When referencing overlapping `DEP`s, state the relationship explicitly (complementary, non-conflicting, superseding, or merely referenced). — Duplicated process descriptions drift out of sync — the canonical source becomes authoritative, and any local restatement silently contradicts it. Naming the relationship prevents readers from assuming two overlapping `DEP`s conflict or that one supersedes the other when it doesn't.
<!-- rule:86 -->

<!-- rule:140 -->

Applies to docs like `draft/0006-channels.rst` and `draft/0007-official-projects.rst`.

Naming an automating codemod (e.g. `django-upgrade`) plus a proof-of-concept lets them skip manual edits entirely. Splitting long guidance into a howto page and quoting verbatim error strings ensures that searching the error text surfaces the fix instead of leaving users to grep the changelog.
  - Move lengthy migration guidance to a dedicated howto page and quote exact error messages users will hit — makes docs findable via search on the error text

Keep pre-release milestones ~1 month apart (alpha→beta ~5 weeks) and leave ~2 weeks between RC and final, avoiding major holiday/vacation windows — contributors and release managers are unavailable during those periods, so a schedule that overlaps them slips or ships under-tested. Applies to files under both `draft/` and `accepted/` DEPs. — Scheduling around GSoC, DjangoCon US, and holiday/vacation gaps keeps releases on time and fully tested, since the people doing the work are actually available. The 1-month/2-week spacing gives each milestone enough soak time without drifting. Because this convention spans `draft/` and `accepted/` DEPs (e.g. DEP 0020, DEP 0101), it belongs at the repo root rather than in a module-specific doc.

## API Design

<!-- rule:37 -->
- Implement the shared handler mapping protocol (`__getitem__`, `__contains__`, `.get()`, `default`, iteration/`in`) on Django registries (caches, storages, connections, task backends, providers) — callers check aliases via `alias in registry` or `registry.get(alias)` rather than one-off methods like `is_configured()`, so all backends expose the same API. — These conventions come from Django's core handler base class and are shared across caches, storages, connections, task backends, and providers. Deviating — e.g., adding `is_configured()` or naming a registry after the managed unit of work — fragments the public API surface, breaks code that treats these registries polymorphically through standard mapping operations, and risks shadowing. Public `DEFAULT_<RESOURCE>_ALIAS` constants let callers resolve defaults the same way everywhere and keep the default discoverable in docs and `__all__`.
  - Expose the default resource alias as a public `DEFAULT_<RESOURCE>_ALIAS` constant (e.g., `DEFAULT_DB_ALIAS`, `DEFAULT_CACHE_ALIAS`) in `__all__` and the public reference docs — callers reference it directly instead of adding predicates such as `is_configured()` to hide or resolve the default.
  - Name registries/factories after the container/host that provides access to the resource, not the managed unit of work — prevents one-off APIs, ambiguity, and shadowing.
<!-- rule:134 -->
- ## Proposed rule text (bullet form) — Widening sentinels to `str` lets typos and unknown values type-check, so valid sentinels are only discovered at runtime; naming the sentinel enum and the affected parameter in docs makes them discoverable statically and prevents misuse.
  - Model API sentinel values as members of a dedicated enum/type, and list those types in the signature — not `str`; prevents accepting arbitrary values that bypass type checks
    - In docs, name the exact parameter or return value each sentinel/empty value applies to — keeps special-case semantics tied to the right slot
  ## Rationale (for the AGENTS.md author's context)
  A sentinel widened to `str` (e.g. `mode: str = "auto"`) makes every typo and unknown string type-check, so callers discover valid sentinels only at runtime. A named enum (e.g. `AutoMode.AUTO`) makes the valid set discoverable, catches bad values statically, and gives a stable symbol to reference in docs. Ambiguous docs ("empty means default") leave readers guessing which parameter is affected, so naming the exact parameter/return value prevents misuse at call sites.
  ## Placement
  Root `AGENTS.md`, category `api_design` — applies to any public API/typing/docs change, not tied to the draft spec files where it was observed.
<!-- rule:15 -->
- Define handler/receiver contracts as runtime-checkable `Protocol`s — registrations accept plain functions or callable classes with bound methods and state without breaking existing callers — This project supports hybrid signal/task handlers that can be sync or async, so APIs must accept both plain callables and object-based handlers without breaking existing registrations. Explicitly named sync/async callables remove argument-order ambiguity and make registration self-documenting. Canonical-plus-one-way-delegation prevents the infinite recursion that bidirectional sync/async wrapping produces, and raising on missing implementations prevents silent `sync_to_async`/`async_to_sync` overhead that hides whether a handler is truly async. `django.dispatch` must keep `@receiver` untouched so existing third-party signal receivers continue to work.
  - Preserve the simple-callable path when extending a registration API; dispatch on the registered object's shape at registration/connection time — keeps existing callers working and avoids forcing them onto new types
  - Expose sync and async paths as explicitly named callables (`sync_call`/`async_call`, or `sync_handler`/`async_handler`), never as registration flags or positional tuples — makes registrations self-documenting and removes ordering ambiguity
  - Designate one direction as canonical (prefer sync) and auto-generate the other with one-way delegation — bidirectional delegation causes infinite recursion
  - Never define sync and async variants that call each other; if bridging defaults are provided, document how recursion is avoided
  - Raise a clear exception at definition/registration time when an advertised sync or async impl is missing — prevents silent `sync_to_async`/`async_to_sync` wrapping overhead
  - For Django signals, leave the existing `@receiver` decorator unchanged and add an opt-in connection method on the `Signal` instance (e.g. `hybrid_connect`) that branches on receiver kind and accepts either a plain callable or a class/`Protocol`-based handler with paired sync/async impls — keeps `Signal` APIs backward-compatible for third-party handlers
<!-- rule:141 -->
- Require explicit `name` on DEP `Index`/`Constraint` subclasses — auto-generated names collide silently across specs and break reproducibility — These conventions keep DEP `Index`/`Constraint` specs stable and self-documenting: explicit names make specs reproducible, keyword-only options keep signatures backward compatible, and per-algorithm classes eliminate invalid option combinations.
  - Use `__init__(self, *fields, **options)` for DEP index specs — fields positional, options keyword-only, so adding options never shifts call sites
  - In DEP doc examples, pass expressions as explicit kwargs (e.g., `FunctionalIndex(expression=...)`) — models the real call shape for readers
