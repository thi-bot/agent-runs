## Code Style

<!-- rule:61 -->
- In Django templates using i18n, include `{% load i18n %}` and wrap every user-visible string (labels, buttons, headings, placeholders, ARIA labels, prose) in translation tags. Use the canonical `{% translate %}` tag (not the legacy `{% trans %}` alias) for short strings. Use `{% blocktranslate trimmed %}` for multi-line or interpolated strings, placing template variables inside the block rather than appending them after a `{% translate %}` string; in text/plain email templates, do not use the `trimmed` option (newlines are visible) and insert only intentional line breaks. In `{% blocktranslate %}`, only include a `with` clause for attribute lookups, filters, or renamed variables; omit it for simple variables. If a variable needs a filter, apply the filter in the `with` clause and reference the resulting variable inside the translated block. Reuse existing translation strings rather than hardcoding or duplicating msgids. — This rule governs how user-visible strings are wrapped for translation in Django templates across the repository (e.g. `djangoproject/templates/blog/`, `djangoproject/templates/aggregator/`, `djangoproject/templates/foundation/`, `docs/templates/`). Each clause prevents a specific i18n bug: untagged strings ship untranslated to users; mixing `{% trans %}` and `{% translate %}` fragments the template style; appending variables after a `{% translate %}` string strips them from the translator's context; `trimmed` in text/plain emails silently removes meaningful newlines; `with` clauses on simple variables add noise for translators; filters inside a translated block obscure the msgid; and hardcoded or duplicated msgids split translators' work across identical strings.
<!-- rule:65 -->
- Remove dead CSS/SCSS — initial-value declarations, cascade/specificity-overridden props, duplicate or orphaned selectors, and empty `@include`/directive blocks — so stylesheets only contain what actually renders; keep intentional overrides, fallbacks, and specificity hooks (they change output). — Dead stylesheets mislead readers about which rules apply, invite copy-paste of already-dead patterns, and make cascade debugging harder; preserving intentional overrides/fallbacks avoids breaking intentional edge-case behavior.
<!-- rule:19 -->
- Match the surrounding file's existing style — indentation, blank lines, naming, spacing — mixed conventions within one file are a common review reject — The repo spans Python, SCSS, JS, and templates, and files are edited piecemeal; introducing a second style inside a file creates noisy diffs and inconsistent sections that reviewers flag. The SCSS and `djangoproject/static/js/` specifics reflect the conventions already in place there, so following them keeps new code indistinguishable from existing code and avoids reformatting churn.
  - In SCSS: use 4 spaces (not tabs), a space before `{`, one blank line between rule sections, and close every block with `}`
  - In `djangoproject/static/js/`: use the file's indent width (no tabs/mixed), space before `{` (`function() {`, not `function(){`), and keep short calls with simple object args on one line when nearby code does
  - Skip extra blank lines after class declarations and around newly added settings/top-level assignments
<!-- rule:1 -->
- Apply repeated-pattern changes to every occurrence, not just the flagged instance — Partial fixes leave inconsistent formatting, spelling, localization, or HTML structure scattered across files — search the file, PR, or codebase as appropriate so the pattern is uniform everywhere.
<!-- rule:108 -->
- In templates, use `<ul>`/`<ol>` with `<li>` for item groups and `<dl>` with matched `<dt>`/`<dd>` pairs for term/definition content — semantic lists give screen readers and search crawlers the structure they need to announce counts, relationships, and definition pairs that generic `<div>`s and styling-only headings obscure. — Generic `<div>` containers, heading tags used purely for visual styling inside `<li>`, and presentational classes on lists all strip the semantic signal assistive tech relies on, while an unmatched `<dt>` (no paired `<dd>`) is invalid HTML and causes screen readers to mis-announce definition lists.
<!-- rule:161 -->
- Reverse internal template links with `{% url 'namespace:route' %}`, `{% host_url %}` (host-aware), or `{% url 'document-detail' ... %}` — never hardcode paths or absolute URLs; keeps links valid when routes change. — Hardcoded paths silently break on URL restructuring; named reversing keeps templates in sync with `urls.py`. For `document-detail`, keep `url` as the canonical doc path so documentation links resolve correctly.
<!-- rule:77 -->
- Centralize styles in `djangoproject/scss/` (e.g., `_style.scss`) and apply them via classes — inline `style` attributes, `<style>` blocks, and page-specific CSS cause divergence and duplication. Reuse existing classes before adding new ones. — Ensures all SCSS under `djangoproject/scss/` and `foundation` shares a single source of truth so styles stay consistent across templates.
<!-- rule:49 -->
- Default to `const`; use `let` only when the binding is reassigned — `var`'s function-scoping and hoisting cause reassignment bugs that block-scoped bindings can't. — Applies across all JavaScript files (`static/js/mod/*`, `static/js/*`).
  - Use `const` for UPPER_CASE constants and for conditional values: prefer `const x = cond ? a : b` over an `if` that mutates a `let`/`var` — keeps the binding immutable and makes the value's origin obvious.
<!-- rule:259 -->
- Keep lines within the configured max length (`E501` via `flake8`/`black`/`pre-commit`, ~80 for legacy JS) — consistent wrapping keeps diffs and reviews sane. — The limit is enforced by the project's linter/formatter config across all modules (Python tests, forms, legacy JS), so violations fail CI rather than getting silently reformatted.
<!-- rule:305 -->
- Use hanging indents for multi-line calls and collection literals, with trailing commas and aligned closing delimiters (never align under the opening paren) — keeps diffs minimal when items are added and matches existing Django model declarations in the same file (e.g. `Meta.indexes`); keep declarations on one line when they fit. — Trailing commas and hanging indents give clean, consistent diffs when the last item is added or removed, and aligning under the opening paren breaks as soon as the callee name changes length.
<!-- rule:233 -->
- Prefer `pathlib.Path` idioms over `os.path`: compose with `/` (not `Path.joinpath()` or `os.path.join`), use `read_text()`/`write_text()`/`path.open()` instead of `open(path, ...)`, and pass `Path` objects directly rather than casting with `str()` — keeps path handling consistent and avoids brittle string joins. Applies to all Python in `docs/`, `djangoproject/`, `tools/`, `releases/`. — Keeps path handling consistent across the codebase and avoids brittle string/separator joins and redundant conversions; `Path` is path-like so casts to `str()` are unnecessary.
<!-- rule:92 -->
- In HTML templates, never nest block elements (`<ul>`, `<div>`, `<p>`) inside `<p>`; use one `<p>` per paragraph and `<div>`/`<span>` for other containers, indenting tags to match DOM nesting — browsers auto-close `<p>` at the first block child, silently corrupting the DOM and breaking styling/layout in ways that are hard to trace. — Browsers implicitly close an open `<p>` when a block-level child appears, so nesting `<ul>`/`<div>`/`<p>` inside `<p>` produces a DOM that doesn't match the template source. This silently breaks CSS selectors, spacing, and JS hooks across `djangoproject/templates/`. Accurate indentation makes the real DOM structure visible so these mismatches are caught in review.
<!-- rule:231 -->
- Use `Model.objects.bulk_create([...])` instead of repeated `.create()` in loops and test setup — collapses N inserts into one query; keep the returned list if objects are needed for relations or assertions. — Repeated `.create()` calls trigger N database round-trips, slowing test setup and bulk data paths; `bulk_create` issues a single query. The returned objects carry their PKs, so retaining the list preserves the ability to wire up relations or assert on the created rows — dropping it forces an extra query.
<!-- rule:135 -->
- Use Django's localization-aware date/time formatting in templates: named constants (`DATE_FORMAT`, `TIME_FORMAT`, `DATETIME_FORMAT`, `MONTH_DAY_FORMAT`), the `date` filter, timezone filters like `utc`, and formats defined centrally in `formats.py` — a hardcoded format string, manual component concatenation, or a model property that duplicates a built-in filter bypasses `L10N` and drifts from every other template. — The rule prevents localization breakage and format inconsistency: hardcoded strings ignore `USE_L10N`/locale switching, manual concatenation reorders components per locale, and model properties duplicating template filters create a second source of truth for formatting that must be maintained in parallel. Choosing the exact-precision constant and binding values with `{% with %}` keeps templates readable and avoids needless re-evaluation of filters.
  - Match the format constant to the precision you actually need (use `'Y'` for year-only rather than `YEAR_MONTH_FORMAT`) and bind repeated filtered values once with `{% with %}` — avoids over-formatting and redundant filter calls that obscure the template's intent.
<!-- rule:214 -->
- Render form fields with Django helpers — `{{ form.<field>.id_for_label }}` / `label_tag` for label-input binding, `{{ form.<field>.as_field_group }}` wrapped in a `<div>` for whole fields — hardcoded `id_<field>` and hand-rolled label/error/input markup break label association whenever a field name or form prefix changes, and drift from Django's own rendering. — Django's form helpers derive IDs and prefixes at render time, so hardcoding `id_<field>` or rebuilding markup silently breaks label/input association and diverges from Django's output as fields are renamed or prefixed. Using `as_field_group` inside `<div>` containers keeps field groups and the submit row structurally uniform; mixing in a `<p>` container breaks that consistency.
  - Wrap the submit-button container in a `<div>` to match `<div>`-based field groups — a `<p>` here breaks layout consistency with `as_field_group` output.
<!-- rule:42 -->
- Inline single-use variables and constants at their use site; compose derived boolean properties from existing boolean helpers instead of re-checking underlying fields — redundant indirection obscures intent and duplicates field checks that drift out of sync. If a one-off variable is truly needed, name it for its immediate use, not descriptively. — Single-use locals and re-checked boolean properties (e.g. testing `self.x` inside a property that already has a `has_x` helper) add layers readers must unravel and silently fork the source of truth.
<!-- rule:4 -->
- Keep PR changes scoped to the stated purpose; revert unrelated whitespace-only, formatting, or drive-by edits. Move unrelated dependency/package removals to a dedicated issue or PR. — Unrelated edits bloat diffs, hide the real change from reviewers, and make clean reverts impossible.
<!-- rule:115 -->
- Use `{% with name=value %}` (not legacy `{% with value as name %}`) to bind repeated expressions once — matches current Django syntax and avoids duplicate evaluation. — Placed at repo root as a global Django-template code-style convention: it applies across both `djangoproject/templates` and `docs/templates`, so a directory-scoped rule would be missed outside those trees. Keeping template content DRY and using the modern `{% with %}` syntax prevents drift between duplicated copies and takes advantage of Django's per-`{% block %}` scoping rather than fighting it.
  - `{% with %}` variables are scoped to the enclosing `{% block %}` — define cross-block values in the view context or a context processor instead.
  - Consolidate repeated markup (loops, language/`hreflang` link tags, messages rendering) into a shared loop, a reusable `{% include %}` partial, or a base/layout template — copies drift out of sync and diverge silently.
  - Only pull shared boilerplate into a page template when that page actually uses it — dead includes obscure inheritance and clutter the template.
<!-- rule:350 -->
- Update CSS selectors and reset browser defaults when swapping HTML tags for semantics/accessibility — orphaned selectors silently break the visual design — Changing tags like `<div>` → `<section>` for semantics drops existing selector matches and picks up different browser default styles, so tagged elements must be paired with updated selectors and explicit resets/overrides in `docs/templates` and `djangoproject/templates` to preserve the intended appearance.
<!-- rule:79 -->
- Style with purpose-specific CSS classes, not bare element selectors — element-level styles leak into every matching tag and break unrelated templates. — Applies across `djangoproject/templates` and `members/templates` where shared HTML tags are reused for different purposes; element selectors cannot be safely scoped per context.
<!-- rule:154 -->
- Text files should end with exactly one trailing newline: ensure a single newline (LF) after the last content line, and remove any trailing blank lines. — Prevents noisy diffs and merge conflicts from whitespace-only changes at EOF.
<!-- rule:424 -->
- Use single quotes for Python string literals; double quotes only when the string contains a `'` (e.g., `"it's"`) — matches existing codebase style and avoids needless escaping — Keeps string quoting consistent across the codebase (docs, fundraising, etc.) and avoids escaping single quotes inside strings.
<!-- rule:210 -->
- Normalize text with a single `re.sub` (compile when reused) instead of repeated `.replace()` calls or punctuation loops — one pass avoids per-character overhead and keeps normalization consistent — These guidelines keep text and URL normalization cheap and uniform across `docs/templatetags/docs.py` and `djangoproject/middleware.py`. Repeated `.replace()` calls and per-character loops cost multiple passes over the input, and conditional `split`/`join` adds branching overhead on every request. Running the default response before any normalization means the typical request skips the rewrite work entirely, only paying for it on the rare `Http404` path.
  - In `djangoproject/middleware.py`, normalize URL paths via the same single-`re.sub` approach rather than conditional `split`/`join` branching — minimizes per-request work on the hot path
  - Call the default response first in middleware, and fall back to normalization + redirect only when it raises `Http404` — keeps the common (non-404) request on the fast path
  - Apply this normalization style in `docs/templatetags/docs.py` too — shared pattern across the repo avoids divergent behavior
<!-- rule:121 -->
- Commit only intentional migrations; fold unreleased ones into the preceding migration; exclude from unrelated PRs. — Keeps history reviewable and prevents spurious numbered files from piling up across `blog/migrations`, `docs/migrations`, and `members/migrations`.
<!-- rule:316 -->
- Interpolate the count placeholder (`%(count)d`, `{{ num_results }}`) into both `ngettext`/`{% blocktranslate count %}` forms — hardcoding `1` or adding `"Only"`-style qualifiers breaks languages whose plural rules differ from English, since both branches share one msgid — Both singular and plural forms are keyed by the same msgid, so a hardcoded `1` or a count-specific qualifier like `"Only"` leaks an English assumption into every translation — languages with more than two plural categories can't express the correct form, and translators have no placeholder to work with.
<!-- rule:388 -->
- In member templates (`members/templates/members`, `djangoproject/templates/members`), render member images with the thumbnail-with-logo fallback — use `{% if obj.thumbnail %}{{ obj.thumbnail.url }}{% else %}{{ obj.logo.url }}{% endif %}` rather than nesting `.url` directly off `obj.thumbnail`, and keep the model's existing `logo`/image field in the output instead of omitting it — thumbnails aren't guaranteed to be generated, so an unguarded `obj.thumbnail.url` raises a `ValueError`, and dropping the logo field leaves members with no image at all. — Thumbnails may not exist for every object; the fallback preserves rendering. Omitting the logo field regresses members that previously displayed an image.
<!-- rule:206 -->
- Use semantic landmark elements (`<nav>`, `<search>`) for navigation and search regions instead of `<div>`/`<span>` with ARIA roles — native landmarks are announced reliably by screen readers and work without JS. When multiple nav landmarks sit on one page, give each a unique accessible name via `aria-label`/`aria-labelledby` (e.g. `'Primary'`, `'Main'`) so users can distinguish them. — This applies to any frontend template under `docs/templates/` or `djangoproject/templates/` (headers, search results, doc pages), so follow it wherever you touch markup.
<!-- rule:224 -->
- Hide decorative `<img>`/icons from screen readers — `alt=""` on decorative `<img>`, `<span>` or `aria-hidden="true"` on decorative icons. — Prevents double-announcement and noise for assistive-tech users across all HTML/Django templates in the repo.
  - Skip descriptive `alt` when adjacent visible text already conveys meaning — screen readers would otherwise announce the same content twice.
<!-- rule:240 -->
- Apply layout classes directly on `<nav>` instead of a wrapping `<div>` — nav/pagination markup stays minimal — The WHY — why does this matter? (backward compat, prevents bugs, consistency, etc.)
  - Put links directly in `<nav>` for simple nav groups; skip `<ul>`/`<li>` — same semantics, less markup
  - Use `<span>` for non-interactive current-page indicators instead of `<li>` — marks them as non-interactive
  - For the current link, omit `href` and set `aria-current="page"` — native semantics replace custom classes
  - Don't add `class="active"` or `aria-disabled="true"` to current items — `aria-current` already covers state
  - Style current items via `a[aria-current]` or `a:not(:link)`, never `.active` — keeps CSS tied to semantics
<!-- rule:270 -->
- Use `<h1>`-`<h6>` only for real page/section titles; use `<p>` or other non-heading elements for nav and short link text in header blocks — headings form the accessibility tree that screen readers navigate by, so misusing `<p>` for titles or headings for non-headings breaks that structure. — Screen readers and assistive tech rely on the heading outline to jump between sections. `<p>`-styled titles vanish from the accessibility tree entirely, while heading tags on nav links or other non-heading UI inject phantom sections that distort that outline — both make the page harder to navigate non-visually.
<!-- rule:39 -->
- Detect platform shortcut modifiers with `event.metaKey` on Apple and `event.ctrlKey` elsewhere — a handler listening for the wrong modifier makes the shortcut silently dead — no change needed
  - Format shortcut hints natively: `⌘ K` (U+202F, no `+`) on Apple, `Ctrl + K` elsewhere — hints that don't match the detected modifier mislead users about how to trigger the action
<!-- rule:304 -->
- Use ES6 `class` for constructors and prototype-based objects, not function-constructor + `prototype` assignment — avoids error-prone manual prototype wiring and matches the pattern already used in `static/js/mod/character-counter.js` and `static/js/fundraising-heart.js`. — Class syntax is clearer and less error-prone than manual prototype assignment, and keeps constructor style consistent across the JS codebase.
<!-- rule:239 -->
- Prefer `dataclass` with named fields over tuples/positional sequences for multi-field structured data, especially when parsing external API responses or usage logic — named fields keep call sites readable and refactor-safe — The rule enforces `dataclass` usage over tuples for structured data, especially when extracting from usage logic or external APIs. When mapping tuple results, the tuple must be unpacked into the constructor (`Dataclass(*item)`, `starmap`), not passed as a single positional argument. Verbose structures should live in dedicated modules away from consuming code.
  - Unpack tuple results into dataclass constructors (`Dataclass(*item)`, `starmap(Dataclass, items)`) instead of passing the tuple as one positional arg — otherwise the whole tuple lands in the first field
  - Move verbose extracted dataclasses/constants into a dedicated module rather than alongside the consuming code — keeps usage logic focused
<!-- rule:253 -->
- Use early-return guard clauses instead of deep nesting — flattens conditionals and event handlers so the main logic stays readable and preconditions are explicit. Add a brief comment for non-obvious early returns (e.g. `// skip when already synced`). — Deeply nested `if` blocks in conditionals and event handlers bury the primary logic and make preconditions easy to miss; early returns surface what must be true up front, and comments explain guards whose reason isn't obvious from the condition alone.
<!-- rule:104 -->
- Never hand-edit generated files (`robots.docs.txt`, `tools/release-data.json`) — regenerate them via their scripts (`python manage_translations.py robots_txt`, `python generate_release_roadmap.py --first-release <version> --date <YYYY-MM>`) — Hand-edits silently diverge from the generator and get overwritten on the next run, so committed output must always match what the command produces.
<!-- rule:319 -->
- Search all references before deleting a field, method, or `QuerySet`/manager method; if unused, remove it promptly — stale dead code misleads readers, and premature deletion breaks templates, admin, and callers. — Deletions of fields, methods, and `QuerySet`/manager methods ripple into templates, admin, migrations, and other modules, so verifying no references remain before removal prevents broken callers. Deleting promptly once confirmed unused keeps the codebase free of dead code that misleads future readers and searches.
<!-- rule:312 -->
- Use `tuple`/`set` literals by usage; reserve `frozenset` for required immutability or hashing — Keeps Django config in `djangoproject/settings/` and `djangoproject/middleware.py` readable and consistent — a `LOCALE_PATHS` tuple expresses order, `{'POST'}` expresses membership, and unnecessary `frozenset` wrapping adds noise without benefit.
<!-- rule:219 -->
- Keep accessible names non-redundant in HTML templates — duplicates make screen readers announce the same name twice, and `visuallyhidden` labels deprive sighted users of context. Use visible `<label>` text for form fields, action-describing `visuallyhidden` text for icon-only controls (not the field's label), and drop nested `span.visuallyhidden` when an `aria-label` already names the control. — Screen readers announce both the `aria-label` and any nested `visuallyhidden` text, so duplication forces users to hear the same name twice. Conversely, hiding useful `<label>` text with `visuallyhidden` removes visible context that sighted users rely on. Icon-only buttons need their own action description, not a copy of the field label, so the announced name matches the actual button purpose.
<!-- rule:143 -->
- Prefer CSS logical properties (`inline-start`/`inline-end`, `block-start`/`block-end`) over physical ones (`left`/`right`/`top`/`bottom`), and verify directional glyphs (arrows, chevrons) match the target reading order — hardcoded physical directions and unmirrored icons break `RTL` locales silently. — Direction-sensitive UI reads correctly in both `LTR` and `RTL` only when logical properties and reading-order-aware icons are used consistently across templates and stylesheets.
<!-- rule:271 -->
- Nest headings one level per section and match open/close tags (`<h4>...</h4>`) — mismatched or skipped levels break the document outline and screen-reader navigation — Heading levels communicate document structure to browsers, assistive tech, and TOC generators. A `<h4>` closed with `</h3>` or a section jumped from `<h3>` to `<h5>` produces an invalid outline that breaks accessibility tooling; similarly, an outline list whose nesting doesn't track the headings it summarizes renders a TOC that misrepresents the page.
  - Mirror heading hierarchy in outline markup like `<ul class="list-outline">` — top-level headings as top-level `<li>`s, sub-headings in nested `<ul>`s, so reformatting or wrapper `<ul>`s never shift what counts as top-level
<!-- rule:78 -->
- Scope style overrides to the target element instead of editing shared classes in `djangoproject/scss/_style.scss` — Shared style classes are consumed across many templates; changing them ripples to every consumer, so audit usages first and only edit globally when verified safe.
<!-- rule:118 -->
- Use options-object forms for viewport APIs: `scrollTo({ top, left, behavior: 'smooth' })` and `focus({ preventScroll: true })` — positional args like `scrollTo(x, y)` silently turn smooth scrolling into an instant jump, and a bare `focus()` competes with a following `scrollIntoView()` for the viewport. — The positional `scrollTo(x, y)` form has no way to express smooth behavior, so it drops any existing smooth-scroll intent and causes an abrupt jump; `focus()` scrolls the element into view by default, which fights the explicit `scrollIntoView()` call that is supposed to own the scroll. Passing the options object keeps behavior explicit and avoids double/competing scrolls.
<!-- rule:9 -->
- Prefer `datetime.timezone.utc` over `get_fixed_timezone(0)` for UTC — standard, timezone-aware, matches repo convention — `get_fixed_timezone(0)` and `date.today()` produce naive/local-time values that silently diverge from the timezone-aware timestamps used elsewhere in the project, causing off-by-one dates and comparison bugs in tests and production code.
  - Use `timezone_today()` instead of `date.today()` in the members app and tests — keeps dates timezone-aware and consistent
<!-- rule:169 -->
- Build URLs with `urllib.parse` helpers — `urljoin()` for path segments, `urlencode()`/`quote()` for dynamic query values — instead of string concatenation or f-string interpolation, which produce malformed or injection-prone URLs when values contain `/`, `?`, `&`, or spaces. — Prevents broken URLs from unescaped slashes/special characters and injection via user-derived values.
<!-- rule:105 -->
- Use flexbox properties (`justify-content`, `gap`, `align-self`, auto margins) for alignment and spacing in flex layouts — not `float` on flex children or empty spacer elements (`scss/_console-tabs.scss`, `templates/includes/header.html`). — `float` is ignored on flex children and spacer `<div>`s add template noise, so control alignment on the container/item where flex actually honors it.
<!-- rule:247 -->
- Scope CSS selectors to the nearest component container, not page/section ancestors — lower specificity keeps overrides working; before hoisting a generic selector like `span.title` out of component scope, verify no unrelated elements match it — High-specificity ancestor prefixes make later overrides require equally specific selectors or `!important`, and hoisting a generic selector globally can unexpectedly style unrelated elements. Keeping rules component-scoped preserves override-ability and prevents cross-component style leaks.
<!-- rule:419 -->
- Match CSS selector names exactly to markup identifiers and use kebab-case (`#back-to-top`, not `#backtotop`) — invalid or mismatched names are silently dropped, so check the compiled CSS when a style refuses to apply. — CSS silently ignores unknown properties and unmatched selectors, so a typo in `_style.scss` produces no error — only missing styles. Kebab-case multi-word IDs/classes keep selectors consistent with the markup they target and make mismatches easier to spot during review.
<!-- rule:335 -->
- Use transparent backgrounds and source-of-truth hex colors in all static/generated SVGs (`tools/`, `djangoproject/static/`) — matches the page theme and stays in sync with the mirroring JS palette instead of drifting into near-match hex values. — SVGs rendered on arbitrary backgrounds need transparency to blend; approximating hex values from the JS palette causes visual drift between generated assets and their source component.
<!-- rule:38 -->
- Match font weights/styles exactly when swapping font loaders — verify `ital,wght@...` variants survive the swap — Dropping or adding a variant in a Google Fonts `<link>` or `webfontloader` config silently changes which weights/styles render, causing fallback fonts or broken italic/bold styling in `base.html` and other templates.
<!-- rule:345 -->
- Use compact, stable labels in roadmap SVGs (`Jan.`, year-only for calver) — full names crowd the chart and go stale; applies in both `generate_release_roadmap.py` copies (`tools/` and `releases/management/commands/`) — Abbreviated month names with periods and year-only calver labels keep the SVG timeline legible without overflow, and stay accurate as dates shift — verbose labels become misleading once the roadmap is regenerated.
<!-- rule:252 -->
- Set all fields before the first `save()`; call `save_m2m()` only after the instance has a PK — avoids redundant UPDATEs and `ValueError` from unsaved instances — Django performs one INSERT on the initial save and a separate UPDATE for every later field assignment, so populating fields first halves the write path. Many-to-many managers also require the row to exist: calling `save_m2m()` (or `instance.m2m.add(...)`) on an unsaved instance raises `ValueError: ... instance needs to have a primary key value before a many-to-many relationship can be used`.
<!-- rule:85 -->
- Format `{% if %}`/`{% else %}`/`{% endif %}` across multiple lines, not as a single-line conditional — long inline conditionals are hard to scan in diffs; when only an attribute value varies, put an inline `{% if %}` inside the attribute instead of duplicating the entire HTML element in each branch — duplicated markup drifts out of sync across edits. — Multi-line conditionals stay readable in diffs, and inlining the conditional on the attribute value avoids duplicating whole elements that can silently diverge when only one branch is later edited.
<!-- rule:167 -->
- Use the standard unprefixed CSS property as the canonical declaration, with vendor-prefixed variants (e.g. `-webkit-*`, `-moz-*`) added only as a supplement — never as a replacement. Likewise, remove obsolete Modernizr-style feature-detection fallback classes (e.g. `.mdzr-no-X`) once the detected feature is universally supported by the project's target browsers. — The unprefixed property is the canonical, forward-compatible declaration; prefixes are only a supplement for legacy engines, so dropping the standard form leaves stylesheets broken on the very browsers they target. Obsolete `.mdzr-no-X` fallbacks become dead weight once the feature is universally supported, and keeping them masks real feature support and misleads future contributors about what the codebase actually targets.
<!-- rule:34 -->
- Interpolate dynamic values flat and individually, e.g. `f"{a}{b}"` or `` `${a}${b}` `` — never nest same-style interpolations or interpolate a concatenation — Nested/wrapped expressions like `f"{f'{a}'}{b}"` or `` `${a + b}` `` are hard to read, break syntax highlighting and linters, and differ across languages; flat per-value interpolation stays consistent and portable.
<!-- rule:420 -->
- Match override names exactly to the base-class API — a typo silently creates a non-overriding method that never runs — The typo case is particularly insidious because Python does not error: the method simply never overrides and the base implementation runs instead, leading to bugs that are hard to trace.
  - Call `super().<method>(...)` for small tweaks instead of copying parent code — inherited behavior stays in sync
<!-- rule:336 -->

<!-- rule:71 -->
- Put model query logic on the model's Manager/QuerySet (e.g., `Profile.objects.some_query()`, `Document.objects.search()`), not in views, `utils.py`, or `@staticmethod`/`@classmethod`. — Keeps request handling (extract, validate, pass args) separate from query logic so queries are reusable and testable across the codebase. <!-- rule:96 -->

<!-- rule:194 -->
- Keep search/query methods to a single ORM query — avoid `.count()` existence checks and Python-level branching between queries — Each extra round-trip multiplies latency under load; `Case`/`When`/`Exists`, ordering, and pagination handle fallbacks and conditionals in one query.
