# Documenting Behavior Accurately

> Verifying and precisely stating runtime behavior, edge cases, propagation boundaries, lifecycle, warnings about misuse, and behavior changes.

**When to check**: When documenting runtime behavior, edge cases, lifecycle, warnings about misuse, or behavior changes

## Rules

<!-- rule:4471 -->
- Scope each docs warning to one specific misuse (e.g., separate redundant queries from `n+1` loading in `docs/topics/db/optimization.txt`) — conflated warnings leave readers unsure which fix resolves which problem. — Documentation warnings are prescriptive: readers apply them literally. Bundling distinct performance problems into one warning obscures which change helps, and modeling query patterns that fail at scale (e.g., `__in` with huge ID lists) turns docs into copy-paste sources of production bugs.
  - Caveat or replace unscalable query examples (e.g., `__in` with huge ID lists) in warning sections like `docs/ref/contrib/admin/index.txt` — documented patterns get copied verbatim, so unscalable examples breed unscalable code.
<!-- rule:4831 -->
- Enumerate actual generated outputs in `docs/` rather than hardcoding derived counts — Numbers like page ranges or variant counts silently drift from the inputs they describe, so readers can't trust them
<!-- rule:6249 -->
- When contrasting frameworks or recommended vs. discouraged features in docs, verify each claim against actual framework behavior and explain the capability difference behind the recommendation — phantom restrictions and unexplained preferences mislead readers and make guidance look arbitrary. — Comparative docs in `docs/ref` and `docs/topics` (e.g. `docs/ref/applications.txt`, `docs/topics/templates.txt`) are read as authoritative, so unverified claims about framework behavior and ungrounded recommendations erode trust and can send users down wrong paths.
<!-- rule:2395 -->
- Match verb modality to behavior in DB docs: use definitive voice plus mechanism for fixed/generated behavior (e.g., "the generated SQL will also delete ... via `CASCADE`"), but hedge with "may"/"can" for third-party backend behavior — readers must not mistake generated behavior for a configurable option, nor assume external backend behavior is guaranteed across versions. — Generated or hard-coded database behavior that is documented as optional or uncertain misleads readers into hunting for config knobs that don't exist, while describing third-party backend behavior in definitive terms creates false expectations when upstream versions change. This convention is used across `docs/ref/migration-operations.txt` and `docs/topics/db/aggregation.txt` for database documentation, backends, and migration behavior.
<!-- rule:1553 -->
- State the propagation boundary explicitly when documenting behavior that spreads through object relationships: name which related objects inherit it and which don't — vague metaphors like "whole tree" mislead readers whenever propagation isn't truly transitive (e.g. related objects but not their managers or chained manager operations; see `docs/topics/db/fetch-modes.txt`) — Object-graph behavior is rarely fully transitive, so a "whole tree" phrasing overpromises and sends readers into bugs; spelling out the exact boundary (e.g. related objects inherit X, their managers do not) keeps docs matching the implementation.
<!-- rule:4091 -->
- Verify multi-table inheritance serialization behavior before documenting it — prevents wrong claims about parent fields in `docs/topics/serialization.txt` — Readers of `docs/topics/serialization.txt` rely on it to know whether parent fields are serialized automatically and what extra steps are needed; asserting unverified behavior misleads them and forces a docs fix later.
<!-- rule:4678 -->
- Include the zero-row edge case when documenting parameterized joins (`M × N`) — state resulting rows and give an example per branch, since e.g. `LEFT OUTER JOIN` still emits outer rows with `NULL` subfields and readers otherwise assume empty input yields empty output. — Parameterized query docs describe row counts like `M × N`, but the empty-input branch often behaves differently than readers assume (an empty input to a `LEFT OUTER JOIN` still yields one row per outer row with `NULL` subfields, not zero rows). Documenting the branch and a concrete example prevents users from writing incorrect assumptions about output shape into their code.
<!-- rule:1819 -->
- Lead with the trigger condition, then contrast new vs. existing behavior — readers scan for 'when does this apply?' before details. — Docs for overrides and behavior changes (e.g. `docs/ref/models/`, `docs/releases/`) are consulted by users checking whether their setup is affected; burying the condition or omitting the prior behavior forces them to diff releases manually and mis-tag affected entities. Naming entities with qualified paths (`User.is_active`, not `is_active`) disambiguates across modules where the same short name appears in multiple classes.
<!-- rule:1540 -->
- For lifecycle docs in `docs/ref/` (e.g., `databases.txt`), cover both the open/retained phase and every automatic cleanup point (`end of request`, `end of management command/session`) — readers can't predict resource lifetime otherwise, and gaps force them to read the source; also flag non-obvious mechanics like weak-reference tracking so surprising retention is documented, not discovered. — Documents the active phase and cleanup points together so readers know precisely when resources close; flagging hidden behavior like weak-reference tracking prevents retention surprises, and a single paragraph keeps the topic scannable.
  - Keep lifecycle coverage in a single concise paragraph matching existing topic docs — scattered or verbose notes make cleanup semantics hard to scan.
<!-- rule:3343 -->
- Document renamed terms with a historical note (old name, date, PR link) — e.g., `master` → `main`, March 2021, PR #14048 — so readers searching old terminology can still find the page — Readers and external links often still reference the previous term; without a breadcrumb they assume the docs are wrong or the feature was removed.
<!-- rule:6105 -->
- Describe feature toggles in release notes and admin docs by UI behavior (e.g., "can be toggled in the UI"), not by query params like `_facets` — users read these docs, not the implementation. — Release notes and admin docs target end users who interact through the UI; leaking internal query parameters like `_facets` from `docs/releases/5.0.txt`-style entries confuses readers and ties docs to implementation details that may change.
<!-- rule:6265 -->
- Explain the concrete mechanism when warning against a practice (e.g., why imports inside methods break reloading), not just that it may cause problems — readers need to judge edge cases themselves — Documentation examples are treated as endorsed usage: showing a discouraged pattern without an explicit alternative teaches it, and a vague warning leaves readers unable to tell when the caveat actually applies.
  - Don't present discouraged patterns (e.g., imports inside methods) as normal usage; point readers to the documented public API or safe alternative — doc snippets get copy-pasted verbatim into user code
  - Applies to all files under `docs/` (e.g., `docs/topics/settings.txt`, `docs/ref/applications.txt`)
