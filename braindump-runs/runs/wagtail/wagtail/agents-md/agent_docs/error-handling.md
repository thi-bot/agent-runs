# Error Handling & Validation

> Rules for scoping try/except, raising appropriate exceptions, input validation, logging caught exceptions, atomic transactions, and fail-loud configuration validation.

**When to check**: When adding error handling, validating inputs/configuration, raising exceptions, or scoping try/except blocks.

## Rules

<!-- rule:1272 -->
- Scope `try`/`except` to the smallest operation that can raise the expected exception — narrower scopes prevent unrelated failures from being misattributed or silently swallowed. Remove no-op handlers that only re-raise, and never raise the same builtin exception type (e.g., `TypeError`) used to drive a fallback — use a distinct type (e.g., a `LookupError` subclass) so the fallback's own errors surface at the offending element instead of being caught and masked. — Broad `try` blocks and same-type fallback exceptions hide real bugs by catching errors they weren't intended to handle, reporting failures at the wrong level.
<!-- rule:2939 -->
- Wrap multi-step DB writes in `transaction.atomic()` at the top-level action entry point (e.g., `execute()`, management commands, signal handlers) — not in per-item helpers like `_copy_page()`. This prevents partially persisted/inconsistent data on mid-sequence failure while avoiding a savepoint per item and the 2 extra queries `atomic()` runs even on no-op write paths. If you don't control the calling code path, document the caller's responsibility to open the atomic block. — Being clear about the placement matters: doing this in the wrong spot creates performance penalties.
<!-- rule:1944 -->
- Escape each interpolated value with its syntax's documented mechanism — `re.escape()` per element before joining with `|`, `json.dumps()` for pk/id values — instead of stripping reserved chars or hand-rolling a helper, since removal silently merges distinct terms and invites injection — Reserved characters carry meaning in the target syntax; deleting them collapses distinct inputs into the same pattern (e.g. `foo-bar` and `foo bar` becoming identical `tsquery` terms) and, for SQL, breaks out of the quoted template.
<!-- rule:1557 -->
- Use `with` for single-scope resources like `open(...)` or `ThreadPoolExecutor()` — calling `close()`/`shutdown()` on a context-managed resource double-frees and obscures intent — Three concrete patterns for resource lifetime management: (1) scoped resources use `with` and must not be manually closed, (2) multi-stage/error-path resources must outlive a scope and need explicit ownership, and (3) `mkstemp()` temp files pair creation with `finally`-based deletion to guarantee cleanup on failure.
  - Keep resources needed across multiple validation/processing stages or independent error exit paths outside `with` — scoped blocks close too early for these flows; use explicit open/close or ownership transfer
  - Create `mkstemp()` temp files inside the same `try` whose `finally` deletes them — cleanup still runs when later I/O or copying raises
<!-- rule:917 -->
- Split structured strings with an explicit `sep` and bounded `maxsplit` (e.g. `split(sep, maxsplit=n-1)`, `rsplit(sep, maxsplit=1)`) — stray delimiters otherwise cause unpacking errors, silent truncation, or bad parses. — Without an explicit `sep` and bounded `maxsplit`, extra occurrences of the delimiter either raise `ValueError` on unpacking or silently drop/misassign fields. Bounding the split keeps parsing deterministic across Wagtail Python modules (`wagtail/images`, `wagtail/api`, `wagtail/users`) and client TypeScript (`client/src`).
<!-- rule:1893 -->
- Guard raw/external/legacy/serialized data with `is not None` or explicit presence checks before indexing or attribute access — migrations and backports read rows written by older schemas, where fields/keys may be absent. — Prevents `TypeError`/`KeyError` crashes on historical data; current-version or UI invariants don't hold for stored data read from older rows.
<!-- rule:1163 -->
- Validate enum/choice-like inputs at API boundaries (`ChoiceField` with `choices`, or an up-front check) instead of silently accepting or ignoring invalid values — fail loud, since silent acceptance lets bad values propagate into stored data and only surface much later. — Silently accepting or ignoring invalid feature names or other allowed-value inputs for fixed/enum-value APIs lets callers believe a feature or option is enabled while the code runs without it, and any duplicated valid-option list drifts from the enum/choices source of truth. Validating explicitly at the API boundary and reporting the offending value with !r keeps the failure local and diagnosable instead of surfacing later as missing behavior or inconsistent configuration.
<!-- rule:2095 -->
- Match retrieval to invariants: `.get()` for rows that must exist, `filter(...).first()` + `None` handling when zero/many are valid — `get()` raises `MultipleObjectsReturned` on non-unique lookups — The category is error_handling and the scope is Django ORM queries. Each bullet keeps project-specific identifiers (`Locale`, `QuerySet.get()`, `values_list(..., flat=True)[0]`) and states the failure mode being avoided (`MultipleObjectsReturned`, missing DB row, `IndexError`), so an assistant can pick the right method instead of reflexively catching exceptions.
  - Re-fetch `Locale` with `QuerySet.get()` before saving when it came from a cache or non-standard path — guarantees DB existence; document this requirement for callers
  - Wrap `values_list(..., flat=True)[0]` in `try`/`except IndexError` and return the empty result — scalar lookups have no row-fallback
<!-- rule:268 -->
- Default every destructuring level for external payloads (`CustomEvent.detail`, `wagtail` rich-text entity attrs) — tolerating `undefined` keeps types stable and avoids repetitive `undefined` guards at each consumer — External producers don't guarantee optional fields, so `detail: { value = '' } = {}`, `status = 'success'`, and `text = ''` defaults at the extraction point prevent `TypeError`s instead of scattering `undefined` checks across every consumer. JS entity handlers must likewise tolerate missing attributes passed from `wagtail` Python rich-text handlers.
<!-- rule:1271 -->
- Never `pass` on a caught exception without logging — silent failures are undiagnosable in production. — Silently swallowed exceptions hide failures until they reappear as corrupted state, missing work, or confusing downstream errors, and losing the traceback and error details makes those failures hard to diagnose. Logging caught exceptions with logger.exception()/exc_info=True plus contextual identifiers keeps the failure connected to the operation or record that caused it, while concise logging for expected exceptions and explicitly intentional suppression prevents noisy logs without concealing known failures.
  - Log caught exceptions with `logger.exception()` or `exc_info=True` at ERROR level — plain `logger.error()`/`logger.debug()` drops the traceback.
  - Include context in exception logs (operation, URL/status code, model class/PK) — a bare traceback won't tell you which record failed.
  - Log the exception object itself, not `e.args[0]` — manual arg interpolation is fragile and hides the real message/type.
  - For expected exceptions, log a concise error instead of a full traceback — known failures don't need the extra noise.
<!-- rule:2465 -->
- Use `is None` checks, not truthiness, for absent values — `0`/`False`/`''` are valid and truthiness misclassifies them as additions/deletions in StreamField comparisons (`is_new()`, `is_deleted()`). — None
  - Prefer positive early-return guards for the non-`None` case over wrapping logic in `if/else` or explicit `if value is None: return None` branches.
  - Check `None` sentinels explicitly before unpacking — `try`/`except` around the unpacking masks unrelated `TypeError`s.
  - Keep defensive `None` checks even when the current block type can't produce `None` — future block implementations, custom variants, and manually rewritten data may introduce it.
<!-- rule:26 -->
- Never pass `None`/falsy values to `getattr`, `issubclass`, or `isinstance` — these built-ins validate args before any fallback, so `getattr(obj, None, default)` raises `TypeError` instead of returning `default`. — The built-in's own argument validation runs before `or`/default fallbacks, so unguarded `None` produces a `TypeError` at call time rather than falling through — silently breaking otherwise-fine settings flags (e.g. `wagtail.admin.views.generic`, `admin/widgets`, `blocks`) that happen to be unset. Short-circuiting also keeps the expression a clean boolean instead of raising mid-evaluation.
  - Resolve with a truthiness or `is not None` check first; for type checks, order conditions as `self.model_class and issubclass(self.model_class, Model)` so the expression stays a boolean rather than throwing.
<!-- rule:1552 -->
- Don't use `assert` for runtime validation — reserve it for internal invariants. Assertions are stripped under `python -O`, so they produce generic failures instead of reliable error handling. — Assertions are stripped under `python -O` and yield generic tracebacks rather than actionable errors. Distinguishing internal invariants (assert) from external boundary failures (explicit exception) from recoverable backend issues (documented warning) gives callers predictable, testable error contracts. Applies globally across `wagtail/utils`, `wagtail/contrib/redirects`, `wagtail/api/shared`, and `wagtail/wagtailsearch/backends`.
  For invalid external input, public API contracts, or OS/environment failures, raise explicit domain-appropriate exceptions (e.g., `BadRequestError`).
  For recoverable backend dependency/configuration issues, emit a documented warning (e.g., `RuntimeWarning` with an actionable hint) — don't raise, and don't translate third-party exceptions into `AssertionError`.
<!-- rule:1024 -->
- Resolve required attributes (constructor arg or class-level fallback like `model=None`) in `__init__`, raise `ImproperlyConfigured` on `None` *before* assigning instance attrs — surfaces misconfig at construction, not at request time — Collapsed to three tight bullets: (1) the `__init__` + `ImproperlyConfigured` ordering rule with the original `model=None` example preserved; (2) the fail-loudly/validate-eagerly rule keeping `new URL`, `import_string`, and the endpoint/API-key context; (3) the anti-permissive-guard guidance with its actual justification. Each keeps the project-specific identifiers and explains *why* rather than just prescribing.
  - Validate/parse required config eagerly (`new URL(...)` for endpoints, `import_string` for dotted paths, setup checks) and let errors propagate — don't swallow them or default to a hard-coded endpoint/API key
  - Skip permissive guards for attributes required class-wide — such guards falsely imply subclass configurability when most of the class would need overriding anyway
<!-- rule:270 -->
- Don't add error/fallback branches for empty or unreachable states — they hide real bugs and add dead code — Defensive handling for states that can't occur adds dead code, obscures real failures, and creates false 'error' paths (e.g. rejecting empty templates or demanding an `HTMLElement` when a `DocumentFragment` is legitimately empty). Removing these branches keeps `TeleportController` and template-based Stimulus controllers simpler — but verify alternate data paths first so a genuinely reachable state isn't left unhandled.
  - Treat an empty `DocumentFragment` from a template's `.content` as valid: don't reject empty templates or require an `HTMLElement`; let downstream append/reset logic (e.g. `resetValue=true`) handle emptiness
  - Skip user-facing error/fallback UI for states users can't reach in normal operation
  - Before deleting such a branch, confirm no other data path (imported rich text, API-generated data) can produce the state
<!-- rule:1528 -->
- Keep `Http404` and HTTP semantics in the view layer — model/generic/helper code returns `None` or an explicit sentinel instead, so it stays framework-agnostic and reusable. — Reusable model, generic, and helper code that raises Http404 or calls get_object_or_404 leaks view-specific 404 behavior into callers that only need a missing-object signal, so those callers get an unexpected HTTP exception instead of None or an ORM result. Views must then translate missing objects into 404 responses with safe, constrained lookups such as get_object_or_404(Model, pk=...) so missing objects do not become 500 errors, wrong-object matches, or inconsistent error messages.
  In views, translate missing results via a single-object lookup like `get_object_or_404(Model, pk=...)`, resolve required URL params directly (no redundant fallback branches), and pass a descriptive message when raising `Http404` manually.
<!-- rule:1177 -->
- Accept both `unique_together` and `UniqueConstraint` in mixin/abstract `check()` methods — raise only when *neither* is declared, so subclasses using either form aren't false-flagged during the staggered transition. — prevent false-positive validation errors in reusable mixins/abstract models
  - Match constraints by iterating `cls._meta.constraints` with `isinstance(...)`/`set(constraint.fields)` — field-tuple comparisons against `Meta.constraints` miss alternative representations.
<!-- rule:2322 -->
- Use `422 Unprocessable Entity` for syntactically valid but semantically invalid payloads (e.g. malformed rich text content), and reserve `400 Bad Request` for syntax or general bad requests in API exception handlers — lets clients distinguish validation failures from malformed requests. — Project convention applies across admin JSON endpoints and API v3 error handling (e.g. `wagtail/admin/views/pages/edit.py`, `wagtail/api/v3/errors.py`); a consistent 422-vs-400 split gives clients an unambiguous signal for retry/validation branching.
<!-- rule:1036 -->
- In Django system checks, separate the problem from the fix: put the problem description in `messages` and the remediation in the `hint` argument — keeps diagnosis and remedy distinct so users know both what's wrong and how to act. — Combines three related guidance points from the original rule into tight bullets, preserving the `UniqueConstraint`/`unique_together` example and the concrete phrasing example while adding *why* each matters (users need both diagnosis and remedy; deprecated examples mislead; vague hints don't enable action).
  Make each `hint` actionable: include a concrete, copy-pasteable snippet using the currently-recommended API (e.g. `UniqueConstraint` instead of `unique_together`) — deprecated examples send users toward code that will break again.
  Phrase hints unambiguously (name the exact issue, e.g. "spelling error" rather than "typed correctly") — vague hints leave users guessing at the fix.
<!-- rule:2469 -->
- Raise `NotImplementedError` for intentionally unimplemented or unsupported behavior instead of leaving `TODO`s or placeholder returns — makes failures explicit and prevents silent misuse. For abstract/base methods, name the method in the message (e.g. ``raise NotImplementedError(f"{type(self).__name__}.foo() must be implemented")``), document the return-value contract including edge cases, and add tests asserting the abstract contract raises `NotImplementedError` — so subclasses get clear guidance and regressions get caught. — Leaving a TODO or placeholder for intentionally unsupported behavior lets callers proceed with invalid results, while an abstract method that raises a bare NotImplementedError hides which method must be implemented. Explicit, informative errors and tests that verify the abstract contract prevent silent misuse and keep callers and implementers aligned on the intended contract, including expected return values and edge cases.
<!-- rule:1452 -->
- Aggregate all validation failures into one `Error` instead of failing fast — preserves per-item alignment (index-aligned or `map`-built nested arrays) so callers can report every bad item at once — Throwing on the first failure or emitting per-item warnings loses the item-to-error mapping; callers can't tell users which inputs were rejected without re-validating.
<!-- rule:2384 -->
- Read success/error from status codes, headers, or typed server markers — never sniff response bodies. Body-sniffing misreads valid empty or paginated responses and breaks silently when payloads change. — Reconstructing semantics from payload shape conflates transport success with application errors and produces false failures for legitimately empty responses.
<!-- rule:1189 -->
- In `clean_*`/`clean` methods, derive constraints from model field metadata (e.g. `_meta.get_field(...).max_length`) instead of hardcoding literals — keeps form limits in sync with the schema; reuse the value in both the check and the `forms.ValidationError` message, and never silently truncate input — Single source of truth for constraints; changes to model fields propagate to validation, and surfacing errors preserves user input.
<!-- rule:1452 -->
- Aggregate all validation failures into one `Error` instead of failing fast — preserves per-item alignment (index-aligned or `map`-built nested arrays) so callers can report every bad item at once — Throwing on the first failure or emitting per-item warnings loses the item-to-error mapping; callers can't tell users which inputs were rejected without re-validating.
<!-- rule:1746 -->
- Pass the raw `page` query param (default `1`) straight to Paginator methods like `get_elided_page_range` — letting `Paginator.validate_number`/`PageNotAnInteger` convert and validate avoids duplicating logic and keeps edge-case handling (`page=0`, out-of-range, non-integer) consistent with the framework. — Rephrased into two imperative bullets with the WHY (avoid duplicating framework validation, keep behavior consistent), preserved the specific Wagtail/Django references (`get_elided_page_range`, `Paginator.validate_number`, `PageNotAnInteger`, `page=0`, 200 vs 404), and formatted identifiers in backticks.
  - Cover pagination edge cases in tests, including `page=0`, out-of-range values, and non-integers — assert an out-of-range redirect returns 200 (not 404) and document the observed `page=0` behavior so future changes don't silently diverge.
<!-- rule:2616 -->
- Make nested registry lookups return `None` for any missing key — use chained `.get(key, {})` or `try`/`except KeyError` around the whole chain, never direct indexing. — Keeps the lookup contract stable regardless of registration state; a missing outer key shouldn't raise `KeyError` while a missing inner key returns `None`. Log a warning naming the missing key on `None` return so misconfigurations (misspelled/unregistered feature names) surface without becoming fatal.
<!-- rule:1469 -->
- Split config validation (startup) from request/input validation (runtime) — config errors should fail fast, input errors need domain-specific handling — Startup checks catch deployment misconfig before serving traffic (Django system check or `AppConfig.ready()`, raise `ImproperlyConfigured`); runtime checks raise domain-specific exceptions so callers can react to bad input instead of silently discarding it.
<!-- rule:2632 -->
- Match real CSS/XML/HTML grammars in parsing regexes, not convenient subsets — e.g. in `html_ruleset.py` accept `a[linktype=page]` and `a[linktype='page']`, but require quotes for XML `AttValue`; subsets silently misparse valid input or accept invalid markup — Rule portion is ~85 chars. The specific examples (`html_ruleset.py` file reference, CSS attribute selector variants, XML `AttValue` quote requirement) are preserved because they anchor the abstract principle to concrete project code. The why — silent misparsing of valid input and acceptance of invalid markup — makes the guideline behavioral rather than deontological.
<!-- rule:3090 -->
- Catch exceptions per item in batch management commands — one bad item shouldn't abort the whole run. Put `try`/`except` outside `transaction.atomic()` so the failed item rolls back and the loop continues. — Prevents a single failure from aborting the whole batch and keeps partial progress intact.
<!-- rule:1852 -->
- Compare stored timestamps (e.g., `instance.timestamp` vs `live_revision.created_at`) to determine recency—IDs aren't monotonic across revisions/logs — Revision and log IDs can diverge from creation order after migrations, backfills, or multi-database writes, so ID comparison silently marks newer entries as older.
<!-- rule:2481 -->
- Detect arg mismatch via `inspect.signature` in BC shims calling overridden/third-party methods, not broad `try/except TypeError` — the broad catch masks genuine `TypeError`s raised inside the callee — Broad `try/except TypeError` around a BC shim's call to an overridden/third-party method swallows not just the expected 'unexpected keyword argument' case but also real bugs inside the method, hiding failures behind a silent fallback. Explicit signature inspection via `inspect.signature` targets only the intended backward-compat case, and unrelated `TypeError`s should be re-raised unchanged.
<!-- rule:2523 -->
- Config-dependent warnings: lead with user-visible impact, cite the exact setting (`settings.DEBUG=False`) not 'production' — pinpoints the trigger. — Vague labels like 'production environment' leave users guessing which setting caused the changed behavior; naming the exact value makes the warning directly actionable.
<!-- rule:2703 -->
- Prompt before writing into an existing destination directory in CLI commands (e.g. `wagtail start`) — silently overwriting surprises users and can destroy their files. — Prevents accidental data loss and matches user expectations for destructive operations.
<!-- rule:1339 -->
- Pass defined, non-empty values for `aria-label` and other accessibility attrs to template partials — Django renders undefined context variables as empty strings, yielding silently inaccessible controls
<!-- rule:1306 -->
- Format aggregated form errors manually — strip `*` markers, join with commas, drop `__all__` — `form.errors.as_text()` leaks bullet markers and the internal `__all__` sentinel key into import/redirect views, producing noisy user-facing messages.
<!-- rule:2141 -->
- Build parallel lists and parameter arrays (e.g. SQL column lists + value params) in the same loop — matching lengths by construction, no bookkeeping needed — Aligning by construction eliminates a whole class of `len(a) != len(b)` bugs and the defensive checks needed to guard against them. Padding with `NULL`/placeholders obfuscates which values are real, and silent correction masks the underlying defect at the call site.
  - Never pad a shorter parallel list with `NULL`/placeholders — forces redundant length checks and masks real misalignment bugs
  - If misalignment is genuinely possible, raise an explicit error instead of silently correcting it — silent fixes hide the actual bug
<!-- rule:965 -->
- Guard `.focus()` calls: null-check `querySelector` results and early-return when a menu/component has no focusable items — avoids `TypeError` crashes on dynamically rendered DOM that may render empty. — Dynamically created or conditionally rendered menus/lists can legitimately produce `null` from `querySelector` or contain zero focusable children; calling `.focus()` unguarded throws and breaks rendering.
<!-- rule:838 -->
- Catch `Exception` (not `OSError`) when calling pluggable storage backends like `.size` — S3 and other non-local backends raise types outside `OSError`; re-raise `SystemExit`/`KeyboardInterrupt` so they aren't swallowed. — Non-local storage backends (e.g. S3) surface failures as non-`OSError` exceptions, so narrow catches silently miss real errors; `SystemExit`/`KeyboardInterrupt` must propagate to preserve user interruption semantics.
