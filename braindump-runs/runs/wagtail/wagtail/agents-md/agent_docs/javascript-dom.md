# JavaScript & DOM Patterns

> Rules for client-side JS: native APIs, DOM selection/state, event listeners, class/dataset usage, string/replace idioms, and controller lifecycle.

**When to check**: When writing or editing client-side JavaScript or DOM manipulation code.

## Rules

<!-- rule:1966 -->
- Prefer native browser APIs over jQuery/`XMLHttpRequest` in frontend JS: `fetch` for requests, `document.querySelector`/`querySelectorAll` for lookups, `addEventListener` for events, and `classList`/`setAttribute`/`element.checked` for DOM mutation — trims the jQuery dependency and keeps new code on the platform APIs. — Preserves the project-specific surfaces the rule spans (admin templates, telepath widgets, public APIs) and the exact native API replacements, so an assistant can apply the swap mechanically rather than guessing which jQuery method maps to what.
  - Apply this in any file you're already touching, including admin templates, telepath widgets, and public APIs, and remove the now-unused `import $ from 'jquery'` — incremental migration costs nothing extra when the file is open anyway.
  - Keep jQuery/`XMLHttpRequest` only when a concrete capability requires it (e.g. `XMLHttpRequest` upload progress) or an unsupported-browser polyfill is needed — otherwise the native equivalents already cover the use case.
<!-- rule:259 -->
- Use ES6 template literals (` `${x}` `) for interpolation and dynamic strings; reserve `+` for arithmetic — mixing `+` into string building invites `"1" + 1 === "11"` bugs and obscures intent. — When `+` is used to build strings with dynamic values, it becomes ambiguous with arithmetic and hides interpolation mistakes that template literals make explicit. Conversely, wrapping static strings or already-string values in template literals adds noise, obscures intent, and makes readers search for interpolation that is not there.
<!-- rule:150 -->
- Use `data-*` attributes as JS behavior hooks and `class` for styling only — keeps HTML/tag changes from breaking interactions — Concise bullets in imperative mood. Preserves project-specific selectors and identifiers (`[data-form-side]`, `header [data-w-slim-header-buttons]`, `:not(.deleted)`, `DEFAULT_CLASS`). Each bullet carries why: prevents breakage, prevents silent failures, prevents CSS/JS drift. Stays within the frontend scope without re-stating it.
  - Select behavior targets with dedicated `data-*` selectors (e.g. `[data-form-side]`, `header [data-w-slim-header-buttons]`), not CSS classes, IDs, structural selectors (`ul > li > a`), tag selectors (`li`), or stacked negative class filters; update the JS selector constant when the hook changes
  - Prefer robust selectors (`data-*`, stable IDs, global refs, state pseudo-classes like `:not(.deleted)`) so DOM restructuring doesn't silently break behavior
  - Fall back to a class/ID/element selector (or scope to a stable container) only when no `data-*` hook is practical, and note it as a documented deviation
  - When a selector must use a shared class constant, interpolate it (e.g. `.${DEFAULT_CLASS}`) instead of hardcoding the literal — prevents drift between CSS and JS
<!-- rule:666 -->
- Initialize UI components at lifecycle points where DOM and state are ready — never gate readiness with `setTimeout`/async callbacks. In React, put state-driven DOM side effects (e.g. focus after menu opens) in a `useEffect` keyed on that state, not in handlers with delays. Delays are timing guesses that break under variable load and hide real race conditions. — Preserves project-specific guidance (React function components, `useEffect`) while making the intent actionable.
<!-- rule:1269 -->
- Use `Object.hasOwn(obj, key)` and `for...of` over `Object.keys()`/`Object.entries()` instead of `Object.prototype.hasOwnProperty.call(obj, key)`, `obj.hasOwnProperty(key)`, or `for...in` with an own-property guard — `for...in` walks the prototype chain and `obj.hasOwnProperty` can be shadowed or overridden, so the modern forms are prototype-safe without a manual guard. — Prototype-safe own-property access and iteration; avoids shadowed/overridden `hasOwnProperty` and inherited-key bugs in JS objects, including plain data objects from `JSON.parse` and client/API payloads.
<!-- rule:245 -->
- Pair every `addEventListener`/`.on` with a matching `removeEventListener`/`.off` in the component's delete/unmount teardown — even when the DOM node is being removed — to prevent leaks and stale callbacks — Unremoved listeners leak memory and fire stale callbacks against detached or rebound DOM nodes; anonymous inline handlers can't be unbound at all, and mismatched refs/options silently fail to detach.
  - Remove previously-attached listeners before re-binding handlers or detaching their elements — avoids duplicate handlers firing
  - Register a stable named handler (e.g. a method bound once in the constructor) instead of an anonymous inline function, and remove it using the exact same callback reference and options (e.g. `{ capture: true }`) — only identical refs/options unbind
<!-- rule:1901 -->
- Keep `function` expressions for callbacks relying on dynamic `this` (jQuery `.each()`, `.map()`, `.on()`) — arrows capture `this` lexically and silently break element-specific behavior; use `event.currentTarget` if you need an arrow. — Arrow functions inherit `this` from the enclosing scope, which is almost never the matched element inside jQuery handlers — a silent runtime bug rather than a lint error.
<!-- rule:1958 -->
- Write CSP-safe code and docs examples: avoid `eval`, inline `on*` handlers, and `javascript:` URLs — CSP silently blocks them at runtime; use external listeners, `data-*` attrs, or nonce-friendly patterns instead — Applies to Python, templates, and markdown examples alike, since docs snippets get copied verbatim into templates and would break under a CSP.
<!-- rule:458 -->
- In JS class methods, use `this.<field>` for instance fields and `this.constructor.<member>` or `ClassName.<member>` for statics — bare identifiers or `this.<member>` on a static silently resolve to the wrong scope (`undefined`), as seen across `DismissibleController.ts` and `telepath/widgets.js`. — A bare identifier or a `this.`-prefixed static lookup doesn't throw — it just reads `undefined`, so the bug surfaces far from the class method that caused it. Being explicit about the receiver keeps instance vs. static access distinct and makes failures loud instead of silent, which matters across the shared `client/` JS/TS code (`DismissibleController.ts`, `telepath/widgets.js`, admin `telepath/widgets.js`).
<!-- rule:1926 -->
- Read selection/UI state from native form controls (`checked`, `selected`, jQuery `:checked`) instead of mirroring it in `data-*` attrs or parallel JS state — a single source of truth can't drift; when tracking elements, keep the DOM node reference, not a parsed dataset value — Duplicated state and dataset round-trips desync from the DOM (e.g. after a user click or form reset), causing stale selections in admin templates, form previews, and bulk-actions JS.
<!-- rule:152 -->
- Use `classList.add`/`remove`/`toggle` instead of reassigning `element.className` — reassignment silently drops every other class on the element — DOM class state is additive; `className =` overwrites it, `toggle`'s second arg makes the boolean the single source of truth, and exclusive modifiers must be cleared to avoid conflicting styles.
  - Prefer `classList.toggle(className, condition)` over `if`/`else` calling `add`/`remove` for the same class — one code path, no drift between branches
  - For mutually exclusive modifier classes, remove the sibling modifiers before adding the active one — otherwise stale modifiers stack up
<!-- rule:734 -->
- Default to `const`, use `let` only when reassignment is needed, and never `var` — prevents accidental rebinding and hoisting bugs; declare at first assignment rather than pre-declaring to keep scope tight. — Block-scoped `const`/`let` catch reassignment and temporal-dead-zone errors that `var` silently permits, and declaring at first assignment keeps values close to their use, avoiding `undefined` gaps.
<!-- rule:1439 -->
- Init browser entrypoints with `document.addEventListener('DOMContentLoaded', ...)` or the shared `domReady` utility, **not** `window.onload`/`load` — the load event waits on all assets and can miss or double-run init — Condensed into five imperative bullets that preserve the key identifiers (`DOMContentLoaded`, `domReady`, `window.onload`/`load`, React render, top-level scope, global namespace) and the existing-element exception, while adding the *why* for each (asset-timing, duplicate init, namespace pollution). Split into bullets because it covers distinct behaviors (event choice, registration site, helper placement, deferred queries, exception) that AI editors need to apply selectively.
  - Register DOM-ready handlers once at module/top-level scope, never inside functions that can re-run (e.g. React render) — repeated registration leaks listeners and duplicates init
  - Put init logic and its helper functions inside the callback — keeps them out of the global namespace
  - Also wrap queries for template content that may not exist yet in a DOM-ready handler so they run after main content is available
  - Exception: if the init function already receives an existing DOM element, call it directly instead of deferring to a ready listener
<!-- rule:872 -->
- Reuse the existing dirty-form check for change detection and lazy-submit dedup, and cache the serialized form state across comparisons — re-serializing or rebuilding `FormData` per call makes repeated diffs quadratic and drifts from the canonical check. Preserve intentional re-submission; document any divergence or added optimization. — Two bullets split the general dirty-form/dedup rule from its specific Wagtail admin preview instance. Preserves key identifiers (`FormData`, dirty-form check, Wagtail admin form preview, `keyup`, `MutationObserver`) and gives a concise why for each: quadratic re-serialization / canonical-check drift, and missed programmatic updates.
  - In the Wagtail admin form preview auto-update, poll and diff serialized `FormData` using the same serializer as the dirty-form check, seeding the baseline to an empty value rather than the current form state — change/`keyup` listeners and `MutationObserver` miss programmatic and async updates.
<!-- rule:490 -->
- Return native `Promise<T>` and use plain `resolve()`/`Promise.withResolvers()` instead of custom thenables or `resolve(undefined)`; custom Promise machinery breaks `instanceof Promise` checks and cross-library interop. — Native Promises interoperate with async/await, `Promise.all`, and library code that relies on `instanceof`; custom thenables and redundant wrappers silently diverge from the native contract typed by `Promise<T>` signatures.
<!-- rule:77 -->
- When `@typescript-eslint/no-use-before-define` is triggered, reorder the code so the referenced function or const is declared before its first use instead of adding an `eslint-disable-next-line` (or similar) suppression comment. Prefer this reordering for both function declarations and handler/const declarations. — This is a general TypeScript/ESLint code-style behavior, not a module-specific or entity-specific rule. It describes how to resolve `@typescript-eslint/no-use-before-define` violations anywhere in the codebase (function declarations and handler/const declarations), which applies to any TS/JS file rather than a single module. Although the observed PRs are concentrated in `client/`, the rule is language-wide and behavioral, so placing it at the repository root (`AGENTS.md`) maximizes findability and reuse across the codebase.
<!-- rule:158 -->
- Match DOM lookups to intent: use `getElementById` for known IDs (fastest, keeps references consistent with related config), `querySelector` for the first match (never `querySelectorAll(...)[0]`, which scans the whole DOM), and `querySelectorAll` only when aggregating over all matches — Using the wrong lookup wastes work (full DOM scan + array indexing) and diverges from how related config references elements by ID, causing inconsistency across modules.
<!-- rule:2181 -->
- Before re-rendering, remove any previously-appended node via its stable `data-*` selector — prevents duplicate/stale DOM when a routine runs more than once — Rendering routines that run multiple times, or chains of sequential DOM mutations, leave duplicate, stale, or dead nodes in the DOM if prior output isn't cleared by a stable selector before re-appending, if mutations are made only to be overwritten by `innerHTML`/`.html()`, or if a fragment carrying the target's own root is written via `.html()` instead of `.replaceWith()`. These patterns produce visual glitches, memory leaks, and event-handler duplication that only surface on re-render.
  - Skip DOM mutations that a following `innerHTML`/`.html()` call immediately discards — the work is dead and hides stale nodes
  - Use `.replaceWith(fragment)` rather than `.html(fragment)` when the fragment includes the target node's own root element — `.html()` would nest a duplicate root instead of replacing it
<!-- rule:3020 -->
- Mount dialogs at `document.body` or end-of-DOM, not inline — keeps positioning/stacking predictable across `client/src/includes/dialog.js` — Dialogs rendered inline inherit ancestor `overflow`, `transform`, and `z-index` stacking contexts, which breaks overlay positioning unpredictably. Mounting at a predictable document root in `client/src/includes/dialog.js` avoids this. The exception exists because panel-scoped dialogs should stay within the panel's DOM for correct lifecycle and focus behavior.
  When a dialog is intentionally scoped to a surrounding panel, insert it adjacent to its triggering template/container instead.
<!-- rule:661 -->
- Access browser and third-party globals as `window` properties (e.g. `window.docsearch`, `window.READTHEDOCS_DATA`, `window.location`) rather than bare identifiers — this satisfies ESLint's `no-undef` in `docs/_static/js/` and elsewhere without adding suppressions. When another rule bans the API itself (e.g. `no-alert`), still qualify it as `window.alert` and disable only that rule with `// eslint-disable-next-line no-alert` — never suppress `no-undef`. — Keeps ESLint's `no-undef` passing without blanket suppressions, so real undefined-variable bugs stay detectable while `no-alert` and similar intentional bans are disabled narrowly and precisely.
<!-- rule:265 -->
- Use ES6 property shorthand (`{ key }`, not `{ key: key }`) and name params after the target property — matches the idiomatic style across the `wagtail` JS and client TypeScript code. — Keeps object literals terse and lets variable/parameter names document the property they populate, avoiding redundant `key: key` noise that reviewers flag.
<!-- rule:2876 -->
- Build `SelectionState` atomically with `new SelectionState({ anchorKey, anchorOffset, focusKey, focusOffset })` — `createEmpty()` + chained `.set()` leaves the selection transiently inconsistent and is easy to desync — Atomic construction plus anchor-then-focus ordering ensures the selection is never in an inconsistent intermediate state, and keeps related fields grouped for readability. Applies to any Draft.js `SelectionState` construction, including in `client/src/components/Draftail/CommentableEditor/CommentableEditor.js`.
  - Order `SelectionState` fields and grouped `.set()` calls anchor-pair before focus-pair (`anchorKey`/`anchorOffset`, then `focusKey`/`focusOffset`) rather than interleaving start/end — mirrors Draft.js semantics and keeps selections readable in diffs
<!-- rule:247 -->
- Use one-shot registration (jQuery `.one()` or `addEventListener(..., { once: true })`) for handlers that should fire only once — avoids manual cleanup and duplicate-firing bugs
<!-- rule:1440 -->
- Declare lookup tables as `static ... as const` class constants, not per-instance or in-method maps — builds once and keeps the mapping in one place. Reference from instance code via `(this.constructor as typeof ClassName).xOptions[key]` when TS can't infer the concrete class for `this.constructor`. — Class-level constants avoid rebuilding mapping objects per instance or per call, and let subclasses override mappings via `this.constructor` without extra plumbing.
<!-- rule:1267 -->
- Prefer regex literals over `new RegExp(...)` for static patterns — literals avoid double-escaping bugs and read clearly — Two related concerns: (1) a literal is the shortest, least error-prone way to express a fixed pattern, while `new RegExp(...)` should be reserved for patterns assembled at runtime (e.g. from user input or config); (2) in hot loops, constructing/compiling the same regex on each call is pure overhead — compiling once at module scope amortizes the cost and keeps the pattern in one place. Applies to both `client/src/utils/urlify.ts` and `wagtail/admin/rich_text/converters/html_to_contentstate.py`.
  - Hoist regexes used in repeated code paths to module level (e.g. `re.compile` in Python) — recompiling per call wastes CPU
<!-- rule:805 -->
- Derive search/submit controller params from rendered markup and URL state: — 
  - Read the query param name from the input's `name` attribute rather than a hardcoded value — keeps the config reusable across forms and in sync with the template.
  - Serialize the containing form, then merge that result with the current URL query params — preserves active filters instead of overwriting them.
  - Keep the default/no-JS submit pointed at the full-page results endpoint; reserve partial HTML fragments for the JS-enhanced interaction — progressive enhancement degrades cleanly.
<!-- rule:1402 -->
- Derive badge counts and their visual state from the same stable count value — indirect sources like `collection.length` or Stimulus target/DOM scans go stale because `Tippy` detaches or hides closed content. — 
<!-- rule:2820 -->
- Guard against unusable values with truthiness checks (`if (!store[key])`) for lookups, mappings, and `dynamic config-map` keys, and with `in` + `typeof x !== 'undefined'` for feature detection — never compare identity against `null`/`undefined`, since absence and unusability rarely line up and identity checks silently pass on empty-but-invalid values. — Checking usability rather than identity catches unset, missing, and empty-but-present values in one branch, so `selector/store` lookups, Wagtail `admin` config keys, and `client` feature detection don't fail open on falsy-but-present values or break when a property exists with an `undefined` value.
<!-- rule:2240 -->
- Prefer `.at(0)`/`.at(-1)` and `Object.values()` over index math or manual loops — avoids off-by-one bugs — Built-in accessors like `.at(-1)` replace `array[array.length - 1]`, and `Object.values()` replaces loops tracking first/last values; both read cleaner and eliminate the off-by-one errors that manual index arithmetic invites.
<!-- rule:1471 -->
- Don't add dummy `href="#"` to pass `jsx-a11y/anchor-is-valid` — bind a real URL or disable the rule at file level — Fake hrefs ship broken links and inflate perceived a11y compliance. In test files and `.stories.tsx`, bind real URLs via story args (e.g. `args.url`), a shared URL variable, or an in-page fragment matching an existing section `id`. If a custom link intentionally diverges from anchor semantics, add a file-level `/* eslint-disable jsx-a11y/anchor-is-valid */` instead of a fake `href` or changing component behavior.
<!-- rule:1810 -->
- Clean up state in the callback that deactivates it (e.g., clear timers when `loading` → `false`) — otherwise timers and subscriptions outlive the state and leak — Tying teardown to the same transition that ends the state keeps lifecycle symmetric; scattering cleanup elsewhere leaves stale timers running after the state is gone.
<!-- rule:1844 -->
- Default a form's `method` to `'GET'`, then uppercase it before comparing against uppercase HTTP method constants like `'GET'` — missing values become `undefined` otherwise, and the Fetch spec matches methods byte-uppercased, not as HTML form values. — Prevents `undefined` methods and case mismatches; Fetch normalizes methods to byte-uppercase, unlike the HTML form spec.
  - Applies anywhere a `fetch()` request is built from a form's `method` value (e.g. `client/src/controllers/SwapController.ts`).
<!-- rule:108 -->
- Rewrite once this way: — This keeps DOM attribute mutations explicit and targeted rather than batched/implied. Processing independent attributes in their own read-transform-write sequence prevents stale-read bugs and makes each change traceable; when iterating a collection (e.g. `querySelectorAll` results), writing only after confirming the element's ID/selector means unrelated nodes are never accidentally modified.
  - Read-transform-write each DOM attribute separately; guard collection writes with an ID/selector check — sequential blocks avoid stale reads, and the selector guard leaves non-matching elements untouched instead of silently mutating them
<!-- rule:1265 -->
- Use `str.replace(pattern, replacement)` — the source string is already the receiver, so passing it as an argument silently no-ops the replacement. — `String.prototype.replace` is called on the source string; supplying it again as the first argument instead of the search pattern produces no match and hides the bug.
<!-- rule:1403 -->
- Use `CountController`'s built-in conditional class states (`active`, `max`, `over`) and label/count-output features for selection-count UI instead of ad-hoc class additions, custom rendering, or custom class-toggling JS. — Keeps count UI consistent across choosers and avoids duplicated state logic that drifts from `CountController` behavior.
<!-- rule:1979 -->
- Guard controller lifecycle methods with `isReady`/`this.ready` early-returns, not `after(fn, n)` — call counts break when lifecycle order changes — readiness flags are self-documenting and robust to extra or reordered calls
<!-- rule:2508 -->
- Recalculate derived UI state (visibility, enabled, action states) in your page-load/init handler — browsers restore form values without firing `change`, so relying on events alone leaves the UI out of sync. — Firefox/Chrome restore form values on reload/back-forward without dispatching `change` or `input`, so handlers bound only to those events render stale visibility/enabled/action state. Deriving state from control values during init guarantees the rendered interface matches the restored values. Applies to any JS/HTML init handler that reads form controls — e.g. `wagtailforms/index_submissions.html` and similar pages.
<!-- rule:2728 -->
- Handle both `Space` and `Enter` in keyboard activation handlers for button/toggle elements — browsers fire both on native buttons, so ignoring one breaks expected accessibility behavior — 
<!-- rule:2912 -->
- Don't `Number()`-coerce `dataset`/`data-*` values used as IDs or keys — keep them as strings unless the data contract guarantees numerics and numeric behavior is required. — `dataset` is always strings; coercing IDs breaks `Map`/object lookups keyed by string, drops leading zeros, and silently loses precision on large numeric IDs.
<!-- rule:2906 -->
- Use `React.Children.count(children) > 0` to detect received children — `children` can be `[]` (so `!== null` fails) and `ReactNode` has no guaranteed `.length` (triggers `TS2339`) — React `children` is `ReactNode`, which may be an empty array, single element, string, boolean, or number — so `children !== null` and `children?.length > 0` are both unreliable.
<!-- rule:1266 -->
- Order chained `String.prototype.replace` calls specific-before-broad — a broad/substring pattern can match inside a literal you intend to remove, silently corrupting the output. — Broad replacements applied first may consume or partially alter substrings that a later specific removal expects to match, producing corrupted strings.
<!-- rule:2727 -->
- Use shared key constants from `core.js` (e.g., `wagtail.keys.ESC`) instead of hard-coded numeric `keyCode` values — names the intent and survives keycode deprecation — Numeric `keyCode` values are opaque at the call site and deprecated in the DOM spec; referencing named constants from `core.js` keeps keyboard handling self-documenting and consistent across modules.

- Name reconciling controller methods with a `sync*` prefix and declare sync params like `data-w-sync-bubbles-param` as other forms do — mismatched conventions silently break pairing between controllers and forms. — ...
<!-- rule:3022 -->
- Resolve data-attribute CSS selectors with `Element.closest(selector)` and bind related listeners (hover/mouseleave) to that nearest matching ancestor — consumers can pass any valid selector, and behavior targets the element they chose instead of an assumed fixed parent. — Using `closest()` instead of an assumed parent keeps the component composable: any valid CSS selector works, and events fire on the element the consumer actually targeted rather than a hardcoded ancestor.
<!-- rule:736 -->
- Scope JS locals to their consuming function; hoist call-invariant constants — avoids per-call recompute — Runtime-dependent values belong in the smallest scope that uses them, but constants derived from the enclosing context shouldn't be recomputed on every invocation — hoisting them out keeps hot paths cheap and intent clear.
<!-- rule:1963 -->
- In JSX, write static string props as string literals (e.g. `className="foo"`), not wrapped in expression containers (e.g. `className={'foo'}`). — This is a general JSX code-style convention, not specific to a single component, file, or module. Although the observed evidence comes from client/src/components/Explorer/ExplorerHeader.js, the rule applies to all JSX attributes wherever they appear and was originally scoped globally. Placing it in the root AGENTS.md makes it discoverable for any AI assistant working anywhere in the repo and avoids overfitting a global style preference to the one directory where it was first observed.
