# Python Code Style and Readability

> Pythonic style and readability: avoiding redundant coercions, pathlib I/O, constants, short keyword formatting, repeated lookup variables, DRY normalization, direct access, string/regex transforms, class ordering, list mutation, declarative argument lists, numeric formatting, path parsing, generator wrapping, grouping, regex precision, pass usage, and list-vs-tuple conventions.

**When to check**: When writing or reviewing Python code for style, clarity, formatting, normalization, and idiomatic constructs.

## Rules

<!-- rule:3617 -->
- Avoid redundant `str()` coercion when the type contract is met — e.g., write `str(escape(x))`, not `escape(str(x))` — keeps typing consistent across keys and values — Once a value is converted, operate on the converted variable: don't wrap equality operands already strings, don't nest a conversion inside a helper that already coerces its argument, and drop truthiness checks whose else-branch returns the value unchanged. Redundant conversions add noise, obscure intent, and can silently change object identity — reusing a mapping's original keys avoids mixed key/value types downstream, and coercing keys and values together keeps the shape consistent.
  - Preserve original objects (e.g., a mapping's keys reused as keys); coerce only when a string is explicitly required (e.g., Windows environment variables)
  - Apply coercion to keys as well as values to avoid mixed key/value types
<!-- rule:1024 -->
- Prefer `pathlib` text-mode I/O (`Path(...).read_text()` / `write_text()`) over `open()` + `.read()`/`.write()`, and write strings in text mode (`open(path, 'w')`) rather than binary mode + `.encode('utf-8')` — fewer call sites, no manual encode/decode. — Rationale embedded above: consolidating on pathlib text-mode APIs keeps file I/O consistent and avoids the encode/decode mistakes and non-UTF-8 regressions that arise from hard-coding `utf-8` on user paths.
  - Pass `encoding='utf-8'` only when content is known UTF-8 (project-bundled files, or replacing a `bytes.decode()` that defaulted to UTF-8); omit `encoding` for user-configurable paths so the platform/locale default doesn't regress non-UTF-8 files.
  - Apply this idiom at every similar I/O site — mixing styles across the codebase causes inconsistent encoding behavior and confusion.
<!-- rule:578 -->
- Hoist shared or derived constants to module scope and reuse them; keep single-function values local — re-deriving constants like `SESSION_HASHED_KEY_PREFIX` at each use site risks drift, while hoisting one-offs (e.g. test-validated `reason.startswith("...")` literals) pollutes the module namespace. — Composite constants built from constituents (e.g. `SESSION_HASHED_KEY_PREFIX = SESSION_HASHING_ALGORITHM + SESSION_KEY_DELIMITER`), static lookup tables, and formatted message prefixes that double as matching keys should live at module scope and be reused so parallel definitions cannot diverge. Values only used within a single function — including one-off prefix checks whose literal wording is asserted by tests — stay function-local to avoid polluting the module namespace.
<!-- rule:1098 -->
- Keep short keyword args on the same line as the call/definition when they fit — e.g. `RelatedModel.objects.create(simple=cls.s1)`, `parser.add_argument()`; keeps formatter output stable and diffs minimal — These conventions are what the project's formatter (Black-style) produces, so writing code this way matches `git` diffs and CI checks; stray trailing commas in `widget=` declarations in particular trigger unwanted multiline reformatting of Django form fields.
  - In Django form fields, keep short `widget=...` calls (e.g. `forms.RadioSelect(attrs={"class": "..."})`) on one line and omit the trailing comma after the final arg — a trailing comma makes the formatter force the whole field declaration multiline
  - When a call would exceed the line-length limit, move the offending arg (e.g. `fail_on_restricted`) to its own continuation line — avoids over-length lines without reformatting the rest
<!-- rule:4918 -->
- Bind repeated subscript lookups to a named local — Re-indexing `d[a][b]` or `dict[key]`/`dict.get(key)` more than once in a block hides intent and risks drift if the key expression changes — bind once to a descriptively named local and reuse it.
<!-- rule:3766 -->
- Centralize shared normalization in helpers like `clean_name`; hoist repeated conversions into locals — avoids drift when logic changes and prevents redundant work in loops. After refactoring, drop now-redundant ops (e.g. `('%s' % x).strip()`, re-applied `tuple(...)`/`list(...)`). — Duplicated path/name normalization (whitespace stripping, slash conversion, prefix removal) and inline conversions (`tuple(value) if isinstance(value, list) else value` become inconsistent as they evolve across call sites, and recomputing per-iteration wastes work in hot paths like `db/models/` or `http/request.py`. A single `clean_name`-style helper keeps behavior aligned, and removing stale normalization (e.g. `('%s' % x).strip()`) prevents double-processing bugs after refactors.
<!-- rule:297 -->
- Prefer direct attribute/property access over temp vars and wrapper functions — cached, side-effect-free reads gain nothing from indirection — These rules keep attribute access expressive and honest about side effects: cached reads don't need indirection, side-effect-only statements don't need assignment, and side-effecting helpers shouldn't be called just to unwind their effect. Commenting and testing non-obvious side effects (especially when a direct assignment becomes a setter/helper) prevents silent breakage in remote callers.
  - Use bare attribute access for side-effect-only statements; extract long repeated property chains to a local variable for readability
  - Replace side-effecting helpers with direct operations rather than calling then undoing — undoing hides the coupling and invites bugs
  - Comment non-obvious side effects/ordering constraints, and add a test when swapping direct assignment for a setter/helper — prevents silent breakage in callers
<!-- rule:184 -->
- Make `__str__` return a plain `str` — never `.encode()`, never recurse via `str(self)` — `.encode()` yields `bytes`, which raises `TypeError` when Python 3 expects `str`; calling `str(self)` (or `text_type(self)`) inside `__str__` recurses infinitely. Return the underlying string directly or delegate to a non-`__str__` helper, and keep a single `__str__` rather than a parallel `__unicode__` path so both Python 2 and 3 resolve to the same method.
<!-- rule:393 -->
- Compose string/regex transforms into one ordered expression (e.g., `replace(...).strip()`, `delimiter.join(...)`, one regex with groups) — chained rewrites are order-dependent, so keeping them adjacent avoids breakage from earlier edits and shows intent without variable churn. — String/regex transformations in this codebase (e.g., `django/contrib/postgres`, `django/db/backends/sqlite3`, `django/utils/ipv4`, frontend JS) rely on steps executing in a fixed order — composing them into one expression keeps that order visible; split reassignments or ad-hoc helper calls make it easy to reorder or skip a step and silently change output. Loops and `split()`-filter-`join()` idioms do the same job with more surface area to get wrong.
  - Inline trivial one-off ops like a single `re.sub()` at the call site; in small pure helpers return the composed transformation directly instead of reassigning the parameter and returning it.
<!-- rule:4318 -->
- Strip whitespace and use `str.casefold()` for case-insensitive comparison (e.g. `value.strip().casefold()`); use the same normalized form when checking whether a value differs from its default during serialization or display — `str.lower()` mishandles Unicode (e.g. `"ß"`, Turkish `"I"`) and unstripped whitespace makes `"Value "` spuriously differ from `"value"`, causing wrong writes and inconsistent output — `str.casefold()` handles Unicode case folding that `str.lower()` misses, and stripping surrounding whitespace prevents spurious mismatches when comparing against defaults or user input. Applying the same normalized comparison in both comparison and serialization/display paths keeps behavior consistent across `db/migrations`, `db/models`, `utils`, `core`, and `contrib/postgres`.
<!-- rule:3978 -->
- Order top-level classes by relationship, not alphabetically: base class first with its subclasses adjacent, and any class before the classes that reference it; fall back to alphabetical only for unrelated classes. — Preserves logical grouping (base→subclass, dependency order) over alphabetization, matching the convention in Django's `django/db/models/functions/` and `contrib/postgres/` modules so readers can follow class hierarchies in place.
  Rationale: Keeps dependency and subclass relationships scannable in-file, matching how existing pairs are ordered in modules like `django/db/models/functions/*.py` — reordering a base past its subclasses hides the hierarchy and breaks the convention contributors rely on when mirroring an existing pair.
<!-- rule:980 -->
- Mutate existing lists in place: use `list.extend(iterable)` or `list += iterable` for multiple items, and `existing.extend(expr for item in iterable)` for transformed items — avoids allocating a new list and avoids quadratic copying from `list = list + other` in loops — In-place `extend`/`+=` avoid allocating and discarding a temporary list on every concatenation, and prevent the O(n²) copying that `list = list + other` causes inside loops. This convention is applied repo-wide (e.g. `django/utils`, `django/db/models`, `django/template`, `django/forms`) so readers can rely on existing lists being extended rather than rebound.
<!-- rule:890 -->
- Use `pass` only for syntactically empty bodies; never add it when a docstring or code is already present. — `pass` alongside a docstring or code is dead weight and signals confusion about whether the body is empty. For intentionally empty bodies, prefer `pass` over `...` or `return None` and add a short comment — this makes the no-op deliberate rather than a placeholder someone forgot to fill in.
<!-- rule:5124 -->
- Build call and subprocess arg lists declaratively — inline single-use positionals (`fn(*it)`), splat reused or conditionally-built tuples/lists (`fn(*args)`), and form `argv` as one list expression (`['tool', *args[:-1], ...]`) instead of mutating with `pop()`/`extend()`. — Duplicated call sites and mutable intermediates drift out of sync and obscure the final argument shape, so declarative splats keep call/argv construction in one place and reviewable.
<!-- rule:5261 -->
- Use numeric format specifiers (`%04d`, `f'{n:_.{p}f}'`, `'{:0<6.6}'.format(v)`) for zero-padding, fixed width, grouping, and decimal precision instead of manual concatenation, slicing, or `.ljust()` — hand-rolled width math drifts and diverges across call sites. — Manual width handling produces inconsistent output and off-by-one padding bugs; format specifiers encode the intent directly. Minimal specifier edits keep reviews focused on the actual fix.
  When fixing an existing format, change only the numeric specifier (`%i` → `%04i`) rather than rewriting the surrounding format string — keeps diffs minimal and avoids regressions in unrelated formatting.
<!-- rule:4513 -->
- Parse file paths with `os.path.splitext()`, `Path.suffix`/`Path.suffixes`, and `Path.with_suffix()`; never split on `'.'`. — Naive splitting on `'.'` breaks on multi-part suffixes (`.tar.gz`) and dotted directory names, and corrupts filenames. When parsing a path with separate format/compression extensions, split extensions off `PurePath.name`, then reattach `PurePath.parent` to the base so the base retains the full path and parts keep the `[folders/name, format, compression]` shape. Compare `suffix` including the leading dot (`suffix == '.js'`), since `Path.suffix` returns the dot. Spell `with_suffix()` correctly — misspellings like `with_suffic` raise `AttributeError` at runtime.
<!-- rule:3463 -->
- Wrap generator/comprehension args to a function call at clause boundaries when they exceed the line limit: keep each `for <var> in <iterable>` clause intact, never break right after `for`, and put `if` filters and the closing `)` on their own lines — matches Django's prevailing style, so line-ending diffs stay minimal and reviewers don't re-format — Splitting mid-clause (e.g. after `for`) makes the comprehension read as broken code and diverges from how the same construct is formatted in other Django modules like `django/db`, `django/utils`, and `django/contrib`, generating noisy review diffs.
<!-- rule:4733 -->
- Group items by each item's own key, not the first element's type — mixed collections silently collapse into one group otherwise — In collection aggregation, assuming a shared key from `items[0]` misclassifies heterogeneous input. Prefer `dict`-based grouping keyed by the group id, or sort by the key before `itertools.groupby` since it only groups adjacent items; accumulate into one mapping rather than parallel keys/values lists to avoid desync.
<!-- rule:2258 -->
- Size validation regexes to exact valid inputs: use `{n}` not `{n,n}`, explicit alternations like `(\d{3}|\d{6})` over permissive ranges, require every meaningful component, and reject malformed input (missing values, trailing separators/whitespace) — prevents accepting invalid strings downstream. Skip tightening when downstream parsing already normalizes non-matches. — Tight regexes reject malformed input at the boundary rather than relying on downstream code to clean up, and matching bounds across analogous components (and in tests) keeps validation consistent across the module.
  - In Django date/time regexes (e.g. `django/utils/http.py`, `django/utils/dateparse.py`), bound numerics to valid ranges — hours `[01][0-9]|2[0-3]`, minutes/seconds `[0-5][0-9]` — and apply the same bounds to analogous components in the module; allow `60` seconds only for leap-second compliance, otherwise exclude it deliberately.
  - In tests, assert the exact allowed formats instead of permissive ranges — mirrors the tightened production regex so tests actually catch regressions.
