# Testing Patterns and Coverage

> Rules for writing tests, fixtures, test infrastructure, tags, and regression coverage for changed behavior.

**When to check**: When writing, modifying, or reviewing tests, fixtures, or test infrastructure.

## Rules

<!-- rule:5997 -->
- Put source-map test coverage in the `source_map.js`/`source_map.css` fixtures, not generic `module.js` fixtures — keeps source-map behavior testable in isolation from unrelated module parsing — Keeping source-map coverage in the dedicated fixtures prevents unrelated module-parsing tests from masking source-map regex regressions, and including data: URI examples ensures those edge cases cannot silently break when storage.py is changed.
  - When changing source-map parsing/rewriting regexes in `django/contrib/staticfiles/storage.py`, add representative examples (including `data:` URI cases) to the matching fixture — verifies the regex rewrite against real edge cases
<!-- rule:2863 -->
- Cover all supported UUID versions (`UUIDv4`, `UUIDv7`) when testing UUID defaults like `id` — a single-version test misses regressions in the untested generator. — uuid defaults like id are generated by different strategies, so testing only one leaves gaps in the others
<!-- rule:4951 -->
- For duplicate-attribute checks (e.g. `db_table`), skip models where `model._meta.managed` is `False` — unmanaged models may legitimately share tables. Test cross-app collisions and managed/unmanaged pairs sharing a `db_table` (assert no errors). Mirror `test_m2m_table_name_clash` wording: name the registering model and the triggering field, without asserting fields non-auto-created models lack. Don't exercise unrelated options like `db_table_comment` against unmanaged handling — they muddy the signal and imply false coupling. — Unmanaged models (`managed = False`) intentionally point at externally-managed tables, so treating them as duplicate owners produces false system-check errors — the check lives in `django/core/checks/model_checks.py` and its tests in `tests/invalid_models_tests/`, `tests/introspection/`, and `tests/check_framework/`. Matching `test_m2m_table_name_clash` message style keeps assertions comparable across checks, and pairing managed/unmanaged models isolates `managed = False` as the single variable under test.
<!-- rule:3844 -->
- Before adding CSS class rendering tests, search for existing coverage of the same behavior; still test every branch of conditional class logic (e.g., permission-based classes in `django/contrib/admin/templates/`) — duplicate tests bloat the suite, but skipped branches hide regressions when a class silently stops rendering. — Duplicate tests bloat the suite; untested branches silently regress when class output changes.
<!-- rule:1237 -->
- Placement rationale: The rule is a general, language-agnostic engineering practice (make minimal bug fixes and always add a regression test), not tied to any single directory, module, or file. Evidence from source comments spans multiple directories (`django` and `tests`), confirming the rule is applied repository-wide rather than within one module. As a behavioral guideline that should govern all bug-fixing work, its most findable and appropriate home is a root-level AGENTS.md so that AI assistants apply it across — 
<!-- rule:6256 -->
- Test every branch of `hasattr`/`__name__` helpers; include a `lambda` when inspecting callables — Helpers that dispatch on attribute presence or `__name__` fail silently for anonymous callables, so exercising each branch with a representative object plus a `lambda` catches misrouted dispatch before it ships.
<!-- rule:4756 -->
- Test inheritance-aware class-level caches through subclass access — assert identity with the base value and that sibling caches stay scoped — Class-level caches that live on the defining class can be silently shared, copied, or shadowed per subclass (e.g. `__dict__` lookups in `django/views/debug.py` / `django/db/models/fields/related.py`); a subclass read returning a different object or leaking a sibling's entries only surfaces when a test actually goes through the subclass.
<!-- rule:1429 -->
- Use a custom class whose `__reduce__` raises an explicit exception (e.g. `ExceptionThatFailsUnpickling`) to test unpickling failures — built-in objects fail differently on CPython vs PyPy, so tests can pass spuriously or break by interpreter; document the failure mode in the test name/comment and explain non-obvious `pickle.loads(pickle.dumps(...))` round-trips. — Built-in objects' unpickling failure modes vary between CPython and PyPy, making tests nondeterministic; explicit `__reduce__` failures and documented round-trips keep the test's intent legible.
<!-- rule:1104 -->
- Inject the vetted accessibility checker (`axe` / Accessibility Insights, or the `axe-core` engine it bundles) into the browser from the test runner rather than shelling out to a standalone CLI — keeps the check in-process and reproducible across environments. — External CLI checkers diverge from CI browser state and add a separate failure surface.
<!-- rule:2489 -->
- Use `@tag`/`@tags` decorators instead of a `tags` class attribute — matches Django's public API and keeps tags greppable. — Direct `tags` attribute assignment bypasses the documented decorator API and is harder to search for. Runner must inspect both the method and its `TestCase` class, otherwise class-level tags silently fail to filter any of that class's tests.
  - In `filter_tests_by_tags`/`DiscoverRunner`, check tag attrs on both the test method and its `TestCase` class — class-level tags must apply to every method in the class.
<!-- rule:3853 -->
- Test every locale-assignment scenario when changing `makemessages` locale-dir resolution or fallback (e.g. `or not self.settings_available`) — `test_correct_translatable_file_locale_dir` pins the expected ordering, and untested tweaks silently change which dir wins, especially when an app locale dir is explicitly set in `LOCALE_PATHS` — Changes to `makemessages` locale-directory resolution or fallback conditions (e.g., `or not self.settings_available`) must be accompanied by regression tests covering each locale assignment scenario, including when an app locale directory is explicitly set in `LOCALE_PATHS`.
