# Accessibility and Semantic Markup

> Semantic HTML choices, heading hierarchy, landmark names, accessible names, decorative icon handling, focus indicators, and forced-colors/contrast support.

**When to check**: When writing or reviewing HTML markup, components, and interactive styling for a11y

## Rules

<!-- rule:175 -->
- Use headings only for real document outline: one `<h1>` per page, then `<h2>`/`<h3>` with no skipped levels — screen-reader navigation breaks on non-sequential or decorative headings — Headings drive the assistive-tech document outline; decorative or skipped levels make navigation confusing, so visual subheadings like `hero__subheading` belong on a `<p>` and any level change must cascade to descendants to keep the hierarchy sequential.
  - Mark visual-only subheadings (e.g. `hero__subheading`) as `<p>` with the styling class, not a heading element — keeps the a11y outline free of non-structural entries
  - When a heading's level changes, re-level its descendant headings to the immediately following level — prevents orphaned or skipped levels in the outline
<!-- rule:171 -->
- Set an explicit `$color--*` text/icon `color` in any selector that changes `background` (variants, hover/state, decorative overlays) — inherited colors silently fail contrast checks against the new background, so contrast must be verified at the point of change. — In `wagtailio/static/sass/components/`, variants and hover states frequently swap backgrounds without touching `color`. Because `color` is inherited, the text/icon keeps the colour from the base state, which may not contrast correctly against the new background — producing unreadable labels or icons on hover/overlay states. Setting the `$color--*` token explicitly in the same selector keeps the pairing local and auditable, and makes contrast verification straightforward.
<!-- rule:88 -->
- Choose HTML elements whose semantics match the content: use `<ul>`/`<ol>`/`<li>` for repeated list and grid items, and dedicated elements like `<blockquote>` for quotations or `<figure>` for media instead of generic `<p>`/`<div>` wrappers. Reserve `<article>` for content that is independently self-contained and syndicatable, and keep `<div>` for repeated list/grid items that are not self-contained. — Semantic markup keeps templates accessible and machine-readable; over-semanticizing with `<article>` on non-self-contained items (e.g. per-card grid items) misleads screen readers, RSS extractors, and search indexing.
<!-- rule:153 -->
- Put distinct accessible names on the landmark element itself (`<nav>`, `<header>`, `<main>`, `<section>`), not inner elements like `<ul>` — screen readers announce landmarks from their own label, so a name on a child leaves the landmark unlabeled; prefer `aria-labelledby` pointing to an existing translatable heading over a literal `aria-label` so names stay translatable and in sync with visible text. — Assistants adding nav or section markup in any template (e.g. `wagtailio/project_styleguide/templates`, `wagtailio/roadmap/templates`) otherwise either label the wrong node or hardcode English strings; anchoring to an existing heading keeps landmarks uniquely named and localized.
<!-- rule:64 -->
- Use `aria-expanded`/`aria-controls` only on toggle buttons over expandable regions, updating `aria-expanded` on open/close — stale ARIA misreports state to screen readers; drive non-expandable components (e.g., alerts) with state classes instead — Screen readers trust `aria-expanded` to announce collapsed/expanded state. Leaving it on non-expandable components (alerts) or failing to sync it on toggle advertises an interactive region that doesn't exist, breaking accessibility for assistive-tech users.
<!-- rule:152 -->
- Mark decorative icons with `aria-hidden="true"` — otherwise screen readers announce redundant SVG noise inside already-named controls. Leave meaningful icons unhidden. — Screen readers will announce the inline SVG or icon inside a control that already has an accessible name, producing duplicate or meaningless output. Decorative icons (inline SVG, icons inside controls with accessible names) should be hidden; icons that themselves convey meaning must stay exposed.
<!-- rule:170 -->
- Scope forced-colors styles in `@media (forced-colors: active)` using system keywords (`CanvasText`, `Canvas`, `ButtonText`) — never hard-coded values or `$color--*`; keep non-contrast affordances like `stroke-width` outside the query so default design stays intact. — System keywords let the OS remap colors to the user's high-contrast palette, while project `$color--*` variables and hard-coded values ignore it and can render invisible or unreadable content. Keeping visual affordances outside the query prevents the forced-colors rule from altering the standard design.
<!-- rule:154 -->
- Give each element one accessible-name source: never override visible text with `aria-label` or stack redundant `u-sr-only` text beside one — duplicated names confuse screen readers — - Duplicated or conflicting accessible names make screen readers announce labels twice or contradicting the visible text, so sighted and non-sighted users get different information.
- Icon-only controls with no accessible name are announced as "link" or "button" with no purpose, blocking navigation for screen-reader users.
- Repeated links sharing identical visible text produce a link list where every entry reads the same; the `aria-describedby` target supplies the unique context (which item, which section) needed to choose the right one.
  - Give image/icon-only links and buttons an explicit `aria-label` taken from the item's human-readable name — otherwise they are announced as unlabeled
  - Disambiguate repeated links with identical visible text via `aria-describedby` pointing at a per-item element with a unique generated `id` — identical "Read more" links are indistinguishable in a link list
<!-- rule:194 -->
- Skip `target="_blank"` on external links — respects the user's browser and assistive-tech navigation preferences — Forcing new tabs overrides user settings; when it happens anyway, screen readers give no announcement of the context switch unless the visually hidden `u-sr-only` hint is present.
  - If a link must open in a new tab, pair it with `<span class="u-sr-only">(opens in a new tab)</span>` — warns screen reader users of the context change
<!-- rule:204 -->
- **Never remove focus outlines without a high-contrast replacement** — `outline: none` on interactive elements strands keyboard users; always pair with a visible `:focus-visible` style. — Removing the default outline without a replacement makes keyboard navigation impossible for users who rely on it. In Sass components, prefer `&:focus-visible` over `&:focus` so focus rings only show for keyboard/assistive input, not mouse clicks, and ensure hover/focus states are *more* visible than the base state (stronger color, underline, contrast against dark backgrounds) — never reduced opacity, which hides interactive affordances.
<!-- rule:166 -->
- Use `u-sr-only` (not `display: none`) to visually hide content that must stay accessible, and delete component SCSS rules that `display: none` the same element — `display: none` removes text from the accessibility tree, so screen readers can't reach it. — `display: none` removes content from the accessibility tree entirely, so screen readers never announce it — visually hidden labels (e.g. form labels in sign-up forms) become unreachable. The project's `u-sr-only` utility hides content visually while keeping it accessible. Because a component's SCSS often applies `display: none` to the same element, leaving it in place silently re-breaks accessibility even after the template is fixed; the conflicting rule must be deleted too.
