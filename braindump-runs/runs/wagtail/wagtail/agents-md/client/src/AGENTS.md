# client/src/ Guidelines

## Code Style

<!-- rule:2863 -->
- Organize `client/src/` by semantic folder: `components/` (React components only), `includes/` (shared non-React modules and UI widgets imported by other client code), `utils/` (small generic utilities and hooks), `entrypoints/` (Webpack entries only) — prevents misplaced modules and duplicated logic — The rule defines folder semantics and placement conventions that apply across the entire `client/src/` subtree (components/, includes/, utils/, entrypoints/) rather than to any single file or narrow entity. It is module-scoped (client-side source only), not repo-global, so `agents_md_dir` at `client/src` is the natural home: an assistant working on any file under `client/src` will load this AGENTS.md and get the folder conventions, which directly guides naming and placement decisions. Broader ro...
  - Document each folder's purpose and conventions (e.g. `includes`, `utils`, `endpoints`) in the relevant `AGENTS.md` so contributors pick consistent names and locations
  - Reuse existing shared utilities and extract inline helpers into `utils/` instead of duplicating logic
<!-- rule:1808 -->
- Read `document.currentScript` synchronously at the top level of `client/src/entrypoints` scripts — it's `null` inside `DOMContentLoaded` and later callbacks, so deferring breaks script-origin detection. — `document.currentScript` is only populated during synchronous script execution. Capturing it inside async callbacks yields `null`, so the entrypoint can't determine its own `<script>` tag (needed for resolving chunk URLs / base paths).
<!-- rule:1577 -->
- Keep admin entrypoints thin — globals go in `client/src/entrypoints/admin/core.js`, feature logic in its own module — Entrypoints are shared load-time contracts; centralizing `window` registrations in `core.js` keeps the bundle's global surface auditable, and pushing cohesive logic out of `page-editor.js` into dedicated modules stops that file from becoming an unmaintainable catch-all. Don't expose new `window` globals unless a sibling module truly needs them — Redundant admin entrypoint files and dead global exports leave multiple sources of truth for `window` registrations, so a global can appear registered while its owning entrypoint is unused or removed inconsistently. Letting `page-editor.js` grow into a catch-all for feature logic hides shared behavior, and when that behavior is removed from only one sibling admin entrypoint, duplicated code and stale entrypoints remain.
<!-- rule:2706 -->
- Call `.forEach()` directly on `document.querySelectorAll()` results — never spread to an array (`[...nodeList]`, `Array.from(...)`, `[].slice.call(...)`) or null-guard with `if (collection)`. `querySelectorAll` always returns a `NodeList` (empty on no match) and the project's browser baseline implements `NodeList.prototype.forEach`, so casts and guards are dead code. — Simpler and consistent with the project's browser baseline; the array cast and null check are unnecessary defensive code that imply a `NodeList` may be null or non-iterable when it never is.
<!-- rule:1174 -->
- Extend the shared dropdown initializer in `client/src/entrypoints/admin/core.js` (`$('.dropdown').each(...)`) instead of adding one-off scripts — keeps dropdown behavior consistent and discoverable. Apply behavior narrowly to only the dropdowns that need it (e.g. Tippy only on the header dropdown, `hide_on_click=True` only for modal-launching buttons) — avoids unintended side effects on unrelated dropdowns. — Centralized initialization prevents duplicated/drifting dropdown logic, and narrow targeting avoids regressions in dropdowns that don't need the extra behavior.
<!-- rule:515 -->
- Resolve DOM refs from the target element passed into `init`/`render` (e.g., `container`), not from associated controls like a panel's toggle — prevents grabbing the wrong node or an undeclared identifier — DOM queries against related controls (e.g., a panel's toggle) or undeclared identifiers silently resolve to the wrong element or throw, and break as soon as the surrounding markup changes. Reusing the in-scope `container`/element parameter keeps `client/src` init, event-dispatch, and closure code bound to the element it actually owns.
<!-- rule:3001 -->
- Extract large helpers from `client/src/entrypoints/admin/**/*.js` into dedicated modules under the sibling `includes/` directory — `export default` the helper and `import` it back, leaving the body and call sites untouched. Keeps entrypoints scannable without churning call sites. — Admin entrypoint files grow bloated as helpers accumulate; moving them to sibling `includes/` modules preserves readability. Preserving the function body verbatim and re-exporting via `export default` keeps the diff minimal and avoids breaking existing callers.
<!-- rule:2891 -->
- Select userbar menu items by ARIA semantics, not tag/class selectors: resolve controlled elements via `aria-controls`, query `[role="menu"]`, and cover every supported role (`menuitem`, `menuitemradio`, `menuitemcheckbox`) or fall back to the containing `li` — hard-coded `[role="menuitem"]`/tag selectors silently miss mixed-role menus. — Keeps userbar menu selection and focus management working across mixed-role menus and varied item markup, so new item types (radios, checkboxes, disabled inputs) don't silently break keyboard navigation in `client/src/entrypoints/admin/`.
  - When moving focus to the first menu item, query any focusable descendant (`a[href]`, `button:not([disabled])`, `input:not([disabled])`, `[tabindex]:not([tabindex="-1"])`) instead of hard-coding `a` — menus mix links, buttons, and inputs.
<!-- rule:3037 -->
- Style tables in Storybook doc stories by adding shared CSS (e.g. `border-spacing` for row/cell padding) to the existing `:root` variable `<style>` block; skip `.docutils` and per-cell inline padding. — `.docutils` adds unwanted alternate row coloring, and inline padding duplicates boilerplate across every cell — the shared `:root` block keeps `client/src/**/*.stories.tsx` tables consistent and DRY.
<!-- rule:2054 -->
- **New DOM elements: single HTML template string; jQuery mutators only mutate existing ones** — each class/attribute must be set exactly once on the construction path, so re-adding a class already present in the markup (or duplicating `.attr()`) is a bug. `appendColumnButton` chains `.addClass()`/`.attr()` only because it mutates an existing element, not because that's how new elements should be built. — New elements' static attrs, classes, and ARIA belong in one template string so each is declared once; chained `.attr()`/`.addClass()`/`.html()` calls are for elements whose attributes or contents change after creation. Distinguishing the two avoids duplicate-set drift, where markup and later mutators disagree about an element's final state. The `appendColumnButton` reference clarifies that its chained style reflects mutation, not the element-creation convention.

## Testing

<!-- rule:1533 -->
- **Verify behavior changes to `client/src/**` JS modules before merging — untested client code ships broken silently** — Client-side behavior changes are invisible to the backend test suite, so regressions only surface for users. The colocated `{module}.test.js` convention makes the fix trivial where coverage already exists; where it doesn't, the manual-flow check is the minimum bar for catching broken `entrypoints/`, API client, or `Draftail` source behavior.
    - Has colocated Jest tests? Add/update the sibling `{module}.test.js` covering new behavior and new branches.
    - No tests (e.g. `Draftail` sources, API clients, `entrypoints/`)? Manually walk the full user flow plus edge cases: confirm/cancel paths, each selection and search scenario.
<!-- rule:1602 -->
- Test every behavior-altering `data-*` attribute in `client/src/includes/*.test.js` — build fixture HTML with the attribute on the component root (plus a target `id` on an outer ancestor for selector attrs like `data-header-selector`), initialize the component, and assert the resulting behavior (e.g. `data-breadcrumb-item` element gets handled, listener attaches to the resolved ancestor). In `breadcrumbs.test.js`, verify `data-header-selector` resolves any CSS selector and wires interactive listeners to that ancestor. — These `data-*` hooks are the public integration surface for the components; untested attributes silently break consumers that rely on selector-based wiring.
<!-- rule:1792 -->
- In `client/src/utils/urlify.test.js` locale tests, use characters from the target locale's alphabet, realistic words, and cross-locale words with identical spelling when isolating mapping behavior — invalid or contrived data makes tests pass/fail for the wrong reason — The guideline turns the raw requirement into a single imperative bullet scoped to the actual test module. It preserves the key project-specific reference (`client/src/utils/urlify.test.js`) and the three concrete constraints (valid alphabet, realistic words, identical cross-locale spellings) while adding the *why*: bad test data produces misleading results. The 'when isolating mapping behavior' qualifier keeps the scope of the identical-spelling constraint precise rather than over-broad.

## Error Handling

<!-- rule:90 -->
- Validate required DOM/controller preconditions early — required template elements, element `id` attributes, and global deps like `window.telepath` — and throw a descriptive error when missing instead of silently returning or reading undefined values. — Silent failures hide broken DOM contracts until a user hits a confusing runtime error; a named throw surfaces the missing element or global at the call site (e.g. in `client/src/includes/userbar.ts` and `client/src/controllers/BlockController.ts`).
<!-- rule:1546 -->
- In browser event listeners use `console.error` + early return instead of `throw`, and `preventDefault()` on invalid events when rendering custom validation errors — throwing breaks handlers, and the native validation UI conflicts with custom error display — Preserves: browser/event-listener scope, `console.error` pattern, early-return pattern, `preventDefault()` on invalid events. Explains why (broken handlers, UI conflict) rather than a rule-of-law justification. Scoped to client/src by placement.

## API Design

<!-- rule:1781 -->
- In `client/src/includes/contentMetrics.ts`, expose one focused function per metric, separate raw score calculation from display-label mapping, and pass prerequisite values explicitly (e.g., `getReadingTime(wordCount)`, `getLixScore(lang, text): number`, `getReadabilityLabel(lang, score): string`) — keeps utilities composable, localizable, and easy to test. — The guideline is derived from the raw rule that content-metric utilities should have one focused function per metric and separate concerns. The rephrased version is imperative and clear, includes the why (composability, localization, testability), avoids deontological language, fits in a bullet point, and preserves the specific file path `client/src/includes/contentMetrics.ts` and example function signatures with backticks.
<!-- rule:2847 -->
- Initialize widgets from the `render`/`renderState` argument, not from ad-hoc defaults — this makes the render arg the single source of initial state. Treat `setState` as optional: implement it only where the widget genuinely supports state mutation, never as a fake/no-op, since a misleading `setState` causes silent bugs in consumers. Container blocks may recurse `setState` only when every descendant block supports it — otherwise the container would report success while children stay stale. — In `telepath` widget APIs and integrations (StreamField block containers, `client/src/entrypoints/draftail.js`), `render`/`renderState` is the authoritative path for initial state; `setState` signals real post-init mutation capability, so faking it breaks consumers' expectations and recursive container state changes silently do nothing when any descendant lacks support.

## General

<!-- rule:1638 -->
- Type non-standard browser globals by augmenting `Window`/`JQuery` in `client/src`'s shared `.d.ts` instead of casting to `any` at call sites — a single declaration keeps every usage type-checked. If a global is untyped, declare it as `any` with a comment noting real types are still needed. — Concise, imperative, preserves the `Window`/`JQuery` identifiers and the `client/src` shared declaration file convention; explains the why (centralized typing beats per-call-site casts) and keeps the untyped-global escape hatch advisory rather than rule-based.
<!-- rule:1604 -->
- When replacing legacy telepath behavior with `BlockController`, delete the superseded init code from the telepath block files and tag compat guards (`if (!window.telepath)`) with a comment noting they can be simplified/removed once `telepath.js` is deleted — prevents dead code accumulation and surfaces cleanup targets for the migration — Leaving the old init code alongside the replacement creates two competing sources of truth for block initialization. Flagging compat guards as temporary keeps the deletion of `telepath.js` from being blocked by unnoticed `window.telepath` checks.
<!-- rule:472 -->
- In barrel files like `client/src/index.ts`, use direct re-exports (`export { name } from './module'`) for every entry — consistent shape keeps imports predictable and traceable — Uniform direct re-exports avoid re-mapping overhead and make each symbol's origin obvious from the barrel
<!-- rule:2535 -->
- Name JS files by role: `camelCase` for importable modules, `kebab-case` for route/endpoint files (e.g., `chooser-modal.js`), lowercase feature names in `includes/` (e.g., `dialog.js`) — Consistent import paths prevent resolution failures on case-sensitive filesystems (Linux CI) and make a module's purpose obvious from its path. Record the convention in the style guide / contributor docs so new files don't drift.
