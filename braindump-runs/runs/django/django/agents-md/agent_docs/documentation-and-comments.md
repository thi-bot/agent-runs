# Documentation, Docstrings, and Help Text

> Rules for writing accurate documentation, docstrings, inline comments, error/help text, and user-facing explanations.

**When to check**: When writing or updating docs, docstrings, inline comments, error/help pages, or troubleshooting notes.

## Rules

<!-- rule:3698 -->
- Reference Django signals by exact canonical name with correct `pre_`/`post_` prefix and link via Sphinx `:data:` role (e.g., `:data:`~django.test.signals.setting_changed`) — signals are module-level data attributes, so `:func:`/`:py:` misresolve and typos like `pos_delete` break links and grep-ability. — Distilled a cross-cutting documentation convention into three actionable bullets. Preserved the Sphinx role specifics (`:data:` vs `:func:`/`:py:`), the canonical reference file path (`docs/ref/signals.txt`), and the release-note phrasing pattern. Added the WHY (link resolution failures, drift between analogous sections, disambiguation of affected models).
  - Keep `docs/ref/signals.txt` internally consistent: reuse the phrasing already used for the same condition in adjacent sections, and apply wording/grammar fixes to all analogous signal sections — inconsistent duplicates drift and confuse readers comparing signals.
  - In release notes, name each signal with its model/class (e.g., "the ``pre_save`` and ``post_save`` signals for ``LogEntry``") and use Django's "signals are sent" wording — matches canonical docs prose and disambiguates which model is affected.
<!-- rule:6133 -->
- Warn in docstrings/docs when a helper is internal-only or has surprising limits: the restriction, shared-state side effects (e.g. model caches), and whether it's private/unsupported — callers otherwise misuse it or assume it's stable and thread-safe. — Undocumented constrained internals get reused outside their safe context and silently break when the helper or schema changes.
<!-- rule:6211 -->
- Use Python 3 stdlib APIs in doc examples and doctests (`range()`, `urllib.request`, not `xrange()`, `urllib.urlopen`) — Py2-only calls fail when doctests execute and get copy-pasted into user code. — Doctests run under the project's Python 3 interpreter, so `xrange()`/`urllib.urlopen` raise errors during test collection; the same snippets are also the primary reference users copy, so stale Py2 idioms propagate into downstream code.
<!-- rule:850 -->
- Qualify performance claims in prose docs with conditions, workload, or order-of-magnitude scale — unqualified comparisons ("A is faster than B") and vague phrasing ("performance considerations", "the whole results") mislead readers on different workloads; label micro-optimizations as such and prefer qualitative thresholds over environment-specific timings. — Performance effects only hold under specific conditions, so unqualified or dismissive claims leave readers unable to judge whether the effect applies to their workload.
<!-- rule:4840 -->
- Write comments as positive prose stating the invariant (e.g. `checks the name starts with ...`), not the mechanism or what the code avoids — readers need the expected condition, not a narration of the bug it prevents. — Negative or mechanism-narrating comments drift out of sync with the code and bury what actually holds true; positive invariant statements stay accurate and tell the next reader what to rely on.
<!-- rule:417 -->
- Title error pages and troubleshooting notes by the user-visible failure (exact terminal text when shell envs differ), not internal exception names — users match their actual error; prefix admin validation-error titles with `Error:` — screen readers announce the state — This prevents users from failing to find troubleshooting guidance because pages are named after internal exceptions instead of the exact visible error they search for, and prevents screen-reader users from missing that an admin validation page is an error because its title lacks the `Error:` prefix.
<!-- rule:418 -->
- **Order error/help content as: general explanation → exact error/check message → diagnostics/settings/verification.** In `django/views/templates/csrf_403.html`, `docs/**/*.txt` how-tos, and troubleshooting guides, put the CSRF explanation before the `bad_origin` block or settings-troubleshooting sections — readers must confirm *what* failed before they can act on *why*. — This ordering prevents readers from hitting a CSRF 403 or documentation error without first understanding what failed, which happens when `bad_origin`, settings/verification details, or troubleshooting notes appear before the general explanation or away from the triggering command.
  - **Place troubleshooting notes right after the command/step that triggers the error**, just before the help-section paragraph. Notes at the top of the page or in unrelated sections lose readers, who hit the problem at a specific step.
<!-- rule:4174 -->
- Escape raw invisible/unprintable characters (`\xa0`, zero-width space) as explicit sequences like `\xa0` — raw invisibles hide in diffs, break parsers, and can't be reviewed. — Invisible characters are undetectable in review and diffs, and documentation that under-specifies the escaped set (e.g., "less than 32") leaves readers believing characters outside that range pass through when they don't.
  Use a visible stand-in (e.g., `. . .`) when a parser/highlighter demands a character — an invisible one silently changes behavior with no trace in review.
  In comments and docs (`django/utils/html.py`, locale `formats.py`, `docs/`), list the exact characters actually escaped by range (C0, DEL, C1) and describe current behavior — an incomplete bound like "less than 32" misinforms readers about what the code handles.
<!-- rule:842 -->
- Describe query-compilation/preparation flags by runtime conditions, not `True`/`False` — booleans often select branches their value doesn't imply, so docs in `django/db/models/expressions.py` and `docs/ref/models/lookups.txt` mislead readers. — The flag value can select behavior based on runtime conditions, not its literal boolean. Documenting the exact conditions prevents readers from assuming `True`/`False` maps directly to the described behavior.
<!-- rule:1675 -->
- Comment non-obvious test setup hacks (e.g. `sys.path` edits, `__unittest = True`) in test setup/helper modules — undocumented workarounds silently break when refactored — These mechanisms (e.g. `sys.path` manipulation for imports, `__unittest = True` flags) have nonlocal effects that aren't obvious from reading the surrounding test code, so a refactor that looks safe can silently change import resolution or test-runner behavior. An inline comment pinning down what the hack controls keeps future readers from removing or mis-copying it.
<!-- rule:3988 -->
- Include a nested example when documenting nesting-capable constructs — Flat examples leave readers inferring nesting syntax (e.g., `{% if %}` inside `{% if %}`, nested `Meta` classes, enum groups), which leads to misuse and support churn.
<!-- rule:4268 -->
- Document why functions, hooks, and lifecycle methods intentionally run multiple times  prevents readers mistaking intended repeats for bugs or redundancy. — A reader encountering a function, hook, or lifecycle method that fires more than once cannot tell whether the repetition is deliberate or a defect. Naming the concrete trigger (e.g. a re-render, retry, or event re-emission) or the reason each invocation is needed removes that ambiguity and stops future maintainers from "fixing" correct code or duplicating guards against it. Without this, reviewers and debugging engineers waste time re-deriving intent from call sites or git history, and redundant-looking calls become easy targets for accidental removal.
<!-- rule:5070 -->
- Spell out the access mechanism (e.g. `attribute-style dict lookup`, `alias lookup` in the storage dict), not `can be retrieved` — vague phrasing hides lookup semantics readers must code against — Docs are read by users who must reproduce the exact lookup (e.g. template variable resolution via attribute-style dict lookup, or storage retrieval by alias); a vague "can be retrieved" leaves them guessing and leads to wrong assumptions in their own code.
<!-- rule:6378 -->
- Comment non-obvious implementation choices inline — perf optimizations, exact class-identity checks, deliberate compatibility/error-handling — explain the *intent*, not the mechanics. Without rationale, future maintainers may "fix" or delete deliberate behavior they mistake for a bug. This convention spans the whole repo (e.g. `django/contrib/admin/sites.py`, `django/core/management/commands/shell.py`), so apply it anywhere code mirrors another implementation or intentionally deviates. — Explains why the rule matters: prevents future maintainers from removing or "fixing" deliberate behavior. Preserves example file paths and scope (global). Concise, imperative, includes WHY.
<!-- rule:5972 -->
- Comment each magic numeric CSS value with what it offsets and how it was derived (`django/contrib/admin/static/admin/css`) — hard-coded offsets/heights break silently when the referenced element or viewport changes, and the comment is the only cue that they're coupled. — Hard-coded numeric CSS values are usually derived from some other element (viewport offsets, heights that must match a sibling). Without an inline comment stating what they account for and where the number came from, no future reader can tell that the value is coupled to another element or safely update it. The comment is the only documentation cue that makes the coupling visible, preventing silent layout regressions when the referenced element changes.
<!-- rule:6038 -->
- Explain counterintuitive behavior via its language rule, not a workaround — Readers of `docs/ref/templates/language.txt` and `docs/topics/q-objects.txt` can't generalize from workarounds; citing the relevant rule (e.g. operator precedence, template evaluation order) and showing the correct syntax — such as a parenthesized expression — teaches the underlying model and prevents the same confusion elsewhere.
<!-- rule:1401 -->
- Comment *why* a mid-iteration mutation or defensive copy is safe — restating the operation hides the bug or ordering risk the copy guards against, so reviewers can't tell intentional mutation from accidental aliasing. — restating the operation hides the bug or ordering risk the copy guards against, so reviewers can't tell intentional mutation from accidental aliasing.
<!-- rule:5736 -->
- Update `docs/topics/signing.txt` when changing public APIs in `django.core.signing`. — Document new or modified APIs in the matching use-case section (`Verifying timestamped values`, `Protecting complex data structures`, `Using the low-level API`) with examples. Describe the signing pipeline in execution order with signing last, since the timestamp is covered by the signature — documenting it out of order produces examples that don't match real verification behavior.
<!-- rule:3765 -->
- Add inline comments for non-obvious string normalization/sanitization — records what external input (env vars, config specs) is transformed into identifiers/filenames, and why — Normalization logic is easy to misread as arbitrary mangling; explaining intent (e.g. which chars are stripped to make a safe identifier) prevents future edits from silently breaking filename/identifier safety or external-input handling.
<!-- rule:5546 -->
- Match validator help/error text to its regex — list every char the pattern permits (e.g., `\w` includes `_`) and name charsets by script (e.g., "Latin letters"), not nationality (e.g., "English letters") — so users get accurate allowed-character guidance regardless of locale. — Mismatched or culturally-scoped descriptions (e.g., calling `\w` "English letters") mislead non-English users and drift from the actual validation behavior; naming the script ("Latin letters") and enumerating permitted characters keeps the message truthful for everyone reading the error.
