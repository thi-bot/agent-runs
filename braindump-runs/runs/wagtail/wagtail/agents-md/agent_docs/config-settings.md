# Configuration & Settings

> Rules for settings, feature flags, config merging/defaults, system checks, lint config, CI configuration, and dependency-config sync.

**When to check**: When adding or modifying settings, feature flags, config defaults, CI, or tooling configuration.

## Rules

<!-- rule:1356 -->
- **Keep at least one CI job testing Django's latest upstream stable branch** — Catches regressions in upcoming patch releases before they ship — not caught by pinned Django versions in normal test jobs. Add the job to both `.github/workflows/test.yml` matrices and any retained `tox.ini` environments, installing via `git+https://github.com/django/django.git@stable/<latest>.x#egg=Django`. Mark the job `continue-on-error` so upstream instability doesn't block the main CI. When a new Django stable series ships, retarget this entry to the newer branch and drop the stale one — otherwise the job silently stops covering the upcoming release.
<!-- rule:1449 -->
- Use the exact config key name (case, style, whitespace) when renaming or referencing settings — lookups are string-based, so near-miss names silently hit the wrong or missing key — String-keyed config (in `wagtail/`, `client/`, and settings handlers) fails silently or misroutes when a key's case/style/suffix/whitespace drifts, or when a similarly named unrelated setting is modified by accident
<!-- rule:1821 -->
- Source CSRF for admin non-GET requests from `WAGTAIL_CONFIG.CSRF_TOKEN` and `WAGTAIL_CONFIG.CSRF_HEADER_NAME` — keeps one source of truth and avoids stale tokens from embedded `{{ csrf_token }}` or hardcoded headers — Consolidates CSRF sourcing across the admin frontend so tokens are read from a single config, preventing drift and stale tokens across `client/src` controllers, `wagtail/admin/templates`, and `wagtail/wagtailimages/templates`.
  - Don't query `input[name="csrfmiddlewaretoken"]`, pass CSRF through Stimulus `data-*-value` attributes, or hardcode `X-CSRFToken` — these duplicate config and drift out of sync
  - Use `ActionController` to build POST-action forms and inject the token — centralizes CSRF handling across admin controllers
  - When writing `{% csrf_token %}` manually, put it immediately after the opening `<form>` tag — keeps form scripts and `ActionController` able to locate it reliably
<!-- rule:1375 -->
- Guard optional imports, admin filter registration, queries, and hooks with `getattr(settings, "FLAG", False)`. — Disabled features must not pay import costs, register feature-specific filters, or run extra queries — keeps inactive code paths free.
<!-- rule:2744 -->
- Read optional Django settings with `getattr(settings, 'NAME', default)` or `hasattr` — direct `settings.NAME` raises `AttributeError` when unset. — Convention
  - For expensive fallbacks (e.g. `Site.find_for_request`, DB queries), guard with an explicit `if hasattr(settings, 'NAME')` instead of passing the fallback to `getattr` — avoids evaluating the lookup on every call.
<!-- rule:104 -->
- Keep lint/format rules enabled repo-wide; use the narrowest scope for exceptions — Global disables silently exempt new files and hide real issues; scoped overrides keep coverage while allowing justified exceptions
<!-- rule:938 -->
- Never commit generated or transient artifacts (build outputs, compiled/minified assets, logs, captured command/test output, scaffolding like `wagtail/`/`mysite/` stubs) — add matching patterns to `.gitignore` instead, since tracked artifacts churn diffs, leak machine-specific paths, and re-surface on every rebuild; version control should hold only maintained source. — Repo-wide commit policy: any file under paths like `static/` assets, `search_promotions.log`, or generated `package.json` outputs is reproducible from source, so tracking it creates noisy diffs and stale files. `.gitignore` entries (e.g. `*.log`, `dist/`, `build/`) prevent re-adding them in future PRs. Remove any already-tracked artifacts from the PR before merge.
<!-- rule:494 -->
- Remove config options, selectors, and call-site keys with no consumer — dead entries mislead readers and accumulate cruft — Speculative attributes for unimplemented abstractions, options no longer in a dependency's API, and unused keys at call sites all become misleading noise; deleting them keeps the config surface honest.
<!-- rule:837 -->
- Merge config in one pass: `{ ...defaults, ...options }` / `$.extend` with defaults → parsed provider URL params → caller overrides → required/computed params last — key order encodes precedence, so nothing can accidentally clobber a required value — Preserving spread order and never popping/stripping keys keeps callers able to override defaults while required/computed values stay locked; defensive edge-case handling or post-hoc mutation silently breaks precedence.
<!-- rule:107 -->
- Define widget/controller defaults centrally on the Stimulus controller or its shared attribute helper — let templates omit data attributes that just restate them. Bind primary HTML config via the `value` attribute/property (not params or `event.detail`); only expose overrides with a concrete reuse case, apply behavior-specific values at the usage level, and keep selection-independent fallbacks (e.g. preview size) in controller/JS logic rather than template data attributes. This keeps `client/src/controllers/*` and their `wagtail/admin/templates` callers from drifting out of sync and prevents stale defaults from leaking into user-specific behavior. — 9 PRs spanning `client/` and `wagtail/admin/templates` show defaults duplicated across controller and template causing drift; primary config passed as `value` avoids lossy param/event details; selection-independent fallbacks coupling to template state caused preview bugs.
<!-- rule:507 -->
- Default new config options to preserve existing behavior for current callers — avoids breaking changes. For conditional legacy behavior use a falsy/`None` tri-state (e.g. `Optional[bool] = None`), define precedence so existing options still take effect, and document unset/falsy behavior. — This rule governs how configurable options, defaults, and settings are designed across the repository — new options must never silently change behavior for existing callers (backward compat), and tri-state defaults are needed when legacy behavior is conditional so older options keep working alongside new ones.
<!-- rule:644 -->
- Match migrated linter/formatter rules to existing conventions — preserve `lines-after-imports`, override false-positive rules against domain vocabulary, and keep disruptive rules non-blocking until contributors can satisfy them — prevents churn that hides real diffs — Two coupled guidelines: (1) config-tool adoptions/migrations should conform to the project's prior formatting rather than forcing wholesale rewrites, since unrelated churn obscures real changes; (2) reviewers need a rule-by-rule mapping of old→new in the PR (not the config file itself, which should stay clean) to spot equivalence gaps.
  - Document old-to-new rule mappings for tool migrations in the PR description (not inline in the committed config) — lets reviewers assess migration coverage and equivalence gaps
<!-- rule:508 -->
- Use full dotted paths like `{app}.apps.{AppConfig}Class` for Django apps in `INSTALLED_APPS` and user-facing messages/docs — bare app labels can't resolve custom `AppConfig`s and mislead readers. — consistency, correctness
<!-- rule:1730 -->
- Prefer config formats that support comments (`YAML` over `JSON`) when non-obvious rationale or caveats need documenting inline — `JSON` can't express them — non-obvious config decisions stay discoverable next to the setting they affect
<!-- rule:2345 -->
- Treat `.nvmrc` as the single source of truth for the project's Node.js version. — Keeping CI, dev VM, and contributors aligned on one version avoids "works on my machine" drift and untested runtime combinations.
<!-- rule:155 -->
- Introduce a config option only if it's honored across all relevant logic — half-threaded flags silently mislead callers — Placement rationale: The rule expresses a general behavioral/design principle about configuration options (end-to-end contracts, no dropped flags, no hardcoded defaults when wrapping utilities, pass options only when they vary). Its original scope is global and it is not tied to any single language, module, or file pattern. Although the sampled evidence happens to come from client-side controllers and utils (client: 3), the rule is about how configuration options should be threaded through arbitrary code, so an AI assistant benefits from seeing it globally.
  - Forward every relevant option when wrapping a utility — dropping flags or hardcoding defaults breaks callers
  - Pass an option to a helper only when it actually varies there — avoids dead params and fake flexibility
<!-- rule:2968 -->
- Mirror PostCSS plugins from `client/webpack.config.js` into Storybook's Webpack/PostCSS config — drift silently breaks Storybook's styling. — Storybook compiles styles independently of the app, so any PostCSS plugin added or changed in `client/webpack.config.js` must be duplicated in the Storybook config or stories render with stale/broken CSS.
<!-- rule:1805 -->
- Fall back to defaults for missing optional config keys — don't throw, assume presence, or log `console.error`; a default makes the key expected, not an error. — A missing key with a defined default is expected, not a failure — throwing or noisy logging breaks callers and pollutes logs for normal states. Use `.get(key, {})` for optional mapping config. Note `.get(key, {})` does not guard against an explicit `None` (e.g., `dict.update(None)` raises), so decide per call site whether to coerce `None` to the fallback or fail fast.
<!-- rule:1374 -->
- Default string-typed config/controller values to `''` when unset is valid — whitespace placeholders and non-empty domain constants become hidden sentinels that break equality checks and force callers to know magic values. — Empty string is the natural representation of 'unset' for string-typed fields; inventing whitespace or domain-specific non-empty defaults introduces implicit sentinels that leak into comparisons, serialization, and caller logic.
<!-- rule:1988 -->
- Validate configured collections like `panels` and `form_layout` eagerly, raising clear errors for malformed structures or unknown item names — silently filtering them out defers the failure to cryptic downstream code that's harder to trace back to the config — Eager validation with actionable errors surfaces config typos and structural mistakes at load time, rather than letting them manifest as obscure failures deep in rendering or processing logic.
<!-- rule:497 -->
- Centralize custom Axe rules/checks in the shared `axe_custom_rules` / `axe_custom_checks` lists (defined in the shared `a11y-result` module) rather than private attributes or client-side implementations — one source of truth keeps Python and TS sides in sync — Duplicating rules across `wagtail/admin/userbar.py` and `client/src/includes/userbar.ts` drifts; the shared module is the coordination point.
<!-- rule:506 -->
- Store Axe-core `include`/`exclude` selectors as arrays; normalize string-or-array inputs before use — Arrays keep your own config consistent and support multi-selector cases, while normalizing incoming values (via `Array.isArray` or wrapping) prevents breakage when callers pass a bare string.
<!-- rule:861 -->
- Keep Django's default SQLite test DB — don't set `DATABASE_NAME` to a file path unless persistence (e.g. `--keepdb`) is required — Using the built-in `django.db.backends.sqlite3` in-memory/temp DB avoids stale file state and CI-specific drift; overriding it to a file path breaks Django's test isolation.
<!-- rule:188 -->
- Disable the `prefer-destructuring` ESLint rule and only destructure when pulling multiple properties from the same source — single-property access should use explicit `obj.prop` since mandatory destructuring hurts readability without benefit. — Forces destructuring for single properties adds noise and obscures the source object; destructuring only pays off when it groups multiple extractions from the same source.
<!-- rule:800 -->
- Extend the existing CircleCI docs-linting job for new doc linter checks — don't add a separate GitHub Actions workflow. Validate the baseline against real docs PRs and clear false positives before marking the check required. — Keeps all docs linting in one pipeline (avoids duplicate/conflicting CI), and validating against real PRs prevents a noisy required check that blocks valid contributions.
<!-- rule:2325 -->
- Install deps (e.g. `requirements.txt`, apt packages) before `COPY . .` in Dockerfiles — keeps dep layers cached when app source changes — When deps install before `COPY . .`, Docker reuses the cached dependency layer on source-only changes; otherwise every edit reinstalls the full dep tree. Merging sequential setup `RUN` commands (e.g. apt install + venv creation) with `&&` does the same for system-level setup layers.
<!-- rule:1302 -->
- Prefer SVG icons over legacy icon fonts — wrap remaining legacy `font-family` usage in a Sass variable so `.stylelintrc.js` rules can be enforced globally instead of permanent `null` exceptions. — Icon fonts are deprecated; migrating them to a Sass variable lets `.stylelintrc.js` enforce rules repo-wide (e.g. in `wagtail/contrib/` styleguide templates) without permanent exceptions.
<!-- rule:2223 -->
- Makefile/gulp/npm orchestration targets should delegate to the canonical aggregate command (e.g. `npm run lint`) or invoke the tool's CLI directly — re-listing sub-scripts drifts out of sync and adds dead wrappers. — Keeps build targets single-sourced: the aggregate script stays the source of truth, so adding/removing a step in `npm run lint` propagates automatically instead of silently diverging.
<!-- rule:2826 -->
- Verify design tokens before committing: diff migrated definitions in `client/scss/elements/_root.scss` against the old Sass/Figma source, and confirm `theme('colors.*')` references exist in the theme config — stale or missing tokens silently render wrong colors. — Design tokens are split across SCSS partials (definitions) and component files/code (references); drift between the two produces silent visual bugs that are hard to trace. Diffing against the authoritative source and checking the theme config catches mismatches before they ship.
<!-- rule:2569 -->
- Centralize CSS/SCSS declaration-order enforcement in the shared `stylelint-config-wagtail` config (via `stylelint-order`) instead of inline `scss-lint:disable DeclarationOrder` comments — a single source of truth stays consistent across `client/**/*.scss` and stays maintainable. — Shared config applies uniformly to every `client/**/*.scss` file and is easier to update than scattered inline disables.
<!-- rule:2719 -->
- Verify script paths in CI config/scripts exactly match repo paths and commit them with the executable bit set (e.g., `git update-index --chmod=+x .circleci/conditional-builds.sh`) — mismatched paths or missing exec bits break CI runs before any code executes. — CI failures from typo'd paths or non-executable scripts waste pipeline runs and are hard to debug — 404s or 'permission denied' errors surface far from their cause. Ensuring paths match and exec bits are set lets CI invoke scripts directly without runtime `chmod`.
<!-- rule:1725 -->
- Expose customized matching as a single regex config value, not token arrays — joining tokens hides regex semantics and hard-codes defaults — Consumers can't see or override the final pattern when it's built by joining tokens; a single regex value keeps validation surfaces explicit, opt-in, and predictable across both `wagtail` and client TypeScript matching code.
<!-- rule:2323 -->
- Use Debian-based `python` images in Python Dockerfiles (e.g. `wagtail/project_template/Dockerfile`), not Alpine — musl libc slows builds and lacks many prebuilt wheels. — Alpine's musl libc forces source builds and misses many prebuilt wheels, so image builds are slow and fragile; Debian/glibc images have broad wheel coverage. `-slim` keeps images small, but the full Debian image is needed once native build deps are involved (or when a package manager would otherwise pull in a second Python runtime, producing a larger and inconsistent final image).
  - Default to `python:<version>-slim`.
  - Use full Debian (e.g. `python:<version>-buster`) when building native deps (`Pillow`, `mysqlclient`, `psycopg2`) or when installing packages would drag in a competing Debian Python runtime and bloat the final image.
<!-- rule:836 -->
- Use `get_available_image_extensions()` (Django's full image extension list) — not Wagtail's configurable `get_allowed_image_extensions()` / `WAGTAILIMAGES_EXTENSIONS` — in accessibility and content checks that must detect any supported image, so images aren't missed when the setting is later restricted. — `WAGTAILIMAGES_EXTENSIONS` is user-configurable and may shrink over time; checks that must recognize any valid image (e.g. the accessibility item in `wagtail/admin/userbar.py`) break silently if they depend on it.
<!-- rule:1562 -->
- Check for sentinel values like wildcard `'*'` in list-valued settings and use membership (`value in setting`) rather than exact equality (`setting == [value]`) or positional checks (`setting[0] == value`) — sentinel handling must be order-independent. — List-valued settings may contain additional values or reorder their elements, so exact equality or first-element checks silently miss the sentinel and cause incorrect behavior on valid configurations.
<!-- rule:2445 -->
- Chunk large-payload records in conservative batches (e.g., 500) — bounds per-batch memory — Prevents OOM and memory spikes when records contain large payloads
<!-- rule:2900 -->
- Check `PageSubscription.comment_notifications` and the recipient's user-profile prefs before notifying — user-profile opt-out overrides per-object flags — The user-profile setting is a global opt-out and must win over per-object subscriptions, or users who've disabled notifications keep getting them from subscribed objects.
<!-- rule:2925 -->
- Treat `APPEND_SLASH`-style settings as fallback: match the exact URL first, then redirect to the slash-appended URL only when no exact match exists and the slashed form does. Never suppress explicitly defined non-trailing-slash routes — they must stay resolvable and take precedence. Keeping exact-match resolution ahead of the slash fallback prevents the setting from shadowing or breaking deliberately defined routes. Avoid the common mistake of conditionally removing non-slash routes based on the setting; the setting only decides the redirect, not what URLs are valid. — An `APPEND_SLASH` setting is a convenience for users, not a routing override — if it removes or blocks explicitly defined non-slash routes, legitimate endpoints silently 404, breaking existing clients and contracts. Resolving exact matches first preserves backward compatibility while still redirecting sloppy trailing-slash requests.
<!-- rule:2992 -->
- **Separate test namespaces; avoid broad `find_packages(exclude=...)` globs.** — Globs like `*tests*` partial-match a namespace, silently shipping or dropping subpackages and blurring what gets distributed.
<!-- rule:2324 -->
- Pin the distro in Docker base image tags (e.g. `python:3.6-stretch`, not `python:3.6`) — floating language-only tags silently swap the underlying OS on rebuild, breaking builds and changing runtime behavior. — Language-version-only tags are mutable aliases; when the upstream image's default distro moves (e.g. Debian stretch → buster), `docker build` pulls a different base without any change to the Dockerfile, which can break package installs, C library assumptions, and reproducible builds. Naming the distro makes the OS dependency explicit and stable.
<!-- rule:2317 -->
- Use `useradd -p '!' --no-create-home` for Dockerfile service users — disables password login and avoids unused home dirs — Locking the password prevents credential-based access to the service account; skipping the home dir shrinks the image and avoids stray files. Only override when the app explicitly needs a writable `$HOME`.
<!-- rule:2553 -->
- Define registry instances once in a central module and import that shared instance everywhere — re-instantiating per use site (e.g. `template_tags`) causes divergent state and config drift — Global registry instances must be single-source-of-truth. Instantiating locally at call sites (including in template tags) creates multiple registries that drift apart, causing bugs where one code path doesn't see updates made to another.
<!-- rule:1307 -->
- Use `ruff check .` and `ruff format --check .` in `.circleci/config.yml` instead of a separate formatter like `black` — one tool keeps CI config and its dependencies in sync — Single tool for both linting and formatting means fewer CI dependencies to pin, one config source, and no drift between what lints and what formats.
<!-- rule:859 -->
- Configure coverage `concurrency` (e.g. `multiprocessing,thread` in `pyproject.toml`/`setup.cfg`/`.coveragerc`) when CI runs tests in parallel — disabling `--parallel=1` trades fast CI for accurate coverage. — Parallel test execution combined with coverage needs explicit concurrency config so coverage.py aggregates worker data; forcing `--parallel=1` avoids the config but defeats the speed benefit and is a common cause of missing line coverage in CI.
<!-- rule:2985 -->
- Run tests against the installed distribution, not just the source tree, and add a `check-manifest` pre-commit hook whenever `setup.py` filters with `find_packages(exclude=[...])` — manual include/exclude patterns silently omit required sub-packages or ship unwanted files (see `torchbox/wagtailmedia` `.pre-commit-config.yaml` for the hook setup). — Packaging filters and source-tree tests are both blind to what actually lands in the sdist/wheel, so this catches missing sub-packages before release.
<!-- rule:2802 -->
- Treat Wagtail format settings as Django-localization-dependent — e.g. `WAGTAIL_DATE_FORMAT` maps to `DATE_INPUT_FORMATS`. Add a system check in `wagtail/admin/checks.py` that warns when the configured value isn't among the effective Django formats. — Silent fallbacks in widgets (`wagtail/admin/widgets.py`) surprise users when their configured format isn't actually applied.
<!-- rule:3062 -->
- Place subsystem-specific configuration types and loaders in the subsystem's dedicated config module `config/{subsystem}Config.js`, not in a generic utility config file — keeps each subsystem's config discoverable and self-contained. — The rule is architectural and applies across subsystems; the two-part guidance (placement + single source) is best expressed as two tight bullets to keep each under the length target while preserving the `config/{subsystem}Config.js` pattern reference.
  Use a single configuration JSON script/source per subsystem — a second script or tag for the same subsystem creates competing sources of truth.
<!-- rule:751 -->
- Don't add backend-specific guards/warnings (e.g., `isinstance` checks for `LocMemCache`, `FileBasedCache`, `DummyCache`) to optional cache features — Django's cache abstraction already handles them; document recommended backends instead. — Backend-specific guards duplicate Django's cache abstraction, age poorly, and miss real incompatibility conditions; documenting suitable backends and targeting shared technical constraints keeps the API portable and the constraints clear.
  - If a guard is truly needed, target the underlying incompatibility (e.g., caches that don't share state across processes/servers) and cover all backends sharing it.
  - Name the concrete constraint (multi-process isolation, `settings.DEBUG`) — vague labels like "production environment" or "thread safety" obscure the real condition.
