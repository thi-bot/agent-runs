# Naming Conventions

> Rules on spelling, consistent verbs and sibling names, symmetric paired members, descriptive method/helper/variable names, loop-variable naming, and queryset parameter naming.

**When to check**: When naming a new identifier (variable, function, method, class, parameter, or mapping key)

## Rules

<!-- rule:1427 -->
- Use conventional, correctly spelled identifiers across code, docs, fixtures, and tests — misspelled public names (e.g. `pickable`, `unsecure`, `deffer_fields`) become permanent API/typing liabilities — Public identifiers like Django model fields, options, and documented names are effectively frozen once released; a misspelling in `pickable` (correct: `picklable`, per Python's `pickle` docs and `non_picklable_attrs`), `unsecure` (correct: `insecure`), or `deffer_fields` (correct: `defer_fields`) forces users to code against the typo forever and makes later correction a breaking change. Verifying spelling against standard references and Django conventions up front avoids that trap for variables, parameters, model options/fields, docs, fixtures, test names, and test data.
<!-- rule:1608 -->
- Spell identifiers, comments, and test names correctly using standard English and canonical tech names (`postgres`, `formatted_sql`, `expiry`, `overridden`, `raccoon`); fix misspellings rather than preserving them from prior code — typos harden into public API surface and propagate through pluralized references. — Misspellings in class/method/identifier names become permanent API surface once published, are painful to rename later, and multiply wherever the identifier is referenced or pluralized. Standard English and canonical technology spellings (e.g., `postgres`, `formatted_sql`, `expiry`) keep names discoverable and greppable, and prevent inconsistency when contributors copy-paste from prior code.
<!-- rule:1408 -->
- Match sibling verb/parameter naming in a module — synonyms fragment the API and defeat grep — When identifiers, parameters, and verbs drift into synonyms within a module, callers can no longer predict names from pattern, and searching for `create_permissions` or `register_backend` misses the divergent versions. Reusing the established `{action}_permissions` and `register_*` prefixes keeps permission-helpers and URL-backend registration discoverable and consistent across the Django codebase.
  - Use `{action}_permissions` in `django/contrib/auth/management/__init__.py` (e.g. `create_permissions`, `rename_permissions`) and `register_*` in `django/utils/url_config.py` — ad-hoc `inject_*_operations`/`add_*` variants hide the established convention from readers and greps
<!-- rule:426 -->
- Name loop variables after the value the iterable actually yields, and use that variable directly inside the loop body — never shadow, reassign, or reuse outer/stale names, re-index the iterable, or rely on Python's leaked for-loop variables. Bind any rename to a new clearly named local, and use distinct descriptive names when nesting loops. — Iterating and then indexing the iterable again (or reading a leaked loop variable after the loop) breaks as soon as the iterable is a one-shot iterator like a generator or `zip`/`map` result, and shadowing an outer name silently corrupts the enclosing scope's value — a common source of subtle bugs in `contrib/admin`, `db/models`, and `migrations`.
<!-- rule:4930 -->
- Name paired members symmetrically — same base name and visibility prefix (e.g., `_apply_operations`/`_unapply_operations`, `_get_token`/`_set_token`) — asymmetric names hide the pairing and break `grep`-based discovery. — When two members are a pair (forward/reverse lifecycle, getter/setter, constructor/destructor), a shared base name with matching visibility makes the relationship obvious at a glance and keeps both halves findable with a single search. Mismatched names (e.g., `_apply_operations` vs `_reverse_operations`) force readers to trace the code to discover the pairing, and tools like `grep` or IDEs can no longer surface both halves together.
<!-- rule:2054 -->
- ```markdown — A generically named method reads as a general-purpose helper, so callers reuse it in contexts it never handled and get silently wrong results — the wrong scope, ordering, or execution context — instead of an error that would have sent them to the right method.
  - Name methods for their exact return value, ordering, and execution context (e.g. `_earliest`, `_is_referenced_by_fk_constraint`, `get_facet_counts`) — generic names like `_is_referenced` or `_earliest_or_latest` imply broader applicability than the method actually has, causing callers to misuse it
  ```
<!-- rule:3232 -->
- Name helpers, transforms, and context managers verb-first on their target (`normalize_json`, `table_to_model_name`, `debug_transaction`, `execute_hook`, `measure`) — call sites then read as action-on-target, and names stay stable when internals change — Implementation-shaped names lie at the call site: `json_normalize`, `debug_transaction_end`, `add_execute_hook`, and `timed` each encode how the code currently works rather than what the caller is asking for, so a caller reaching for `debug_transaction_end` gets only half a lifecycle and a caller reading `timed` cannot tell what is being measured — and when the internals shift, the misleading name must be changed and every call site along with it.
    Why: noun-first (`json_normalize`), lifecycle-boundary (`debug_transaction_end`), mutator-derived (`add_execute_hook`), and state/adjective (`timed`) names describe implementation details rather than the operation, so they mislead readers and get renamed whenever the implementation shifts.
<!-- rule:3689 -->
- Name variables, attributes, arguments, and mapping keys after the data they hold, not its shape or source — misleading names (e.g. `_qs` for a value that isn't a ready-to-use query string) cause downstream misassumptions — Names that describe shape or source rather than contents mislead readers about what a value actually is (e.g. `_qs` implying a query string, `pk_set` implying primary keys), and collapsing distinct state into positionally indexed tuples obscures meaning. Reusing Django-reserved names (`label`/`app_label`) for non-app-label values breaks the convention that code and users rely on when introspecting `MIGRATION_MODULES` or template `libraries`. The `meta_`/`_items` scheme signals both origin (`HttpRequest.META`) and picklability constraints, which handler-specific `_attrs` names hide.
  - Represent distinct query or context state with separate, descriptively named attributes instead of positional tuple indexing
  - Reserve Django names for their true meanings: don't call an `m2m_changed` `pk_set` arg when it may hold `to_field`-relation values, not primary keys; use `module_name` for `settings.TEMPLATES[*].OPTIONS['libraries']` keys and `app` for `MIGRATION_MODULES` keys (which may be an app label or app config path); keep `label`/`app_label` for actual app labels only
  - For HTTP request metadata, name parsed comma-separated sub-values of a single header after those values (`_items`, `_keywords`, `_directives`), not `_headers`; prefix non-picklable entries taken from `HttpRequest.META` as `meta_*_items` (e.g. `meta_non_picklable_items`), not handler-prefixed `_attrs`
<!-- rule:4864 -->
- Name helpers by semantic purpose, not mechanical transformation — `ensure_hashable`, not `list_to_tuple`; `serialize_result`, not `obj_to_dict`. — Purpose-based names (`ensure_hashable`, `_expr_refs_base_model`, `serialize_result`) stay accurate when the implementation changes, while mechanical names (`list_to_tuple`, `_expr_refs_alias`) become lies once the underlying structure shifts. For serialization helpers, encode serialization intent, accessor behavior, and return format in the name — prefer `serialize_result` or `get_inline_formset_json` over vague suffixes like `obj_to_dict` or `_data`. When you change a helper's implementation, rename it to match what callers can now rely on.
<!-- rule:6015 -->
- Use `queryset` / `querysets` (never `qs`) for queryset parameters and locals — matches Django's public API naming so callers and tests read consistently across `django/db/models`, `django/forms`, and `django/contrib/admin`. — Django's own APIs use the spelled-out `queryset`; abbreviating to `qs` in a third-party or contrib module breaks the naming users already expect when reading signatures, docs, and `objects.get_queryset()` call sites.
