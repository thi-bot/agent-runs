# Dependencies & Packaging

> Rules for dependency manifests, lockfiles, version pins/extras, packaging config, and third-party library integration.

**When to check**: When adding, updating, or declaring dependencies, or changing packaging configuration.

## Rules

<!-- rule:142 -->
- Sync `.pre-commit-config.yaml` hook `rev` and `additional_dependencies` with pins in `pyproject.toml`/`setup.py`/`requirements.txt`/`package.json` — a bump on either side must land in the same change, or pre-commit runs a different tool version than CI/installs use. — Preserves concrete file paths, the `.pre-commit-config.yaml` fields (`rev`, `additional_dependencies`), and the auto-rewrite hazard (`pre-commit autoupdate`) that justifies placing notes above blocks rather than inline. The imperative form plus the WHY (version drift between pre-commit and CI/installs) makes the rule checkable without being deontological.
  - Record cross-file pins as a grouped comment above the dependency block or a standalone `# NOTE` above the field, never inline/trailing — `pre-commit autoupdate` and formatters rewrite those lines and silently drop the note.
<!-- rule:1954 -->
- Use `npm ci` for Node dependency installs in CI and docs; fall back to `npm install` only when no lockfile exists. — `npm ci` installs exactly from the lockfile, ensuring reproducible builds across CI (`.circleci/config.yml`, `.squash.yml`) and docs builds (`.readthedocs.yml`) and avoiding lockfile drift that `npm install` can introduce.
<!-- rule:347 -->
- Commit `package.json` changes and regenerated lockfiles (`package-lock.json`/`npm-shrinkwrap.json`) together — keeps installs reproducible and CI from drifting; align Node/npm versions (`nvm use`) to avoid spurious lockfile diffs. — Lockfiles record the exact resolved dependency tree. Committing `package.json` edits without the matching lockfile regeneration lets consumers and CI resolve different versions than you tested — a common source of "works locally, breaks in CI" bugs. The second half of the rule guards against the opposite failure: a stale local Node/npm version rewriting the lockfile in ways that don't reflect the intended dependency change, polluting the diff and hiding the real update.
<!-- rule:2416 -->
- **Declare each dependency exactly once in the manifest that owns it** — everything else (tox.ini, CI, docs, other workspaces) should consume that declaration, not re-list the package. Duplicated declarations drift out of sync and silently pin different versions. — Cross-cutting dependency convention spanning client/, react-streamfield/, .github/, package.json, setup.py, and tox.ini, so it belongs in a repo-wide AGENTS.md rather than any single directory.
  - **Python: `setup.py`/`pyproject.toml` extras are the single source of truth.** tox.ini, `.github/` workflows, and `docs/requirements.txt` should reference the extra (e.g., `.[test]`) instead of repeating pinned packages — keeps CI and test envs matching what users install.
  - **JS/workspaces: declare a package in the `package.json` of the workspace whose code imports it directly**, not the root `package.json`. Remove declarations that merely duplicate a dependency already provided transitively (e.g., via a shared config package like the one backing `react-streamfield`).
  - **Frontend libraries consumed by a host app: put host-owned framework/runtime libraries (e.g., `react`, `redux`) in `peerDependencies` and externalize them from the distributed bundle** — bundling a second React copy breaks hooks and context in the host. Align versions via the host's `dependencies`, not its `devDependencies`.
  - **Non-shared runtime libraries go in `dependencies`** and should resolve through the consumer's npm build, not be bundled — keeps the published bundle small and dedupable.
  - **Never add a `devDependency` for a package already managed as a peer dependency of a shared config package** — update that shared config package instead, so all consumers inherit the change.
<!-- rule:667 -->
- Don't rely on JS load/execution order to coordinate module init — `webpack` entrypoints and `defer`red `<script>` tags aren't ordered by network timing, parsing, or caching, so interdependent modules may run before their dependencies exist. — Ordering isn't guaranteed due to network timing, parsing, and caching.
<!-- rule:812 -->
- Pin dependencies in `setup.py`/`pyproject.toml`/`tox.ini` as `pkg>=min,<next_major`, not bare names — set `min` to the lowest version compatible with the project's minimum supported Python/framework, not the current release; add upper bounds only to block known/plausible breaking changes, and apply the same convention when editing existing deps so downgrades and compatible upgrades both stay installable. — Bare names resolve to whatever is latest, so an old release can't install and a fresh CI run can pick up a breaking upstream change; a `min` tied to the supported Python floor keeps the declared floor honest, and capping below the next upstream major avoids blocking compatible minor/patch updates while still guarding against known incompatibilities.
<!-- rule:3045 -->
- Read versions from `__version__`/`importlib.metadata` or backend package metadata, never literals — hardcoded strings drift from the real version and silently break consumers that compare against them. — Single source of truth keeps version comparisons (e.g., in `client/src/utils/deprecation.ts` and `wagtail/templatetags/wagtailcore_tags.py`) accurate across the stack.
<!-- rule:2415 -->
- Put `boto3`, image codecs, and other feature-specific deps in `[project.optional-dependencies]` extras, not core — keeps base install lean — Core dependencies are installed for every user; forcing unused libraries on them bloats installs and creates avoidable version conflicts. Extras let users opt in only to the integrations they need, and `setup.py`/docs should reference the extras extra name consistently.

<!-- rule:2901 -->
- Guard optional/third-party app permissions, symbols, and relations with `apps.is_installed("<app_label>")` — prevents import and lookup errors when the app isn't installed — A bare reference to a permission, symbol, or relation from an optional app (e.g. in `wagtail/search/models.py` or `wagtail/admin/wagtail_hooks.py`) breaks imports and runtime lookups whenever that app is absent; the `apps.is_installed(...)` check keeps the project usable without all optional dependencies.
<!-- rule:1275 -->
- Treat backwards-incompatible changes as major releases — batch them to avoid version churn — Breaking changes (dropping Python versions, changing public APIs, requiring registration updates) force users to migrate. If no other breaking changes are queued for the next release, delay the change so multiple breaks ship together in one major bump. When you do ship one, bump the version in `setup.py` and keep `{versionadded}` markers and upgrade-consideration docs aligned — mismatched metadata misleads users about what will break.
<!-- rule:1780 -->
- Fallbacks for missing optional deps/APIs must return a behavior-equivalent result or raise explicitly — never silently return the input unchanged (hides failures from callers relying on the documented contract). — Silent identity returns mask missing-dependency bugs and violate the helper's documented contract across `client` TypeScript and `wagtail` Python code.
<!-- rule:2689 -->
- Bump `package.json` deps to the latest version and apply the upgrade's source-code migrations (CSS class names, APIs) in the same change — partial upgrades leave the codebase on incompatible APIs. — Upgrading the manifest without migrating call sites leaves the repo in a half-upgraded state where old API/CSS usage silently breaks or drifts further from upstream with each release.
<!-- rule:2179 -->
- Generate against the project's pinned deps and the generator's supported version, not the local env — keeps emitted templates/migrations runnable for users whose installs differ from yours — keeps generated templates/migrations runnable for users whose installs differ from yours
<!-- rule:2758 -->
- Skip heavyweight date libs (`moment`) — prefer `Intl.DateTimeFormat`/`Intl.RelativeTimeFormat`, `date-fns`, or `luxon`; bundle bloat and i18n gaps hurt every consumer. — Native `Intl` APIs cover formatting and relative-time needs without extra bytes or locale-data drift; `date-fns`/`luxon` stay tree-shakeable and immutability-safe when a library is genuinely needed. Requesting a pre-formatted field from the API avoids duplicating formatting logic in components entirely.
<!-- rule:2717 -->
- Generate versions in PEP 440 format (`.devN` for nightly; reuse existing `alpha`/`beta`/`rc`/`final` types, not custom SemVer types like `dev`) — setuptools, pip, and PyPI parse PEP 440, so custom types break installation. — Split into two bullets: the packaging-format rule with the pip/PyPI rationale, and the generation/validation sync rule with the specific files and the KeyError trap. Preserved all project-specific references (`wagtail/utils/version.py`, `scripts/nightly/get_version.py`, `VERSION` tuple, `.devN`, `alpha`/`beta`/`rc`/`final`). The KeyError detail is the most valuable bit — it's the concrete failure mode.
  When introducing a new release type into the `VERSION` tuple or `scripts/nightly/get_version.py`, update `wagtail/utils/version.py` in the same change: add it to the valid-release-type mapping, make the lookup tolerant of unknown values (don't index-into-dict — that raises `KeyError`), and update docstrings/comments to list all permitted types and the expected packaging format. Version generation and validation must stay in sync or nightlies will fail to parse.
<!-- rule:2130 -->
- Drop deprecated Setuptools constructs (`zip_safe`, custom `bdist_egg` commands/imports/checks) from packaging configs like `setup.py` and `wagtail/utils/setup.py` — modern Setuptools removed them, so keeping or explicitly setting them causes build failures and warnings. — Preserves project-specific references (e.g., `wagtail/utils/setup.py`, `zip_safe`, `bdist_egg`) so AI assistants know exactly what to remove when editing any packaging file.
<!-- rule:1816 -->
- Keep `docs/Makefile` Sphinx options compatible with the minimum `Sphinx` pinned in `setup.py` — bump the pin when adopting newer flags (e.g. `--fail-on-warning`) so docs builds don't break for users resolving the old minimum. — The build option and the dependency floor must move together: adopting a Sphinx flag that only exists in a newer release while leaving the `setup.py` minimum untouched lets installs resolve an older Sphinx that rejects the flag, failing `make -C docs` downstream.
<!-- rule:2136 -->
- Never import the package itself in `setup.py` or build logic — build frontends run setup in an isolated env where it isn't installed yet, so such imports fail (or worse, silently pick up a stale installed copy). — Isolated builds can't import it yet
<!-- rule:2286 -->
- Pin `django-tasks` to `>=0.8,<0.9` in `pyproject.toml` until a release formally supports Django 6.0 — upstream breakage reaches downstream projects otherwise. When you change the constraint or land a compatibility fix, update the related guidance and release notes in the same change (e.g. 0.10.0 already carries the Django 6.0 fix, so 0.11.0 is unnecessary). — 
<!-- rule:2393 -->
- Add framework type stubs (e.g. `django-stubs`) as dev deps and use direct attribute access like `request.user` — `getattr()` workarounds hide type errors and multiply across call sites. — One dev dependency fixes every call site; per-site `getattr()` fallbacks scatter unchecked attribute access and mask real breakage when the framework API changes.
