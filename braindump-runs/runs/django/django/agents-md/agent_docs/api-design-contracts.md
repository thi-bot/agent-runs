# API Design & Extension Points

> Design public APIs and extension points: preserve subclass types, centralize connections, use public hooks, keep base/subclass responsibilities clear, and avoid mutable accumulator patterns.

**When to check**: When designing public interfaces, extension points, handler hierarchies, or reusable helper functions.

## Rules

<!-- rule:844 -->
- Define expressions via the `resolve_expression` protocol, not by subclassing base `Expression` — preserves subclass identity for downstream specialization — Django's ORM dispatches on expression type during query resolution; collapsing a subclass into `Expression` breaks code that needs to distinguish and specialize specific expressions (e.g. in `django/db/models` compilation and `tests/lookup`, `tests/queries`).
<!-- rule:4325 -->
- Keep perf/algorithm changes behavior-preserving + staged rollout — prevents operational regressions — Rewriting hot paths or algorithms shifts execution cost and can silently change edge-case behavior; a behavior-preserving diff verified against the old implementation, plus a staged rollout, catches regressions that unit tests miss before they hit production.
<!-- rule:2030 -->
- Expose `is_no_color` on the shared style module and keep predicates like `supports_color()` side-effect free; init optional libs only in `color_style()` or at import behind a module-level availability flag. — Predicates are called speculatively, often multiple times; side effects there break idempotence and can trigger optional imports unexpectedly. Centralizing `is_no_color` avoids divergent detection logic across call sites such as `django/core/management/utils.py` and `color.py`.
    Rationale: Duplicated detection at call sites drifts out of sync, and initializing inside a predicate fires optional-dependency imports (and any resulting errors) on a mere check — e.g. `django/core/management/utils.py` querying `color.py` for color support should never mutate shared state.
<!-- rule:3339 -->
- Use `hash(obj)` for non-cryptographic hashing instead of `hashlib` digests, and never call `obj.__hash__()` directly. — `hash()` is faster and caches string hashes, while `hashlib` is overkill for non-crypto use; calling `obj.__hash__()` bypasses the `hash()` protocol and breaks for objects where `__hash__` is `None` (unhashable types), so prefer `hash()` and reserve `hashlib` for actual cryptographic needs.
<!-- rule:473 -->
- Pass `pathlib.Path` objects to library APIs; only call `str()` for external CLI tools. — Preserves native path semantics across `django/` and `tests/`, and avoids the Windows-specific bug where a `str()`-converted path is interpreted as drive-relative instead of working-directory-relative.
  - When converting a `Path` for an external command on Windows, prefix it with `.\` so the path resolves relative to the working directory rather than the drive root — bare converted paths silently point at the wrong location.
  - Most libraries (and the `django/` internals) accept path-like objects natively; keeping `Path` avoids encoding and separator bugs that appear once paths become `str`, while CLI tools require a real string.
<!-- rule:3538 -->
- Normalize or decode **all** representations of a URL-derived identifier before comparing them — ASCII-only forms aren't automatically safe from URL-reserved characters (e.g. `/`, `#`, `%` may still be percent-encoded). Differences in decoding between sites that build vs. consume an identifier (as in `django.contrib.admin` and `django.utils`) let reserved characters slip past comparison, causing lookup mismatches or access-control bypasses — so apply identical normalization to every form before equality, membership, or path checks. — Percent-encoded and literal forms of the same identifier can differ in raw string comparison even when they mean the same thing. If some code paths (e.g. those feeding `django.utils.html.urlize` or `django.contrib.admin` views) decode and others don't, reserved characters like `/`, `#`, or `%` can evade filtering, leading to inconsistent lookups and potential security bypasses. Normalizing uniformly prevents these mismatches.
<!-- rule:6008 -->
- Reach into framework internals only via public APIs — private attribute mutation breaks on `Django` upgrades — The rule is a general behavioral/API-design principle (use public APIs, avoid mutating private state, remove obsolete compatibility shims) that applies broadly rather than to any single module. Evidence shows it was applied across multiple disparate directories within the django project (django/contrib/admindocs, django/urls, django/template), confirming cross-cutting scope.
    - Why: `Django` internals (e.g. in `django/contrib/admindocs`, `django/urls`, `django/template`) change without notice; mutating them silently breaks users on the next release.
  - Remove compatibility shims once the minimum supported framework version exposes the needed attribute or API
    - Why: shims kept past their `Django` version gate obscure the real code path and complicate future upgrades.
<!-- rule:6020 -->
- Keep settings-key aliases (e.g. `databases`) off generic base classes like `BaseHandler` — put them on the concrete subclass owning `settings_name`, so the base stays reusable across handler families. — Aliases tied to a specific settings key on the base class leak handler-specific concerns into every subclass and make the base unusable for unrelated handler families. Shared resolution logic belongs in `BaseHandler`; per-instance derivation belongs in an overridden `configure_settings()`, not in mutations of global `django.conf.settings`.
<!-- rule:5249 -->
- Merge helper results once at the outermost call — return the value (or an intermediate like a `list` of pairs), or thread one accumulator created fresh when omitted. Don't `update()` in each recursive branch, and don't add optional mutable accumulator params whose return value is sometimes ignored: per-level merges duplicate logic across branches, and half-used accumulators let callers silently drop results. — Per-level merging duplicates `update()` logic across branches and makes the aggregate's ownership unclear; optional mutable accumulators that are only sometimes consumed invite callers to discard partial results without noticing.
<!-- rule:1742 -->
- Prefer public extension points (e.g., middleware) over subclassing internal handler classes — internal classes can be refactored or removed without notice, breaking your code on framework upgrades — Internal handler classes and their orchestration methods (like `cleanup_headers()`) are implementation details that can shift between versions; hooking into them couples the codebase to unstable APIs and silently breaks on upgrades. Public extension points and narrow hook methods (like `set_content_length()`) are the contract the framework actually maintains.
  - Only document/test handler classes confirmed as public API — locks in behavior the framework hasn't committed to supporting
  - If subclassing is unavoidable, override the narrowest hook responsible for the behavior (e.g., `set_content_length()`) rather than a broader orchestrator that calls it (e.g., `cleanup_headers()`) — keeps your override resilient to changes in the surrounding flow
<!-- rule:2931 -->
- In backend/plugin factory helpers, select the config/registry entry first and instantiate through one uniform path, passing the same contextual kwargs (e.g. `provider`) to every backend; return the first match and raise only when nothing is configured — ad-hoc branching per subsystem makes `django/core/mail` and `django/template` backends diverge in behavior and error handling. — The rationale: uniform selection and kwargs keep backends interchangeable and error handling predictable; per-call-site branching in Django's mail and template factories leads to inconsistent backend behavior and missed `provider` context.
<!-- rule:5824 -->
- Store lazily initialized resources in a sparse `dict` populated on first use, not preallocated placeholders. — Preallocation eagerly consumes memory/connections for indices never touched, and forces `__dir__`/autocomplete-style introspection to either lie or instantiate everything just to answer metadata queries.
