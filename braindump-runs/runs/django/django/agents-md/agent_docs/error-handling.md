# Error Handling and Resource Cleanup

> Rules about raising clear errors, using sentinels and state validation, guarding edge values, and cancellation-safe resource cleanup.

**When to check**: When handling errors, validating preconditions, or cleaning up resources.

## Rules

<!-- rule:4637 -->
- Assign each process-pool worker a unique ID at spawn; don't derive IDs from `incrementing_counter % pool_size` — out-of-order worker termination makes recycled IDs collide — Modulo-derived IDs assume workers exit in FIFO order; when a worker dies out of order, its recycled ID still points at a live worker and two workers end up sharing an ID. Remapping IDs hides that collision along with whatever caused the worker to terminate in the first place, so the underlying termination bug resurfaces under load.
  - Treat worker-ID remapping as a symptom fix — find why workers terminate rather than masking the resulting missing-resource failures
<!-- rule:1026 -->
- Use `gzip.open(path, mode='rt', encoding='utf-8')` and iterate the text-mode file for decoded strings — `mode='r'` returns bytes, so `.decode()` on each line is redundant and error-prone — Opening gzip files in text mode with `encoding='utf-8'` gives you decoded `str` lines directly. Using `mode='r'` (binary) forces manual `.decode()` calls per line, which is easy to forget, mixes concerns, and produces `TypeError` when a `str` is passed where bytes are expected.
<!-- rule:955 -->
- Use a unique sentinel (not `None`) when restoring optionally-present attributes in `finally`/cleanup blocks — `None` can't distinguish "attribute was absent" from "explicitly set to `None`", causing cleanup to resurrect or drop attributes incorrectly. — Cleanup code often restores attributes it may have temporarily added or overwritten. If the prior value was `None` but the attribute did not exist at all, branching on `None` will wrongly `del` or wrongly re-assign. A module-level sentinel (or `object()`) makes the "was absent" case unambiguous and keeps `finally` paths from corrupting object state.
<!-- rule:1049 -->
- Use `getClientRects().length === 0` or `offsetParent === null` to test element visibility — `offsetHeight`/`outerHeight` miss elements hidden by ancestors (e.g. clipped or `visibility`-hidden), so they falsely report hidden elements as visible — The `offsetHeight`/`outerHeight` check misses elements hidden by ancestors (e.g. clipped or `visibility`-hidden), so hidden elements are falsely reported as visible.
<!-- rule:3066 -->
- Format bytes in error messages with `%r`, not `.decode()` — decoding in error paths can itself raise, masking the original exception — Using `.decode()` to format bytes in an error path can raise `UnicodeDecodeError` from invalid UTF-8, replacing the real exception with a misleading decoding failure, whereas `%r` always safely renders the bytes and preserves the original error context.
<!-- rule:3168 -->
- Make state-specific attributes on result/state objects raise when accessed in other states, not return `None` — forces callers to check `result.status` first, avoiding silent sentinel misreads. — Returning `None` hides misuse: callers that skip the `result.status` check get plausible-but-wrong values instead of a loud failure at the point of the bug.
<!-- rule:3969 -->
- Name the function and violated constraint in precondition error messages (e.g., `` `setup_test_environment() was already called and can't be called more than once.` ``) — callers only see the string, so an unnamed failure forces them to read your source to diagnose it — The error string is the only thing surfaced to callers when a precondition breaks; naming both the function and the specific constraint lets them diagnose and fix the call site without opening the raising code.
<!-- rule:4552 -->
- When building a value from a base (hash digest, filename, index name) plus a caller-supplied suffix under a `max_length` constraint, compare the suffix length against the remaining budget: return the combined value immediately when it fits, and raise a clear error when it doesn't. — Silently truncating the suffix (or the base) produces values that look valid but collide or point at the wrong resource — e.g. two distinct filenames mapping to one stored blob, or two db indexes sharing a truncated name. Failing loudly on overflow forces callers to shorten their suffix explicitly, and the early-return path keeps the common fitting case free of trimming/iteration overhead.
<!-- rule:5655 -->
- **Guideline:** — Path-based checks in `django/core/checks/security/base.py` and `django/core/checks/caches.py` can each detect multiple relationships between two paths (`equal`, descendant, ancestor). Resolving the exact relationship before wording the warning hint ensures the message names the correct relationship and direction, so users are not misled into debugging the wrong path. Emitting no warning when none of the supported relationships apply avoids false positives.
  - Name the exact path relationship (`equal`, descendant, ancestor) in warning hints — resolve which relationship holds and its true direction before wording the message, and emit nothing when none of the supported relationships apply. Mislabeling the direction (e.g., reporting an ancestor relation as descendant) sends users debugging the wrong path; path checks like `django/core/checks/security/base.py` and `django/core/checks/caches.py` share this pattern across the codebase.
<!-- rule:4589 -->
- Guard sentinel/edge values (`DatabaseDefault`, null relations) in **every** render path, not just one. — A guard added to only one branch (e.g. the `if boolean:` early return) or one helper lets sibling paths — `display_for_field` vs `display_for_value`, or other call sites — still emit the raw sentinel, producing broken output that only shows up on the untested path.
<!-- rule:6031 -->
- Store callbacks in one ordered queue as `(sid, func, is_robust)` tuples instead of separate queues — preserves execution order across differing error semantics. — Check the `execute` flag before `is_robust` when running the queue, so the `try`/`except` wrapper only wraps callbacks that actually run; splitting queues or checking robustness first breaks ordering guarantees and lets skipped callbacks still be exception-handled.
<!-- rule:6218 -->
- Enforce size/count limits on delimited request/query-string parsing in a small helper using the parser's public API or `str.split(sep, maxsplit)`; raise `SuspiciousOperation` on overflow — parser internals and stateful `str` subclasses break when the parser changes and hide the limit from the caller. — Parser internals are unstable across versions, and a custom stateful `str` subclass with manual/recursive scanning is fragile and surprising; `SuspiciousOperation` is Django's canonical signal that the input is malformed/suspicious.
<!-- rule:2906 -->
- Put resource release and handler/state restoration (`close`, `pop_connection`, deregistration) in `finally`, and `asyncio.shield` awaited cleanup (e.g. extract into a `_aexit` coroutine) — a `CancelledError` raised during `__aexit__` otherwise skips commit/rollback/close and leaks DB connections; never depend on an un-awaited scheduled task to clean up — `CancelledError` can be raised mid-teardown of async context managers, so any cleanup not in `finally` or not shielded gets skipped, leaving connections popped, handlers un-deregistered, and transactions uncommitted/unrolled — corrupting shared-resource bookkeeping for later callers.
<!-- rule:2020 -->
- Make close/cleanup best-effort: wrap `close()` in `try/except` and set `self.<resource> = None` after closing. — Health-check and cleanup helpers must not raise on close failures, and clearing the attribute (e.g., `self.connection = None`) prevents reuse of a closed resource.
