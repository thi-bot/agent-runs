# Docstrings & Inline Comments

> Rules on class docstrings, grammatical comment prose, documenting non-obvious operations/side effects/regexes, commenting ordering constraints, grouping related constants, callable-name notation, and removing comments that restate code.

**When to check**: When writing or editing docstrings and inline code comments

## Rules

<!-- rule:1831 -->
- Write callables with trailing `()` in prose (comments, docstrings, docs, release notes, user-facing messages) — e.g. `method_name()`, `ClassName.method()` — so readers can tell calls apart from variables, attributes, classes, and modules, which stay bare. — Bare names read as attributes or variables, so omitting `()` in prose makes it ambiguous whether you mean the callable itself or a value; the convention keeps comments, docstrings, and docs unambiguous about what's being referred to.
<!-- rule:4732 -->
- Comment non-obvious defensive operations inline — e.g. why an iterator is materialized, `None`/blank values are filtered, or a shared object is copied — naming the hazard they avert, since silent removals otherwise reintroduce the bug. — Defensive code (materializing iterators, filtering `None`/blank values, copying shared objects) often looks redundant to readers and gets "cleaned up" unless the inline comment states which underlying hazard or invalid values it guards against; across modules like `django/db/models`, `django/db/migrations`, `django/template/loaders`, and `django/core` these guards exist for non-obvious reasons that aren't evident from the call site alone.
<!-- rule:2439 -->
- Start public class docstrings with a concise present-tense noun phrase (e.g. `Represents ...` in Sphinx `.. class::` docs) — consistent openings make API references scannable and avoid article/hedging errors. — Docstrings are the primary interface documentation users read when scanning APIs; a consistent present-tense opening (noun phrase in `__doc__`, third-person `Represents ...` under `.. class::`) keeps Sphinx references uniform and prevents distracting errors like `An class`, hedges (`meant to`), analogies (`Like @property`), or vague 'wrapper' phrasing. Document the class's intended purpose and full scope, not just the subset currently implemented, so readers know the contract rather than the current state.
<!-- rule:4152 -->
- Write comments as complete grammatical prose: full sentences, correct punctuation, articles for SQL keywords as common nouns ("an INSERT statement"), and standard technical casing (`SQL`, `Postgres`, `Oracle`, `auto-increment`, `per table`). — Comments are documentation — prose keeps them readable and unambiguous, and consistent casing disambiguates keywords from identifiers.
<!-- rule:5549 -->
- In parsing/formatting docstrings, list only non-redundant supported input formats with concrete I/O examples — collapsing subsets under a documented superset and scoping broad claims like `ISO 8601` to actual sub-formats prevents readers from assuming support the return type can't provide — Docstrings for parsers/formatters are the contract callers read before passing input. Enumerating redundant sub-formats (e.g., both `YYYY-MM-DD` and `YYYY-MM-DDTHH:MM`) or making unscoped standard-format claims implies the utility accepts inputs it silently rejects or can't round-trip through its return type — leading to runtime failures in code that looked correct.
<!-- rule:976 -->
- Document non-obvious side effects (process termination, implicit resource/config init, input mutation, state changes) at the call site, docstring, or reference docs — state exact triggering conditions, scope, and every affected model/option, verified against the implementation — stale or partial side-effect docs mislead users about model/queryset/field behavior in ways the code never did — Side effects that differ from documented behavior are worse than undocumented ones: users trust reference docs for `QuerySet` options, model setters, and formset operations, so an inaccurate scope (missing affected model, wrong condition) causes silent bugs. Verifying against implementation keeps docs honest as code changes.
<!-- rule:394 -->
- Comment every complex or non-obvious regex above the pattern describing what it matches (with example inputs) and any assumptions — regexes are write-only, so without context future readers break subtle parsing like the date/interval formats in `django/utils/dateparse.py`. For long or punctuation-heavy patterns, compile with `re.VERBOSE` and split across lines so each alternative is documented inline. Link the governing specification when the pattern implements a standards-defined format. — Regexes are notoriously hard to reverse-engineer, so a comment above the pattern (what it matches, example inputs, assumptions/limits) lets maintainers avoid breaking subtle parsing logic. Multi-line `re.VERBOSE` patterns make each alternative self-documenting, and spec links anchor the pattern to its authoritative definition instead of a guess from the author's memory.
<!-- rule:6202 -->
- Comment only non-obvious code — edge cases, API-call rationale, complex conditions; delete comments/docstrings describing behavior that isn't implemented (common after porting) — Self-explanatory code doesn't need restating, and stale docs that outlive the code they described actively mislead readers — a wrong comment is worse than none.
<!-- rule:3445 -->
- Group constants/attributes that share purpose under one section comment, and document any non-obvious ordering or similar-looking attributes with distinct roles — readers can't infer grouping intent from names alone, so unexplained splits or sorts look arbitrary. — Readers can't infer grouping intent from names alone, so unexplained splits or sorts look arbitrary.
