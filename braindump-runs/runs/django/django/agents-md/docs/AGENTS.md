# docs/ Guidelines

## Documentation

<!-- rule:75 -->
- Match reStructuredText heading underlines/overlines to the exact text length — mismatches trigger docutils/Sphinx build warnings or broken rendering — Underlines that are shorter or padded with trailing punctuation cause build noise and inconsistent rendering across the `docs/**/*.txt` tree. Applying the same underline style and length to all sibling headings at the same level keeps the section hierarchy stable so Sphinx resolves levels correctly.
<!-- rule:5811 -->
- In docs prose, use `setup` as the noun/adjective and `set up` as the verb — swapping them reads as a grammar error to users. — Documentation is user-facing prose; inconsistent `setup`/`set up` usage looks like a typo and undermines trust in the docs. The one-word form is the noun/adjective ("run the setup script"), the two-word form is the verb ("set up the environment"). Since every occurrence lives under `docs/`, keep this convention in `docs/AGENTS.md` so it stays scoped to the prose it governs.
<!-- rule:3110 -->
- Reflow reST tables to fit content — column widths track the longest cell, separators contiguous, `| ` spacing consistent. — misaligned markup renders incorrectly or breaks Sphinx table parsing; inconsistent spacing makes diffs noisy.
  Rationale: misaligned table markup renders incorrectly or breaks Sphinx table parsing, and inconsistent spacing makes diffs noisy.
<!-- rule:73 -->
- In `docs/` prose, use `that` (no comma) for restrictive relative clauses and `which` (comma) for non-restrictive — matches Django docstring style and keeps clauses unambiguous — Restrictive clauses identify the noun they modify and take no comma; a comma changes the meaning by making the clause parenthetical. `that`/`which` swapping is the reader's only signal for this distinction, so mixing them (or inserting a stray comma) makes docs read ambiguously — the same convention holds across `docs/` and Django docstrings, so anything else looks inconsistent.
  - Bad: "a file, that you want to link" / Good: "a file that you want to link"
<!-- rule:1852 -->
- Use a single cross-platform name for commands and OSes in docs — drop `.exe` suffixes and `(...)` platform notes, prefer `Unix`/`POSIX` over `Linux` unless the behavior is Linux-only, and write `macOS`, not `Mac OSX` or `Apple computers`; mixed spellings make docs read inconsistently and confuse readers on other platforms. — Docs are read on every platform, so a single canonical name lets readers match text to their own environment instead of guessing which form applies to them.
<!-- rule:2244 -->
- ### CSRF documentation (docs/ref/csrf.txt, docs/howto/csrf.txt, CSRF template docs) — 
  - Recommend masked token via `{% csrf_token %}` DOM lookup for client-side/user-facing examples, and server-side token retrieval for server-rendered templates — insecure acquisition patterns teach users to write exploitable code.
  - Prefer `fetch()` examples with `X-CSRFToken` and `mode: 'same-origin'`; drop obsolete jQuery cross-domain snippets — the old pattern is misleading under Django's current CSRF model and modern fetch semantics.
  - Call out settings like `CSRF_COOKIE_HTTPONLY` that make cookie-based JavaScript token reads fail — silent failures here confuse users debugging their setup.
  - For `CSRF_COOKIE_DOMAIN`, state explicitly that a leading dot (e.g. `.example.com`) allows cross-subdomain requests — vague "supports subdomains" phrasing leaves the behavior ambiguous.
<!-- rule:1212 -->
- In `docs/faq/*`: phrase headings as concise, natural questions (prefer short prepositional phrasing over wordier constructions); extend an existing entry or page with a short inline note rather than adding a new section or page for basic explanations; and always pair a question with a direct answer, stating current limitations explicitly when something is unsupported. — The FAQ is scanned and searched by phrasing, so question-style headings, inline notes instead of stub sections, and explicit answers about unsupported behavior keep entries findable and prevent users from reading absence of an answer as evidence a feature exists.
<!-- rule:2716 -->
- In `docs/`, name the exact lifecycle trigger (`on initial settings load`, `during form instantiation`, `startup time` for `__init__()`) instead of vague "startup"/"run-time"/"immediately" — ambiguous timing hides real ordering bugs readers can't diagnose — Applies to Django documentation covering lifecycle, initialization, middleware, and lazy QuerySet behavior. Explicit triggers and evaluation stages prevent readers from inferring wrong timing and writing code that assumes side effects fire at construction (a common source of locking and N+1 bugs).
  - In `docs/` QuerySet prose, say a query is **evaluated**, not **called**, and state the trigger (`after the queryset has been evaluated`) — readers need to know when row locks, memory loading, and DB hits actually occur
  - In `docs/` examples, separate queryset construction from evaluation and annotate where side effects fire — unannotated examples imply construction triggers the query
  - State lifecycle prohibitions explicitly alongside the positive form (e.g., "You cannot import models at module level") — the constraint is the actionable part, not just the workaround
  - Place lifecycle/initialization/middleware timing guidance at `docs/` level (spans `ref/applications.txt`, `ref/files/storage.txt`, `ref/forms/widgets.txt`, `topics/http/middleware.txt`), not per-file
<!-- rule:4398 -->
- Curate index pages (`docs/index.txt`, release indexes): group links under concise topic headings with a one-line description, lead with getting-started/core map, put help/meta sections last, and skip stub-only or per-version nav-only indexes — landing pages must orient readers, not dump links. — A reader who lands on `docs/index.txt`, `docs/releases/index.txt`, or `docs/internals/contributing/maintainers/index.txt` has no context yet; a flat or nav-only index duplicates the sidebar and gives no entry point or sense of where to start.
<!-- rule:2962 -->
- In `docs/`, lead warnings and notes with the cause and consequence; show only intended output in examples — buried impact and extra object reprs obscure the point readers scan for. — This documentation style applies across `docs/ref/contrib/admin/index.txt`, `docs/topics/db/fetch-modes.txt`, `docs/ref/django-admin.txt`, and `docs/ref/models/querysets.txt`, where warnings and suppressible-warning notes are written cause-first and examples are trimmed to the target output. Leading with the conditional circumstance or padding examples with object reprs and repeated descriptions makes readers hunt for the actual behavior change.
<!-- rule:3563 -->
- Write idiomatic, unambiguous prose in `docs/`: `than` (not `then`), `except` (not `but`) after `other`, `compared to` (not `vs.`), commas around contrastive `though` — Docs are read literally — swapping `than`/`then` or `vs.`/`compared to` produces sentences that parse but mean the wrong thing, and inconsistent editorial choices across `docs/ref/models`, `docs/topics`, and `docs/releases` make the docs feel unmaintained.
<!-- rule:3129 -->
- Write concrete, realistic examples in `docs/topics/*`, `docs/ref/*`, and `docs/intro/tutorial*.txt` — `pass`-only stubs and toy snippets like `calculate_meaning_of_life` never demonstrate the concept — Documentation under `docs/` (topic guides, reference docs, tutorials) teaches by example. Placeholder stubs and abstract toy cases fail to show real usage, and examples that contradict the concept or depend on un-shown setup actively mislead readers following the guide top-to-bottom.
  - Follow each conceptual intro with a concrete usage example — abstract prose alone leaves readers unable to apply the idea
  - Place usage examples after the setup/config they depend on — readers follow docs sequentially and can't run snippets referencing not-yet-shown config
  - Ensure examples match the concept being taught — contradictory examples confuse readers more than no example at all
<!-- rule:2618 -->
- In security docs (`docs/ref`, `docs/internals`, `docs/topics`, `docs/releases`), ground claims in authoritative sources and precise threat-model language — imprecise or unsourced security claims mislead users about real risk: — Security documentation is the user's model of risk; vague wording or unfounded threat claims cause users to under- or over-estimate exposure. Anchoring to specs and precise terms keeps guidance accurate across `docs/ref`, `docs/internals`, `docs/topics`, and `docs/releases`.
    - Link attack classes and security terms to their definitions
    - Cite external specs or MDN/W3C references, preserving exact wording and qualifiers
    - Use third-party links when they clarify complex issues
    - State limitations as explicit non-protection, not assumptions about attacker capability
    - Explain boundaries via the underlying security property, not incidental mechanisms
<!-- rule:1292 -->
- Document context processor dependencies when a template tag, admin template, or doc example relies on one — mark it `requires` in the tag's entry in `docs/ref/templates/builtins.txt` if the tag cannot work without it, note it in `docs/ref/templates/api.txt` for `RequestContext`-dependent behavior, and add release notes and call out the dependency in `docs/ref/contrib/admin/` examples. Render all documented examples with `RequestContext` so the behavior is actually exercised. — Users copy examples verbatim; if the context processor isn't installed the tag renders silently empty and the docs look like a bug. Marking `requires` distinguishes hard dependencies from optional ones, and rendering examples with `RequestContext` keeps the documented output honest.
<!-- rule:2281 -->
- In `docs/howto/deployment/**`, document only interfaces Django or the page's own server actually supports — wrong examples (e.g., RSGI on a server page, `runserver` as production) mislead users configuring real deployments. Use the documented server's command (`uvicorn myproject.asgi:application`) and recommended extras (`uvicorn[standard]`), list all supported protocols, and mark dev tools like `runserver` as development-only with links to production servers. — Deployment howtos are copy-pasted directly into production configs; unsupported interfaces, bare-package installs, or unlabeled dev servers cause broken deploys and inflated support burden.
<!-- rule:1051 -->
- Use `log in` for interactive flows and `authenticate` only for mechanisms/protocols in `docs/topics/auth/` and `docs/releases/` — conflating them misleads readers about what users actually experience during login versus what an auth backend does. — It prevents docs from conflating user-facing login behavior with backend authentication mechanics and from hiding real user consequences behind internal implementation terms, so readers always understand what users actually experience.
  - Describe auth state by its user-facing effect in `docs/topics/auth/*.txt` (e.g. "this account cannot log in") instead of internal terms like 'unusable password' or vague phrasing like 'unrestricted access' — readers need to understand the actual consequence, not the implementation detail.
<!-- rule:5550 -->
- Release note for input-format/API changes: state the delta from prior support and the canonical output — verify claims against the pre-change implementation (`docs/releases/3.2.txt`, `docs/releases/5.0.txt`, `docs/ref/unicode.txt` set precedent). Don't advertise brittle/unofficial formats as fully supported unless labeled last resort. — Changelogs overstate what changed when authors describe total current support instead of the delta, so users can't tell what's new. Claiming support for formats that were never stable (or never actually worked) misleads readers into depending on them. Naming the canonical/normalized output tells users what they'll actually get back, which is what most readers of a format-change note need.
<!-- rule:1313 -->
- When documenting `INSTALLED_APPS` ordering, name `INSTALLED_APPS` as the precedence factor. — Django docs describe app precedence inconsistently across files (e.g., `docs/ref/django-admin.txt`, `docs/howto/custom-shell.txt`, `docs/topics/db/fixtures.txt`). Stating `INSTALLED_APPS` explicitly as the controlling factor, using user-facing terms like "earlier entries take precedence", and describing the practical effect keeps the explanation unambiguous for readers who expect one consistent story. Refer to same-named models from lower-precedence apps as "overridden models" accessible via the `<app_label>_models` module — this is the only way to reach them once overridden.
<!-- rule:1303 -->
- Document only behavior you've verified against the implementation; delete unverifiable claims in `docs/topics/*` and `docs/ref/*` — unconfirmed prose about serializers, security side effects, or runtime objects misleads users and outlives the fix. — Inaccurate documentation is worse than missing documentation: readers trust `docs/` over source, so a claim about automatic serializer behavior or a security side effect that was never implemented becomes a de-facto spec, gets copied into integrations, and survives refactors that silently diverge from it.
<!-- rule:3211 -->
- In `docs/` Sphinx sources, place each section's content *under* its `.. module::` directive so module context sticks for the whole section. — `.. module::` and `.. currentmodule::` set the implicit target for `:class:`, `:func:`, and `:meth:` roles in Sphinx. Getting placement or scope wrong makes xrefs resolve to the wrong object (or fail to resolve), and pointing at internal modules breaks links when internals get renamed  which is exactly the churn release notes and public API docs are supposed to survive. A single page-level `currentmodule` is only safe when everything on the page shares one namespace; release notes never do, so they must use full paths.
  Put `.. currentmodule::` below the page/section heading, declare it once per section (not again once active), and point it at the public import path users actually write (`pkg.Public`), not the internal implementation module.
  Don't use one global `currentmodule` on a page documenting several modules/APIs  their references would silently resolve against the wrong namespace.
  In `docs/releases/`, skip `currentmodule` and write full dotted paths (`pkg.mod.Class`)  release notes mix many modules, so a shared context produces wrong cross-references.
<!-- rule:3773 -->
- Use parameter-first phrasing: "the `A` and `B` parameters", not "the parameters `A` and `B`" — reads naturally in docs prose and matches Django's documentation style — Parameter-first phrasing and correct number agreement keep prose readable and consistent across `docs/releases/*.txt`, `docs/ref/`, and deprecation notes, avoiding the stilted "the parameters X and Y" construction that reads as authoring noise in release notes and API reference.
  - Match grammatical number to count — singular `argument`/`parameter` for one, plural for many (e.g., "the `extra_tests` argument for `DiscoverRunner.build_suite()`"); deliberately singular usage like "named arguments" is intentional
<!-- rule:874 -->
- Write mirrored docs with parallel phrasing — reuse the existing wording, swap only the entity name, and cross-reference with "similar to `<X>`" or "as in `<method>()`" — so paired sections don't drift apart and mislead readers comparing them — Readers compare mirrored sections (e.g. paired how-to guides, settings, or security behaviors paralleling a documented mechanism) side by side; divergent wording implies the behaviors differ when they don't. Reusing the original phrasing makes true differences stand out.
<!-- rule:570 -->
- Document free-standing template context vars as a bulleted list under the template name (e.g. `` * ``template.html`` with the following variables available...``), not Sphinx `.. attribute::` — attribute directives need a bound documented object and otherwise emit broken, meaningless targets — The text could be made clearer and more consistent for the AI assistant by organizing the requirements into concise bullets, retaining code references, and providing rationale for each rule. The current format is a long paragraph that is harder to scan for actionable guidelines. Splitting into bullets helps the AI assistant quickly identify and apply each rule. Additionally, the explanation for why `.. attribute::` is problematic is retained and made more precise.
  - For each variable, state its exact type and structure: list-of-objects vars expose named attributes (not raw values), and use the precise class name when similar ones exist (e.g. `BoundField` vs `Field`)
  - Add a `.. tip::` when a context key shadows the wrapped object it exposes (e.g. key `field` vs `field.field`) — otherwise readers confuse the two
  - Call the template context a dictionary with 'entries', not 'values', and state types explicitly — keeps reference pages precise and consistent across docs
<!-- rule:527 -->
- Match screenshot style across `docs/*/_images/` (e.g., `docs/intro/_images/`, `docs/ref/contrib/admin/_images/`): ~800px wide, tight crop to the relevant UI, no browser/device chrome, no horizontal scrollbars, correct UI state for interactive actions, consistent with neighboring screenshots — uniform framing keeps rendered docs visually coherent and prevents layout breakage. — Inconsistent screenshot dimensions or stray browser chrome break doc page layouts and make the documentation look unmaintained; scoping to the `_images/` convention lets assistants find and match existing examples.
<!-- rule:1304 -->
- In `docs/`, use the real project name — never `PROJECT_NAME`-style placeholders — Placeholders leak into rendered docs and confuse readers who can't tell which project the guide targets; concrete names also keep docs search-friendly.
<!-- rule:2743 -->
- Name UI elements by their verbatim label plus the exact app/surface they live in, not by screen position or screenshots — positions and screenshots drift as UIs change, and labels stay searchable — UI copy and layout change often; screenshot- or position-based references break silently, while verbatim labels remain greppable and verifiable. Applying a label correction everywhere in `docs/` keeps howto, intro, faq, index, and image docs mutually consistent.
  - Quote UI labels with the app's exact capitalization, spelling, and punctuation (e.g. `Save changes`, not "save changes"), and apply any label fix to every other occurrence in the file and in related `docs/` pages — partial updates leave readers hunting for UI that no longer exists
<!-- rule:4812 -->
- Call environ-backed values "WSGI environ values", not "HTTP headers" — environ is broader than headers, so header terminology misleads readers. — WSGI environ carries more than HTTP headers (e.g. `SCRIPT_NAME`), so calling all environ values "headers" is inaccurate. Consistent terminology and audience-appropriate links (PEP 3333 for reference, the WSGI site for how-to) keep docs accurate and navigable across `docs/ref` and `docs/howto`.
  - Describe environ-backed attributes as "the WSGI environ including available HTTP headers" — signals that headers are a subset of environ keys.
  - Use non-header examples like `SCRIPT_NAME` when showing keyword args that set environ values — header-only examples hide the general mechanism.
  - Link reference docs to the PEP 3333 environ-variables section; link how-to/deployment docs to `https://wsgi.readthedocs.io/en/latest/` — matches each doc's audience.
<!-- rule:3469 -->
- Use keyword-only args for public APIs — prevents breakage when adding parameters — When a public function accepts positional arguments, inserting a new parameter in any position silently rebinds every existing caller's values to the wrong names, producing wrong behavior rather than an error; keyword-only arguments force callers to name each argument so new parameters can be added without breaking or corrupting existing call sites.
<!-- rule:741 -->
- Document what a symbol actually does, not what it appears to do. — Prevents docs that lie about behavior — mismatches between `docs/ref`/`docs/releases` and implementation mislead users.
<!-- rule:2572 -->
- Document only the tested, supported public API contract — omit backend-specific or optional guarantees (e.g., stricter error-raising for cross-task result IDs) unless every supported backend commits to them. — Reference docs and examples are read as the contract, so anything documented — even accidentally — becomes expected behavior users depend on. Behavior that only some backends provide, or that emerged from implementation details rather than design, cannot be preserved as the framework evolves without locking in quirks.
  - Enumerate accepted types and describe conversions with standard terminology (e.g., "converted to a string") only when coercion is an intentional part of the contract; otherwise omit incidental or untested automatic conversions — undocumented behavior users rely on becomes a compatibility trap.
  - Show direct API usage in examples; avoid explicit casts or manual conversion workarounds — examples teach the intended contract, and workarounds imply the API is harder to use than it is.
<!-- rule:4232 -->
- Document full scope of impact for settings that change shared/global behavior — name affected built-ins (e.g. `admin`), third-party apps relying on defaults, and existing vs. newly created objects; state required declarations as obligations. Present third-party defects and user-side workarounds as non-normative with limitations, not supported behavior. — Scope of impact and obligations are the actionable parts; omitting them leads users to assume defaults are safe and to mistake third-party defects or workarounds for supported behavior.
  Rationale: Reference docs are read as contracts — omitting scope leaves users to assume defaults are safe and to treat broken behavior in built-ins or dependencies as supported when it isn't.
<!-- rule:1545 -->
- When documenting ORM related-object fetching in `docs/topics/db/*` and `docs/ref/*`, present the simplest default fix before advanced techniques, and list every supported prefetch/`select_related` option — including `Prefetch()` with an explicit `queryset` and `prefetch_related_objects()` as a fallback — so readers can choose the right tool. Explain or remove incidental `prefetch_related()` calls in examples, and document the supported alternative for unsupported feature interactions instead of saying they 'will not produce expected results'. — Readers need the default fix before advanced recipes, a complete list of options to avoid reimplementing what Django already offers, and a working alternative rather than a dead-end warning when features don't interact.
<!-- rule:3130 -->
- Move detailed side-by-side good/bad examples to a separate tutorial page, not the main guideline section in `docs/internals/contributing/writing-documentation.txt` — keeps guideline sections scannable so readers looking for a rule aren't wading through lengthy examples — Contributor docs like `writing-documentation.txt` are read as reference: readers skim for the rule, not for extended comparisons. Embedding long good/bad pairs inline buries the guidance and makes sections harder to scan, so detailed examples belong on dedicated tutorial/training pages that guideline sections can link to.
<!-- rule:4438 -->
- Write docs for the reader's immediate needs — welcoming tone on landing/index pages and taglines, never claiming exhaustive coverage; overpromising completeness sets expectations the docs can't meet and erodes trust when readers hit gaps (see `docs/index.txt`, `docs/internals/contributing/writing-documentation.txt`) — This governs documentation prose style and was validated against files under `docs/` (e.g. `docs/index.txt`, `docs/internals/contributing/writing-documentation.txt`), so it belongs in `docs/AGENTS.md` where landing/index and prose files live. Framing coverage around what readers need rather than completeness keeps expectations honest and avoids the disappointment that follows unmet promises. Keep it scoped to documentation content, not repo-wide behavior or file-sync rules.
<!-- rule:5060 -->
- Write device/browser/hardware docs inclusively: attribute behavior to one platform only when genuinely platform-limited, prefer universal terms (`power usage` over `battery usage`), and avoid vague modifiers before device lists (`smaller mobile and tablet devices`) — narrow phrasing misleads users on the hardware it omits. — Single platform claims in docs mislead readers whose supported hardware is not that platform; universal terminology (`power usage` vs `battery usage`) stays true across devices, and bare qualifiers like `smaller` imply unstated comparisons. Keeping this in `docs/AGENTS.md` scopes it to the documentation tree where the evidence lives.
  Placed in `docs/AGENTS.md`: the rule governs documentation prose across `docs/releases`, `docs/ref`, and `docs/faq`, so it belongs at the docs root rather than a single subdirectory, and a repo-root file would wrongly extend it to non-doc code.
<!-- rule:5696 -->
- Use `nested within` or `in` when documenting nested constructs in error conditions — `later nested`/`as` imply replacement or sequence, not containment — Prevents docs from suggesting a nested construct replaces or follows another when it's actually contained inside it, which misleads readers about the error's structure.
<!-- rule:3991 -->
- Refer to templates by fully qualified path in double backticks + ``template`` — Django doesn't namespace app templates, so bare filenames imply namespacing that doesn't exist — Django does not namespace app template paths, so a bare filename like ``post.html`` wrongly implies a namespacing scheme that does not exist. Writing the full path (e.g. ``blog/post.html`` template, ``django/forms/errors/list/text.txt`` template) as a reST inline literal followed by the noun `template` gives readers an unambiguous, greppable reference that matches how Django actually resolves templates.
<!-- rule:6241 -->
- In auth/redirect docs, phrase redirects to name the destination ("safe for redirecting to", "redirect after login") instead of terse nouns ("safe for redirect") or `next`-arg jargon — readers need the user-visible outcome, not implementation detail. — Terse forms like "safe for redirect" and request-level details like the `next` function argument leave readers guessing where they'll land after authentication; naming the destination makes the documented behavior unambiguous.
<!-- rule:1510 -->
- Write opt-in/optional settings as one sentence: state the capability or preference ("if turned on, you can…"), how to enable or opt out, and the scope it applies to — users act on capabilities, not passive consequences. Include the condition that keeps the alternative safe (e.g. "as it can be empty") so enabling it doesn't feel risky. Applies across `docs/howto`, `docs/ref`, and `docs/releases`. — Readers decide faster when a setting description says what they get and how to switch it on or off in one line; burying it in passive phrasing or omitting the scope forces them to hunt through `docs/ref` or `docs/howto` for what the flag actually does.
<!-- rule:4281 -->
- Describe runtime behavior by general trigger + full impacted scope, not narrow examples — vague docs hide which processes are affected — Reading "`AppConfig.ready()` during testing" leaves readers unsure if the behavior applies to all startup or just tests; generalizing to "project startup" and "every process" prevents misapplied assumptions. When behavior is hookable/overridable, name the exact hook, entry point, or runner method/phase (e.g., the runner method) rather than a vague phase or "at the start" — third parties extending it need the precise location to override safely.
<!-- rule:4208 -->
- For pluggable APIs, document the default and required complements, then link the ecosystem page and custom-implementation guide — never present one backend as standalone or link a specific third-party package. — Signals that the API is interchangeable and that extra components are needed; keeps docs tied to the curated ecosystem list instead of ossifying one vendor (e.g. `docs/topics/email.txt`, `docs/topics/auth/customizing.txt`).
<!-- rule:5302 -->
- Pair unoptimized/optimized query examples side by side and state both mechanism and concrete gain — lets readers in `docs/topics/db/optimization.txt` and `docs/ref/models/querysets.txt` see what changes and why it's faster, instead of trusting a vague 'faster' claim. — Readers comparing query variants need the before/after side by side plus the mechanism ('uses a `JOIN` instead of N queries') and the concrete payoff ('no additional database queries are issued'). Without this, optimization docs become unverifiable assertions that drift from the code they describe.
<!-- rule:3864 -->
- In docs, show auto-generated files (`startproject`, code generators) unmodified — readers copy examples verbatim and expect them to match real generator output; put required edits in the prose that follows, not as pre-labeled modifications. — Generated examples are copied verbatim and regenerated often, so any mismatch between docs and actual generator output, or any hedge about whether a file exists, turns into user confusion and stale duplication.
  - Document generated-file variants as differences from the generated file — link to it and describe only the changes, so duplicated content can't drift out of sync with the generator.
  - State default project contents definitively: "will already exist if you created your project using the default project template", not "should already exist" — hedged wording leaves readers unsure whether a missing file is their mistake or a bug.
<!-- rule:2184 -->
- Put backend-only behavior in that backend's docs, not the generic `Engine` reference — keeps the API reference backend-agnostic — Documenting backend-only features in the generic `Engine` reference makes them look universally supported; naming the backend class and marking non-Django syntax (such as `template.html#partial_name` and its `outer#inner` chaining limits) as unsupported prevents users from expecting them on other engines.
  - Name the supporting backend class and model docs on existing options like `string_if_invalid`
  - Flag backend-only syntax like `template.html#partial_name` (Django-only, not Jinja2) as unsupported for other backends
  - State which chained/nested forms (`outer#inner`) are unsupported and why
  - Attribute Django-provided helpers/context variables to "Django's Jinja2 template engine", not the underlying template language
<!-- rule:985 -->
- Document param/setting relationships with `:setting:` refs; call caller overrides "specified values" — an unannotated `settings.AUTH_USER_MODEL` arg reads as the literal string `"auth.User"`, and undocumented precedence hides which value wins. — The rationale explains why the rule matters in the codebase.
<!-- rule:2805 -->
- Describe each format directly in `docs/topics/serialization.txt` and `docs/topics/signing.txt` — state what it does and its actual defaults (e.g. "`JSON` by default"), not just how it contrasts with `pickle`. — Readers come to these files to learn a format's actual behavior; naming-only descriptions, unexplained acronyms, generic failure-mode warnings, or `dumpdata` prescriptions leave them without the specifics they need, and framing a format only as a contrast to or imitation of `pickle` hides what it actually does.
  Explain usefulness with a realistic use case plus the processing model — e.g. "JSONL is useful for populating large databases since data is processed line by line rather than loaded into memory all at once."
  Spell out unfamiliar acronyms, use active voice, and name concrete specifics: the serializer, the added key/field, the container, and the value's source.
<!-- rule:1875 -->
- Encode an explicit list of log messages in the documented deletion workflow in `test_runner.py` and verify each message appears in `docs/` that reference sccache and `sccache_stats_writer.py`. The exact messages will be surfaced to users and downstream tooling, so they must match the real code to avoid silent divergence between tests, docs, and behavior. — Documents/test_runner.py and docs/ reference our sccache integration and stats plumbing. If the documented deletion messages drift from the actual code, users and downstream tooling see stale guidance; an 8th message is being added in ci_tools and silently missing from the docs undermines that guidance. Encoding the list makes the contract explicit and keeps tests, docs, and behavior in sync.
<!-- rule:4588 -->
- This rule belongs in docs/AGENTS.md as a documentation-scope convention. — Keeping documentation-scope conventions in docs/AGENTS.md prevents them from being scattered across code-focused rule files or omitted entirely, which would cause inconsistent documentation practices and make agents miss the intended standards.
<!-- rule:6117 -->
- Reserve `module` for a single `.py` file — write "package" for a PyPI-installable distribution ("Install the :pypi:`package-name` package.") or a directory of modules, and "sub-package" when nested, so Python terminology matches what readers install and import. — Python's own docs distinguish package (installable/importable collection) from module (single file); mixing them confuses readers about whether something is pip-installable, a directory, or a file.
<!-- rule:1190 -->
- In `docs/` accessibility pages (`accessibility.txt`, `writing-documentation.txt`, `outputting-pdf.txt`), treat formal standards/conformance as a baseline only, not the whole guide — pair them with an inclusive commitment statement, community resources, accessible examples/alternatives, prominent warnings against inaccessible formats, and candid notes on gaps and realistic testing expectations. — Standards lists tell contributors what conformance looks like but not which formats to avoid, where gaps remain, or what has actually been tested — leaving readers without actionable guidance when authoring docs.
<!-- rule:1198 -->

## File-Specific Rules

### `docs/Makefile`

<!-- rule:6113 -->
- In `docs/Makefile` `help:` entries, mirror the Make target name exactly and keep the `@echo` / two-space indent / padded-name / `to <description>` format — so listed commands can be copied verbatim and the help block stays scannable. — Exact target names let users copy each `help:` line straight from `make help` output into the shell; stray renames or formatting drift break that copy-paste workflow and make the listing inconsistent.

### `docs/_ext/djangodocs.py`

<!-- rule:4735 -->
- Only set `role="heading"`/`aria-level` on TOC-listed `desc` nodes in `docs/_ext/djangodocs.py` — Nodes marked `:no-contents-entry:`/`:nocontentsentry:` are hidden from the TOC, so exposing them as headings desyncs the accessibility tree from the visible contents.
<!-- rule:4663 -->
- In `docs/_ext/djangodocs.py`, when cloning nodes via `update_all_atts()` (e.g. in `visit_console_html()`), clear `ids`, `names`, and `dupnames` on synthetic nodes or suffix them with `-win` — duplicate HTML `id` attributes break anchor links and HTML validity. — `update_all_atts()` copies all attributes including `ids`/`names`/`dupnames`, so cloning an existing node into the doctree re-emits the original anchor as a second `id` attribute. Browsers then resolve `#the-id` to whichever copy appears first, silently redirecting links to the wrong element (or none), and the generated HTML fails id-uniqueness validation. Synthetic nodes that don't need anchors should drop these attributes entirely; nodes that do need distinct anchors (like the console output window) should suffix them with `-win` so both anchors remain reachable.

### `docs/_ext/github_links.py`

<!-- rule:1715 -->
- Test wildcard-import resolution in `docs/_ext/github_links.py` to assert `import_locations` merge — removing `self.import_locations |= locator.import_locations` must break it — The merge line is what makes symbols from wildcard imports visible to the locator; without a test asserting it, the line can be deleted and the docs link resolver silently stops finding symbols from `from X import *` modules.

### `docs/conf.py`

<!-- rule:4570 -->
- Keep `docs/conf.py` mock-module and Django-app lists minimal: only entries that resolve a real import/viewcode warning (verify by removing each one), plus a comment stating the criterion. Unneeded mocks mask genuine import errors, and the comment stops maintainers from re-adding or pruning entries arbitrarily. — Extra mocks in `docs/conf.py` hide real import/viewcode issues that would otherwise fail the docs build — and without a stated criterion, maintainers can't tell which entries are load-bearing versus leftover cruft.

### `docs/howto/composite-primary-key.txt`

<!-- rule:1959 -->
- In `docs/howto/composite-primary-key.txt`, put the composite PK limitations in the main 'Migrating to a composite primary key' section, not a note — a `CompositePrimaryKey` can be added to an existing model, but altering its fields is unsupported, `makemigrations` still detects changes, and such alterations can trigger `UNIQUE constraint failed`; document the `--fake` / `SeparateDatabaseAndState` workaround there. — Scoped to the composite-primary-key howto: AI assistants editing this file need the limitation and workaround in the primary migration section (not buried in a note) so users don't miss that altering a `CompositePrimaryKey` is unsupported and can hit `UNIQUE constraint failed`; `AlterField` must raise rather than silently produce inconsistent unique/PK constraints.
  - Make `AlterField` on a `CompositePrimaryKey` raise an error — failing loudly prevents silently producing inconsistent unique/PK constraints.

### `docs/howto/csrf-protection.txt`

<!-- rule:5858 -->
- In `docs/howto/csrf-protection.txt`, describe the CSRF cookie and `Vary: Cookie` as safe but session-scoped for caching — they force responses to be cached per browser session, so shared/effective caching is impractical; never claim cache middleware works "well" with CSRF-protected responses — oversells compatibility and misleads readers into expecting shared cache hits. — Django's CSRF cookie causes each browser session to get its own cache entry via `Vary: Cookie`, so shared caches see misses. Framing cache middleware as working "well" with CSRF-protected responses sets users up for unexpected cache behavior.

### `docs/howto/sqlite-json1.txt`

<!-- rule:5161 -->
- In `docs/howto/sqlite-json1.txt`, document `LD_PRELOAD` as one concise bullet; cover only the `LD_PRELOAD` env var needed for SQLite/JSON1 — extra env-var guidance dilutes the howto and sends readers chasing settings this file doesn't actually require — Keeps the howto scoped to the one step users must perform for SQLite/JSON1, so readers aren't misled into setting unrelated environment variables.

### `docs/howto/windows.txt`

<!-- rule:2754 -->
- In Windows setup docs (e.g., `docs/howto/windows.txt`), avoid instructing users to add Python to `PATH`; instead show `py --list` / `py -3.8` for interpreter selection and `venv` activation for the current session, and cover how the Microsoft Store build affects `py` and `PATH`. — Adding Python to `PATH` shadows other installs, breaks `py` launcher version selection, and disrupts system tools — documenting the launcher and `venv` keeps users on the interpreter they actually chose.
<!-- rule:2755 -->
- In `docs/howto/windows.txt`, present missing-command caveats (e.g. `py` not recognized) as `.. admonition::` blocks with symptom-based titles near the first triggering command — treats these as general issues, not artifacts of one install method — Explaining command-availability gaps as general symptoms instead of tying them to a single install method keeps the docs accurate for readers on any setup; placing the admonition right before the failing command means users hit the caveat exactly when they'd hit the error, rather than as inline prose they may have skimmed past.
