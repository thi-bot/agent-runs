# Naming Conventions

> Rules for naming variables, parameters, classes, methods, modules, constants, loggers, registries, and settings after their domain role, type, or behavior.

**When to check**: When naming variables, functions, classes, modules, settings, or identifiers.

## Rules

<!-- rule:266 -->
- Name variables and object/template properties after the domain concept they hold, not generic placeholders (`data`, `result`, `match`, `trans_label`, `specific`, `return_value`) — include model context when it's non-obvious (`user_pk_field`, `found_renditions`, `status_label`, `theme_name`, `author_id`); if you catch yourself renaming a value at its use site or reusing a name for a different role, fix the definition instead (`instance`→`parent`, split `theme_name` into `profile` + `theme_name`) — placeholder names force readers to trace context and hide the moment a variable's role has drifted. — Clear names communicate domain intent at a glance; generic names paper over role drift and lead to aliasing (`instance`→`parent`) or conflated concepts (`theme_name`), which obscures bugs and slows readers of the Wagtail codebase.
<!-- rule:16 -->
- Name loop, callback, comprehension, and `catch` variables after what they hold — `action` when iterating `actions`, `field_name` when iterating form fields, `index` (not `i`/`idx`/`ii`), `error` for instances, `error_class` for exception classes; abbreviations obscure intent at review time — Descriptive names make iteration and error-handling intent readable without tracing back to the source collection, and `error` vs `error_class` disambiguates instance from type. Applies cross-language (TypeScript Stimulus controllers, Python models/templatetags/tests).
<!-- rule:910 -->
- ## Naming — Consistent cardinality in names lets AI assistants and humans infer a value's shape from its identifier alone, avoiding bugs where a single item is iterated or a collection is treated as scalar. Descriptive plurals and dropping `multiple_` keep names scannable. The agent-interface exception preserves the mental model of a single composable actor (`MultiRuleRewriter`) rather than a passive bag of rules.
  - Name identifiers by cardinality — plural for collections, singular for single items — so readers infer shape without reading the type. A Wagtail hook that may yield multiple values is `hook_result`/`hook_buttons`, never a singular `button`.
  - Prefer descriptive plurals over generic role names, and drop redundant quantifiers like `multiple_` — the plural already conveys multiplicity.
  - Exception: a class composing multiple internal items but exposing one callable/agent interface takes a singular agent noun (e.g. `MultiRuleRewriter`) — it reads as one agent, not a container.

<!-- rule:272 -->
- Name DOM-element and jQuery variables in `lowerCamelCase` and prefix jQuery objects with a leading `$` (e.g. `$editor`, `$input`) — keeps code consistent and avoids markup-coupled names — Naming by semantic role (e.g. `message`, `pagination`, `triggerElement`, `addColumnMenuTrigger`) rather than an assumed HTML tag (`Div`) or markup shape means refactors of the template don't force variable renames, and a leading `$` signals at a glance that the value is a jQuery object/collection. Updating all sibling jQuery variables in a scope to share the `$` convention prevents mixed styles from confusing readers. In `client/src/entrypoints/contrib/typed_table_block/typed_table_block.js`, this means renaming `baseElement` → `triggerElement` and `addColumnMenuBaseElement` → `addColumnMenuTrigger` since those hold the add-column menu trigger.
<!-- rule:628 -->
- Name parameters after the model fields/attributes they populate, reusing the same name through caller, callee, and `__init__`; skip descriptive prefixes for collections (use `pages`, not `list_of_pages`) — consistent names keep related APIs greppable and readable across `admin/views`, `contrib/settings`, and `contrib/modeladmin`. — Consistent parameter naming across call sites, helper methods, and constructors makes code easier to trace and reduces the chance of passing the wrong collection or field name when refactoring.
<!-- rule:580 -->
- Register checks with stable, project-namespaced IDs that mirror the setting or condition they validate (e.g. `wagtailcore.E004`, `wagtailadmin_base_url`) — docs and error messages reference these IDs, so renaming them breaks user-facing references. — Users and docs cite check IDs verbatim; renaming them silently breaks already-published references.
<!-- rule:1128 -->
- Resolve log models via `log_registry.get_log_model_for_model(model)` instead of importing `ModelLogEntry` directly — custom models register their own log entries, and hardcoding breaks them. — Cache/custom model subclasses register their own log entry classes; hardcoding `ModelLogEntry` silently bypasses them and produces broken audit trails.
<!-- rule:33 -->
- Keep `models.py` / `models/` for ORM definitions only — put model utilities in named modules like `model_usage.py` or a `utils` package — Django discovers models by module; mixing utilities there bloats imports and slows app loading.
<!-- rule:1856 -->
- Treat a leading underscore as a hard private boundary: use it only for members truly internal to a class or module. If subclasses or other classes must call a method, it's public API — name it without the underscore (e.g. rename `_annotate_queryset` to `annotate_queryset`). Conversely, don't call another class's `_`-prefixed members, and don't relocate an internal `_helper` to a shared location unless it's genuinely reusable and promoted to public (un-underscored) API. — The underscore is a contract, not decoration: it signals 'safe to change without notice'. Calling another class's `_` member silently breaks that contract and couples you to internals that may be refactored. Conversely, hiding a method that subclasses or other modules must call forces them to reach into privates anyway — promoting it to public (dropping the underscore) makes the dependency explicit and refactor-safe across areas like `admin/views/workflows.py`, `admin/views/pages/listing.py`, `admin/panels.py`, and the `static_src` JS blocks.
<!-- rule:993 -->
- Name settings, options, and attributes for the exact behavior they control (`is_page_listing_enabled`, not `enabled`) — over-broad names mislead callers about scope and invite misuse. — Generic or implementation-flavored names hide what the option actually governs, so future readers pick the wrong flag or assume it affects more than it does. Naming for the specific target keeps intent discoverable and limits blast radius when the setting changes.
<!-- rule:797 -->
- Omit redundant suffixes like `_for_obj` when the enclosing class or sole argument already implies the target — avoids stutter and keeps call sites readable — The rule is global, so it's placed at repo root. The key actionable content is the naming pattern (`_for_obj` suffix) and the triggering condition (sole argument or enclosing class). Rationale explains why: stutter/redundancy hurts readability. Backticks preserve the concrete identifier so AI assistants can pattern-match.
  - Example: a method taking only `obj` should not be named `do_thing_for_obj` — `do_thing` already reads unambiguously at the call site
<!-- rule:2220 -->
- Keep legacy names like `classname` in existing code, use `form_classname` in new code, and mark legacy names in naming-convention tables (e.g., `docs/contributing/general_guidelines.md`) as existing-code-only. — Preserves backwards compatibility for existing APIs and subclasses (e.g., in `wagtail/blocks/base.py`) while steering new code toward the standardized convention — undocumented exceptions cause contributors to keep copying the old name.
<!-- rule:19 -->
- Name TS interfaces and type definitions in PascalCase, capitalizing each word in compound names — e.g. `DateTimePicker`, not `Datetimepicker` — Preserves word boundaries so compound type names stay readable and consistent across `client/src/includes` and `client/src/controllers`.
<!-- rule:2552 -->
- Name registry modules for their domain (`model_field_registry.py`, not `registry.py`) and module-level objects with a `*_registry` suffix, not a bare plural. — Generic names collide and hide what's registered; duplicated module/object names confuse imports and grep
<!-- rule:821 -->
- In docs, docstrings, and code, reference models/classes by their exact canonical attribute and accessor names (include the owning model in config docs, prefer provided accessors over chaining raw attributes) — rename drift between definitions and call sites breaks readers and users who copy examples; also call plain class-level model members `attributes`, not `properties`, since Python reserves that term. — Keeps docs and examples copy-pasteable, prevents definition/call-site name drift, and avoids the technically incorrect `properties` label for plain class-level members.
<!-- rule:961 -->
- Rename misleading or ambiguous functions in place instead of adding `Real`/`Actual`/`True`/`Proper` variants — the precise name belongs to the correct implementation, and qualifier-prefixed clones leave two ambiguous siblings behind. — Give the cleanest name to the implementation that actually does the work. If `getUser` is misleading, rename it to `getUserFromCache` and let that be the correct name, rather than keeping `getUser` for the wrong thing and adding `getRealUser`. Qualifier-prefixed names (`RealFoo`, `ActualFoo`, `ProperFoo`) are a smell that the original name was wrong — fix the original instead of stacking a second function on top.
<!-- rule:1038 -->
- Match `Meta.fields`, `cleaned_data[...]` keys, local bindings, and `clean_<name>` overrides to exact model field names; validate any overridable clean-name output before use — typos silently skip validation. — Django treats form field names as lookup keys into the model/cleaned_data — a mismatch (e.g. `clean_username` for a `user_name` field) is not an error, it just never runs, so validation is bypassed with no signal. Deriving clean-name output from user input without validating it can also produce lookups against non-existent attributes.
<!-- rule:1611 -->
- In range filters and adapters, name bounds to match inclusive semantics and generality — Names that imply exclusive semantics or specific subtypes mislead callers and break adapter reuse across value types; the pattern spans `wagtail/admin/filters.py`, `wagtail/admin/active_filters.py`, and `wagtail/contrib/forms/views.py`.
<!-- rule:1927 -->
- Rename case-only file changes in two steps (`Tags.md` → `temp.md` → `tags.md`), after confirming the convention in `AGENTS.md` — Git silently ignores case-only renames on case-insensitive filesystems (macOS/Windows). — On case-insensitive filesystems Git sees `Tags.md` and `tags.md` as the same path, so a direct rename can be missed and the change never lands in the commit.
<!-- rule:1234 -->
- Name audit log actions as `wagtail.<category>.<subaction>` (e.g. `wagtail.publish.schedule`), never underscore-flattened names like `wagtail.copy_for_translation`. Place each sub-action under the parent it semantically belongs to — scheduling a publish is `wagtail.publish.schedule`, not `wagtail.publish`. Identifiers appear in `wagtail/core/models.py` and `docs/advanced_topics/audit_log.rst`, so consistent dotted namespaces keep the log queryable and docs aligned with code. — Flat or misleading names make audit logs hard to filter and force downstream consumers to reverse-engineer what an action meant.
<!-- rule:932 -->
- Match the naming style of neighbouring constants/properties (e.g. keep `lower_camel_case` in Wagtail modules) — mixed styles within one file read as inconsistently authored and break grep/search patterns — A module that mixes `lower_camel_case` and `snake_case` for the same kind of thing is confusing to readers and makes text search unreliable.
<!-- rule:2007 -->
- Use title case at every Storybook title level (`'Shared / Buttons'`), name exports after what they demo (`all`, not `base`), and make headings self-contained (`Small buttons (secondary)`, not `(secondary)`) — stories render standalone in docs and the sidebar, so generic or inherited names hide what's actually shown — Stories are viewed individually in docs and grouped in the sidebar across `client/` and `wagtail/`; title case keeps the tree scannable, descriptive export names remove guessing in the controls panel, and self-contained headings survive being rendered out of order.
<!-- rule:2233 -->
- Default to `logger = logging.getLogger(__name__)` — keeps logger names in sync with the module without manual maintenance. — Loggers are part of the user-facing configuration surface; choosing names deliberately (module default vs. explicit public name) keeps the package renameable and lets users target specific functional areas.
  - Assign an explicit public-namespace name (e.g. `logging.getLogger('wagtail.search.auto_reindex')`) only when the logger must survive a package rename or covers a distinct functional area — users wire logging config to these names, so internal/legacy paths like `wagtail.wagtailadmin` would break them.
  - Use a separate logger per functional area (e.g. auto-reindexing vs. general search) rather than sharing one, so users can filter each concern independently.
<!-- rule:374 -->

<!-- rule:947 -->
- Name model fields to make the stored value's type/shape explicit: suffix URL fields with `url` (`external_link_url`, not ambiguous `external_link`), keep a shared base across paired fields (`external_link_url` / `external_link_title`), and describe the semantic content (`link_text` for displayed label, not `link_title`). Self-documenting names keep paired fields symmetrical and prevent misreading an FK/char field as a URL or vice versa. — Amazon-explicit field names make schema intent obvious without checking migrations or related models, and consistent bases keep paired fields greppable and refactorable together.
<!-- rule:898 -->
- Use `rendition` — not "cropped image" — for generated image variants in command names, filenames, variables, docstrings, help text, and docs; one term keeps rendition code and docs greppable and consistent. — The terminology is a repo-wide naming convention spanning `wagtail/core`, `docs/advanced_topics/images`, and `docs/releases`, so it belongs in global scope.

<!-- rule:2821 -->

<!-- rule:988 -->
- Name per-report toggles `WAGTAIL_{FEATURE}_REPORT_ENABLED`; reserve `WAGTAIL_{CONCEPT}_ENABLED` for concept-wide settings — the suffix tells operators exactly what the flag gates, so e.g. rename `WAGTAIL_PAGE_TYPES_ENABLED` to `WAGTAIL_PAGE_TYPES_REPORT_ENABLED` (updating settings, docs, and tests). — Without a distinguishing suffix, `WAGTAIL_{CONCEPT}_ENABLED` flags are ambiguous: admins can't tell whether they disable a single report or the whole feature, leading to misconfigured deployments.
<!-- rule:2612 -->
- Never name variables, params, or methods after built-ins (`list`, `dict`, `filter`, `id`, `type`) — shadowing breaks callers that rely on the built-in. Use `filters`/`filtering` instead. — Shadowing a Python built-in silently breaks any code in that scope that calls the original name, producing confusing `TypeError`/`AttributeError` bugs that are hard to trace back to the shadowing identifier.
<!-- rule:1509 -->
- Give every migration/`Meta.indexes` index an explicit `name`; in abstract models use `%(app_label)s`/`%(class)s` placeholders — Django's auto-names truncate at 30 chars and duplicate across abstract subclasses, breaking later migrations — Django auto-generates index names from table+column names, hashing past 30 characters; abstract models inherit the same literal name in every subclass, producing duplicate index names that fail on migration or clash on any later rename. Explicit, placeholder-based names stay unique and descriptive.
<!-- rule:2979 -->

Documenting the guarantees and intended downstream use keeps the contract explicit for future overriders.
<!-- rule:2093 -->

<!-- rule:1764 -->
- **Use `name="next"` for hidden redirect-target inputs in Django forms and Wagtail admin controllers** — Django's `LoginView`, `redirect_to_login`, and `@login_required` read `next` from `request.GET`/`request.POST`, so renaming it (e.g. to `redirect`) breaks post-auth redirects. Rename the local JS variable freely, but keep the `name="next"` attribute intact. — Unchanged attribute name preserves compatibility with Django's built-in redirect machinery; JS variable naming has no external contract, so it is safe to change.

<!-- rule:2851 -->

State-based names (`Temporary`, `Pending`) make the distinguishing role explicit and generalize across model types.
